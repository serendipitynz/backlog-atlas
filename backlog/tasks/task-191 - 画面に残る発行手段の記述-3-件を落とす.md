## 数え直し — Description の 3 件は過少だった

Description は「文言表の画面へ出る値に **フラグ形の正規表現** をかけて 3 件で全部」と書いていたが、
doc-11 §8 の 発行手段の記述 が対象にするのは **サブコマンド名・フラグ名・引数** である。
フラグ形の網は引数を拾わない。

数え直しは `update.rs` が実際に渡す文字列からトークン集合を取り（フラグ 37・引数値 3・
サブコマンド 13）、文言表の **文字列リテラルだけ**（註を落としたうえで）に掛けた。結果は
**6 キー = 12 文字列、加えて英語のみの 1 文** である。

| 3 | `projectDetail.renameUpdatesTasks` | 参照するタスクも更新する（外すと --no-update-tasks） |

## 走査

`src/lib/screen-text.test.ts` に `ISSUING_FLAG` を足した（`--…` の形の画面文）。
**捕まえるのはフラグ名の半分だけである。** 引数は `clear`・`keep`・`reassign` のように普通の語
でもあるので、テキストだけからは決められない — 今回の 3 件がそちらで、読んで見つけている。
同ファイルの当該節とファイル頭註にそう書いた。

見誤りうる相手は inline の CSS カスタムプロパティ（`style="--modal-inset: …"`）だけで、
宣言の位置にしか現れないので必ず `:` が続き、先読みが外す。`var(--x)` はこの木では
`<style>` ブロックの外に 1 件も無い（`screenText` がそのブロックを潰す）。

**修正を外すと落ちることを先に確かめた** — 文言表 2 ファイルを stash して流すと、この走査だけが
落ち、6 行（3 キー × 2 ファイル）を名指しした。引数の 3 件はそこに出ない。走査の限界を
書いたとおりに測った形である。

ファイル頭註の「§8 の他 3 種は読み手の判断が要り、検査が持てるのは 設計文書参照 だけ」という文を
直した。版表記の走査が既に 設計文の写し の半分を持っており、今回フラグ名の半分が加わったので、
「持てるのは 2 種の半分ずつ」と書き替え、**緑が §8 充足の主張にはならない** ことを明記した。
