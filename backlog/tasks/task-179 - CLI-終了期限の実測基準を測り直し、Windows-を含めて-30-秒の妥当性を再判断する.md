## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
decision-18 は CLI 終了期限 30 秒を「実測した所要時間は期限より 2 桁小さい」ことで正当化しており、Context 3 の実測は **2026-08-02・macOS・タスク 110 件**のものである（`task edit -s` が 189〜240ms、`task list --plain` が定常 272〜288ms）。**同じリポジトリを 2026-08-15 に同じ macOS で測ると 2.37〜2.49s で、約 10 倍である**（台帳が管理ファイル 223 件＝タスク 177・doc/decision 46 へ増えたため）。**「2 桁小さい」は現在成り立たない。**

## 有効な実測は 1 組だけである（2026-08-15）

この日の調査で数字は多く採れたが、**変数を 1 つだけ変えた対は次の 1 組しか無い。**

**同一の機械・同一のプロジェクト・同一の config で、`git` の実体だけを替えたもの**（オーナーの Windows、サンプルプロジェクト、`check_active_branches: true`）:

| `git` の実体 | `backlog task edit -s` 1 回 |
|---|---|
| native `git.exe` (Git for Windows 2.34.1) | **0.72s** |
| wslgit | **36.0s**（**49.6 倍**） |

**wslgit は `git` 呼び出しごとに `wsl.exe` を起動して WSL 境界を越える。**同じ config で `check_active_branches: false` にすると 36.0s → 3.47s、さらに `filesystem_only: true` で 0.252s まで落ちるので、**36 秒のほぼ全部が git の起動回数 × wslgit の 1 回あたりのコストである。**

**オーナーの `pnpm tauri dev` で更新操作が CLI 終了期限 30 秒に達していた原因はこれである。**

## 成立していない比較（この行は警告として残す）

**macOS と Windows を比べた数字は、この時点で 1 つも無い。** 採れた値は次のとおりで、**どの対も台帳が違う。**

- macOS の値はすべて **backlog-atlas**（管理ファイル 223 件、コミット多数）で測った。
- Windows の値はすべて**サンプルプロジェクト**で測った（規模・コミット数は未確認）。
- **`personal-planning` を一度「代替にならない」と判断したが、それも誤りだった** — 「コミットが無いので `check_active_branches` の走査対象が存在せず、git コストが構造的に発生しない」と推論したが、**オーナーの Windows サンプルプロジェクトも同じくコミット 0・ブランチ 0 でありながら 36.0 秒掛かっている。** コストはブランチの本数ではなく **git の起動回数**に比例する — 走査対象が空でも、CLI は「アクティブブランチを調べる」ための git を呼ぶ。**この推論は測らずに書いた因果で、事実に反していた。**

**2026-08-15 の作業中に「Windows は macOS より 3.3 倍速い」と一度記録したが、撤回した** — 0.72s（Windows・サンプル）と 2.37s（macOS・backlog-atlas）を並べたもので、変わっていたのは OS ではなく台帳である。

## 条件を揃えた対（2026-08-15）

**変数を OS だけに絞った対。**両側とも **タスク 2 件・doc/decision 0 件・コミット 0・ブランチ 0**、config は `check_active_branches: true`・`filesystem_only: false`・`remote_operations: true`・statuses 5 値で同一。macOS 側はこの条件に合わせて作った使い捨てプロジェクト、Windows 側はオーナーのサンプルプロジェクト。計測は `backlog task edit -s` で、**status が実際に変わる呼び出し**である。

| | macOS | Windows ＋ native git | Windows ＋ wslgit |
|---|---|---|---|
| `task edit -s` | **0.28s**（定常 6 回。初回 0.51s） | **0.72s**（定常 3 回: 719・731・719ms） | 36.0s |

**OS 差は約 2.6 倍。両側とも定常値なので、この値に留保は無い。**

**Windows 側のプロジェクトは NTFS（ネイティブの Windows ドライブ）上にある** — `\\wsl$\` でも `wsl.localhost` でもない。**したがって wslgit の 36.0 秒にファイルシステム越境のコストは含まれておらず、49.6 倍は `wsl.exe` の起動と境界越えだけで説明が付く。**

**計測の非対称が 1 つある**（結論には影響しない）: macOS 側は `In Progress` ↔ `To Do` を交互にして毎回 status を変えたが、Windows 側は同じ `-s "In Progress"` の繰り返しなので 2 回目以降は状態が変わっていない。**3 回とも同値で、状態が変わった回とも差が無いので、書き込み自体はコストではなく全部が固定オーバーヘッドである。**

**この規模では台帳の件数が効かない** — `personal-planning`（8 件）も同じ 0.28s で、2 件との差が測れない。コストはプロセス起動の下限に支配されている。**したがって件数のずれた先行の対（0.72s 対 0.285s、2.5 倍）も結論は同じだった。**

**この対に残る留保は無い。**着手する回が測り直すのは台帳規模を変えたときの伸び方のほうで、この 2 件どうしの比ではない。

## 台帳規模の効き方## 台帳規模の効き方（macOS 同士、2026-08-15）

| 台帳 | 管理ファイル | `task edit -s` |
|---|---|---|
| `personal-planning` | 8 件 | 0.28〜0.29s |
| `backlog-atlas` | 223 件 | 2.37〜2.49s |

**約 28 倍の台帳に対して約 8.5 倍**で、線形より緩い。**同じ伸び方が Windows でも成り立つなら、223 件の台帳で約 6 秒**になるが、**これは投影であって実測ではない。** 30 秒に対しては、それでもなお余裕がある。

## このタスクが残っている理由

**期限を超える利用者が現に居ることではない** — その入口は wslgit で、Atlas にも backlog CLI にも非は無く、利用者側の git 設定で解ける。**残っているのは decision-18 の Context 3 が現在偽であることのほうである。**

- 記録された macOS の値が同じリポジトリで約 10 倍になっている。
- **Windows の実測を 1 つも持っていない**（上表は Windows 同士の比較であって、Windows と macOS の比較ではない）。
- **測り直す条件が書かれていない。**台帳規模で伸びる値なので、いつ偽になるかを言えないまま置かれている。

## 判定の経緯

**2026-08-15 に一度 m-3 として起票し、同日 m-4 へ移した。** 起票時の根拠は「この規模の台帳を持つ Windows 利用者は Atlas から何も更新できない」で、それが wslgit 固有の事象と判明したことで前提ごと消えた。**native git では同じ操作が 0.72 秒で、30 秒に対して約 41 倍の余裕がある。**
