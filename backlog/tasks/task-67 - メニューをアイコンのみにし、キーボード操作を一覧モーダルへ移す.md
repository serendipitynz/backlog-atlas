## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
メニューのボタンを lucide の menu アイコンだけにする（文言なし）。キーボード操作の一覧をメニューの中に常設するのをやめ、「キーボード操作表示...」というメニュー項目にして、選ぶとモーダルで一覧を出す。lucide は依存を増やさず、必要な SVG を src/lib/icons/ にインラインで持つ（ISC ライセンス、再配布可）。
<!-- SECTION:DESCRIPTION:END -->

- [x] #2 メニューに「キーボード操作表示...」があり、選ぶとキーボード操作一覧がモーダルで出る
- [x] #3 メニュー本体にキーボード操作の一覧が常設されていない

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-03 に実装した。

**決定先行判定: decision は不要、doc-7 §2.1 と doc-11 §2.4 を改訂・新設した。** 決 印は無いが指示書の
規則どおり着手時に当たった。変わる契約は 3 つで、いずれも doc であって decision ではない。反転する
判断が無いので decision は 1 件も書いていない。

1. doc-7 §2.1 のメニューの中身の列挙に、キーボード操作の一覧を開く項目が 3 種類めとして入る。
   並びは 入口 → 一覧 → 行非表示の群 と定めた（群は非表示行の数だけ伸びるので、固定の項目を
   その後ろに置くと開くたびに位置が変わる）。
2. 画面で割り当て一覧を読む先が、メニュー内の畳んだ表からモーダル 1 つへ移る。正本は
   `shortcuts.ts` のままなので §2.1 の「1 箇所に持ち」は不動で、変わるのは画面上の置き場だけ。
3. §2.1 の「操作の近くにも併記する」— **アイコンのみのボタンでは併記を `title`・`aria-keyshortcuts` と
   一覧モーダルが担い、`aria-label` は名前だけを持つ**、をユーザーが 3 案から選択した（2026-08-03）。
   可視の chord をアイコンの隣に残す案と、併記の要求自体を緩める案は採らなかった。画面設計案 01 の
   ☰ も文言・chord なしの `title` だけなので、01 に沿う形でもある（doc-12 §2.4 の転記）。
   担い手の言い分けは doc-7 §2.1 と doc-11 §2.4 で揃えてある（レビュー [P3]。当初は doc-7 だけが
   `aria-label` を担い手に数えていて、実装は doc-11 のほうと一致していた）。

doc-11 は §2.4「アイコン」を新設した（§2 の末尾に足し、既存の番号は動かしていない — `doc-11 §4`・
`§5` はコード註と decision から番号で参照されている）。§1 用語に アイコン と アイコンのみのボタン を
加え、置き場・写すだけで描き直さない・寸法 1em・`currentColor` のみ・常に `aria-hidden`・
`aria-label` 必須 を規則として書いた。TASK-69・71・72・77 はこれを引く。

**対応表を先行確定した**（`_sandbox/referent-table-task-67-icons.md`）。争点は 3 つで、アイコン
（lucide の図形）と文字グリフ（☰・⚙）を同じ語で呼ばないこと、割り当て一覧（doc の語）と
キーボード操作の一覧（画面の語）が同一物だと固定すること、併記の指示対象を決めること。

**lucide は写した。依存は増えていない。** 出典は lucide v1.17.0（ISC）の
`dist/esm/icons/menu.mjs` の `__iconNode` と `defaultAttributes.mjs`。`src/lib/icons/lucide.ts` が
図形データ（`ICONS`・`IconName`・`ICON_VIEWBOX`・`ICON_STROKE_WIDTH`）、`src/lib/icons/Icon.svelte` が
描画を持つ。`IconShape` は使う SVG 要素の閉じた union で、いまは `path` 1 種類だけ。**`rect` を
パスへ潰さない**のは、潰したものが lucide に似た図形であって lucide の図形ではなくなり、後から
区別できないため（TASK-72 の copy・TASK-77 の警告記号が `rect`・`circle` を要れば union を増やす）。
**その「メンバーを足すとコンパイラが描画分岐を要求する」約束を実際に持つのは
`lucide.ts` の `drawnShape` の網羅 `switch`** であって、テンプレートの `{#if}` ではない（下の
レビューの項）。ISC 告知をリリース物へ載せるかは TASK-97。

**一覧をモーダルへ出したのは、メニューが 2 つの役を持っていたため。** 表はメニュー項目より長く、
`details` で畳んで下に置くと、開いた瞬間にメニュー自身の `max-height` を超えて入口が上へ流れる。
読むためのものと選ぶためのものを同じ層に積まない、という形にした。メニューの幅は 30rem → 24rem
（5 列の表が要求していた幅なので、表が出た以上は残す理由が無い）。

**モーダルを立てる 3 行を `raiseModal()` へまとめた。** 被せ層を 1 枚に落とす・☰ へ先にフォーカスを
移す、の 2 つは登録・設定・一覧の 3 経路すべてに要る。TASK-66 が入れたこの 2 行が 3 か所へ増える
ところだったので、1 か所に寄せた（TASK-74・76・86 がモーダルの閉じる経路を触るときも、ここを見れば
足りる）。

**`render.ts` の `announced` が `aria-label` を先に読むようになった。** アクセシブル名の計算順であり、
かつアイコンのみのボタンには文字が無いので、内容へ落ちる実装では空文字と照合することになる
（`byLabel(host, "button.header-entry", "メニュー")` が既存 3 件で使われている）。

**コンポーネントテストを 1 件足した**（画面横断契約の「モーダルの出口」に 2 経路追加、計 534 件）。
検査は移した先を名指しする: メニューに表が無いこと、モーダルが `SHORTCUTS` と同じ行数を持つこと、
Escape と自身の閉じるの両経路でフォーカスが ☰ に戻ること。**3 種の mutation で落ちることを実測した** —
`raiseModal()` の `menuButton?.focus()` を外すと 3 件（新規 1 件を含む）、メニューへ表を戻すと 1 件、
`SHORTCUTS` を `slice(1)` にすると 1 件。TASK-66 の教訓（移した先を名指しする検査を足す）をそのまま
適用した。

**実エンジンで測った。シェルも載せられることが分かった（以降の UI タスクへの注意）。**
TASK-66 は「ハーネスが効くのは部品、効かないのはシェル」と書いたが、**Vite の dev サーバへ
playwright で `/`（本物の `index.html` → `App.svelte`）を開けば、境界が失敗した状態のシェルがそのまま
描かれる**。Tauri IPC が無いので CLI 縮退・読取失敗の帯が立つが、固定ヘッダのレイアウトはそれで
変わらない。境界の偽物を組む作業は要らなかった。測った値（WebKit）:

- **固定ヘッダの ☰**: `aria-label="メニュー"`・`title="メニュー（M）— …"`・`aria-keyshortcuts="M"`、
  ボタン内の可視テキストは空、ボタン 26×26・図形 16×16、**画面名との上下中心のずれ 1px**
  （`.menu-anchor` に `align-self: center` を置いた理由がこれ。アイコンだけのボタンは baseline を
  持たないので、ヘッダの `align-items: baseline` のままでは図形が見出しの下へ垂れる）。
- **メニュー**: 登録（⌘N）・設定（⌘,）・キーボード操作表示…・行非表示をすべて戻す（保留・理由つき）の
  4 行で、**表は無い**。
- **アイコンの寸法**（`_sandbox/icon-check/`、WebKit と Chromium で一致）: 周囲 1rem で 16×16、
  2rem で 32×32、0.72rem で 11.52×11.52。`stroke` は親の `color` と同値、`aria-hidden="true"`、
  パス 3 本。
- **一覧モーダル**（本物の `Modal.svelte` ＋ `ShortcutHelp.svelte`）: 9 行 = `SHORTCUTS` と同数、
  ダイアログ 706×427、フォーカスは「閉じる」。

**この測定が欠陥を 1 件見つけて直した**: 「入力欄内」列が全行で折り返し、表の高さが 523px まで伸びて
いた（9 行すべてが 2 行になる）。`発火する`／`発火しない` は 2 値の答えなので `white-space: nowrap` を
与え、427px になった。自動検査では出ない類（`jsdom` はレイアウトを走らせず、`render.ts` の矩形は
検査してはいけない値）で、**部品を実エンジンに載せなければ目視まで残っていた**。

**フロントエンドのフォーマッタは無い**ので当てていない（TASK-66 と同じ理由）。静的解析は
`pnpm run check`（svelte-check、287 ファイル・0 errors）、試験は `pnpm test`（534 件）、
`pnpm run build` も通した。**Rust 側は 1 行も触っていない**ので `cargo test`／`fmt`／`clippy` は
実行していない。

**レビュー（PR #49、1 ラウンド。[P2] 2 件・[P3] 4 件を全件対応して APPROVED）で設計が 2 か所変わった。**
どちらも **コードが自分について書いた主張が実際には成立していなかった**型で、直した後に
壊して落ちること・既存 2 例との差を実測してから返答した。

1. **`IconShape` の網羅は `drawnShape` へ移した。** 「union にメンバーを足すとコンパイラが
   `Icon.svelte` の描画分岐を要求する」と註・モジュール冒頭・doc-11 §2.4 に書いていたが、
   テンプレートの `{#if}` はそれを持たない — TypeScript は判別子で絞るのが *union* に対してだけで、
   メンバー 1 つの `IconShape` では `{:else}` の型がその形自身になり `never` にならないので、
   網羅呼び出しは今日はコンパイルできず、分岐を欠いたままでも `svelte-check` は 0 errors を返して
   空の `<svg>` を描く。**種別 → 要素の写像を `lucide.ts` の `drawnShape`（`switch`）へ移し**、
   テンプレートはその戻り値を `<svelte:element>` で描くだけにした。`strict: true` の下では
   メンバー追加で `switch` が非網羅になり TS2366 が関数名で出る。`rect` メンバーを足して
   `pnpm run check` が `drawnShape` を名指しで落とすことを実測した。**代償**は
   `DrawnShape.tag` が素の string になり、要素名と属性がテンプレートで型検査されなくなること。
   データの隣の小さな関数 1 つに閉じた危険と引き換えに、黙って描かれない経路を消した。
2. **`ShortcutHelp.svelte` の「閉じる」を見出しの隣へ移した。** `Modal.svelte` は mount 時に
   最初のフォーカス可能要素へ `focus()` し、`focus()` は backdrop のスクロール域へその要素を
   送り込む。9 行の表の下に唯一の「閉じる」があると、ダイアログより背の低いウィンドウで
   **見出しと先頭行を飛ばした位置で開く**。380px で実測すると backdrop が 102px スクロールし
   見出しが -57 の位置にあった。`header` へ移した後は 0 と +47。`Settings.svelte`・
   `ProjectRegister.svelte` は元から同じ形で、この 2 例との差が説明されていなかったのが原因。

残る [P3] 3 件は、`aria-label` を併記の担い手に数えていた doc-7 §2.1 の文言（上の 3.）、
`raiseModal()` 導入後も古い場所を指していた `App.svelte` の註 3 か所、`src/` に残っていた
`_sandbox/` 参照と `header.ts` の `…` の根拠の広げすぎ。

**実機での目視（ユーザーが実施、2026-08-03）: 依頼した 3 点とも問題なし。**
(1) 実データを載せたヘッダで ☰ が 26px の枠として小さすぎないか、(2) メニューの
「キーボード操作表示…」から一覧が開き、Escape でも「閉じる」でもフォーカスが ☰ に戻るか、
(3) 一覧モーダルの表が実機のウィンドウ幅でも折り返しすぎないか、の 3 点。上の実測が
playwright の WebKit までしか塞いでいなかったぶん（WKWebView・実データ・フィルタ帯や上部帯が
立った状態）を、この目視が埋めた。
