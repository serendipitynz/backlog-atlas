## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
workspace_open は登録順に全ルートを直列で開くので、利用者が最初のカードを見るまでの待ちは全ルートの読取時間の合計になる。TASK-94 の規模計測が実測した値は、1 ルート 200 タスクで 1 ルート 11.5ms・10 ルート 317.2ms・20 ルート 639.5ms（macOS arm64・release・2026-08-23）で、これは同じ規模のフロントエンド再計算時間 7.2ms の 90 倍にあたる。実測で最も大きいのはこの項であり、部分再読込はここに一切効かない（初回読取は定義上すべてのファイルを読む）。品質評価書 2026-08-01 のパフォーマンス節が並べた改善順にはこの項が無く、decision-42 が実測に基づいて順序を入れ替えた。取りうる形は 2 つある。ルートごとの読取を並行に走らせるか、直列のまま 1 ルート読み終えるごとにその行を描いて全体の完了を待たせないかである。前者は decision-18 のプロジェクト単位ロックの取り方に触れるので、ロック順の議論を伴う。後者はフロントエンドが既に loadBySlug をルートごとに持っているので、境界の返し方を変える話になる。どちらを採るかは着手時に決める。
