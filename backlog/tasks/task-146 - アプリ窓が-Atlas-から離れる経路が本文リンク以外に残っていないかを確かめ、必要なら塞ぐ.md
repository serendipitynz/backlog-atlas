## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-142 の目視（2026-08-11）で判明したことの残りである。**本文リンク については doc-8 §9.3 が閉じた** — `href` を置かないので engine がリンクとして扱わず、文脈メニュー・中押し・引きずりのどれも経路にならない。**本タスクが扱うのは、本文がリンクを 1 つも持たなくても成り立つ経路のほうである。**

**なぜ重いか**: 目視で確かめられたのは「窓が離れる」ことだけではない。**Atlas は戻る控えを持たない**ので、離れた先から主画面まで戻る手段が実用的でない（右クリックの戻るしか無く、連打できないため転送が挟まると戻れない）。つまりこの型の欠陥は、起きたら**操作不能**である。用語節の定義により、発生条件の限定は公開阻害の判定に入らない。

**まだ測っていない**: 候補は「別アプリから URL を窓へ引きずり込む」経路で、Tauri の `dragDropEnabled` が既定で drag-drop を横取りしてフロントエンドへ事象として渡す作りなので、**そもそも航行が起きない可能性がある**。**起きるかどうかを先に測る** — 測る前に塞ぐと、要らないガードを足したうえでその根拠を書けない。この環境では実機の webview を出せないので、目視での確認が必要である（playwright からは native な drag も文脈メニューも出せない）。

**塞ぐ場合の手段の見当**: 窓を Rust 側で作れば `on_navigation` で航行を拒める（現在は `tauri.conf.json` の `app.windows` が窓を宣言しているので、窓の生成を Rust へ移す変更になる）。**その形を採るなら契約であり、doc と decision に書く** — 「アプリ窓は決して航行しない」は doc-8 §9.3 が本文リンクについて言っていることを窓全体へ広げる主張になる。TASK-98（CSP 有効化）とも隣接する。
