## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-142 の目視（2026-08-11）で判明したことの残りである。**本文リンク については doc-8 §9.3 が閉じた** — `href` を置かないので engine がリンクとして扱わず、文脈メニュー・中押し・引きずりのどれも経路にならない。**本タスクが扱うのは、本文がリンクを 1 つも持たなくても成り立つ経路のほうである。**

**なぜ重いか**: 目視で確かめられたのは「窓が離れる」ことだけではない。**Atlas は戻る控えを持たない**ので、離れた先から主画面まで戻る手段が実用的でない（右クリックの戻るしか無く、連打できないため転送が挟まると戻れない）。つまりこの型の欠陥は、起きたら**操作不能**である。用語節の定義により、発生条件の限定は公開阻害の判定に入らない。

**まだ測っていない**: 候補は「別アプリから URL を窓へ引きずり込む」経路で、Tauri の `dragDropEnabled` が既定で drag-drop を横取りしてフロントエンドへ事象として渡す作りなので、**そもそも航行が起きない可能性がある**。**起きるかどうかを先に測る** — 測る前に塞ぐと、要らないガードを足したうえでその根拠を書けない。この環境では実機の webview を出せないので、目視での確認が必要である（playwright からは native な drag も文脈メニューも出せない）。

**塞ぐ場合の手段の見当**: 窓を Rust 側で作れば `on_navigation` で航行を拒める（現在は `tauri.conf.json` の `app.windows` が窓を宣言しているので、窓の生成を Rust へ移す変更になる）。**その形を採るなら契約であり、doc と decision に書く** — 「アプリ窓は決して航行しない」は doc-8 §9.3 が本文リンクについて言っていることを窓全体へ広げる主張になる。TASK-98（CSP 有効化）とも隣接する。

**前提が動いた（2026-08-15、decision-34）。** TASK-81 が `dragDropEnabled` を `false` にした — Windows で画面内のドラッグ&ドロップを成立させるために外す必要があり、Atlas は OS のドラッグ&ドロップ事象を 1 か所も消費していないので外して失う機能が無かった。**したがって、上で「そもそも航行が起きない可能性がある」と述べた横取りは、もう掛かっていない。** 測る対象は外した後の状態であり、この段落より前の「まだ測っていない」の見当はその点だけ古い。

**測る機会が 1 つ先に来る。** TASK-81 の AC #7 が macOS・Windows・Linux の実機の前に人を立たせるので、**その回に「別アプリから URL・ファイルを窓へ引きずり込む」を 1 回ずつ試せば、本タスクの『まだ測っていない』はその場で埋まる。** **TASK-81 の受入条件には入れていない** — 入れると、もし航行が起きた場合に TASK-81 の完了が本タスクの対策待ちになるためで、測るのを一緒にすることと、完了を結び付けることは別である。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## この回で決めたこと

**測定が先で、塞ぐのは後である**（起票の指示）。**測定器は 航行ゲート 自身に置いた** — 許否を 1 つも
変えず、試みられた URL だけを出す形である。**目視だけにしなかったのは、目視が「試みが無かった」と
「試みを engine が断った」を区別できないからで**、後者なら engine か URL が変われば通る。切り分けと
測定結果、塞ぐ形は decision-37 が持つ。語は TASK-146 の対応表 初版で本文より先に固定した。

## 測定（2026-08-18、macOS 実機、オーナーが操作）

5 つの操作を 1 回ずつ。**航行の試み は 3 件で、3 件とも 引きずり込み だった。**

- URL をブラウザから引きずり込む → `https` の 1 件。窓が離れた。文脈メニューの戻るで帰れた。
- `.png` を Finder から引きずり込む → `file:` の 1 件。窓が離れた（画像が開いた）。**文脈メニューに
  戻るが無く**、⌘← で帰れた。
- `.md` を Finder から引きずり込む → `file:` の 1 件。窓が離れた。文脈メニューの戻るで帰れた。
- 添付画像・タスクカード・選択文字を窓内で引きずる → **どれも 0 件**。窓は離れない。

**初期読み込みが必ず 1 件記録されるので、0 件は「測定器が動いていない」ではない。**

## AC #3 の読み

**AC #2 と #3 は排他の枝として書かれているが、測定はその両方を出した** — 引きずり込み の 3 つに経路が
在り、窓内の引きずり の 3 つに無かった。**#2 は前者を、#3 は後者を記録しているものとして両方を満たしと
した。** #3 の「なぜ起きないか」のうちコードで言えるのは 1 つだけで（カードが載せるのは `text/plain` の
横断タスクID であって engine が読み込み要求に変えられる値ではない）、**残り 2 つは読みである。**
decision-37 はそう書き分けてある。**この読みを採らない場合は #3 を書き改める必要がある。**

## 実装の形

**窓の生成は `tauri.conf.json` に残した。** 起票の見当は「窓を Rust 側で作れば `on_navigation` で拒める」
だったが、**tauri 2.11.5 の既定の 航行ゲート は窓の作り方によらず plugin の `on_navigation` を必ず通す**
ので、plugin 1 つで届いた。**出所は名指しせず最初の航行から学ぶ** — 名指しは macOS・Windows・開発中で
3 つになり、2 つの platform 慣習と 1 つの設定に追従させ続けることになる。

**比べるのは scheme・host・port の 3 つで、`Url::origin` は使えない** — `tauri://localhost` のような
特殊でない scheme では opaque origin を返し、opaque origin は互いに等しくならないので、アプリ自身の
再読込が拒まれる。

## レビュー用の確認事項

**8 件の試験は、規則を 5 通りに壊して落ちることを確かめてある**（常に許す・scheme を見ない・host を
見ない・port を見ない・origin でなく URL 全体で比べる）。**1 本目に書いた scheme の試験は落ちなかった** —
`http` と `https` を同じ host で比べる形は port の既定値 80・443 の差で落ちてしまい、scheme 比較を
押さえていなかった。port を持たない custom protocol 同士（`tauri:` と `asset:`）で比べる形へ直してある。

**オーナーの目視（2026-08-18、macOS）**: 画面がふつうに描かれること・3 つの引きずり込みで何も
起きないこと・本文リンク が既定ブラウザで開くこと・添付画像 が描かれることの 4 点を確認した。
**Windows・Linux は未測定である**（経路の在否も、ゲートが同じに効くことも）。
