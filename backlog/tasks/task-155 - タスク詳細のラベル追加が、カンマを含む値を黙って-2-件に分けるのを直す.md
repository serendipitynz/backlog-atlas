## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
タスク詳細の編集セッションでラベルを追加すると、カンマを含む値が保存時に 2 件のラベルへ分かれる。v1.48.0 の task edit --add-label は 1 個のカンマ区切り値として読むため（実測。--add-label "a,b" で labels が a・b の 2 件になった）で、Atlas 側にこの入力を拒む検査が無い（src/lib/edit.ts の buildSave の labels 節）。同じ規則は既に別経路で守られている: 新規タスク作成モーダルのラベルと文書のタグは commaReason で拒む（src/lib/comma.ts。TASK-151 が manage.ts から移した）。したがって同じ入力が作成では拒まれ編集では通るという非対称であり、しかも編集側は divergence（edit.ts）がラベルを突き合わせないので事後通知にも載らない。dependencies も --depends-on がカンマ区切り全置換なので同型だが、値が TASK-ID なので現実の入力にカンマが入りにくい。References は --ref を参照ごとに繰り返すので分割は起きない。TASK-151 のセッションで、assignee の同型を直しているときに見つけた。公開阻害には当たらないとこちらは判断した（保存後の画面に 2 件のチップが出るので結果は見えており、データは失われない）。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 実測 (Backlog CLI v1.49.3、2026-08-20)

- `task edit --add-label "a,b"` は labels に `a`・`b` の 2 件を書く。各要素の前後空白を落とし、空要素を捨てる（`" c , d "` は `c`・`d`、`"e,,f"` は `e`・`f`）。
- `task edit --remove-label "x,y"` は、labels に `x,y` を 1 件持つタスクに対して終了コード 0 と `Updated task TASK-1` を出しながら 1 件も消さない。存在しないラベル名を渡したときと同じ結末で、doc-5 §3.1 の 沈黙無変更 である。
- `task edit --depends-on "TASK-2,TASK-3"` は依存を 2 件書く（doc-5 §3 の既存記述どおり）。
- カンマを含むラベルは CLI では書けない（作成側 `-l` も編集側 `--add-label` も分ける）ので、その状態は管理ファイルの手編集から来る。**一度書かれると CLI はそれを保つ** — 別のラベル操作を通すと `- 'x,y'` と引用して保存し直した。

## 掛け先の数え上げ (AC #2)

画面の欄ではなく `src-tauri/src/update.rs` が値をカンマ連結する箇所で数えた。**6 つあり、規則が掛かっていたのは 3 つだった**。

| オプション | 経路 | 改訂前 |
|---|---|---|
| `task create --labels` | 新規タスク作成モーダル | 掛かっていた |
| `doc update --tags` | 文書のタグ | 掛かっていた |
| `task edit --assignee` | タスク詳細の編集セッション | 掛かっていた |
| `task edit --add-label` | 同上 | 掛かっていなかった |
| `task edit --remove-label` | 同上 | 掛かっていなかった |
| `task edit --depends-on` | 同上 | 掛かっていなかった |

フロントエンドは自分でカンマ連結をしない（`join(",")` は crate 側だけにある）。発行元は `manage.ts`・`edit.ts`・`lane-drop.ts` の 3 つで、`lane-drop.ts` は status だけを送る。

## 理由文が 2 つある理由

追加側と削除側で結末が違うので、文も 2 つにした。追加側は既存の `commaNotAllowed` を再利用し（打ち直せる値なので「2 件に分かれます」が当たる）、削除側は新設した（打ち直しても変わらないので、述べるべきは削除できないことである。doc-11 §5 の形に合わせて `Atlas からは` を残した）。**assignee・dependencies・タグに削除側の場合は無い** — 非空全置換なので、カンマを含む既存要素は渡す集合から外れて消える。ラベルだけが増減で発行され、消す値そのものが引数になる。

## 関門は渡す値に掛ける

`draft.labels` ではなく `addLabels`／`removeLabels` に掛けた。カンマを含む既存ラベルを残したままの保存は、そのラベルがどちらの引数にも現れないので CLI が現に正しく行える — draft に掛けるとそれを拒む。`edit.test.ts` にその 1 件を置いた（関門を draft へ移すと落ちることを確認済み）。

## 走査 (`src/lib/comma.test.ts`)

数え上げを、7 つめが生えたときに落ちる形にした。`update.rs` の `join(",")` を全部拾い、オプション名へ帰属させ、表の行と突き合わせる。**`.opt(` を前提にした形にしていない** — positional へ連結された値も同じように読まれるので、名前へ帰属できない連結は飛ばさず落とす。各行は実際の関門を走らせて拒否を確かめるので、行があるだけでは通らない。**走査自身の源泉も押さえた**（`update.rs` を現に読んでいること、植えたオプションを見つけること、`#[cfg(test)] mod tests` の切り落としが 1 項目の `#[cfg(test)]` を巻き込まないこと）。確認: 修正を外すと関門の 3 行が落ち、`update.rs` へオプションを 1 つ植えると数え上げの 1 本が落ちた。

## 採らなかった案

- **カンマを含む既存ラベルのチップの 削除 を無効化する**（doc-8 の 最後の 1 件 と同じ形）。`listEditor` は 4 つの欄が共有していて、要素ごとの可否を持たないので、その契約を広げることになる。拒否は保存を押す前に出る（`buildSave` は派生値）ので、いま得られるものとの差は小さい。
- **crate 側にも関門を置く**。空集合の 3 件は両側にあるが、カンマの関門は assignee も frontend だけに持っている（理由文を組むのは frontend であり、crate は文を組まない。decision-35）。既存の形に合わせた。
