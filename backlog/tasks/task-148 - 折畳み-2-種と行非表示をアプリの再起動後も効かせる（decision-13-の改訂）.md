## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
2026-08-11 のユーザーの要求である。**列折畳み・行折畳み・行非表示 を、アプリを終了して起動し直した後も効いたままにする。再起動をまたぐ保持 とは、アプリの終了と起動をまたいで値が効いたままであることを指す。**

**decision-13 の改訂を要する（決定先行）。** 同 ADR の「アプリ設定を持たない値」がこの 3 値を名指しで除外しており、doc-7 §5.1・§5.4 の 2 か所がそれを引いている。

**除外の根拠 1 文は、そのままでは 3 値のうち 1 値にしか掛かっていない。** decision-13 が書いているのは「次回起動時に前回どけたものが消えたままだと、**行非表示の「件数も読めない」性質と相まって**、登録したはずのプロジェクトが失われたように読める」であり、**根拠が名指ししている性質を持つのは 行非表示 だけである** — 行折畳み はレーンヘッダ行と列別件数を残し（doc-7 §2.3）、列折畳み は列名と行ごとの件数を残す（doc-7 §2.2）。doc-7 §5.4 が並び順を保存する根拠に使った判定（次回起動時に効いていても「登録したはずのものが消えた」とは読めないか）を同じく当てると、折畳み 2 種はその判定を通る。

**行非表示 についても、根拠が前提にしていた状態は 2026-08-09 に変わった。** TASK-131 が表示・非表示をメニューのプロジェクト一覧へ一元化し、**一覧は登録済みプロジェクトを常に全件並べ、非表示の行も印の無い行として並ぶ**（doc-7 §2.1）。decision-13 が書かれた時点では、一覧は非表示の行だけを並べていた。起動直後に「登録したはずのプロジェクトが失われた」と読める経路が今も残っているかは、**着手時に確かめる** — 残っているなら 3 値のうち 行非表示 だけを除外に留める道がある。

**着手時に確かめること**: 保存する値の形（列折畳み は正準ステータス列 4 つ＋未分類区画、行折畳み・行非表示 は slug の集合で、台帳から消えた slug が保存値に残ったときの扱いが要る）、`KNOWN_SCHEMA_VERSION` の引き上げ（decision-13 の Consequences。現在 3）、`src/lib/settings.ts` の `mergeDraft` と `normalize` の両方へ通すこと、設定モーダルの「ここに無い項目」区画（`Settings.svelte:16`）が 3 値を挙げている記述。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**決定先行の争点は 1 件だった。** 折畳み 2 種を保存することは doc-7 §5.4 が並び順に当てた判定から落ちるので争点にせず、置き場と 台帳に無い slug の扱いはこちらの判断で足りた。ユーザーへ出したのは 行非表示 の 1 点で、**2026-08-18 に「3 値すべて保存する」を選択**。提示した実測は、**Linux では 総件数 が画面に出ない**ので（2026-08-15 実測、decision-31 の Linux の改訂）行非表示 を復元した起動では メニューのプロジェクト一覧 だけが状態を述べる、という事実である。

**decision-13 は「再起動をまたぐ保持の改訂 (2026-08-18)」節で改訂した**（decision-31 の「Linux の改訂」と同じ形。撤回した Decision の項と項目表の導入文にはそれぞれ「先に下の節を読むこと」の 1 文を付け、原文は残した）。項目表に 3 行を足し、導入文の 2 つの限定（「既定値」・「特定の台帳エントリに紐づかない」）が末尾 3 行には掛からないことを §3 に書いた。

**着手時に確かめた 4 点のうち 2 点が起票時と違っていた。** `KNOWN_SCHEMA_VERSION` は 3 ではなく **5**（6 へ上げた）。**設定モーダルの「ここに無い項目」区画は既に撤去済み**で（TASK-123）、3 値を挙げているのは `Settings.svelte` 冒頭のコメントだけだったので、そこを直した。残る 2 点（`mergeDraft`・`normalize` の両方を通す）はそのとおりだった。

**キーは `collapsed_columns`・`folded_rows`・`hidden_rows`。** `default_` を付けないのは、保存するのが前回の実行で効いていた値そのもので、新しいものに与える既定ではないからである。`collapsed_columns` の要素型は Rust 側に `GridColumn` を新設した（`StatusColumn` は `Serialize` だけを持ち、未分類列に当たる値も無い）。**4 トークンが `StatusColumn` のものと一致することは検査が保つ** — 綴りが離れると、保存値が画面の知らない語で列を名乗る。

**復元時の正規化 は 2 つの規則を持つ**（doc-7 §5.1 に定義を書いた）。台帳に無い slug を落とす（AC #5）ことと、正準ステータス列 4 つがすべて入っている列集合を（未分類列を残して）空として読むこと。後者は画面の控えからは作れない値で（doc-7 §2.2）、利用者の選択を近似できる規則が無いのでどの列も読める状態へ倒す。

**行の側の正規化は `applyLedger` に置いた。起動では設定の読み取りが台帳より先である** ため、設定が届く場所で正規化すると保存された slug が全部落ちる — **これは実測した**（正規化を `applySettings` へ移す変異で、コンポーネント試験 2 本が落ちる）。`removeProject` が持っていた 2 行の filter は同じ規則の 2 つ目の機構になるので落とし、`applyLedger` に寄せた。

**保存は押下ごと**で、既定の並び順（`applyCardOrder`）と同じ形。書き手は 4 つある（列折畳み・行折畳み・表示切替行・すべてのプロジェクトを表示）。**保存が拒まれたら doc-11 §4 の ⑤ 通知 が述べる** — 3 値の控えはアイコンのみのボタンで 1 行の文を置く場所が無く、並べ替えの台帳書込みの失敗が既に同じ ⑤ を使っている。

**新しい試験は、修正を外して落ちることを確かめてから出した**（8 通りの変異: `normalize` の 3 行削除・`mergeDraft` の 3 行削除・`applyLedger` の正規化削除・`restoredColumns` を素の写しに・`storeGridState` の呼び出し削除 2 か所・正規化を `applySettings` へ移動・Rust のキー一覧から 3 行削除・`GridColumn` の serde を snake_case へ。すべて対応する試験だけが落ちた）。`wire_tokens.json` の `GridColumn` を snake_case に書き換える変異でも、フロントエンドの照合が落ちることを確かめた。

**検証**: `pnpm test` 1008 件・`pnpm run check` 0 error・`pnpm run lint` clean・`pnpm run build` 成功。`cargo test` 455 件・`cargo fmt --check` clean・`cargo clippy --all-targets -D warnings` は既定の 1.96.0 と **CI が使う 1.97.1 の両方**で clean。**AC #2 の実アプリでの再起動確認は目視依頼**（macOS。自動検査が押さえているのは、押下がファイルへ届くことと、保存値で起動すると畳まれた状態で描かれることまで）。
