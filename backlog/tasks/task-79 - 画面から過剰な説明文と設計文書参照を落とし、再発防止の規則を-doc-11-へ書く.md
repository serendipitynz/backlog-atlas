## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
「絞り込みは既定のままです。戻す条件も解除する条件もありません。」のような説明的な内容が設定画面・プロジェクト詳細を中心に散見される。そのような説明が必要だと感じる時点で UI として問題がある。必要な説明は残す（プロジェクトの登録解除のように、押した結果が取り返しにつくかどうかを述べるもの）が、状態を読めば分かることの言い換えは落とす。残すものはツールチップへ移して実操作のノイズを抑える。doc-3 §4.2 のような設計文書の節参照は利用者に意味がないので全廃する。

設計文の一文がそのままボタンラベルになっている箇所も同種の問題として直す。代表例は GitHistory.svelte:186 の「全面シングルビューで全件と関連解決の状態を読む」で、doc-8 §5 の一文である（画面設計案 02 の同じボタンは「全面表示で開く →」）。

範囲: このタスクが全画面を対象にする。当初は「個別画面ぶんは各画面タスクの受入条件で片付ける」前提で書いたが、削除の受入条件を実際に持つのは TASK-74 だけで、TASK-62・63・64・66・72 には無い。一方このタスクの AC #1・#2 は全画面を対象にしているため、実行者がどの画面を誰が扱うのか判断できなかった（2026-08-01 のレビュー指摘）。委譲はしないことにして境界を閉じる — TASK-74 が撤去した設定画面ぶんを除き、残る全画面の過剰な説明と設計文書参照はこのタスクで落とす。

## 4R の [P1] 2 件（2026-08-08）

**どちらも同じ誤り**: 「この理由は区画が既に出している」を、**区画ごとに確かめずに列挙した**。

- `REASONS_STATED_ON_SCREEN` の 7 件のうち 3 件が前提を満たしていなかった。文書**更新**フォームの
  title には（必須）が無く（作成モーダルにしか無い）、「変更はまだありません」「説明は変更されて
  いません」には寄りかかる印がそもそも無い。**doc-11 §5 は `disabled` の控えについては
  「常時表示する補助文」しか認めていない**ので、文を消した時点で理由が `title` だけになっていた。
  更新フォームには（必須）を足し、残る 2 つの控えは **§5 の 2 つ目の形**（`aria-disabled` ＋
  `aria-describedby`、常時 DOM にある span を区画が述べているときだけ不可視）へ移した。
- フィルタ帯は**既に §5 の 2 つ目の形**を採っていたのに、理由を null にしたことで
  `aria-describedby` の指す span が描かれなくなった。`title` も undefined で、**理由が丸ごと消えた**。
  span を無条件に描き、不可視の理由を持たせた。

**教訓（5R で 1 段狭めた）**: **可視の文を落としてよいのは、区画がその理由を可視で述べているとき**で、
そのとき控えは §5 の 1 つ目の形（常時表示する補助文）を満たしているので `disabled` のままでよい
——「（必須）」と書かれた空欄がその実例である。**区画が何も述べていない理由を隠すには 2 つ目の形が要る**
（`aria-disabled` ＋ `aria-describedby`）。4R の記録は「可視の文を落とせるのは `aria-disabled` のときだけ」
と書いていたが、これだと（必須）印に寄りかかっている 5 箇所（`disabled` のまま）が字面で矛盾する
（5R の [P2]）。**判定は控えの属性ではなく、区画が理由を述べているかどうかが先で、属性はその帰結である。**
「区画が述べている」を根拠にするときは**その区画を 1 つずつ開いて確かめる** — 列挙は事実であって規則
ではない、と自分で §8 に書いた通りである。

## 6R の [P2] — 狭めすぎた条文を、2 つの licence に分けて決着させた

5R で §8 を「隠してよいのは区画が理由を可視で述べているときだけ」へ狭めたが、**その条文の下では
「変更はまだありません」「説明は変更されていません」を隠せない**（どちらのパネルにも下書きが baseline と
同じであることを示す表示が無い）。**規則を書いた同じ PR の中に反例がある、が本 PR で 3 度目。**

**レビュワーの推奨は「2 件を列挙から外す」（文を戻す）だったが、採らなかった。** 目視がその 2 文を
名指しで不要と判断しており、**§5 の 2 つ目の形は理由を不可視にすることを元から認めている**（doc-11 §7 も
「理由を可視で出すかどうかは中身が決める」と書いている）ので、欠けていたのは実装ではなく条文の側だった。

**§8 は 2 つの licence を書き分ける形にした**: ①区画が理由を可視で述べている（印の付いた空欄。控えは
`disabled` のままでよい）、②理由が「まだ入力していない・まだ変えていない」だけを述べ、次の動作が
フォームから明らかである（§5 の 2 つ目の形にして a11y ツリーへ残す）。**原因が画面の外にある理由
（CLI 縮退・台帳読取専用・発行中・競合）はどちらにも当たらず必ず可視**とし、床を残した。
定数名も `statedOnScreen` → **`omitsSentence`** へ改めた — 旧名は①しか指しておらず、②を載せた時点で
名前が嘘になっていた。

**判断の型**: レビュワーの指摘は「条文と実装が食い違う」で正しく、**閉じ方が 2 つあるときに製品判断が
既に出ている側を動かさない**。動かすのは条文である。
