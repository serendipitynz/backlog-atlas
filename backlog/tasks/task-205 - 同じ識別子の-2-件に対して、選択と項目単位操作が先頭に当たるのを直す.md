## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-190 ＋ TASK-174 の実装で分かれた残り（2026-09-17）。**あちらは `{#each}` の鍵だけを直した** —
鍵が内容由来だったので同じ id・同じ `#N` の 2 件で区画が丸ごと落ちており、鍵を所在パスと位置へ替えて
2 件とも描けるようにした。**描けるようになって初めて見えるのがこの不具合である。**

**先頭一致 とは、同じ識別子を持つ 2 件に対して、選択・編集・項目単位操作が読み取り順で先に来たほうだけを
対象にする状態を指す。** 2 か所ある。

1. **プロジェクト詳細の 3 区画の選択。** `ProjectDetail.svelte` は選択を id の文字列で持ち、
   `documents.find((c) => c.id === docSelection)` で解決する（マイルストーン・決定事項も同型）。
   同じ id の 2 件では、2 枚目のカードを押しても 1 枚目が閲覧に出て、**両方のカードが「読んでいる」の
   強調を受ける。** `managedSelection` が decision-45 §1 へ渡す所在パスも 1 枚目のものになる。
2. **タスク詳細の受入条件の 項目単位操作。** `edit.ts` の下書きは受入条件を `number` で指しており、
   `toggleAcCheck` は `find((item) => item.number === number)` で 1 件目に当たり、`acRows` は
   `delta.check.includes(item.number)` なので **同じ #N の行が両方とも印を変える。**
   `acDeltaForCli` の `survivors.indexOf(number)` も 1 件目の位置を返す。

**単純に所在パス鍵・位置鍵へ寄せれば済む話ではない**ので、着手回に形を決める。
- 選択を所在パスへ替えると、`milestone rename` がファイル名も書き換えるため（doc-9 §4.2.1 の実測）
  **改称のたびに選択が落ちる。** いまは id で持っているので改称をまたいで選択が立っている
  （`ProjectDetail.svelte` の該当箇所がその理由を註に持つ）。所在パスと id の両方を持つ形になりうる。
- 受入条件の下書きを位置で持つと doc-5 §3 の 項目単位操作 の写像が変わる。CLI 側は
  `--check-ac` が削除後の位置を採り `--remove-ac` が読み取り順の位置を採る、という 2 つの枠を
  すでに持っており、そこへどう載せるかを決める必要がある。

**次リリース基準の判定**: 押したカードと開くファイルが食い違い、押した受入条件と印の付く行が食い違うので、
**利用者の行動を誤らせる**側に入る。加えて TASK-190 ＋ TASK-174 は**例外という大きな失敗を、静かな
食い違いへ替えている** — 直す前は画面が消えるので気づけた。m-4 として起票する。
