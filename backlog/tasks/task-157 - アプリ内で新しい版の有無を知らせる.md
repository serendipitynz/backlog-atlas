## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
decision-30 は v0.1.0 で自己更新を持たないと決め、版の告知は README と GitHub Releases の watch に置いた。watch していない利用者には新しい版が出たことが何も届かないので、その穴をアプリ側から塞ぐ。

行うのは版の告知だけである（decision-30 の語）。新しい版の取得も入れ替えも行わない — それは手動入れ替えのままで、アプリは Releases のページを既定ブラウザで開くところまでを担う。

新規依存も自プロセスの外向き通信も増やさずに書ける見込みがある。gh は decision-29 の外部コマンド解決で既に解決済みなので、gh release view を固定サブコマンド・引数配列（AGENTS）で子プロセスとして起動すれば、通信は gh のプロセスが行い、認証も利用者のものが効く。

引く契約は decision-14 だけではない。decision-14 は当初「呼び出しにタイムアウトを設けていない」と書いており、それを改めたのが decision-18・19 である。したがってこの照会も次を通す。① decision-19 の Decision 節が定める「gh 照会期限を 30 秒とし、gh の 1 回の起動ごとに掛ける」② その待機は、同じ節が共有モジュールへ移した期限付き待機を使い、独自に書かない ③ decision-14 の Decision 節が定める gh の起動条件（GH_PROMPT_DISABLED と GH_NO_UPDATE_NOTIFIER）を立てる。gh 不在・未認証・照会失敗・照会期限到達はいずれも縮退であって失敗ではない — 版の告知が出ないだけで、他の画面は変わらない。

いつ照会するか（起動時か利用者の操作時か）、結果をどこに出すか、照会の頻度と失敗の見せ方は、doc-11 の縮退の書き方に沿ってこのタスクで決める。決めた結果が doc の改訂を要するかどうかも着手時に判定する。

## 決定先行になった

着手時に 決 印は付いていなかったが、AC #6 が「決まっており／doc の改訂が要るかどうかの判定が済んでいる」を
受入条件にしていたので、指示書の入口の 1 つ目に当たる。**争点は 2 点をオーナーへ出し、同日回答を得た**
（2026-08-24）。

- **照会の時点**: 起動ごとに 1 回、自動で（アプリ設定に切替を持たない）。
- **告知の出し先**: ☰ の印 ＋ メニュー 1 行（上部帯を新設する案を退けた）。

**決めるものと、規則から落ちるものを分けて出した。** 照会の形（decision-14 の固定引数配列）・期限と起動条件
（decision-19 の共有の期限付き待機）・版の比較（既存の `Version`）・開く先（既存の既定ブラウザ起動）・
依存と接続（0 件・0 本）・失敗のとき何も出さないこと（AC #5）は、どれも既存の契約から落ちるので争点にしていない。

対応表は本文より先に確定した（初版 2026-08-24、告知の出し先 1 行を第 2 版で確定）。

## 残した契約

- **decision-44**（新規）— 版の告知は起動ごとの gh 照会 1 回で行い、出し先を ☰ の印とメニュー 1 行に置く。
- **doc-7 §2.1** — メニューに リリースページを開く の行を足し、項目の並びを 入口 → キーボード操作一覧 →
  リリースページ → プロジェクト一覧 に改めた。**Atlas の外へ出る行は押下でメニューを閉じる**ことも、
  既存の「群で決まる」規則へ 3 つ目の理由として書いた。
- **doc-11 §4** — **版照会 の失敗は ⑤ 通知 に載せない**という例外を理由付きで書いた。字面では ⑤ の
  「押下そのものが無い起動時の失敗」に当たるので、当たらないと決めた軸（その失敗が利用者から何を取り上げるか）を
  残した。**リリースページを開く の押下の失敗は ⑤ である。**
- AGENTS 和英は触っていない。起動順序・メニュー・上部帯はどれも doc が正本で、AGENTS は写しを持たない。

## 実測 (2026-08-24、この作業機)

**gh 2.97.0 で `gh api --hostname github.com repos/<owner>/<repo>/releases/latest --jq '.tag_name'` を測った。**

- 温まった照会は **0.49・0.57・0.62 秒**。**初回だけ 6.80 秒**で、これは冷えた接続ぶんである。
  decision-19 の gh 照会期限 30 秒には冷えた回でも遠い。
- **未認証は確かに縮退へ落ちる** — 設定ディレクトリを空にしてトークンを外すと **exit 4**、stderr は
  `gh auth login` の案内。**パブリックリポジトリでも `gh api` は認証を要する。**
- 返る値は `v0.1.0`。**`--paginate` は要らない**（`releases/latest` は単一オブジェクト）。

**画面は借り物 playwright で、実物の `App.svelte` を WebKit と Chromium に載せて測った。**

- **印** は 5×5px の円、`--info`、控えの右上隅。**10 テーマすべてで地に対して 5.86:1 以上**（最小
  atlas-light 5.86、最大 rose-pine 10.37）。**図形に触れない** — 控え 24.625px の中央に図形 11.953px なので
  隅は 6.33px で、5px の点は 1〜6px を占めて 0.33px 空く。**5px が触れずに置ける最大である。**
- **☰ の名前** は「メニュー（新しい版があります）」/「Menu (a new version is out)」へ変わり、告知が無いときは
  「メニュー」に戻る。**版の値は名前に入れていない。**
- **メニューの行** は「リリースページを開く」＋右に「新しい版 0.2.0」/「Version 0.2.0 is out」。
  **区切り線は 2 本**（リリースページ行の前後）で、告知の有無で位置は動かない。
- **パネル幅** は WebKit 184.97 → 235.08（ja、告知あり）→ 290.91（en、告知あり）、Chromium 196.06 → 246.17 →
  290.80。**上限（24rem と窓幅 90% の小さいほう）には当たらず、横方向のはみ出しは 3 状態とも 0px。**
- **Windows の枝**（Windows の UA を渡して 重ね型 を false にした状態）でも印は出て、`pageerror` は 0 件。
- **押下の失敗**（既定ブラウザが起動しない側）ではメニューが閉じ、⑤ 通知 に境界の文が出て、`pageerror` は
  0 件。**印は消えない。**

## 測っていないこと（目視の依頼範囲）

- **実機の Tauri 窓では測っていない。** 上はどれも borrowed engine の上の実物のコンポーネントで、
  実機の WKWebView・WebView2・WebKitGTK では見ていない。
- **`gh` を持たない実機・未認証の実機での画面**は見ていない。どちらも縮退で何も出ない側なので、
  「何も変わっていないこと」を目で確かめてもらいたい。
- **印が本物のデータで出るのは v0.2.0 の公開後である。** それまで 公開されている版 は 利用中の版 と
  等しいので、実機で印を出すには照会の答えを差し替える必要がある。上の測定はハーネスのつまみでそれを行った。

## 途中で見つけたもの

- **ハーネスの偽 IPC が、既定ブラウザ起動の失敗を実物と違う形で返していた。** `{ kind, detail }` だけで
  `reason` を持っておらず、画面側が `reason.reason` を読んで投げ、⑤ 通知 が出ないまま unhandled rejection に
  なっていた。**製品側の不具合ではなくハーネスの不備**だが、これがあると押下の失敗を測れない。同じ形だった
  本文リンクの側も併せて直した。**偽 IPC は wire の形をそのまま返すこと。**
- **自分で書いた試験 1 本が過剰主張だった。** `lookup` の「stdout の先頭行を読む」を名乗っていたが、
  全体を `trim()` して渡す変異でも緑になる（`Version::parse` が空白で切って先頭トークンを取るため）。
  **主張を「照会が書いた tag が答えになり、tag の後ろの出力はそれを変えない」へ書き換えた。**

## 変異で確かめたこと

提出前に修正を外して落ちることを確かめた。

- 版の比較を落とす → 2 本が落ちる。
- 終了状態の門を落とす → 1 本が落ちる。
- 待機の `Err` を「答えなし」ではなく成功として扱う → 不在の枝と期限到達の枝が独立に落ちる。
- 起動時の照会に `await` を付ける → 画面横断契約の 1 本が落ちる。
- 起動時の照会を落とす → 同じ 1 本が落ちる。
