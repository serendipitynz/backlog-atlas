## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
PR #64 の目視フィードバック (2026-08-05) 由来。区画ナビに「決定事項」を足し、対象プロジェクトの backlog/decisions を一覧・閲覧できるようにする (閲覧のみ)。読み取り層は decisions を走査しているが (decision-24 で不整合の対象が管理ファイル 1 件へ広がったため)、**画面に出す区画が無い** (`ProjectDetail.svelte:884` の註)。

**2026-08-13 に m-3 から m-2 へ繰り上げた（ユーザー判断）。** PR #109 で README を公開向けに書き直したとき、ユーザーがこのアプリの位置づけを「複数のプロジェクトのタスク・文書・**決定事項**を横断的に管理するためのツール」と述べた。閲覧手段が無いまま公開すると README がその位置づけを書けないので、v0.1.0 に入れる。

**README への追記もこのタスクの範囲である。** PR #109 の README は「できること」に決定事項を挙げていない（無い機能を書けないため）。実装したら和英の「できること」へ 1 行足す。**AGENTS.md / AGENTS.ja.md「リリース」節がタグ前に README と出荷ビルドを突き合わせることを求めているので、落としても TASK-102 の直前で捕まる。** それでもここで足すのが正しい — あの検査は最後の網であって、書き足す担当ではない。

**更新手段の有無は着手時に実測する。** `backlog decision` は 1.49.3 で `create` のみを持ち、その options は `<title>` と `-s` だけである（PR #109 で実測）。したがって**閲覧のみに留めるのは CLI 側の制約に沿っている** — 更新 GUI を作っても発行手段が無い。

## 決定先行判定

**決 印は無いが契約を変えるので判定を通した**（doc-10 に節を新設するのは契約の変更である）。

1. **区画ナビが 4 項目から 5 項目になる。** 画面設計案 07 は区画ナビを「4 区画すべてが共有する」と
   書いている（doc-12 §8）ので、意図的な逸脱として記録した（doc-10 §10 の 1 件目・画面全体で 9 件目）。
   **07 が意思決定について何も書いていないこと自体は逸脱の根拠にならない** — 書かれていないことから
   外れることはできない。
2. **足す位置**は既存 4 項目の相対順序を変えない位置から採り、そのうち一覧列を持つ 3 区画が隣り合う
   側を選んだ。新規タスク区画だけが一覧列を持たない。
3. **閲覧ヘッダの定義が「編集」を束ねていた。** 新語を立てず定義を広げた — 立てると decision-24 の
   1 本の規則（理由行は選択が開く場所の見出し下）が 2 つの語に分かれる。広げた先は grep で数え、
   偽になる記述が 0 件であることを確かめた（doc-10 18・decision-24 2・decision-25 1・実装のコメント 13）。
4. **件数の置き場**（下の「ユーザー確認」②）。ヘッダの件数を 3 件から 1 件へ減らすので、これも
   意図的な逸脱である（doc-10 §10 の 2 件目・画面全体で 10 件目）。**区画ナビの括弧のほうは逸脱に
   数えない** — 07 は項目を列挙しているが、項目に件数を添えるかどうかを書いていない（TASK-112 の
   フィルタ帯の funnel と同じ扱い）。

## ユーザー確認（2026-08-13）

- **① 閲覧のみでよい。**「backlog browser でも同様の挙動」。**AC #3 の書き直しはこれで確定した** —
  旧 AC #3「提供しない操作は理由つきで区画に載る」は 2026-08-05 の起票で、**2026-08-08 に TASK-123 が
  提供しない操作区画を撤去してユーザーが確定した判断より前**である。doc-11 §5・§8 と doc-10 §9 が
  「控えを置いていない操作の不在を画面で述べない」を例外なしの本則にしているので、旧 AC を字義どおり
  満たすと確定済みの判断を本タスクだけで反転することになる。
- **② 件数は区画ナビの括弧へ、ヘッダはタスクだけ。** 本家 backlog browser が左ナビに
  `TASKS (162)`・`DOCUMENTS (12)`・`DECISIONS (30)` の形で持っているのに合わせた（ユーザー提示の画面）。
  **タスクだけがヘッダに残るのは、この画面にタスクの区画が無いためである** — 区画ナビの括弧は
  「その区画の一覧が何件持っているか」であって、区画を持たないものの件数を置ける場所ではない。
  **`(0)` と「括弧を出さない」を分けた**（`sectionCount` が `number | null` を返す）: 概要と新規タスクは
  数える対象が無く、読み取り前は件数そのものが無い。0 と述べると、その 2 つが「空の一覧」と同じ絵になる。
- **③ README の「閲覧のみで、編集はできません（…）」は不要**（「backlog browser 本家の挙動からも自明」）。
  **落とした。** doc-11 §8 の本則（画面が操作も欄も見せていないものについて、なぜ無いかを述べない）を
  README 側へ広げた形で、新しい例外ではない。
- **目視は 3 点とも回答済み。** ①カードの読みやすさ OK、②件数は上記、③編集の入口が無いこと
  「backlog browser と同等なので、全く違和なし」。**実機の画面写真で確認された**（30 決定事項・
  162 タスクの実台帳）。

## 実測

**Backlog CLI (v1.49.3)**: `backlog decision` は `create` のみを持ち、options は `<title>` と
`-s/--status` だけである（2026-08-13 に再実測）。本文を書く手段は作成時にも作成後にも無い。

**実エンジン** (`_sandbox/decision-check/measure.mjs`。WebKit・Chromium、窓 1280x800)。
**文書区画を対照として同じ数を測ってある。**

- **区画ナビ**: `概要 / 文書 (3) / マイルストーン (3) / 決定事項 (14) / 新規タスク`（両エンジン）。
  **ヘッダは `タスク 7` のみ。**
- **列幅**: 区画ナビ 205.78 / 一覧列 274.59 / ペイン 799.63 px。**文書区画と 3 列とも同値。**
- **一覧見出し行の控え**: 文書区画 1（作成の入口）に対し **決定事項区画 0**。
- **区画の中の押せる控え**: **カードだけ**（`section.split-section button` を全数え上げ、14 枚 = カード数）。
  閲覧ヘッダの控えも 0。**AC #3 はこの 2 つの数え上げで満たしている。**
- **行長上限**: 窓 1900px でペイン 1419.63px に対し本文ブロックは **768px = 48rem で止まる**。
  **文書区画の同じ本文も 768px。** 窓 1280px では 743.66px で上限に当たらないので、その幅の数は
  上限について何も述べていない。
- **ペインだけが先頭へ戻る**: 窓 900x420 でペインは 610（WebKit）/ 629（Chromium）px スクロールでき、
  下端まで送ってから別のカードを選ぶと **0**。**一覧の位置は動かない**: 一覧は 587 / 579 px
  スクロールでき、200 まで送ってから**その時点で見えているカード**を押して **200 のまま**。
- **不整合**: カードの ⚠️ は 1 つ、アクセシブル名は理由の全文、閲覧ヘッダの理由行は 1 行。
- **写せなかったファイル**: 理由行は `解析不能: このファイルを決定事項として写せませんでした` —
  **画面語が実際に刷られるのはこの経路**である（欄も detail も無いときだけ種別の名詞が出る）。
- **横あふれ 0px**、**コンソールエラー 0 件**（両エンジン）。画像は `_sandbox/decision-check/`。
