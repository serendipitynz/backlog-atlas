## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-80 が実装内不統一として分類した 2 件。画面設計案に対応する転記が無く、原文への追随でも逸脱でもない。どちらも作成モーダルで同時に見えるので 1 セッションで扱う。

① **`<select>` の高さが `<input type="text">` と揃わない** (TASK-117 の目視、2026-08-07)。文書作成モーダルの title・type・path が 1 行に並んだとき type だけが低い。ユーザーの指摘は「ここに限らず」で、画面全体に効く規則の欠落として出ている。doc-11 §2.2 (寸法) はフォーム部品の高さを持っておらず、各コンポーネントが素の `<input>`・`<select>` を出しているだけなので、揃うかどうかはエンジンの既定に委ねられている (WebKit と Chromium で `<select>` の既定 padding は違う)。**直す先は 1 画面ではなく doc-11 §2.2 と `app.scss`** — 1 画面で揃えると同じ不統一が次の画面で再発する。

② **作成モーダルの欄の並びが 2 区画で揃わない** (TASK-117 の目視、2026-08-07。2026-08-08 の目視でユーザーが方向を明示)。文書は title・type・path を横 1 行に、マイルストーンは名称・説明を縦に積む (`create-doc.png`)。**文書側をマイルストーン側へ合わせる。** doc-10 §1 は作成モーダルを「2 区画とも同じ型を使う」と定めたが、揃えたのは入口と層であって欄の配置ではないので、同節に欄の配置を含めるかどうかを決める。

`create-doc.png` はもう 1 点、「本文は作成時には渡せません。」を不要と指している。doc-11 §8 の 代替経路の案内 に当たるかを判定してから始末する。

## 着手して分かったこと

- **規則は実装に 3 回書かれていて、doc に 1 回も無かった。** `--bar-control`（1.4rem）・`--head-control`（1.2rem）・`--frame-control`（1.4rem）がそれぞれ「`box-sizing: border-box` ＋ 述べた `height`」を別々に導いており、**揃っていた行は全部それを宣言していて、不揃いだった 4 行は 1 つも宣言していなかった。**
- **AC #3 を実装すると AC #1 の「同じ行」規則がこの指摘を覆わなくなる。** 文書作成モーダルの 3 欄を縦に積むと 1 行 1 部品になるので、「同じ行に並ぶ部品は揃っている」は満たしたまま 27.73 / 18 / 27.73 が残る。範囲を 入力面 にした根拠がこれで、doc-11 §2.2 にもそう書いた。
- **WebKit は、native menulist のまま描いている `select` に著者の `height` を効かせない。** 設定モーダルの 3 つの `select` だけが枠も面も持っておらず、同じ 1 つの `height: 1.75rem` に対して WebKit 18px・Chromium 28px を返した（この差は変更を入れた後に実測して見つけた）。他の 4 画面の `select` で同じ宣言が両エンジンとも効いたのは、そちらが枠と面を持っていたためである。設定モーダルの `select` に入力欄と同じ枠を与えて解決した（`background` は `transparent` ではなく `--inset` — `transparent` では menulist の描画が残り、`select` を入力欄と見分ける矢印も native の描画に付いている）。
- **控えだけの領域はフォーム部品を持たない。** doc-11 §1 の定義は `input`・`select` と**それらと同じ行に並ぶ**押しボタンを指すので、レーンヘッダ行とタスク詳細の見出しの 1 行目（どちらも押しボタンだけ）には当たる部品が 1 つも無い。**初版の §2.2 はその 2 つを「入力面を持たない行」の例に挙げていて、指す先が空集合だった**（PR #97 の 1R [P2]）。§2.2 に 控えの群 を第 2 の対象として立てて直した。
- **その対象の単位は行ではなく群である。**（PR #97 の 2R [P2]）タスク詳細の見出しの 1 行目には、群のほかに**横断タスクID のコピー**が同居しており、それは ID の隣に付いて **ID の寸法から大きさを取る**（doc-8 §2.2 が「ID から離れた位置に置かない」と定めている。実測 21.59px 対 群の 22.39px、両エンジン）。**行で括ると、この 1 件が規則違反になるか doc-8 §2.2 を壊すかのどちらかになる。**1 行に群と、群に属さない控えが同居しうる。
- **AC #5 の対象は着手時点で既に画面から落ちていた。** 「本文は作成時には渡せません。」は TASK-135 の目視反映（`8eaaa64`、2026-08-10）で落ちており、`src/` のどこにも無い。残っていたのは判定の帰属だけで、doc-10 §5 へ書いた。TASK-136 の②と同じ形である。

## 測っていないもの（目視へ回す範囲）

- **実機の Tauri WebView。** 借り物 playwright の WebKit は WKWebView と同系だが同一ではない。Linux・Windows の webview は測っていない。
- **窓幅は 1280×800 の 1 条件だけ。** 28px の欄が狭い窓で折り返しにどう効くかは測っていない。
- **暗いテーマは画像だけ取った**（`_sandbox/task-141/*-atlas-dark.png`）。数値は atlas-light で取っており、高さは色に依存しない。
- **実際にホバー・フォーカスしたときの見え方。** 高さを述べたことでフォーカスリングの位置が変わっていないかは数値では出ない。
- **実行前確認（doc-11 §12）の 2 答えの高さ。** 1.75rem を与えたが、harness で状態遷移の控えに届かず開けていない。**他の 3 か所の確認の群は開いて測ってある。**

3R の [P3] は**その数え上げが開いた画面しか見ていない**ことで（確認・復旧の答えの群が
段階から外れたまま残っていた）、答えの群にも段階を与え、**確認の状態を実際に開いてから測り直した**:
作成モーダルの破棄前確認 22.39・上部帯の破棄前確認 22.39（どちらも 1.4rem）、文書区画の破棄前確認 28

4R の [P3] は**同じ形の 5 件目**（更新前競合の復旧の 2 控え）だったので、**1 件ずつ潰すのをやめて
