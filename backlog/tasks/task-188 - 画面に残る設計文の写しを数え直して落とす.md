## Description

doc-11 §8 の落とす 4 種のうち **設計文の写し**（設計文書の本文の一文を、指示対象を利用者の側へ置き換えずに画面へ刷ったもの）に当たる画面文を、全画面で数え直して落とす。**日英の両方**が対象である — 写しは 文言表 の 2 ファイルに 1 つずつあるので、片方だけ直すともう片方に残る。

**起票のきっかけはオーナーの目視**（2026-08-16、TASK-184 の英語表示確認）。「slug の説明が長い。他の説明文も同様。ちょっと冗長傾向にありそう。日本語も含め」という指摘で、**冗長さの好みではなく既存の契約違反として扱えることが分かった**ため起票した。

**実例（この 1 件は確認済み）** — プロジェクト詳細の `slugImmutable`。doc-10 §4.1 が画面に要求しているのは 2 点だけである: 「変更するには登録を解除して登録し直すこと」「そのとき履歴表示の同一性が切れること」。ところが画面は doc-10 の**設計上の理由文**（「slug は横断タスクID の左辺として全タスクの参照に使われ」）まで写している。これは doc-11 §8 の 設計文の写し そのものである。

- 現状(EN, 約 45 語): `The slug is the left-hand side of every cross-project task ID, so it is referenced by every task and no way to change it is offered. Using a different one means unregistering and registering again, and the Git history view's identity is broken at that point.`
- 現状(JA): `slug は横断タスクID の左辺として全タスクの参照に使われるため、変更手段を提供しません。別の slug にするには登録を解除して登録し直すことになり、そのとき Git 履歴表示の同一性は切れます。`
- 案(EN, 約 25 語): `It cannot be changed. To use a different slug, unregister and register again — the Git history view's identity is broken at that point.`
- 案(JA): `変更できません。別の slug にするには登録を解除して登録し直すことになり、そのとき Git 履歴表示の同一性が切れます。`

**範囲はオーナーが 2026-08-16 に「doc-11 §8 違反だけ」と確定した。** gui-text-minimal（区画の説明は 1 文、項目ごとの解説は `?` ポップアップへ）まで広げない — あちらは `?` の導線が無い区画に新規実装が要り、doc-10/11 の改訂を伴うので決定先行になる。本タスクは**判定基準が doc-11 §8 に既にあるので争点を持たない。**

**数え方**: 画面文（`ja.ts`）の各文について、その文が doc の本文の一文と同じことを述べていないかを見る。**列挙で始めない** — 文言表 の全項目を舐めて判定する。判定した結果は「落とした / 残した（残した理由）」の両方を記録する。doc が画面に要求している項目そのものは落とさない（doc-11 §8 は書き方の規則であって、掲示要求を無効にしない）。

**文言を押さえている試験も一緒に動く。** 文言表 の 2 ファイルだけで閉じる作業ではない — `src/lib/project-detail.test.ts` は `slugImmutableNote()` が「登録を解除して登録し直す」と「同一性は切れます」の 2 つを含むことを主張しており（`:385`・`:386`）、上の 案(JA) は後者を「同一性**が**切れます」に変えるので、**そのままでは落ちる。** 着手する回は `ja.ts`・`en.ts` を触る前に、落とす文それぞれについて**その文言を主張している試験を grep で探す。** 取得子名（`slugImmutableNote`）でも、文字列の断片でも引ける。**これは列挙ではなく手順である** — ほかにも在りうるので、1 件ずつ数え直す。

## 判定基準と、舐めた集合（AC #1）

**判定基準は指示対象である。** doc-11 §8 の 設計文の写し は「設計文書の本文の一文を、指示対象を利用者の側へ置き換えずに画面へ刷ったもの」なので、当たるかどうかは**その文の指示対象が、利用者が画面で見られるものかどうか**で決めた。doc の語彙を使っていることは判定にならない — 指示対象が既に利用者の側にあるなら、語が doc のものでも当たらない。当たるのは、指示対象が**設計の層・部品の名**（読み取り層・更新アダプター・操作写像）、**doc の測定行為**（実測）、**doc の分類名**（同一プロジェクトの移動）のように、画面のどこにも出ていないものである。

**舐めた集合は 文言表 の全項目で、列挙から始めていない。** `ja.ts`・`en.ts` はどちらも**葉が 734**（`shortcutHelp.assignment.*.preventsDefault` の `null` 3 件を除く。鍵集合は `Catalog = typeof ja` が一致を保つので、両カタログの数が一致することは型の側から出ている）。数え方は、カタログを実行時に読んで再帰的に葉を数える（関数の項は placeholder 引数で呼んで文字列にする）。**行数では数えない** — 1 項目が複数行にまたがる。

全項目を読んだうえで、**機械的な裏取りを 2 本**かけた。どちらも「読んだ結果」を疑うためのもので、これ単独では判定にしていない。

1. **doc 本文との最長共通部分列**。各項目の文字列と `backlog/docs/`・`backlog/decisions/` の全文を突き合わせ、14 文字以上重なるものを出す → **85 件**。大半は共有語彙（識別子・ファイル名・画面語）で、一文の写しではない。
2. **設計側の指示対象語の数え上げ**。**語幹で引く**（複合語で引かない）。日本語は 照合・窓・走査・写像・層・アダプター・実測・台帳・正本・本設計・導出・対象プロジェクト・読み取り、英語は read・adapter・mapping・measured・this design・the ledger・scan・window・referent。**註ではなく画面へ出る値だけ**を対象にする（`ja.ts` には `doc-` が 104 回あるが全部 JSDoc で、画面文の値には 1 つも無い）。

**この 2 本目は 1 度取り違えている。** 初回は `照合方法` という**複合語**で引いており、`照合` の語幹なら画面文の値に 4 件ある。**取りこぼしたのは `mark.postCheckConflict` で、レビュー 1R の [P2] がそれを突いた**（下の 7 件目）。**画面文を数える回は語幹で引くこと** — 複合語で 0 件・1 件を得ても、それは「無い」の根拠にならない。

**当たると判定したのは 7 件、当たらないと判定したのは 727 件。**

## 落とした・書き直した 6 件（AC #2・#3）

いずれも日英の 2 ファイル両方を直した。

1. **`projectDetail.slugImmutable`（AC #3）**。doc-10 §4.1 の設計上の理由文（「slug は横断タスクID の左辺として全タスクの参照に使われ、変更は同一性を切る」）を、指示対象のまま刷っていた。**§4.1 が画面に求めている 2 点だけにした** —「変更するには登録を解除して登録し直すこと」「そのとき履歴表示の同一性が切れること」。約 45 語 → 約 25 語（英語）。
2. **`taskDetail.typeNotEditable`**。doc-8 §4 の一文をほぼそのまま写しており、指示対象が 読み取り層・更新アダプター・操作写像 と `--type` だった。**doc-8 §4 は「画面はこの 2 つの理由を Type 区画に述べる」と要求している**ので、撤去ではなく書き直しにした（doc-11 §8:「doc が画面に要求している項目そのものは落とさない」）。2 つの理由は残し、指示対象を利用者の側へ移した。
3. **`taskDetail.commandError.updateRejected`**。「更新アダプターが実行前に拒否しました」の主語 更新アダプター は doc-5 §1 が部品に付けた名で、画面のどこにも出ない。**「更新を実行前に拒否しました」** にした。
4. **`projectDetail.removeMovesTheFile`**。文そのものは doc-10 §6 が画面に要求しているので残し、末尾の **「（実測）」だけを落とした**。指しているのは doc-9 §4.2.1 がその事実を測った行為であって利用者の状況ではなく、decision-27 が 版数 を落としたのと同じ型である。
5. **`projectDetail.rootMoveNote`**。冒頭の **「同一プロジェクトの移動として扱い、」を落とした** — doc-3 §3.2 が台帳操作に与えた分類名である。doc-10 §4.1 が画面に求めているのは「どちらの値が送られるか」で、そこは残っている。
6. **`projectDetail.descriptionHeading`**。**「読み取りは次の `##` までを説明として扱うため」を落とした** — doc-10 §6 の読み取り層についての一文である。§6 が求める理由は「保存しても画面に出なくなる」ほうで、そちらは残した。
7. **`mark.postCheckConflict`**（レビュー 1R の [P2] で足した）。**「照合後競合窓の事後通知」と「窓内の」を落とした** — 照合後競合窓 は doc-9 §1 が「実行前照合の完了から書込み完了まで」と定義した時間帯の名で、その時間帯は画面のどこにも出ていない。**doc-9 §5 が求めているのは 2 つの 理由行 が書き分けられていることだけ**なので、「更新前競合」／「保存後に判明」で足りる。**対になる `preUpdateConflict` の 更新前競合 は残した** — `conflictStopped`・`outcomeConflict`・`versionProbeFailed` が既に画面へ出している語で、ここで初めて出会う名ではない。**同じ事実の利用者側の書き下しは `taskDetail.postCheckMismatch` が既に持っている**（「照合の完了後〜書き込み完了の間に入った外部更新」）。

## 残したもの（AC #4）

当たらないと判定した 728 件のうち、判定が割れうるものを理由付きで挙げる。

- **doc が画面文そのものを指定しているもの**は写しではない。`projectDetail.taskCreateNote` は doc-10 §7 が引用ブロックで画面文として書いている文、`projectDetail.aliasEffect.*.note` の 4 態は doc-10 §4.2 が「行ごとに次の 4 態を区別して示す」として並べたものである。doc-12（画面設計案の転記）に語があるものも同じ。
- **指示対象が既に利用者の側にあるもの**は、語が doc のものでも当たらない。
  - `projectDetail.unregisterScope` の「対象プロジェクトの Backlog ルート・管理ファイル・Git リポジトリには触れません」は doc-3 §4.2 の一文の写しだが、指しているのは画面が現に開いているそのプロジェクトである（直前の文が「このプロジェクト」と名指している）。設計の層も部品も測定行為も指していない。これを当たると取ると、doc の語彙を使った文が全部当たることになる。
  - `swimlane.lastColumnHeld` の「すべて畳むと、どの列のカードも読めない画面になります」は doc-7 §2.2 の一文だが、指しているのは利用者自身の画面である。§5 が求める 不可の理由 でもある。
  - `projectDetail.renameNote`（doc-10 §6 の改称の一文）も同じ — id・milestone 値・タスクはどれも画面に出ている。
  - `projectDetail.overviewReadOnly` の「登録ファイルを書かないので」は、主語も目的語も画面に出ている名（3 区画と 登録ファイル）である。
- **画面文の値に残った設計語は 5 つで、いずれも理由がある**（語幹 `照合`・`走査`・`層`・`対象プロジェクト` で数え直した値）。
  - `settings.storageIndeterminate`「不定（走査対象外の場所にあるファイル）」— 走査 の対象外という事実が指しているのは利用者自身の Backlog ツリーの中の場所である。語そのものは 保存区分 の値の名なので 状態文 に当たる（doc-11 §8 の末項）。
  - `mark.unreadFiles`「…照合できません」と `mark.versionUnverified`「照合対象の版が確かめられませんでした」— 照合 は動詞・目的語として使われており、指しているのは利用者のファイルとその版である。時間帯の名ではない。
  - `taskDetail.commandError.uncheckableTarget` の 照合方法 — **doc-9 §5 が「その理由がバージョン不整合の検出ではなく照合手段の不在であることを示」すことを画面に要求している**。文は設計の部品を主語に立てていない（「本設計が」とは書いていない）。なお doc-9 §4.2.4 により現行の更新操作に照合不能なものは無く、この文は現状どこからも出ない。
  - `shell.projectUnidentified`「対象プロジェクトを特定できません」— 上の `unregisterScope` と同じ理由。
  - `shortcutHelp.assignment.closeOverlay.operation`「開いている層を閉じる」— 層 は 被せ層 のことで、押した時点で画面に出ているものである。`shortcutHelp.scope.overlay` が「モーダル・メニュー・ポップオーバーの内側」と書き下してもいる。
- **「CLI に手段が無い」の形は当たらない**（doc-11 §8 が明文で持つ）。`taskDetail.lastElementHeld`・`draftReadOnly`・`closedReadOnly`・`noWayBackFromClosed`・`criteriaBodyNote` はいずれもこの形で、指しているのは利用者が使っている CLI である。
