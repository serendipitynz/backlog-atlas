## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
2026-08-09 のユーザーフィードバック (`info-label.png`)。設定を保存すると上部帯 ⑤ 通知として「設定を保存しました。」が出る。ユーザーの指摘は「そもそも必要か。必要ならトースト的なものがよい。失敗したときにその内容をアラートのような形で見せるのはアリ」。

**決定先行**: doc-11 §4 は上部帯 6 種を重要度の固定順で積み、⑤ 通知だけが × で閉じられると定めている。⑤ を「成功を伝える場所」として使うのをやめるなら、⑤ に残るものが何かを決め直す必要がある。**⑤ が空になるなら `BandKind` からその 1 種が消える。残る種の総数は書かない** — TASK-131 も ⑥ を落とすので、総数は 2 件の実行順で変わる。加えて TASK-74 の目視が残した「⑤ の変化が分かりづらい」も同じ対象で、こちらで一緒に始末する — 帯を出し続けるなら見え方を直し、やめるなら見え方の問題ごと消える。

失敗の提示は今も押した場所の隣に出る (doc-8 §6.3 / TASK-74)。それを変えるかどうかもここで決める。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
決定先行の手順を 1 セッションで通した（対応表確定 → 争点提示 → ユーザー確定 → 実装 → 試験）。**doc 改訂だけで足り decision は書いていない**（19 例目）。改訂は doc-11 §4 と §7、および §10 の 1 行。

**着手して分かったこと 2 件が、AC の前提を覆した。**

- **⑤ は空にならない。** ⑤ を立てている箇所を全数（10 か所）数えると、成功そのものは 2 件だけで、残り 8 件は失敗・差し控え・画面が述べない帰結だった。したがって **AC #3 の条件節（⑤ が空になるなら `BandKind` から 1 種が消える）は発火せず、`BandKind` は 5 種のまま**である。doc-11 §4 が「閉じた集合は表そのものが持ち、本文はその数を書かない」を TASK-131 で立てたときに TASK-134 が ⑤ を落とす前提で書かれていたので、その帰属を直した — **落ちる行が事前に分からないことこそ、あの規則の値打ちである。**
- **AC #2 は既に実装されていて、欠けていたのは doc だけだった。** `Settings.svelte` の下部操作行が「保存できませんでした: …」を控えの隣に出し、失敗では層を閉じない（TASK-74 AC #2）。**どの doc もその置き場を持っていなかった**ので、doc-11 §7 に項を 1 つ足した（TASK-70 の「doc が覆っていない」型）。

**ユーザーが確定した 3 点**（いずれも推奨案）: ①保存成功はどこにも出さない、②同じ規則が当たるレーンセルの作成成功の帯も同じ PR で降ろす、③AC #4 は ⑤ の見え方を触らずに閉じる。⑤ の左端 4px を `--info` のままにすること・閉じられるままにすることはこちらで決めた。

**doc-11 §4 へ書いた規則**は 2 つある。**発行が通った事実そのものは ⑤ に載せない** — 発行の結果を述べる本則の置き場は **控えの隣の結果文**（発行した控えと同じ層・同じ区画に置く、その発行の結果を述べる文）であり、⑤ はその置き場が無いとき（押下が無い起動時の失敗、控えの隣に置き場を持たないレーンヘッダの並べ替え、押した層が結果より先に閉じるもの）の届け先である。**⑤ に成功が載るのは、押下の結果として画面に現れた姿が押下の名前と食い違い、その理由が画面のどこにも無いときに限る**（状態遷移が詳細を閉じたこと、作成したカードが絞り込みに落ちて出ていないこと）。

**実装は 3 か所。**

- `App.svelte` の `saveSettings`: `notice = "設定を保存しました。"` を落とした。**`null` を代入して落とす**（消すだけにしない）— 保存より前の帯（「設定を読み込めませんでした。既定値で動きます。」）は保存後の設定については偽であり、通った保存の隣に残ると今回が失敗したように読める。`retry` と `move` が成功時に同じことをしている。
- `App.svelte` の `submitLaneCreate`: 発行が通ってカードが絞り込みに落ちないときは帯を立てない。落ちるときと通らなかったときは従来どおり。
- `band.ts` の `BandInputs.notice` の註を、⑤ が運ぶものの範囲へ書き替えた。

**AC #4 は対象ごと無くした。** TASK-74 の目視が言った「保存後の ⑤ の変化が分かりづらい」は、その帯が無くなったので事象として起きない。⑤ だけを強める案は採らない（目立ち方は doc-11 §4 が全種共通で決めており、TASK-74 が既にそう判断している）。**気づくのが遅れて害になるのは、その帯が唯一の報せである場合に限る** — 残る ⑤ はどれも読まれた時点で内容が要るもので、見逃した瞬間に無価値になる成功の報せとは性質が違う。

**画面横断契約を 2 件足した**（`App.component.test.ts`）。「保存が通っても上部帯は立たない」「保存が通らなければ層は残り、失敗は控えの隣に出る」。**二つで一つの規則なので両方置いた** — 片方だけだと残る半分が黙って反転する（成功で帯を立て直しても失敗側は通り、失敗で層を閉じても成功側は通る）。どちらも呼び出し元からしか固定できない: `band.ts` は 通知 か `null` を渡されるだけでどの押下が産んだか知らず、`Settings.svelte` はシェルへ失敗文を返すだけで帯を見ない。

**両方とも変異で確かめてから置いた。** `notice = "設定を保存しました。"` を戻すと AC #1 の試験が落ち、`saveAndClose` から `if (failure === null)` を外すと AC #2 の試験が落ちる。

**実測は回していない。** 変えたのは帯を立てるかどうかだけで、帯・モーダル・レーンセルのマークアップも寸法値も触っていないので、実エンジンで測る対象が無い（測っても変更前と同値になることが分かっている）。

**測っていない＝目視に回すもの**: 実アプリで設定を保存したときに上部帯が立たないこと、保存に失敗したときに設定モーダルが残って「保存できませんでした: …」が下部操作行に出ること、レーンセルで作成したカードが絞り込みに落ちたときだけ帯が立つこと。
