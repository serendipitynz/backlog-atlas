## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
2026-08-11 のユーザーの要求である。**窓の大きさ を、アプリを終了して起動し直した後も引き継ぐ。窓の大きさ とは、アプリ窓の幅と高さの 2 値を指す。**

**契約の欠落である。** 窓の大きさを保持の対象として扱った doc・decision は無い — 「窓幅」は doc-7 §2.1 のメニュー幅上限と doc-8 §2.2 の主列幅が計算に使う入力値としてだけ現れる。`src-tauri/tauri.conf.json` は `width: 1200`・`height: 800`・`minWidth: 640`・`minHeight: 480` を持ち、**毎回 1200×800 で開く**。最小寸法は TASK-145 が doc-11 §13 の規則を成り立たせるために入れた値である。

**依存ゲートを持つ（AGENTS Dependencies）。** 手段が 2 つあり、どちらも新規本番依存の判断に触れる — Tauri 公式の `tauri-plugin-window-state` を入れるか、窓の大きさをアプリ設定ファイル（decision-13）の項目として Atlas 自身が読み書きするか。**着手セッションはユーザーの回答を待つところから始まる。**

**窓の位置は本タスクの範囲に入れない** — ユーザーが述べたのは大きさである。着手時に併せるかどうかを訊いてよい。

**着手時に確かめること**: 復元した大きさが `minWidth`/`minHeight` を下回らないこと、前回より小さい画面で起動して窓が画面外に出る場合の扱い、後者の手段を採る場合は `KNOWN_SCHEMA_VERSION` の引き上げ（decision-13 の Consequences）と `mergeDraft`・`normalize` の両方を通すこと。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
手段は `tauri-plugin-window-state` 2.4.1、導入範囲は `StateFlags::SIZE | MAXIMIZED`（ユーザーが 2026-08-18 に選定）。判断と却下した代替は decision-38、置き場は doc-3 §2.1。

**依存の実測（追加前）**: リリースの 5 トリプルへ `cargo metadata --filter-platform` を流した和集合が 352 → 353 で、増えるのは crate 自身のみ。依存 6 つはすべて `Cargo.lock` に既に在った。

**実行時の実測（2026-08-18、macOS、debug バンドルを `open` して `osascript -e 'quit app'` で終了）**。窓状態ファイル へ値を書いて起動し、終了後に書き戻された値を読む形で 4 件測った。**書き戻しは `update_state` が生きている窓から `inner_size()` を読み直すので、出た値は窓の実際の大きさである**（キャッシュの反響ではない）。

| 入れた値 | 出た値 | 何が言えるか |
|---|---|---|
| 記録なし | 1200×800・maximized=false | 終了時に窓の実寸が記録される |
| 900×700・false | 900×700・false | AC #2 の復元 |
| 400×300・false | 640×480・false | AC #3 の 最小寸法の下限適用 |
| 900×700・true | 900×700・true | 最大化状態 の復元。最大化中は大きさが更新されないので、最大化前の 900×700 が残る |

**設計を 2 度直した。どちらも実測が原因を出した。**

1. `Builder::setup` から補正する初版は動かなかった — `window_created` は `run_on_main_thread` でイベントループへ載るので、setup はプラグインの復元より前に走る。
2. プラグインのフックへ移した 2 版も動かなかった — probe を入れて測ると、Atlas のフックが走る時点で `inner_size()` はまだ復元前の 1200×800 を返し、`Resized(400×300)` はその後に届いていた。**`set_size` は OS がリサイズしてイベントを出すまで窓の報告に反映されない。** 最終形は `WindowEvent::Resized` を見る形で、1 回読みも Windows の同期リサイズ用に併置してある。

**副産物の実測**: 補正が動いていなかった 2 版の測定が「macOS は `set_size` を窓の最小寸法へ丸めない」を示した（400×300 の記録で窓が 400×300 になった）。Windows・Linux は未測定で、イベントを見る形はその 2 つの答えに依存しない。

**3 度目の直しはレビューの [P2] で入った**（PR #138 1R）。**下限の判定を論理ピクセルで行っていたので、拡大率が 2 進小数でないと満たした状態に到達しなかった** — Windows の 130%（拡大率 125/96）では 640 論理が 833 物理へ四捨五入され（`dpi` 0.1.2）、833 物理は 639.744 論理に戻るので、通知ごとに同じ 833 を求め続ける。**判定と resize を物理ピクセルの整数で行い、最小寸法 は切り上げで物理へ移す形へ変えた**（切り上げなのは下限だからで、四捨五入では 833 ＝ 639.744 論理になり AC #3 の下限を割る）。**指摘の副次例（拡大率 1.1）は再現しなかった** — 704/1.1 は正確に 640.0 になる。争点は 125/96 の側で、そちらは実物で確認した。上の実測 4 件はこの形でも同じ値になった（この機械は拡大率 1.0）。

**新しいテストは直しを外して落ちることを確かめた** — 下限適用の除去で 2 本、`CARRIED` を `SIZE` 単独／`all()` にして 1 本、`MIN_WIDTH` を 641 にして 1 本。

**既存の欠陥を 1 件見つけたが直していない**: doc-3 の Git remote 有無属性の項に、閉じていない太字強調が 1 か所ある（`**…値ではない。**remote の URL は…`）。#14 TASK-161 の範囲なのでそちらへ残す。
