## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
2026-08-09 のユーザーフィードバック。現在セル内の並びは `swimlane.ts` の `compareCards` が固定で持ち (priority 降順 → ordinal 昇順 → updated_date 新しい順、doc-7 §5)、利用者は変えられない。絞り込み設定帯から並び順を選べるようにする。

ユーザーが挙げた順序:
- priority 降順 (既定: HIGH > MED > LOW > none) / 昇順 (none > LOW > MED > HIGH)
- task id 昇順・降順
- updated date 昇順・降順
- created date 昇順・降順
- milestone 昇順・降順

**決定先行**: doc-7 §5 が並びを「セル内の安定並び」として固定で定めており、選べるようにするのは契約の変更である。決めることは 3 つ — 選んだ並びをアプリ設定へ永続するか (カードサイズ・詳細配置は永続する)、同順のときに何を第 2 キーにするか (現在の 3 段のうち残す段)、値を持たないタスク (milestone 不在・priority 不在) をどちらの端へ置くか。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## 決定先行（2026-08-10 にユーザーが 3 争点とも確定）

- **永続**: 帯で選んだ順をそのまま既定としてアプリ設定へ保存する（doc-8 §2.2 の 既定の詳細配置 と同じ第 2 の書き手）。
- **値を持たないタスク**: 欠落は方向に依らず常に末尾。priority の 段なし だけは 4 段目の値として方向に従う（原文の「昇順 (none > LOW > MED > HIGH)」どおり）。
- **控えの形**: 10 項目の `<select>` 1 つ。方向がホバーも押下も無しに読め、doc-11 §2.4 に新しい型を足さない。
- **並べる順**（2026-08-10 の目視前フィードバックで追加確定）: 属性は原文の列挙のまま、**方向はどの属性も 昇順 → 降順**。原文は priority だけ 降順・昇順 の順で挙げており、5 属性のうち 1 つだけ逆に読めることが最初に目に付く。**既定（priority 降順）が先頭に来ないことは承知のうえ** — 控えは選択中の値を出すので、既定であることは並びの位置と別の事実である。実測で `<select>` の幅（103px）と帯の高さ（32.98px）は変わっていない。

判断を求めずに規則から落としたもの: 同順の比較規則（下記）、数を数として比べること、この操作にキーを割り当てないこと（帯に常に見えている。TASK-80 が 既定に戻す に下したのと同じ判定）、既定に戻す が並び順に触れないこと（doc-7 §5 がフィルタと並び順を別に立てている）、前後移動（doc-8 §2.2）が `laneNeighbours` 経由で自動追随すること。

## 改訂した契約

doc-7 §5.4（1 本の固定順 → 10 通りの族）・doc-7 §5.2（帯の控えに 1 つ足し、画面設計案 03 に無いことの帰属を書いた。funnel・直前の 1 つを戻す に続く 3 例目）・doc-12 §4.3（転記の側にも同じ 1 行）・decision-13 の項目表に 既定の並び順 を 1 行（原地改訂。項目の追加は同 ADR の Consequences が版管理の対象と定めている）。**新しい decision は書いていない。**

## 同順のときの比較規則

10 通りとも同じ 1 つ: 選んだ並び順 → 既定の 3 段（priority 降順 → ordinal 昇順 → updated_date 新しい順）→ 読み取り順（パス順＝安定ソート）。選んだ並びが priority・updated_date を既に見ているときも、同順ならその段は必ず差 0 を返すので二重に効かない。この 1 本の規則の下で **priority 降順 は改訂前の `compareCards` と同一**で、改訂前の比較関数を試験の中に書き下ろして対照してある（AC #5）。

## 数の並び

`TASK-2` < `TASK-10`、`m-2` < `m-10`。**locale を読まない自前比較**にした。`Intl.Collator(numeric)` は `m-ä` と `m-z` を de では ä 先・sv では z 先に並べる（実測。Node 24・ICU 78.3）ので、既定 locale 次第で同じ台帳が違う並びになる。試験がこの分岐そのものを記録している。数の桁は `Number` に通さず桁数と文字列で比べる（id の大きさに `Number.MAX_SAFE_INTEGER` の保証が無い）。

## スキーマ版

`KNOWN_SCHEMA_VERSION` を 2 → 3 へ。`settings.toml` に `default_card_order`（10 通りのフラットな値）を足し、wire fixture を再録済み（`loaded_settings.json`・`wire_tokens.json`）。`mergeDraft`・`normalize` の両方に通してある。

## 実測（借り物 playwright。WebKit / Chromium。変更前は同一条件で `.order` を display:none で外して測った）

- **帯の高さは全条件で不変**: 既定 32.98px、条件を多数足した状態 60.19px、窓 900px で 87.38px（両エンジン同値）。控え自身の高さは 22.39px で、テキスト欄・＋ 絞り込み・解除の 2 つと同値（`--bar-control`）。**帯の高さは 1 行のまま**（doc-7 §5.2）が保たれている。
- **並び順の群の幅**は 136.17（WebKit）/ 136.63（Chromium）px、`<select>` 単体で 103 / 101.09px。取った幅はすべて `.tokens`（flex:1）から出ており、トークン領域の高さは前後とも同値（22.39 / 49.59px）。
- **select の幅は選択中の項目によらない**（priority 降順 と milestone 降順 で同値）ので、選び替えでレイアウトが動かない。`max-width: 9rem` には当たっていない（＝いちばん長い語も切り詰められていない）。
- 保存が断られた文が出た状態でも帯は 1 行（32.98px）のままで、横あふれは全条件 0px。

## 試験

- 単体（`swimlane.test.ts`）: 10 通りの列挙と語、選んだ順での並び、未分類区画にも同じ順が効くこと、方向の反転、数として比べること、サブ番号を桁ではなく区切りで比べること、locale 非依存、priority 段なし が方向に従うこと、欠落が常に末尾であること、同順の 3 段と読み取り順、10 通りとも反対称で自分自身と 0 になること、既定＝改訂前と同一。
- 画面横断契約（`App.component.test.ts`）: 帯で選ぶと並びが変わり既定として保存されること、**保存が断られても選んだ並びが画面に残り、その後の無関係な保存（設定画面の 継続検出）がそれを戻さないこと**。
- **変異で確かめた**: 取り込みの門を外す → 後者が落ちる。欠落を方向に従わせる → 2 件落ちる。数を文字列比較にする → 2 件落ちる。同順の 3 段を空にする → 5 件落ちる。
