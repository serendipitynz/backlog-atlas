## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-03 に実装した。触ったのは `FilterBar.svelte` と `FilterPopover.svelte` の style だけで、
マークアップも振る舞いも変えていない（コメントの追加を除く）。

**決定先行判定: decision は不要、doc-11 §3 と doc-12 §4.3 を改訂・新設した。** 決 印は無いが指示書の
規則どおり着手時に当たった。争点は 1 つに絞れた。

**争点: AC #2 が要求する `padding .32rem` と `gap .35rem` は doc-11 §2.2 の余白段階
（.16 / .25 / .3 / .45 / .6 / .75 / 1rem）に無い値だった。** 3 案（段階へ丸める／段階に 2 刻み足す／
段階は目安だと doc-11 に書き直す）を提示し、ユーザーが 1 案目を選択した（2026-08-03）。両方 .3rem へ
丸めてある。差は padding で 0.32px・gap で 0.8px。原文の値と丸めた理由は doc-12 §4.3 に表として
残し、AC #2 の文言にも書き足した。**doc-11 は 1 文字も変えていない** — 見分けの付かない差を捨てる
ほうが、段階を段階のまま保てる。

doc-11 §3（チップの 4 系統）には、**絞り込みトークンはこの 4 系統に入らない**ことを書き足した。
AC #2 のトークン角丸 4px は §2.2 の「ボタン 4px」であって「チップ 3px」ではない、という判断が
どこにも書かれていなかったため。トークンは内側に自分を解除する `×` を持つ操作要素で、対象に付いて
その状態を述べるチップではない。4 系統へ 5 つめとして足さないのは、あの 4 つが「対象に付く札を
混ぜない」ための区別で、押せるものを入れると区別の軸が 2 つになるためである。

doc-12 は §4.3「案A の寸法」を新設した（**既存の番号は動かさず** §4.1・§4.2 の後ろへ足した。
TASK-67 と同じ理由）。画面設計案はリポジトリの外にあり読者が開けないので、AC が挙げた寸法の
出どころをここへ転記した。

**崩れの原因は 3 つあり、いずれも実測で確かめた（WebKit・1280px）。**

1. **控えごとに高さが違い、揃え方も 3 通りだった。** `.bar` が `align-items: flex-start`、`.add`
   だけが `align-self: center`、`.control` が `align-items: baseline`。上下中心はトークン 17.39・
   解除の 2 つ 17.78・＋ 絞り込み **27.08** とばらけていた。
2. **テキスト入力だけが 2 段だった。** 属性名を入力欄の上に積んでいたので、この 1 つだけが 41.38px
   で、帯の高さ（55.16px）はこれが決めていた。案A は帯を常に 1 行と置く。
3. **折返し 2 行の頭打ちが 2 行に足りていなかった。** `.tokens` の上限は
   `calc(--token-line * 2 + 0.2rem)` = 43.2px だったが、`--token-line` は枠を含まない高さで、
   トークンの実寸は 1px の枠 2 本を足した 22.00px。2 行ぶんは 22 + 3.2 + 22 = 47.2px なので、
   **2 行目が 4.2px 切れた状態でスクロールしていた**（AC #1）。

**直し方は「帯が高さを 1 つ持つ」形にした。** `--bar-control: 1.4rem` を `.bar` が持ち、トークン・
テキスト入力・＋ 絞り込み・解除の 2 つがそれを取る。属性名は入力欄の左へ移した（消していない）。
`.tokens` の上限も同じ値から計算する。**全員に `box-sizing: border-box` を与えた** — このリポジトリに
全体リセットは無く、枠を含む高さでなければ上限の計算が成り立たないため。

**測った値（WebKit・1280px、既定状態）**:

- **帯**: 55.16 → **32.98px**（グリッドが 22px 戻る）。`padding 4.8px 12px`（.3rem .75rem）・
  `gap 4.8px`（.3rem）・`align-items: center`・`font-size 11.52px`（.72rem）。
- **高さ**: テキスト入力・トークン・＋ 絞り込み・直前の 1 つを戻す・全解除 が **すべて 22.39px**。
- **上下中心**: 5 つとも **15.99px**（AC #3）。
- **文字**: 属性名 10.24px（.64rem）・値 10.88px（.68rem）・＋ 絞り込み 10.88px（.68rem）・
  解除の 2 つ 10.56px（.66rem）。トークン角丸 4px。
- **値一覧ポップオーバー**: 幅 **240.00px = ちょうど 15rem**・角丸 6px・内容幅 223.63px。
  15rem でも 選択中 n 件・検索を消す・閉じる の 3 つが 1 行に収まり、値の行は件数まで読める。
  **初版は 256.38px（15rem に padding 7.2×2 と枠 1×2 が足されたもの）で描かれていた** —
  `rem` で寸法を書いた箱に `box-sizing: border-box` を与えていなかったため、下の頭打ちと
  まったく同じ content-box の取り違えが 2 ファイル隣に残っていた（レビュー round 1 の [P2]）。
- **折返し**: ちょうど 2 行のとき `scrollHeight` 50 = `clientHeight` 50 で**切れない**。3 行めからは
  スクロールする（頭打ちは効いたまま）。

**3 つの主張を mutation で壊して確かめた**（TASK-67 の教訓。「揃えた」「収まる」と書いたら実際に
落ちることを見る）。ちょうど 2 行の状態で、(1) 上限を枠を含まない旧式の計算へ戻すと `clientHeight`
が 45 に落ちて 2 行目が切れる、(2) トークンから `box-sizing: border-box` を外すと 2 行ぶんが 54 に
伸びて切れる、(3) `.bar` を `align-items: flex-start` へ戻すと控えの中心が 29.59 → 15.99 へ動き、
トークン区画（2 行ぶん）の中心と食い違う。

**キーの割り当ては AC #4 の括弧書きと違っていた。** AC は画面設計案 03 の `⇧F` / `⌥⇧F` を挙げて
いたが、割り当て一覧の正本（`shortcuts.ts`・doc-7 §2.1）は `F` 追加 / `Backspace` 直前の 1 つ で、
**全解除にキーは無い**。TASK-68 はこの差を持ち込んでも直してもいない（扱ったのはレイアウトだけ）。
差は doc-12 §4.3 に記録し、当否は TASK-80 へ送った。AC #4 は事実に合わせて書き換えてある。
全解除にキーが無いことは、帯に 全解除 のボタンが要る理由でもある。**解除の入口はこのタスクで
1 つも増やしていない。**

**コンポーネントテストは足していない。** 検査すべきものが高さ・上下中心・折返しの位置だけで、
`jsdom` はレイアウトを走らせず `render.ts` の矩形は検査してはいけない値だから（AGENTS のテスト節）。
画面ごとのコンポーネントテストを作らない規約にも当たる。代わりに全数を実エンジンで測り、
主張ごとに mutation を当てた。ハーネスは `_sandbox/filter-check/`（`?view=` で 既定・多数・
ちょうど 2 行・ポップオーバー・無効化提示 を切り替え、`?n=` でトークン数を動かす）。

**フロントエンドのフォーマッタは無い**ので当てていない（TASK-66・67 と同じ理由）。静的解析は
`pnpm run check`（svelte-check、287 ファイル・0 errors）、試験は `pnpm test`（534 件）、
`pnpm run build` も通した。**Rust 側は 1 行も触っていない**ので `cargo test`／`fmt`／`clippy` は
実行していない。

**レビュー（PR #50、3 ラウンド。[P2] 1 件・[P3] 4 件を全件対応して APPROVED）で 4 か所直した。**
[P2] の 1 件は**この変更が自分で論じた取り違えを、2 ファイル隣に残していた**もので、残る 3 件も
「今回の変更が持ち込んだ、または今回書いた規則に対する反例」だった。

1. **値一覧ポップオーバーに `box-sizing: border-box` が無かった**（[P2]）。15rem を指定しているのに
   padding 7.2×2 と枠 1×2 が足されて **256.38px = 16.02rem** で描かれていた。トークン区画の 2 行
   頭打ちで直したのとまったく同じ content-box の取り違えで、**同じセッションで 2 度やった**ことになる。
   修正後は 240.00px。doc-12 §4.3 に「`rem` で寸法を書いた箱には `box-sizing: border-box` が要る」を
   一般則として書いた（このリポジトリに全体リセットが無いため）。
2. **頭打ちの計算が gap をリテラルで持ち直していた**（[P3]）。行側の `gap` と別々の数になっており、
   **一致しなければならない 2 つの数を何も一致させていない**という、このタスクが直した欠陥と同じ形。
   `--bar-gap` を足して両方をそこから取るようにした。
3. **`.control` に `white-space: nowrap` が無かった**（[P3]）。今回はじめて固定高になったのに折返しを
   止めておらず、`.token` の側だけが塞がれていた。520px 幅で 3 つとも 22.39px・はみ出し無しを実測。
4. **`.drop`（トークン内の ×）が 3px のままだった**（[P3]）。同じ PR が doc-11 §3 へ書いた
   「押せるものはボタンの 4px」に対する唯一の反例になるところだった。4px にした。

round 2 の [P3] は**台帳の測定値そのもの**で、Notes が 256.38px のまま隣のコミットが 240px と
書いている状態を拾われた。**Done 反映まで持ち越さずその場で直した** — 1 つの PR の中で台帳とコードが
食い違うため。

**実機での目視（2026-08-03）**:

- **(1) 属性名が入力欄の左に来た帯**: ユーザーが実機 Tauri の画面写真を提示した。実データ
  （137 / 194 件・4 プロジェクト、上部帯なし、トークン 2 行）で帯は 1 行に収まり、「テキスト」は
  左端 160px ほどでトークン領域を圧迫していない。**レイアウトとしては問題なし。**
  ただし**別の指摘が出た** — 「テキスト」という語が何を絞り込むのか分からない。帯の先頭に
  lucide の funnel を置き「テキスト」を撤去する形を **TASK-112** として起票した（レイアウトの
  欠陥ではなく語の分かりにくさなので、この PR には足していない）。
- **(2) 15rem の値一覧ポップオーバー**: 同じく実機の画面写真で確認した。実際の値名
  （`milestone-history` など）と件数が両方読め、`.name` の省略も起きていない。**問題なし。**
- **(3) 2 行を超えたときのスクロールの気付きやすさ**: ユーザーが実機で見て、**ぱっと見では
  スクロールできると分からないことを確認したうえで、現実装で許容と判断した**。
  **それでも直さない**のは、気付かせるための余白や指示子を帯へ足すと、画面設計案 03 案A が
  避けた「フィルタ帯がグリッドの高さを奪う」に戻るためである。頭打ちを 2 行に置いたこと自体が
  この費用を承知した上での選択なので、**後続タスクがここに「スクロールできることを示す何か」を
  足すときは、帯の高さが増えない形に限る**。隠れたトークンの条件は効いたままで、
  ＋ 絞り込み のポップオーバー（選択中 n 件）と 全解除 から到達できる。
