## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
2026-08-09 のユーザーフィードバック。現在の絞り込みは Type・通常ラベル・priority・assignee・テキスト・不整合・保存区分の 7 ファセット (doc-7 §5) で、日付の条件を持たない。updated date について指定期間のタスクだけを表示する条件を足す。

ユーザーが挙げた形:
- start 〜 end (両端指定)
- start 〜 now (始端指定)
- 〜 end (終端指定)
- in X days / weeks / months (始端指定のショートカット)

**決定先行**: doc-7 §5 のファセット列に 8 つ目を足す。既存の 7 つはすべて「値の集合から選ぶ」形で、値一覧ポップオーバー (検索 + スクロール + 件数) を共通部品として使っている (doc-12 §4.1)。期間は値の集合ではないので、トークンの見え方も値の選び方もこの部品に乗らない。決めるのはその置き方と、トークン 1 つが期間 1 つを表すのか始端・終端で 2 つになるのか、および `in X days` を評価する時点 (絞り込みを掛けた時刻か、画面を開いた時刻か)。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
決定先行の手順を 1 セッションで通した（対応表確定 → 争点提示 → ユーザー確定 → 実装 → 実測）。**doc 改訂だけで足り decision は書いていない**（18 例目）。改訂は doc-7 §5.2 と doc-12 §4.3。

**ユーザーが確定した 4 点**（いずれも推奨案）: ①入力の置き場は値一覧ポップオーバーの末尾に区画を足す、②トークンは始端・終端で 2 つ、③基準時間帯はローカル暦日へ直して比べる、④相対指定は押した時点で暦日へ固定。残る 3 点（端の包含・暦日を読めないタスクの扱い・相対指定の暦上の意味）はこちらで決めた。

**実測 2 件が設計を決めた。**

- **Backlog CLI v1.48.0 は created_date / updated_date を UTC で書く。** 空の Backlog ルートで `task create` した結果が `'2026-08-09 22:46'`、同時刻のローカル（NZST = UTC+12）は `2026-08-10 10:46`。読み手のローカル暦日へ直さないと、いま更新したタスクが「今日」から時差ぶん外れる。
- **時刻を持たない値が本リポジトリの台帳に 9 件ある**（`updated_date: '2026-07-22'`）。想定上の形ではないので、解析は 2 形を受ける。

**§5.4 の「timezone を発明しない」と衝突しない理由を doc に書いた。** あちらが守るのは 2 値の相対順序で、全体が一様にずれても順序は変わらない。こちらは利用者が名指しした絶対の境界と比べるので、ずれがそのまま取捨に出る。

**新しいモジュール `src/lib/period.ts`** が暦日への変換と相対指定の解決を持つ。実行環境の時間帯を読むのは `SYSTEM_ZONE` 1 か所だけで、試験はオフセットを注入する（runner の TZ を触らない）。**「ショートカット」の語は使わない** — `shortcuts.ts` の割り当て一覧が押鍵の和音に対して持っているので、相対指定 と呼び分けた。

**試験は変異で確かめてから置いた。** 暦日の変換を frontmatter の生文字列に戻すと「終端の日は時刻によらず残る」が落ち（生文字列では `'2026-08-09 22:46' <= '2026-08-09'` が偽）、読めない値を落とす門を外すと AC #4 の試験が落ちる。どちらも実行環境の時間帯に依らずに落ちる。

**実エンジン実測**（WebKit / Chromium × 窓 1440・900px、`_sandbox/filter-check/?period=both`。変更前は同じページで期間区画を `display: none` にして作った）

- **帯の高さは 1440px で 32.98px と不変**。900px では 60.19px で、これは TASK-132 が記録済みの折返し値であり、新しい高さの類は出ていない。
- **値一覧ポップオーバーは 240 × 366.48px（WebKit）/ 365.94px（Chromium）で変更前と同値** — 期間区画は `.values` のスクロール域（`max-height: 17rem` = 272px）の中なので、パネルは 1px も伸びない。中身は scrollHeight 1012 → 1119px（WebKit）。
- **横あふれは帯・パネル・期間区画とも 0px。** トークンは 181.92 / 183.8px（WebKit）・185.17 / 187.06px（Chromium）で、`max-width: 14rem` の内側。
- **日付入力は 180.44 × 27.09px（WebKit）/ 25.41px（Chromium）で、両エンジンとも OS の書式（`01/08/2026`）で表示する。** トークンは暦日を `2026-08-01 以降` と名乗るので、同じ日を 2 つの書式が同時に画面へ出る。doc-7 §5.2 に判断として書いた。

**測っていない＝目視に回すもの**: 実アプリ（WKWebView）での日付ピッカーの開き方とキーボードでの桁送り、期間を効かせたときのグリッドの見え方、暗いテーマでの入力欄の見え方。
