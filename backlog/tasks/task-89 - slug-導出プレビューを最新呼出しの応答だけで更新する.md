## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
ProjectRegister の readDefaultSlug は呼出し開始時の projectRoot をローカル変数へ保持するが、await 完了後に現在の input.projectRoot や呼出し番号を確認せず defaultSlug と defaultSlugKnown を更新する。ルート A の照会後、完了前に B へ変更し、B の応答後に A の応答が届くと、B の入力欄の下へ A 由来の slug 候補が出る。実際の登録時はバックエンドが検証・導出するので誤った台帳書込みが確定するわけではない。

m-2 に置く理由: 利用者は画面に出た slug で登録されると判断するため、表示と登録結果の食い違いは公開阻害の定義（利用者の誤解）に当たる。当初は発生窓が短いことを根拠に m-3 へ置いたが、発生確率は定義に入っておらず、修正も ProjectRegister.svelte 1 ファイルに収まるため m-2 へ改めた（2026-08-01 のレビュー指摘）。

_sandbox/repository-implementation-findings-2026-08-01.md の指摘 6。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-02 に実装した。

**決定先行判定: 不要と判断した。** 決 印は無いが、指示書が「決 印の無いタスクでも着手時に必ず
判定する」と定めているので当たった。doc-3 §3.1 は slug の導出規則（文字種・既定値の作り方・
台帳内での一意性）だけを定め、プレビューの非同期挙動には触れていない。decision-19 は gh 照会に
限定した契約（照会期限・取消・同時照会上限）で、ここは対象外。既存契約に対する欠陥修正であり、
新しい契約も例外も足さないので decision は書いていない。doc の改訂も無い。

**修正の中身**: 呼出しごとにトークンを採番し、最新のトークンを持つ呼出しの応答だけを表示へ
入れる。トークンにした理由は受入条件が許す 2 択のうち、A → B → A と入れ直したときに壊れない
のがこちらだから — ルート照合では 2 つの A の応答を区別できず、先に始めた A の応答を後の A の
ものとして受け入れる。`src/lib/history-read.ts` が既に使っている形でもあるので、このリポジトリで
「どの応答が勝つか」の答えが 2 通りにならない。

**採番は空ルートの早期 return より前で行う**。入力欄を空にする操作は照会を始めないので、後ろで
採番すると、飛んでいる応答が最新トークンを持ったまま残る。これが古い応答の生き残る経路の 1 つ
だった。登録成功後にフォームを空にする経路（`slugPreview.clear()`）も同じ穴を持っていた。

**呼出しの開始時に 未取得 へ戻す**。`history-read.ts` が await の前に `loading` を書くのと同じ。
前のルートの slug を出したまま新しいルートの導出を待つのは、同じ偽の主張を短い時間だけ述べる
ことに変わりない。

**string + boolean の対を 3 値へ畳んだ**。`defaultSlug: string | null` と `defaultSlugKnown` の
対は 4 通りを表せるが、画面が取り得る状態は 3 つで、表せてしまう残りの 1 つ（未取得 なのに
slug を持っている）が、まさに古い応答が作っていた状態だった。`SlugPreview` は
`unknown`（未取得）・`derived`（導出できた）・`underivable`（導出できない）の 3 値。

**導出の失敗は 未取得 に留める**（導出できない にしない）。導出できない はディレクトリ名について
の主張で、利用者に slug の指定を求める。呼出しが失敗したことはその名前について何も述べない。
実際の問題は登録要求が拒否理由付きで報告する（doc-3 §4.1）。

**コンポーネントの外へ出した理由**: 受入条件 #2 が求める「A と B の Promise を任意順で解決する
試験」は制御可能な Promise を要するが、AGENTS のテスト節はコンポーネントテストを画面横断契約に
限っており、画面ごとのテストは作らないと定めている。`history-read.ts` が同じ理由で
コンポーネントの外にあり、その docstring にもそう書いてある。`src/lib/slug-preview.test.ts` は
`unit` プロジェクト（node 環境）で走る 10 件。

**loader 世代は付けていない**（`history-read.ts` との違い）。あちらは読取識別子を鍵に
バックエンドが取消登録を持ち、webview の再読込を跨いで生き残るために世代が要る。こちらの導出は
何も登録せず取消もできないので、トークンはクロージャの外へ出ず、2 つ目の loader の採番と
衝突しようがない。

**主張を壊して確かめた 6 件**: (1) トークン照合を外すと 5 件落ちる。(2) 開始時の 未取得 への
戻しを外すと「導出中に前のルートの slug を出さない」が落ちる。(3) 採番を空ルートの return の
後ろへ動かすと「入力欄を空にすると飛んでいる導出を退ける」が落ちる。(4) 失敗を 導出できない と
して出すと 2 件落ちる。(5) null 応答を出さずに捨てると「導出できない を出す」が落ちる。
(6) 最初の呼出しだけが応答を出せるようにすると 7 件落ちる（応答が自然順に返る場合を固定した
肯定側の試験は、これでしか落ちない）。

**検証**: `pnpm test` 523 件（追加 10 件）、`pnpm run check` 284 ファイル・0 errors、
`pnpm run build` 成功。Rust は 1 行も触っていない（`cargo test` 345 件は本セッション冒頭に
main で実測済み）。**フロントエンドには設定されたフォーマッタが無い** — prettier は
`package.json` にも lock にも無く、設定ファイルも無い（既存の `history-read.ts`・`token.ts` も
素の prettier では警告が出るので、追加した 2 ファイルは既存の書式と揃っている）。静的解析は
`svelte-check`。

slug のヒント行が一度消えてから新しい値になることを確認し、問題なしだった。この環境は
`screencapture` が使えないので、画面の目視はユーザーへ依頼する運用になっている。PR #46 は
