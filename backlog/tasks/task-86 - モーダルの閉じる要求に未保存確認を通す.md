## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
設定モーダルは dirty を計算しているのに、閉じるボタンがそれを参照せず onclose を直接呼ぶ。ProjectRegister も入力をコンポーネントローカルに持ったまま確認せず閉じる。Modal は Escape を受けると無条件で onclose を呼び、App.svelte の onclose がコンポーネントをアンマウントするため入力が失われる。Modal.svelte のコメントは「モーダルを開いても背後の画面をアンマウントしないので未保存入力を失わない」と説明しているが、問題はモーダルを閉じるときに内部フォームをアンマウントすることであり、コメントが実装より強い保証を述べている。共通 Modal の onclose を「直ちに閉じる」ではなく「閉じる要求」として扱い、子フォームが未保存なら破棄確認を出す。_sandbox/repository-implementation-findings-2026-08-01.md の指摘 3、推奨順 3。TASK-74 と TASK-76 で同じ経路を触るため、その後に着手する。

## 決めたこと（doc-11 §7 へ 4 項。decision は書いていない）

TASK-86 は決定先行タスクだった（決 印は後付け・12 例目、doc 改訂だけで足りる 11 例目）。doc-11 §7 は
「TASK-86 の破棄前確認は、その 1 経路の前に置く」と既に書いており、**確認を通すこと自体は契約済み**で、
書かれていなかったのは**置き場**である。doc-8 §6.3 と doc-7 §5.3 は確認を上部帯 ① に固定し doc-11 §4 は
「6 種以外に上部帯を作らない」と閉じているが、doc-7 §2.1 のモーダルはその上部帯を覆う（フォーカス内留めの
ため意図的）。覆っている層の出口が上げた問いを ① に出すと、問いの対象が消えるまで読めず答えられない。

足した 4 項:

1. **モーダルの出口が上げた破棄前確認は、モーダルの中に出す。** 7 種目の上部帯ではなく、同じ ① の告知を
   それを上げた層の中に描いたもの。文言と 2 つの答えは doc-8 §6.3 のものをそのまま使う。
2. **答え待ちと「いま閉じられない事情」は別。** 前者は要求が出ていて答えを待つ状態（× は押せるまま）、
   後者は要求を出さない状態（× は §5 の無効化提示）。**順序は後者が先で、発行中は確認より前に断る。**
3. **問いが立っている間の Escape は、その問いに「編集に戻る」と答える。** 押下は最も内側の開いている層に
   費やされる（doc-7 §2.1）ので、その間の最も内側はモーダルではなく問いである。
4. **下部操作行が要るのは、下書きを書いて出る出口を併せ持つモーダルだけ。** 未保存入力を持つだけでは
   要らない（登録モーダルの「登録」は台帳へ書いても層を出ないので述べ分ける相手がいない）。原文の
   「取消」（doc-12 §2.3）を足すかどうかは TASK-80 のまま。

doc-8 §6.3 には「5 という数は編集セッションの経路の数であり、モーダルの確認は同じ文言・同じ 2 つの答えを
使うが経路も置き場も doc-11 §7 が定める」を 1 文足した（doc-8 の側は覆っていない対象だったので、反していた
わけではない）。

**ユーザーへ出した争点は 1 点だけ** — 設定モーダルの「変更せずに閉じる」も確認を通すか。**(a) 3 経路とも
通す**を選択（AC #2 と doc-11 §7 の「1 経路へ集める」にそのまま従う形。免除すると 3 つの出口が別々の事実を
見ることになり §7 に例外が要る）。置き場・節番号・Escape の扱い・下部操作行の条件はこちらで決めた。
**原文の材料は待たなかった** — doc-12 §2.2 の設定モーダルは保存を持たず（下書きが無い）、§2.3 の登録
モーダルも確認に触れていないので、この点を決める原文が存在しないことを先に確かめた。

## 実装

- **`Modal.svelte` に `confirmDiscard` prop**（`DiscardAnswers | null` = `onproceed` / `onkeep` の対）。
  文言はこの層が `edit.ts` の 3 定数から刷るので、呼び手が同じ喪失を別の言葉で述べられない。`closeBlocked`
  とは別の prop で、確認が立っている間も × は押せる（押せばもう一度同じ問いが出るだけ）。
- **Escape**: `confirmDiscard !== null` なら `onkeep()`、そうでなければ `onclose()`。
- **シェル（`App.svelte`）が旗を持つ**: `settingsDirty` / `registerDirty`（フォームが `ondirty` で上げる）、
  `registerSubmitting`（`registerProject` の中で立てる。`ledgerBusy` と分けたのは、あちらはプロジェクト
  詳細画面が出した命令でも立つため）。`closeSettings` / `closeRegister` は **発行中を先に断り、次に
  `guardDiscard`** を通す。既存の `pendingDiscard`・`guardDiscard`・`discardConfirmed` をそのまま使い、
  答えの片方を `keepEditing` として名前付きにした（帯とモーダルが同じ 2 つの答えを描くため）。
- **帯とモーダルで二重に出さない**: `confirmInModal`（`pendingDiscard !== null && (settingsOpen ||
  registerOpen)`）が真の間は上部帯 ① を立てない。
- **保存して閉じるは確認を通さない**。`Settings.svelte` は `onsaved` という別経路を持つ（下書きは書かれて
  いるので「破棄されます」が偽になる）。`ProjectRegister.svelte` は `submitting` を prop で受け取り、
  ローカル状態を落とした（1 つの事実を 2 つの旗にしない）。
- **`hasRegisterInput`（`ledger.ts`）** が登録フォームの未保存入力を判定する。3 欄のいずれかに空白以外が
  あれば真（`toRegisterRequest` が trim するので、空白だけの欄は発行され得ず確認の対象にならない）。
- **`--modal-confirm-height`**: 確認の行はモーダルの高さを増やすので、自分の高さを区切っている子
  （`Settings.svelte`）がこれも引く。引かないと下部操作行が窓の外へ出る（下記の実測で見つけた）。

## 実測（借り物 playwright、WebKit と Chromium、`_sandbox/settings-check/?confirm=1`）

**確認の行が下部操作行を窓の外へ押し出す欠陥を、実測で 1 件見つけて直した。** 修正前は 1280×800 で
dialog の下端が 799.78px（背景の下余白 32px が 0.22px になり、backdrop が約 30px スクロールする）で、
TASK-74 AC #1 の「下部操作行は常に画面上」が確認の立っている間だけ破れていた。`--modal-confirm-height` を
引く形にしたあとの実測:

| | WebKit | Chromium |
|---|---|---|
| 確認の行の高さ | 36px（2.25rem 固定） | 36px |
| dialog 下端（窓 800 / 640） | 768 / 608 | 768 / 608 |
| 下部操作行の下端（窓 800） | 751（画面内） | 751（画面内） |
| backdrop がスクロールするか | しない | しない |
| 答え 2 つと × の間隔（窓 1280 / 520） | 168.19 / 8px | 134.64 / 8px |
| 角丸（上端） | 5px（6px − 枠 1px） | 5px |
| 左端 4px | `--info`（明 `rgb(33,100,143)` / 暗 `rgb(102,172,220)`） | 同じ |

- **Tab 順は × → 破棄して続ける → 編集に戻る → フォームの先頭**（両エンジン）。確認は巡回の中にあり、
  Escape でも答えられる。
- **窓 520px では問いの文が省略記号になる**（両エンジン、答えの 2 つは × から 8px 空けて残る）。上部帯 ①
  が同じ幅で同じように縮約するのと同じ姿で、doc-11 §4 の「折り返さない」に従っている。既定の dialog 幅
  （44rem = 704px）では省略されない。
- 4 倍解像度の画像を `atlas-light`・`atlas-dark` の両方で撮って形の潰れが無いことを確かめた。

## 検査

- `pnpm test` 585 件（+10）。`pnpm run check` 288 ファイル・エラー 0。`cargo test` 347 件・`cargo fmt
  --check`・`cargo clippy --all-targets` すべて通る（Rust 側は触っていない。CLI 経路も触っていないので
  `--include-ignored` は回していない）。フロントエンドに設定されたフォーマッタは無い（prettier は依存にも
  設定にも無い）。
- **壊して落ちることを確かめた 6 件**: ①`closeSettings` の門を外す → 2 件落ちる、②上部帯 ① をモーダルの
  裏で立てる → 2 件、③確認の描画を落とす → 4 件、④Escape を要求の出し直しに戻す → 1 件、
  ⑤`registerSubmitting` を立てない → 1 件、⑥登録フォームが未保存を報告しない → 1 件。
- **落ちなかった変異が 1 件ある**: 保存して閉じるを `onclose`（＝門つき）へ戻しても全件通る。保存が解決した
  時点でシェルの `settingsDirty` は既に偽になっているためで、この順序に頼らないために `onsaved` を別経路に
  してある。**試験が固定しているのは結果（保存が成功したら確認は挟まらない）であって配線ではない**、と
  試験のコメントにも書いた。
- **既知の限界**: 保存の発行中もフォームの入力欄自体は押せるので、保存を押した後に値を変えると、その変更は
  確認なしに捨てられる（`onsaved` が門を通らないため）。TASK-86 の前も保存する は常に閉じていたので退行では
  ない。フォーム全体を発行中に無効化するかは TASK-74 の範囲の判断で、ここでは変えていない。
