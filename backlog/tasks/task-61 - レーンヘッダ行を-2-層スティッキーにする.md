## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
画面設計案 01 は列ヘッダ行（top:0 / z-index:3 / 高さ 2rem）とレーンヘッダ行（top:2rem / z-index:2）の 2 層をスティッキーにしている。現在の実装は Swimlane.svelte の列ヘッダ 1 層だけがスティッキーで、レーンヘッダ行はスクロールで流れる。プロジェクトを見失うだけでなく、TASK-62 の「このプロジェクトのレーンへ」の着地先が視界外に出る原因にもなっている。
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 縦スクロール中、列ヘッダ行とレーンヘッダ行の両方が常に見える
- [x] #2 レーンヘッダ行が列ヘッダ行の下に重ならず、画面設計案 01 と同じ 2 段の重なり順になる
- [x] #3 行折畳み・列折畳みの状態を変えてもスティッキーの位置がずれない

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-02 に実装した。

**決定先行判定: decision は不要、doc は改訂した。** 決 印は無いが、指示書が「決 印の無いタスクでも
着手時に必ず判定する」と定めているので当たった。doc-7 も doc-11 もスクロール中に何が残るかを
定めておらず（doc-11 は色・寸法・チップの形・無効化の見た目、doc-7 は何をどこに出すか）、
decision-12 の色値一式にも触れない。既存の契約を反転しないので decision は書いていない。ただし
**doc-7 §2.3 には無かった事実**なので、2 層スティッキーと着地の 2 項を足した。

**貼り付ける位置は測る（画面設計案 01 の `top: 2rem` は写さない）。** 01 は列ヘッダ行の高さ 2rem を
前提にした値で、この実装の列ヘッダ行は高さが変わる — 畳んだ列は列名・件数・操作を縦に積み
（doc-7 §2.2）、未対応列は置かない操作の理由 2 文を抱える（同）。固定値を書くと、列を 1 つ畳んだ
瞬間に 2 行の間へスクロール中のカードが覗く。受入条件 #3 が禁じているのはまさにそれなので、
`ResizeObserver` で列ヘッダ行の高さを測り `--lane-top` に載せる。**見出しは全部測って最大を取る**
（1 つだけ測ってグリッドの stretch に頼らない）。**`offsetHeight` ではなく
`getBoundingClientRect().height`** — 行の高さはたいていの文字寸法で小数になり、整数に丸めると
半分の確率で継ぎ目に髪の毛 1 本ぶんの隙間が開く。

**重なり順は 2 / 1 で、01 の 3 / 2 ではない。** このリポジトリの層は既に 3 がポップオーバーとヘッダ
メニュー、4 がモーダルで埋まっている（`FilterPopover` `HeaderMenu` `Modal`）。列ヘッダ行に 3 を
与えると、その上へ開くはずのポップオーバーと同値になる。必要なのは「カードより上・被せ層より下で
2 段」だけなので、局所の 2 / 1 にした。`App.svelte` の `.modal-layer` も 2 だが、`.body` の中で
Swimlane より後ろにあるので同値でもモーダルが上に来る（確認済み）。

**行の先頭に高さ 0 の目印（`.lane-mark`）を置いた。** スティッキーなレーンヘッダ行は、貼り付いて
いる間 `getBoundingClientRect()` が「列ヘッダ行の下端」を返し続け、自分の行が上へ何 px 流れたかを
述べない。`scrollIntoView` が使えなくなるのはこのためで（貼り付いた行は「画面内」と判定され、
上へ流れた行へ戻れない）、着地は `laneScrollDelta` の算術で `scrollTop` を直接書く。`offsetTop` も
同じ嘘をつく（貼り付き分が入る）ので使えない。

**`scrollIntoView` の代わりに算術を選んだのは実測の結果**でもある。高さ 0 の目印に
`scroll-margin-top` を付けて `scrollIntoView({ block: "nearest" })` を呼ぶ案を先に測ったところ、
**WebKit は正しくスクロールし、Chromium は 1 px も動かなかった**（高さ 0 の要素に対する差）。
Windows は WebView2 = Chromium なので、この案は 3 OS で同一に動かない（decision-11）。算術は
両エンジンで同じ結果になる。

**`laneScrollDelta` は純関数**（`src/lib/swimlane.ts`）。判定を `headHeight` に対して行うのが要点で、
0 に対してではない — 2 層になった後の「見えていない」には、画面の外にあるのと、列ヘッダ行の裏に
あるのと 2 通りがあり、後者はどの矩形を読んでも「画面内」と出る。試験 5 件（`unit`、node 環境）。
画面横断契約ではないのでコンポーネントテストは足していない（AGENTS のテスト節）。

**`src/lib/render.ts` に `ResizeObserver` のスタブを足した。** jsdom はこのクラス自体を持たないので、
足さないとアプリを mount するテストが全部この `$effect` で落ちる。何も観測しない実装にしてあるのは、
jsdom がレイアウトを走らせない以上サイズが変わることが無いからで、`getClientRects` のスタブと同じ
「返る数値をテストで検査しない」規則の下に置いた。

**実エンジンで測って確かめた**（`screencapture` が使えないので目視の代わりに数値で）。
`_sandbox/sticky-check/`（コミットしない）に本物の `Swimlane.svelte` を fixtures で mount する
ページを置き、別プロジェクトの playwright で WebKit と Chromium を動かした。結果:
(1) `--lane-top` が列ヘッダ行の下端と 0.01px 以内で一致する（WebKit 71.97 / Chromium 88.16）。
(2) スクロール中、列ヘッダ行は上端、通過済みの行のレーンヘッダ行はその直下に貼り付き、最後に
通過した行のものが最前面に来る（＝いま読んでいる行の名前が出る）。
(3) 列を畳むと列ヘッダ行の高さが変わり（Chromium 88.16 → 75.16）、`--lane-top` が同じ値へ追随する。
行を畳んでも貼り付き位置は動かない。
(4) 着地: 一番下から先頭の行を指定すると `scrollTop` 0 まで戻り、行の先頭が列ヘッダ行の下端に来る。
既に全体が見えている行を指定したときは動かない。

**自動検査で届いていない範囲**: 実際のアプリ（Tauri の WKWebView・実データ・フィルタ帯や上部帯が
立った状態）でのスクロールと、プロジェクト詳細画面から「このプロジェクトのレーンへ」で戻る操作は
見ていない。上の実測は本物のコンポーネントを本物のエンジンで動かしたものだが、画面全体の中での
見え方（帯が積まれたときに 2 行が占める高さの印象など）は別問題なので、目視はユーザーへ依頼する。
