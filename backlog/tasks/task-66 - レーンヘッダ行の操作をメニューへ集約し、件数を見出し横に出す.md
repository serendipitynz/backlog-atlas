## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
現在の固定ヘッダ行（画面名「プロジェクト別スイムレーン」を載せている行）にはメニューと個別ボタンが併存している。メニューだけで足りるので個別ボタンを畳む。あわせて「プロジェクト別スイムレーン」の横に件数を出す。

**指示対象の確定（2026-08-02）**: 起票時のタイトルと受入条件 #1 は対象を「レーンヘッダ行」（doc-7 §2.3 のプロジェクト行ごとの横 1 行）と書いていたが、そこには個別ボタンしかなくメニューが無いため「併存」が成り立たない。併存しているのは固定ヘッダ行（プロジェクトを登録・設定の 2 ボタンと ☰ メニュー）のほうで、件数を出す先も同じ行である。ユーザーが 2026-08-02 に固定ヘッダ行だと確定したので、タイトルと受入条件をそちらへ直した。レーンヘッダ行の ↑ ↓ 隠す 再読込 › はこのタスクの対象ではない。

件数の形式はユーザー指示を採る: タスク数（表示数 / 全件）とプロジェクト数（表示数 / 全件）。画面設計案 01 の見出し横は「表示 {shown} / {total} 件 ・ {laneCount} レーン」で、レーン（プロジェクト）側は表示中のレーン数という単一値であり全件との比を出していない。つまりこの点は 01 からの意図的な変更である。ユーザーは 2026-08-01 にこの差異を認識したうえで指示を優先すると確定した。差異の理由を doc-7 に記録する。

総計の置き場: 画面設計案 03 の判断節は総計（表示 n / m 件）を帯右端に常設し、行見出しの n / m 件を行の内訳として残す（両方出す）としている。01 は総計を見出し横に置き、帯には解除のキーボード説明を置いている。01 のほうが後発の全景案なので 01 を採り、TASK-68 は帯に総計を置かない。この判断を doc-7 に書く。

01 の算出（01:509-515）では shown も total も表示中レーンのみの合計で、行非表示のレーンと読取不能レーンを除外している。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-02 に実装した。

**着手前に指示対象を確定した。** タイトルと受入条件 #1 の「レーンヘッダ行」と Description の
「メニューと個別ボタンが併存している」が指す先が割れていた（レーンヘッダ行にメニューは無いので
併存が成り立たない）。読みが変われば触るファイルも改訂する doc の節も変わるので、独自解釈で
埋めずユーザーへ確認し、**固定ヘッダ行**で確定した。タイトル・受入条件・Description を
その対象へ直してある。**`task edit -t` はファイル名を変えない**ので、ファイル名だけ旧タイトルの
まま残る（TASK-95 と同じ）。

**決定先行判定: decision は不要、doc-7 §2.1・§5.2 と doc-12 を改訂した。** 決 印は無いが指示書の
規則どおり着手時に当たった。変わるのは doc-7 §2.1 が固定ヘッダに置くものの列挙（登録・設定・
メニューの 3 つ → メニュー 1 つ）と §5.2 の総計の置き場で、どちらも doc であって decision では
ない。§2.1 の規則そのもの（ヘッダに出している操作はメニューにも同じものを置く／1 プロジェクトに
閉じた操作を置かない／ショートカットだけが入口の操作を作らない）はいずれも反転していない —
1 つめはヘッダがメニュー以外を出さないことで、3 つめはメニュー項目が併置になることで満たす。
既存 decision の記述も確かめた: decision-13 の「アプリ設定は固定ヘッダの設定（doc-7 §2.1）から
開く」はメニューが固定ヘッダの一部なので真のままで、置き場の正本は §2.1 側にあるため改訂不要。

**総計は 1 か所しか刷らない。** 画面設計案 03 は帯の右端に常設、01 は見出し横と食い違っていて、
後発の全景案である 01 を採った（Description の判断）。実装上は `FilterBar` から `shown`/`total`
の props ごと外し、固定ヘッダへ移した。同じ数を 2 か所が刷る形を残さないためで、doc-7 §5.2 の
「総計の表示」を「総計の置き場」へ書き換えて理由ごと記録した。TASK-68 は帯に総計を置かない。

**2 つの比は数える母集団が違う**（`swimlaneTotals`、`src/lib/swimlane.ts` の純関数）。タスク数は
グリッドが描いている行だけを数えるので、行非表示のレーンは表示数からも全件からも外れる — この
総計はレーンヘッダ行の内訳の総和で、画面に無い行を足すと 2 つが合わなくなる（01 の算出どおり）。
プロジェクト数は全件を台帳のエントリ数にした。**両方から外すと 2 数が常に一致して比が何も
述べなくなる**ためで、受入条件 #3 の「どちらの数からも外れる」はタスク数の 2 数を指すものとして
読んだ（そう読まないと比が成立しない）。ルート読取不能の行は、画面に出ている登録済み
プロジェクトなので表示数に数え、カードは持たないのでタスク数には寄与しない。試験 4 件（`unit`）。

**モーダルのフォーカス戻り先が ☰ になった。** 消したボタンは「どの経路で開いても同じ控えへ
フォーカスを戻す」役を持っていた（`Modal.svelte` は mount 時の `activeElement` を控える）ので、
消すだけだとメニュー項目から開いた場合に戻り先が unmount 済みになる。ヘッダに常時ある ☰ へ
移した。**画面横断契約なので `App.component.test.ts` の 2 件が経路ごと更新されている** —
入口はメニューを開いてから項目を押す 2 手になり、1 手目が 2 手目の押した要素を消すという、
まさにこの戻り先が要る経路をテストが通るようになった。

**ヘッダのボタンが持っていた 1 行説明は捨てずにメニュー項目へ移した**（`HeaderEntry.note` →
メニュー項目の `title`）。ボタンを畳むことで画面から説明が消えるのは、操作の集約とは別の損失で、
移せば済む。

**フロントエンドのフォーマッタは無い**ので当てていない（`package.json` にも lock にも prettier が
無く設定ファイルも無い。素の prettier は既存ファイルにも警告を出す）。静的解析は
`pnpm run check`（svelte-check、0 errors）、試験は `pnpm test`（532 件）、`pnpm run build` も通した。

**PR #48 のレビューで [P2] が 1 件出て、フォーカス戻り先を名指しする検査が入った**（検査が PR 中に
増えたのでここへ戻して記録する）。指摘は、戻り先を消えるボタンから ☰ へ移したのに
`App.component.test.ts` は「モーダルが消えた」しか見ていない、というもの。`Modal.component.test.ts`
が固定するのは「mount 時に active だった要素へ戻す」ところまでで、その要素を決めているのは
呼び出し側だという切り分けが正確だった。登録・設定 × Escape・閉じるの 4 経路へ
`document.activeElement` の検査を足し、**呼び出し側の `menuButton?.focus()` を外すとその 2 件だけが
落ちることを実測してから**返答した。**教訓: 実装の一部を別の要素へ移したときは、移した先を名指しする
検査を足す。「動く」ことの検査は移動の前後で同じに通る。**

**実エンジンのハーネスはこの変更には使えなかった。** TASK-61 で使った `_sandbox/sticky-check/`
（別プロジェクトの playwright で WebKit と Chromium）が立てられたのは `Swimlane.svelte` が props
だけで立つ部品だからで、固定ヘッダは `App.svelte` の中にあり境界（`lib/commands`）の差し替えが
要る — コンポーネントテストは `vi.mock` でそれをしているが、Vite の dev ページからは同じ手が
使えず、ハーネス側に境界の偽物を組む作業が本体の変更より大きくなる。**ハーネスが効くのは部品、
効かないのはシェル**と切り分けて、後者は目視へ回す。

**ユーザーの目視で確かめた範囲（2026-08-02、問題なし）**: (1) 見出し横のタスク数とプロジェクト数の
2 つの比が、読める大きさ・間隔で並ぶこと。(2) 登録・設定のボタンが消えて ☰ だけになったヘッダの
見た目が寂しすぎないこと。(3) メニューから登録・設定を開いて閉じたとき、フォーカスが ☰ に戻ること。
件数の算術は純関数の試験が、戻り先はコンポーネントテストが押さえているので、目視へ回したのは
実エンジンでの見え方と、実データを載せたときの並びの印象である。
