## Description

TASK-118 の実機目視 (2026-08-13) 由来。**決定事項一覧が `decision-1`・`decision-10`・`decision-11`…・`decision-2` の辞書順で並ぶ。** 本家 backlog browser は数値順である (ユーザーの比較画面)。

**原因は読み取り層の `scan.rs:166` の `paths.sort()`** で、`read_dir` の順が OS 依存なのを避けてパスで整列している。**したがって文書一覧・マイルストーン一覧も同じ挙動である** — 決定事項区画で初めて目に付いたのは、その台帳が 30 件持っていたからで、欠陥は 3 種に共通する。**TASK-118 では直していない** (範囲外の同型は直さずに測って報告する、の適用)。

**id を持たない写せなかったファイル (decision-24) の並びも同時に決める** — あちらはパスしか持たないので、数値順の対象にならない。

## 決めたこと（2026-08-14、ユーザー確認）

**並び順の正本は読み取り層に置く。** 画面側に置く案と比べたのは 1 点だけで、**`ProjectModel` を組み立てる場所が Rust の 1 か所しか無い**のに対し、フロントエンドで読み取り結果が届く口はプロジェクトを開く・作業空間を開く・再読込の通知・更新の結果に分かれている。後者へ並べ替えを置くのは列挙であって網羅ではなく、口が増えた回に黙って落ちる。

## 規則の置き場

**新設した doc-4 §7 が 1 か所である。** doc-7 §5.4 が持っていた「数の並びは数として比べる」「比較は locale を読まない」はそこへ移し、**§5.4 は引く側にした** — 非タスク管理ファイルの 3 つの一覧が同じ比較を要ることになったので、2 か所に書くことになるためである。doc-10 は §1 の 一覧列 と 写せなかったファイルの一覧 の 2 語が §7 を引き、§5・§6・§10 はその語をそのまま使う（区画ごとに定義し直さないのが doc-10 自身の書き方である）。

**§7 を末尾へ足したのは、3 章の隣へ挿すと 4〜6 章の番号が動くためである。** doc-10 §10 が同じ理由で採った判断と同じで、理由は §7 の冒頭に書いた。

## 実装

- `src-tauri/src/read/id_order.rs` の `compare_ids` — バイト走査で、数字列は値（先頭の 0 を落として桁数→字面）で比べ、同値なら書かれた綴りの短いほうが先。数字列以外の位置はバイトの順。
- `read_project` が 3 コレクションを `sort_by` で並べる。**安定なので、同じ id を持つ 2 件は読み取り順（パス順）のまま残る。** **タスクは並べ替えない** — カードの並び順は利用者が選ぶもの（doc-7 §5.4）。
- 写せなかったファイルは id を持たないので対象外で、走査のパス順のまま。

## 期待値の正本と、確かめたこと

**doc-4 §7 の 昇順の例 の行が期待値の正本である。** Rust 側（`read::id_order` の検査）とフロントエンド側（`src/lib/id-order.test.ts`）が**両方ともその行を読んで**並べ替え、結果を doc の並びと比べる。規則の実装は 2 つある（読み取り層と、カードの並び順が引く `swimlane.ts` の比較器）ので、期待値まで 2 つに分かれると突き合わせる相手が無くなる。

**壊して落ちることを確かめた**（3 通り）。

- doc-4 §7 の 昇順の例 の 2 件を入れ替えると、**Rust とフロントエンドの両方が落ちる。**
- `read_project` の `sort_by` を 1 行外すと、`the_three_collections_come_out_in_id_order_rather_than_path_order` が落ちる。
- **落ちなかったもの**: `sort_by` を `sort_unstable_by` に替えても、同じ id を持つ 2 件の検査は通る（実測）。この規模では Rust の unstable sort が挿入ソートへ落ちるためで、**あの検査が固定しているのは答えであって並べ替えの安定性ではない。** 検査のコメントにも書いた。
