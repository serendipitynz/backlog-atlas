## Context

TASK-81 は、スイムレーンのカードを列間でドラッグ&ドロップして status を変えられるようにする。
**起票の本文は決めるべき点を 4 つ挙げていた** — 未分類列・CLI 縮退中・楽観更新の可否・バージョン
不整合の表示である。**着手して数え直すと、判断が要るのはそのうち 1 つだけだった。** 残り 3 つは
既存の規則から落ちる。代わりに、起票が挙げていない争点が 3 つ立った。この decision が記録するのは、
その切り分けと、立った争点への回答である。

語と指示対象は TASK-81 の対応表 初版で本文より先に
固定した。以下で使う **列間ドロップ**（タスクカード 1 枚をつまんで同じ行の別の列のレーンセルへ落とし、
`task edit -s` 1 回を発行させる操作）・**受け先**（列間ドロップを受け取って発行へ進むレーンセル）・
**渡る status**（列間ドロップが `-s` へ載せる 1 つの原文 status）・**発行中のカード**（発行が返るのを
待っている間のタスクカード）・**行またぎのドロップ**（別のプロジェクト行のレーンセルへ落とす操作）・
**OS 横取り**（Tauri が窓へ登録した handler が OS の既定動作を止めている状態）・**候補選択の問い**・
**つまめないカード**はその表の語である。

### 既存の規則から落ちるもの（判断ではない）

**起票の 4 点のうち 3 点はここに入る。** decision として記録するのは、判断したからではなく、
**「決めるべき点」として起票されたものが決める余地を持たないと数え直した**ことを残すためである。

- **発行成功までカードを動かす手段が無い**（起票の 3 点目、楽観更新の可否）。カードの列は
  snapshot の status の関数であり、位置を別に持つ場所が無い。楽観的に動かすには snapshot と別の
  カード位置を持つことになり、doc-5 §5（失敗した更新操作は Atlas 側のドメインモデルを変更しない）と
  doc-5 §6（更新の結果はファイルを読み直して初めてドメインモデルへ入る）の両方に反する。
- **バージョン不整合は既存の経路がそのまま持つ**（起票の 4 点目）。`update_apply` が更新前競合を
  返し、CLI を起こさずに再読込する（doc-9 §4-1）。列間ドロップも同じ経路を通るので機構は増えない。
- **未分類列が受け先にならないこと自体**（起票の 1 点目）。未分類列には 列の作成時 status 候補 を
  定義できない。doc-7 §4.1 が 列内新規タスク入力 の入口を置かない理由がそのまま当たる。
- **行またぎのドロップは提供しない操作である。** タスクの所属は台帳エントリが決め（doc-7 §4）、
  ルート間移動の写像は doc-5 §3 に無い。**「今は条件が揃っていない」ではないので、doc-11 §5 により
  受け先にしないだけで、添える理由も無い。**

## Decision

**列間ドロップは、doc-7 §4.1 の 列の作成時 status 候補 にそのまま載せる。** 候補集合を作るのは
`interpret::status::create_status_candidates` の 1 か所であり、列間ドロップはそれを読むだけで、
列対応規則をフロントエンドで逆向きに解き直さない。**受け先になれるのは候補が 1 件以上ある正準
ステータス列のレーンセルだけである。** 発行するのは doc-5 §3 の「タスク status 変更」1 行そのもので、
操作写像は増えない。

以下の 4 つが、2026-08-15 にユーザーが回答した争点である。

### 1. 候補が 2 件以上の受け先では、渡る status を問う

doc-7 §4.1 は 列内新規タスク入力 について **「どの値が渡るかは、候補の数によらず常に入力欄で読める
状態を保つ」** を要求している。**列間ドロップには入力欄が無い。** 宣言順の先頭を黙って渡す案は、
§4.1 が守っている実質（渡る値が画面で読めること）から外れるので採らない。**候補が 2 件以上の受け先
へ落ちたときは、候補選択の問いを立て、選ばれた値で発行する。**

**候補が 1 件の受け先では問わない。** 選ぶものが無く、問いは確認になる。doc-7 §4.1 が候補 1 件の列に
ついて「その原文 status を渡し、渡す値を入力欄に表示する」としているのと同じ扱いで、渡る値が
1 つに決まっていることは画面が読める状態を壊さない。

**候補選択の問いは doc-11 §12 の実行前確認ではない。** あちらが問うのは動作を行うかどうかで答えは
2 つだが、こちらが問うのは渡る値で、答えは候補の数だけある。借りるのは被せ層の作法（同時に 1 枚・
出口は取りやめと同じ）であって、§12 の規則そのものではない — **§12 の `…` の規則も掛からない**
（付ける先の控えが無い）。

### 2. 未分類列の理由は出さない（AC #2 を書き改めた）

**TASK-81 の AC #2 は「未分類列がドロップ先にならず、その理由が読める」と書かれていた**が、
**doc-7 §4.1 は未分類列について理由を画面に出さないことを 2026-08-03 にユーザーが 2 案から選んで
確定している。** 理由は 3 つで、そのうち 2 つは列間ドロップにもそのまま当たる — 押せない控えを
置いていないので doc-11 §5 が理由を要求する対象ではないこと、常設の 1 文が列ヘッダ行の 1 行保持
（doc-7 §2.2）で得た高さをそのまま食うことである。**§4.1 の判断を優先し、AC #2 のほうを
「未分類列がドロップ先にならない」へ書き改めた**（2026-08-15、ユーザー）。

**候補 0 件の正準ステータス列は、これと扱いが分かれる。** doc-7 §4.1 は候補 0 件の列に「置かない
理由を短く書く」を課しており、**その理由は列間ドロップにも当たる** — 同じ列がプロジェクトによって
受け先になったりならなかったりするので、無いことが並びから読み取れない。**`backlog init --defaults`
は `In Review` を宣言しないので、これは辺縁ではなく既定の構成で起きる。**

### 3. CLI 縮退中はつまめなくする

doc-7 §4.1 は 列内新規タスク入力 の入口を「理由付きで無効化」と定めるが、**ドラッグには無効化する
控えが無い。** つまめるが落とすと拒む形は、操作できるように見せてから拒むことになる。**CLI 縮退中は
カードをドラッグの起点にしない**（つまめないカード）。**理由をカードに添えない** — doc-11 §5 が
「画面全体に効く理由（CLI 縮退・台帳読取専用）は上部帯にも出す」と定めており、その 1 文が既に
画面に出ているためである。**カードは押せば詳細を開くままで、失うのはつまめることだけである。**

### 4. `dragDropEnabled` を false にする

**実測（2026-08-15、cargo registry の実ソース）**: `tauri-utils` 2.9.3 の
`WindowConfig::drag_drop_enabled` は既定 `true` で、その doc コメントが
`Disabling it is required to use HTML5 drag and drop on the frontend on Windows` と述べる。
`tauri-runtime-wry` 2.11.4 は `true` のとき wry へ handler を登録し、その閉包は `true` を返す —
`wry` 0.55.1 の `with_drag_drop_handler` の doc いわく、**OS の既定動作を止める**戻り値である。
`src-tauri/tauri.conf.json` は値を書いていなかったので、Atlas は既定で横取りしている側にいた。

**Atlas は OS のドラッグ&ドロップ事象を 1 か所も消費していない**（2026-08-15 実測。`src/` と
`src-tauri/src/` を走査して 0 件）ので、false にして失う機能は無い。**`src-tauri/tauri.conf.json` の
窓設定へ `"dragDropEnabled": false` を書く。**

**macOS・Linux で横取りが HTML5 のドラッグ&ドロップを壊すかは未測定である** — Tauri の doc は
Windows しか名指ししない。**「不可能」ではなく「未測定」なので、3 環境での動作は TASK-81 の実機
受入条件が引き取る。**

## Consequences

- **doc-7 に §4.2 として 列間ドロップ を足した。** 受け先の決め方・渡る status・候補選択の問い・
  CLI 縮退中・行またぎのドロップ・発行中のカードはそこが正本である。**§4.1 の 列の作成時 status 候補
  は 2 つの操作が読む値になった** — 語は「作成時」のままで、**改称しない**。改称すると decision-4・
  doc-7・`ColumnCreateStatuses`（wire）・`create_status_candidates`（Rust）・`lane-create.ts` が
  一斉に動き、得るものは語の正確さだけである。**§4.2 が初出でその読み替えを述べる。**
- **TASK-81 の AC #2 を書き改めた**（Decision 2）。**AC を書き改めた理由がこの decision にあることを
  残すために、書き改めた事実そのものをここへ書いた** — タスクの AC は履歴を持たない。
- **`dragDropEnabled` は今後 load-bearing である。** これを既定へ戻すと Windows で列間ドロップが
  黙って効かなくなる。**AGENTS 和英に 1 項を置いた。**
- **TASK-146（アプリ窓が Atlas から離れる経路）の前提が動く。** 引き継ぎ指示書は「Tauri の
  `dragDropEnabled` が既定で drag-drop を横取りするので、そもそも航行が起きない可能性がある」と
  書いていた。**この decision がその横取りを外すので、TASK-146 が測る対象は外した後の状態である。**
  **TASK-146 の Description へその旨を書いた。**
- **決めるべき点として起票された 4 点のうち 3 点が、決める余地を持たなかった。** 起票時点の
  「決めるべき点」の数え上げは、着手時に数え直す対象である（引き継ぎ指示書の「着手時に『その AC が
  現に満たされているか』を先に見る」の同族で、こちらは AC ではなく Description の数え上げに当たる）。
