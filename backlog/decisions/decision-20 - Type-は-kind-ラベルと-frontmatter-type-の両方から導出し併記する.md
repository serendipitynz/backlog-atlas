## Context

decision-5 は、Type 値の導出を kind ラベル `kind:X` の接頭辞除去に固定し、複数 kind・
kind 無し・未知 Type の 3 つを分けて表示することを定めた。Backlog CLI v1.48.0 が
`task create --type` / `task edit --type` を受け取り、その値を frontmatter へ書くように
なったため、decision-5 が 1 つに固定した導出の前提が崩れている（TASK-110、TASK-58 の起票）。
用語を先に固定する。

- **type フィールド** … Backlog CLI v1.48.0 の `--type` が 1 タスクの frontmatter へ書く単一の
  スカラー値 `type:`。`labels` と並ぶ位置に書かれ、並びではなく 1 値しか持てない。
- **CLI 固定 Type 語彙** … Backlog CLI が `--type` の引数として受け付ける 7 語の集合
  （bug・feature・enhancement・task・chore・docs・spike）。プロジェクトの `config.yml` では
  増減できない。
- **Type 導出元** … Atlas が Type 値を取り出す元になる frontmatter 上の場所。decision-5 の
  時点では kind ラベルの 1 つだけだった。
- **Type の消失** … type フィールドを持つタスクが、Atlas の画面では「Type 未設定」として
  表示され、CLI で付けた値が画面のどこにも現れない状態。
- **Type の二重指定** … 1 タスクの frontmatter が type フィールドと kind ラベルを両方持ち、
  Type 導出元が 2 つとも値を持つ状態。
- **Type 候補** … Type 導出元から取り出した、まだ既知判定も畳み込みも受けていない 1 つの文字列。
- **複数 Type 値** … 1 タスクの Type 値が 2 つ以上ある状態。導出元は問わない。decision-5 の
  「複数 kind」（kind ラベルが 2 つ以上）とは指示対象が違う。
- **Type 候補なし** … 1 タスクがどちらの Type 導出元からも Type 候補を得ない状態。decision-5 の
  「kind 無し」（kind ラベルが 0 個）とは指示対象が違う。
- **Type 編集の非提供** … タスク詳細画面の編集操作が Type 値をどちらの導出元についても
  変更しない状態。
- **同値の重複** … 1 タスクから集めた Type 候補のうち 2 つ以上が、導出元を問わず大文字小文字の
  違いを除いて同じ値である状態（`type: bug` と `kind:bug` の組、`kind:bug` と `kind:Bug` の組の
  どちらも当たる）。

**実測（2026-08-02、この機、backlog 1.48.0）。** 使い捨ての Backlog ルートへ `backlog init` し、
`task create --type` / `task edit --type` を流して frontmatter と `config set` の受理キーを見た。
TASK-58 の記録には依存していない。

1. `--type bug` で作ったタスクの frontmatter は `labels` と並んで `type: bug` を持ち、
   **kind ラベルは作られない**。`--type ""` はキーごと消す。
2. **Type の二重指定を CLI は妨げない。** `--type feature -l 'kind:bug,ui'` は
   `type: feature` と `labels: ['kind:bug', 'ui']` を同じタスクへ書く。
3. **CLI 固定 Type 語彙はプロジェクトで増減できない。** `--type banana` は
   `Invalid type: banana. Valid types are: bug, feature, enhancement, task, chore, docs, spike`
   で失敗し、`config.yml` へ `task_types:`／`taskTypes:` を手で足しても無視され、
   `config set` の受理キー一覧にも Type 語彙は無い。TASK-110 の Description が書いた
   「設定既定の値域」は不正確で、正しくは CLI に固定された値域である。
4. Atlas 側では type フィールドが読まれない。読み取り層は未知の frontmatter キーを
   doc-4 §4 の「保持または無視」に置いており、不整合の契機にもしていない。したがって
   Type の消失は静かに起きる。

判断に効く非対称が 1 つある。**kind ラベルの語彙は開いており、CLI 固定 Type 語彙は閉じている。**
decision-5 が接頭辞除去を選んだ根拠は「kind の語彙は各プロジェクトのもので、Atlas 側の対応表に
写すと `kind:spike` を導入するたび Atlas の更新が要る」ことだった。type フィールドの側は逆で、
値域は Backlog CLI が握っており、プロジェクトは増やせない。それでも Atlas が値域を検査しない
のは、管理ファイルを手で編集すれば任意の値が入り、CLI の版が上がれば語彙も変わるからである。
Atlas にとってどちらの導出元も「文字列が入っている場所」であり、値域の知識は
既知 Type 集合による表示の選択にだけ使う。

## Decision

**Type 導出元を 2 つにする。** kind ラベル（`kind:X` の接頭辞除去、decision-5 のまま）に加えて、
frontmatter の type フィールドを読む。decision-5 が「Type 値の導出は kind ラベルの接頭辞除去と
する」と書いた部分は、**導出元を 1 つに限る趣旨としては本決定が改める**。decision-5 の中心の
判断 — Type は 0 個以上の値の並びであり、どれか 1 つへ丸めず、値を捨てず、既知でない値も
表示する — は反転しない。改めるのは値をどこから取るかだけである。

**両方の値を併記する。優先関係は置かない。** Type の二重指定は decision-5 の複数 kind と同じ
枠組みへ載せ、どちらかを勝たせない。片方を優先すると、負けた側の値を画面から捨てることになり、
それは decision-5 が複数 kind について「どれか 1 つへ丸めず、すべて併記する」と決めた判断を、
導出元の違いを理由に反転することになる。反転する根拠が無い — 二重指定が起きるのは
プロジェクトが両方を使っているときであり、どちらが正本かを Atlas は知らない。

**decision-5 の境界事象 2 つは、発火条件を Type 値の側へ言い直す。** decision-5 は「複数 kind」を
kind ラベルが 2 つ以上、「kind 無し」を kind ラベルが 0 個として条件を書いた。導出元が 2 つに
なると、その個数は表示すべき Type 値の個数と一致しない — `labels: []` に `type: bug` を持つ
タスクは kind 無しに当たるが Type 値を 1 つ持ち、`kind:bug` に `type: feature` を持つタスクは
複数 kind に当たらないのに Type 値を 2 つ持つ。**併記の条件を複数 Type 値、「Type 未設定」の
条件を Type 候補なしとする。** 表示の中身（併記する・「Type 未設定」と出す）は decision-5 の
ままで、変わるのは発火条件だけである。「未知 Type」は元から Type 値の側で条件を書いているので
変わらない。条件を言い直さないと、type フィールドだけを持つタスクについて decision-5 が
「Type 未設定」を、本決定が値の表示を指示することになり、accepted な決定が 2 つ食い違う。

**並び順は kind ラベル由来が先、type フィールド由来が後。** decision-5 の並び順規則
（labels の出現順を保つ）をそのまま先頭に残し、新しい導出元をその後ろへ足す。この順にすると、
type フィールドを持たない既存プロジェクトの表示は 1 文字も変わらない。逆順にすると、
kind ラベルだけのタスクでは同じ表示なのに二重指定のタスクでだけ既存の並びが割り込まれる形に
なり、順序の根拠を 2 通り説明することになる。

**同値の重複は 1 つに畳む。** 大文字小文字を無視して既にある Type 値と一致する Type 候補は
落とし、綴りは先に来たものを残す。同じ分類を 2 度出しても読み手に伝わる事実は増えず、
「複数 kind」の見た目と区別が付かなくなるためである。比較を大文字小文字無視にするのは、
既知 Type 集合の判定が既に同じ比較（ASCII の大文字小文字のみを無視する）を使っている
——decision-5 が綴りを表示データと扱い、照合鍵にしない——ことに揃えたものである。

**畳み込みは導出元を問わない。** `type: bug` と `kind:bug` の組だけでなく、`kind:bug` と
`kind:Bug` の組も畳む。導出元で規則を分けると、画面に出る形が同じ 2 つの状態に別の規則が
当たることになり、その差を読み手に説明できない——doc-8 §4 は Type 値の由来を画面に出さないと
定めているので、読み手には区別する手掛かりが無い。この点だけは decision-5 の挙動を変えており、
`kind:bug` と `kind:Bug` を持つタスクの表示は 2 値から 1 値になる。

**畳むのは表示の解釈であって読み取りではない。** ドメインモデルのタスクは、ファイルが実際に
書いていた Type 候補をすべて保持する。

**空の type フィールドは導出元なしとして扱う。** `type:` が空文字列または空白だけの場合、
Type 値を生まない。CLI の解除操作はキーごと消すので、空値は「空という名の Type」ではなく
手編集の残骸である。

**既知 Type 集合を 10 語へ広げる。** 既存の 5 語（feature・bug・research・writing・
maintenance、doc-2 の列挙）に、CLI 固定 Type 語彙のうち重なっていない 5 語
（enhancement・task・chore・docs・spike）を足す。広げない場合、`--type chore` で付けた値は
Backlog CLI 自身の正規語彙であるのに未知 Type の印付きで出る。既知 Type 集合は表示の扱い
（色・並び）を選ぶためだけの集合であり、値を通すかどうかは決めない（decision-5）ので、
広げても未知 Type の枠組みは変わらない。

**Atlas から type フィールドを編集する経路は今回作らない。** doc-5 の操作写像に `--type` は
足さない。TASK-110 の受入条件は読み取りと表示までを求めており、編集部品の新設はそこに無い。

**その結果は Type 編集の非提供であって、導出元ごとの非対称ではない。** kind ラベル側も
タスク詳細画面からは編集できない — 編集草案が持つラベルは通常ラベルだけで
（`src/lib/edit.ts` の `EditDraft.labels`）、画面は `TYPE_NOT_EDITABLE` で提供しないことを
述べている。理由は導出元ごとに別で、kind ラベル側は読み取り層が保持するのが接頭辞を外した値
であり元のラベル文字列と一致する保証が無いため、type フィールド側は操作写像に `--type` が
無いためだが、利用者から見た結果は同じである。したがって Type の二重指定は Atlas 画面から
解消できず、利用者は Backlog CLI か管理ファイルの手編集による。これは既知の制約として
doc-8 に書き、`TYPE_NOT_EDITABLE` の文面も 2 つの理由を述べる形へ直す。編集経路の追加は
m-3 で判断する。

## Consequences

- 望ましい帰結
  - Type の消失が無くなる。CLI で `--type` を使うプロジェクトでも、付けた値が画面に出る。
  - decision-5 の 3 つの境界事象の表示の中身を書き換えずに済む（発火条件は 2 つ言い直した）。
    二重指定は複数 Type 値として複数 kind と同じ見え方になり、画面側に新しい分岐が要らない。
  - 既存プロジェクト（kind ラベルだけを使うもの。このリポジトリ自身も該当する）の表示は
    変わらない。並び順を kind ラベル由来先行にしたことの直接の帰結である。
- 費用・制約
  - **Atlas は Type の二重指定を解消できない。** Type 編集の非提供により、画面に出ている値は
    どちらの導出元のものも消せない。二重指定を直すには Backlog CLI か手編集が要る。
  - **既知 Type 集合が 2 つの由来を持つ語の集合になった。** doc-2 が列挙した 5 語と CLI 固定
    Type 語彙の 5 語で、後者は Backlog CLI の版が上がれば変わり得る。変わったときに Atlas の
    集合を追随させる契機は無く、追随しなければ新しい CLI 語彙が未知 Type の印付きで出る。
    印が付くだけで値は通るので、不整合にはならない。
  - 既知 Type 集合に `task` が入る。タスク台帳の「タスク」と語が衝突して見えるが、これは
    Backlog CLI の語彙であって Atlas の命名ではないため、言い換えない。
  - ドメインモデルのタスクが持つ Type 候補の並びは、同値の重複を畳む前の値である。
    境界の外（画面）が見るのは畳んだあとの Type 値なので、両者の個数は一致しないことがある。
  - 畳み込みを導出元で分けなかった結果、`kind:bug` と `kind:Bug` を持つタスクの表示が
    2 値から 1 値へ変わる。decision-5 の挙動を変えた唯一の箇所であり、type フィールドとは
    無関係に起きる。
- 後続への影響
  - **decision-5 の「Type 値の導出は kind ラベル `kind:X` の接頭辞除去とする」は、導出元を
    1 つに限る趣旨としては本決定で改めた。** decision-5 にその旨と、境界事象 2 つの発火条件を
    複数 Type 値・Type 候補なしへ言い直したことを注記する。表示の中身は decision-5 のままである。
  - doc-4 は 3.1 の `type` 行と 3.3 の分離境界を、導出元 2 つに合わせて改訂する。doc-7 §3・§4 と
    doc-8 §3 の Type 行は、由来の記述と「未設定」の条件を本決定に合わせる。doc-8 §4 には
    Type 値の由来を画面に出さないことと Type 編集の非提供を書く。doc-5 §3.4 の `--type` の項が
    「この食い違いは TASK-110 で扱う」と予約していた箇所は、本決定の参照へ置き換える。
  - type フィールドの編集経路を作る場合は、doc-5 の操作写像へ `--type` を足し、その値域が
    CLI 固定 Type 語彙に閉じていること（Atlas の既知 Type 集合とは別物であること）を
    入力部品の側で扱う必要がある。kind ラベルの増減とは値域の性質が違うので、同じ部品には
    ならない。
