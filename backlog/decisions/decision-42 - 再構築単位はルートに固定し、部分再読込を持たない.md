## Context

品質評価書 (2026-08-01) のパフォーマンス節は、Atlas が **全ルート直列読込・変更ごとのルート全件
再構築** を前提にしていることを挙げ、改善する場合の順序を「① 無期限待ちを除く → ② ルートごとの
ファイル数・読取時間・snapshot サイズ・フロントエンド再計算時間を計測する → ③ 実測で必要になった
場合だけ部分再読込を入れる → ④ 多数ルートで thread 数が問題になれば監視イベントの集約を見直す」と
書いた。**同節は「部分再読込は設計を複雑にするため、測定なしに導入すべきではない」と明記している。**
本 decision は ② を実行した結果と、それが決めた ③・④ の扱いである (TASK-94)。

判断が要るのは、**設計文書が両論を開けたまま置いており、実装がその片方だけを持っているから**である。

- doc-9 §3 は「通知を受けたら、**変化したファイル (不能ならルート)** を読み取り層の再構築単位
  (doc-4) で読み直す」と書いており、字句どおりならファイル単位が既定でルートが縮退先である。
- doc-5 §6 は「再読込の単位は doc-4 のドメインモデル再構築単位 (**ルート／ファイル**) に合わせる」。
- doc-4 §6 も再構築単位を「**ルート／ファイル**」と書いて TASK-14 へ送っている。
- 実装は `SyncState::reload` の 1 経路だけを持ち、**変更ファイル数にかかわらずルート全体を読み直す。**

**これは余地ではなく食い違いである。** doc-9 §3 を字句どおり読めば実装は要求を満たしていない。
どちらを正とするかは実測が決める問いなので、その実測をここに置く。

### 実測 (2026-08-23、macOS arm64、release ビルド、規模計測)

**規模計測 とは、合成した Backlog ルートを規模ごとに読ませ、読取時間・再読込時間・snapshot の
直列化サイズ・フロントエンド再計算時間・監視の thread 増分を出力する 1 本の実行経路を指す。
合否を持たない** (`pnpm run scale`。Rust 側は `src-tauri/src/scale.rs`、フロントエンド側は
`scripts/scale/frontend.mjs`)。

**全ルート直列読取時間 とは、台帳に登録された全ルートを登録順に 1 つずつ読み、各 snapshot を
組み終えるまでの経過時間を指す。** 窓の生成・IPC 転送・最初の描画は含まないので、**「起動時間」
ではない。**

**下の数はどれも本機 1 台・1 回の実行のものである** (`RUNS` 回のうち各項の最小)。**機械が変われば
動く** — 再開条件をファイル数ではなくミリ秒で書いてあるのはそのためである。

1 ルートの読取 (本文 2,000 バイト、docs 13・decisions 41・milestones 4 は本リポジトリと同数)。
`生 I/O` は同じファイルを解析せずに読むだけに掛かった時間である。

| タスク数 | ファイル数 | 生 I/O | 読取 | 再読込 | 直列化 | snapshot |
|---|---|---|---|---|---|---|
| 100 | 158 | 2.9ms | 5.4ms | 5.3ms | 0.20ms | 416KB |
| 250 | 308 | 5.7ms | 10.7ms | 10.8ms | 0.42ms | 853KB |
| 500 | 558 | 49.1ms | 54.9ms | 60.8ms | 0.78ms | 1,581KB |
| 1,000 | 1,058 | 91.1ms | 109.7ms | 115.6ms | 1.59ms | 3,038KB |
| 2,000 | 2,058 | 149.4ms | 196.0ms | 197.5ms | 3.45ms | 5,955KB |
| 4,000 | 4,058 | 358.7ms | 448.7ms | 452.7ms | 6.77ms | 11,794KB |

**本リポジトリ自身の `backlog/`** (257 ファイル・約 2.7MB) は 読取 14.0ms・再読込 14.2ms・
直列化 1.5ms・snapshot 2,751KB である。**合成ルートは ASCII 本文しか持たないので、多バイト本文の
費用を負っているのはこの 1 行だけである** (合成側が ASCII である理由は `scale.rs` の頭註)。

全ルート直列読取時間 (1 ルート 200 タスク): 1 ルート 10.9ms、3 ルート 86.7ms、5 ルート 146.3ms、
10 ルート 304.7ms、**20 ルート 592.7ms** (snapshot 合計 14,168KB)。

フロントエンド再計算時間 (`buildSwimlane`・全タスク一覧・`collectFacets`・`swimlaneTotals` の
一連。Node/V8。**WebView 上では測っていない**): 1,000 タスク 0.44ms、10,000 タスク 3.46ms、
**20,000 タスク 6.47ms**。同じ payload の `JSON.parse` は 20,000 タスクで 97.9ms である
(**IPC 転送そのものは測っていない**)。

監視 1 ルートあたりの thread 増分は **実測 2 本** (notify 自身の watcher thread と debounce
thread。プロセスの thread 数は 監視 0 件で 2、1 件で 5、5 件で 13、10 件で 23、20 件で 43)。
**`project_watch_start` が `watch_loop` へ spawn する 1 本はこの実測に入っていない** —
`AppHandle` が要るので規模計測では起こせない。**合計 3 本/ルートは実測 2 本と構成による分類
1 本の和であり、3 本を実測したのではない。** notify watcher は 1 ルートにつき 1 つである。

### 実測が示した 4 つ

1. **再読込は読取とほぼ同値である。** どの規模でも差は誤差の中にあり、再読込が読取より安い経路を
   通ってはいない。
2. **読取時間を決めるのはファイル数であって本文の大きさではない。** 250 タスクで本文を 500 バイト
   から 32,000 バイトへ 64 倍にしても 11.2ms → 20.3ms (1.8 倍) にしかならない。
3. **読取時間の 8 割は生の I/O である。** 4,058 ファイルで 448.7ms のうち 358.7ms。解析器は残り
   2 割で、**部分再読込が削るのはこの 8 割のほうである。**
4. **フロントエンドの再計算は律速ではない。** 20 ルート 20,000 タスクで 6.5ms であり、同じ規模の
   直列読取 (592.7ms) の 2% を下回る。**品質評価書が計測対象に挙げた 4 つのうち、これだけは
   桁が違う。**

### 実測の限界

**1 ディレクトリの `.md` が約 350 件と約 400 件の間で、1 ファイルあたりの読取時間が 16.5µs から
86µs へ跳ぶ。** 素の node の read ループでも同じ位置で再現するので Atlas のコードではない。
**原因は特定していない。** したがって **小さいルートで測った 1 ファイルあたりの値を大きいルートへ
外挿できない** — 上の表の生 I/O が 308 ファイルの 5.7ms から 558 ファイルの 49.1ms へ 8.6 倍に
なるのはこれである (1 ファイルあたり 18.5µs と 88µs)。

**測っていないもの**: 窓の生成、IPC 転送、最初の描画、WebView 上の再計算、Windows の thread 数。
**「無視できる」ではなく 未測定 である。**

## Decision

**再構築単位はルートである。** 変更ファイル単位の部分再読込を持たず、監視イベントの集約は現行の
デバウンス 1 段のままとする。

- **doc-9 §3・doc-5 §6・doc-4 §6 の「ルート／ファイル」をルートへ書き換える。** doc-9 §3 の
  「変化したファイル (不能ならルート)」は「変化を観測したルート」になる。**開けたままにしない** —
  実装が片方だけを持っている状態で両論を残すと、次に読む者が食い違いをもう一度見つけ、同じ計測を
  やり直すことになる。
- **失う余地は、この節の 再開条件 が数値で持つ。** 条件付きで残すのであって、捨てるのではない。
- **監視の 2 段目の集約を持たない。** 20 ルートで 43 本 (実測、`watch_loop` を足して 63 本相当) は
  どのデスクトップ OS でも資源圧にならず、集約が減らすのは thread であって時間ではない。

### 再開条件

次のどれかを 規模計測 が示したら、この判断を測り直す。**どれも `pnpm run scale` が出す値である。**

- **1 ルートの再読込がデバウンス窓 250ms を超える。** 超えると、外部ツールが書き続ける間その
  プロジェクトのロックが半分以上の時間握られる。本日の実測では 2,058 ファイルで 197.5ms・
  4,058 ファイルで 452.7ms なので、この点は 2 千件台の後半にある。
- **全ルート直列読取時間が 1 秒を超える。** 本日の実測は 1 ルート 200 タスクで 20 ルート 592.7ms
  なので、同じ規模なら 30 ルート台でこの点に達する。**ただしこの条件が要求するのは部分再読込では
  ない** — 下の 後続への影響 を見る。
- **フロントエンド再計算時間が 50ms を超える。** 本日の実測では 20,000 タスクで 6.5ms であり、
  桁が 1 つ足りない。

**この 3 つは「いま超えていない」ことを述べたものであって、「超えない」ことを述べたものではない。**

## Consequences

- 望ましい帰結
  - **doc と実装の食い違いが 1 つ閉じる。** doc-9 §3 を字句どおり読んだ者が「実装が要求を
    満たしていない」と読める状態が無くなる。
  - 一貫性の分かりやすさと cache invalidation の不在という、全件再構築の利点を保てる。
  - **再開の判断が測定値になる。** 「遅い気がする」ではなく、`pnpm run scale` の 3 つの数で決まる。
- 費用・制約
  - 変更 1 ファイルの外部更新でも、そのルートの全ファイルを読み直す。本リポジトリ規模で 14ms、
    4,058 ファイルで 453ms である。
  - **再開条件は本機 1 台の実測に乗っている。** 遅い機械では同じファイル数でより早く条件に達する。
    条件を「ファイル数」ではなく「ミリ秒」で書いたのはそのためで、測る側の機械で測ることを求める。

### 後続への影響

- **実測で最も大きい項は全ルート直列読取時間であり、部分再読込はここに一切効かない** — 初回読取は
  定義上すべてのファイルを読む。品質評価書が並べた改善順 (部分再読込 → 監視集約) にこの項は無く、
  **順序そのものが実測で入れ替わった。** 起動時の全ルート読取を直列から変える扱いは TASK-199 が
  持つ (m-4。2026-08-23 にオーナーが判定)。
- **規模計測 を「毎回の検証」に足さない。** 合否を持たないので、`pnpm test`・`pnpm run check`・
  `pnpm run lint` の 3 本は 3 本のままである (decision-40 が GUI E2E について採ったのと同じ形)。
  規模計測 が壊れていないことを保つのは `#[cfg(test)]` によるコンパイルだけで、**フロントエンド側
  (`scripts/scale/`) はそれも掛からない** — `tsconfig.json` は `scripts/` を含まないので
  `pnpm run check` も読まない。**触った回に走らせる。**
- 1 ファイルあたり読取時間の段差の原因は測っていない。**特定するなら別タスクであり、本 decision は
  それに依存しない** — 段差があること自体は、外挿を禁じるという形で既に織り込んである。
