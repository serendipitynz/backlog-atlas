集約が害になるものが同じ「版表記」に見える。**7 種類目（付随的な版表記）は着手後に見つかった** —
本決定を書いた時点では実測註に数えており、レビュー後にユーザーの問い（「上げようと上げまいと
ずっと残るものという理解で合っているか」）を受けて 92 件を 1 件ずつ読み直したときに分かれた。
**種別で分けた残余を数として使うときは、残余の中身を 1 件ずつ読む** — 読まずに引き算で出すと、
別の種別がその中に紛れる。

  `update.rs` の `MIN_VERSION` の定義。
- **実測基準版** … 1 つの doc の実測記述が共通に立つ版を、その doc が 1 回だけ宣言した値。

- **版差記録** … 2 つ以上の版の挙動の違い、またはある実測を測り直した経過を述べる文。13 箇所

  2 つの版を名指すことに意味があるので基準版が上がっても動かない。
- **要件の写し** … decision-7 の最低バージョン要件の値を他の文書が本文へ再掲したもの。4 箇所
  （doc-4 §4・doc-5 §3・decision-2・decision-7 の Context）。値の散文側の正本そのもの

- **付随的な版表記** … 版を名乗ってはいるが、測定でも要件の値でも版差でもないもの。2 箇所

## Decision

### 1. 版値はコード側の 1 箇所に寄せる

`update.rs` の `MIN_VERSION` を**コード側の正本**とする。版の比較・試験の入力値・fixture の入力値は
すべてここから導く。Rust の試験は `MIN_VERSION.to_string()` を使い、フロントエンドの試験と fake は
`src/lib/confirmed-version.ts` の `CONFIRMED_CLI_VERSION` を使う。同モジュールは記録
（`cli_readiness.json`）を読むだけで、版文字列を自分では持たない。**したがってフロントエンドの
ソースに版リテラルは 1 つも無い。**

記録を経由するのは、フロントエンドが Rust の定数を直接読めないためである。記録は Rust 側を出所と
する生成物で、`MIN_VERSION` を動かせば `wire_fixtures.rs` が再記録まで失敗するので、`MIN_VERSION`
が単一出所である性質は保たれる。`cli_readiness.json` の ready 見本は要件の値そのものを `version` に
持ち（床にちょうど居る CLI を演じる）、その読みは `wire-fixture.test.ts` が
`command_errors.json` の `minimum` と突き合わせて固定する — 同じ定数の 2 つの記録が一致しなければ
落ちるので、見本を別の版で作り直しても値が黙って入れ替わらない。

### 2. 画面文字列は版を名乗らない

画面に出る文が版表記を持つのは、**利用者の CLI の版と Atlas の動作確認済み版の差そのものを述べる
場合だけ**である。現在それは 1 文しかない（`readinessReason` の unsupported 分岐。`CliReadiness` の
`version` と `minimum` を読む）。他の文 — 最後の 1 件を削除できない理由、draft・completed・archive が
読み取り専用である理由、マイルストーンの削除・改称の hint — は「CLI に手段がない」と述べ、版を
名乗らない。測定は doc-5 §3.1・doc-9 §4.2.1 が持つ。

理由は 2 つある。①**2026-08-11 の目視でユーザーが同じ判断を既に下している**: 状態遷移の確認質問の
初稿「アーカイブから戻す操作は v1.48.0 の CLI にありません」を落とし、版番号は「利用者がその瞬間に
訊いていないことに答える」と述べた（`edit.ts` の `TRANSITION_CONFIRM_QUESTION` の註、
doc-8 §6.5 が測定を持つ）。2026-08-08 の TASK-123 が作成フォームの項目別理由を ノイズ として落とした
のも同型である。②**版を名乗ると真であることを保証できない。** これらの文は `CliReadiness` が
`null`（probe 未応答）や `unavailable`（`App.svelte` が自前で組むため版を持たない）のときにも画面へ
出るので、そこで名乗れる版は無い。差を述べる 1 文だけが、必要な 2 つの値を必ず持っている。

したがって `CliReadiness` の `ready` に動作確認済み版を載せない。載せても使ってはいけない値になり、
`unavailable` との間で同じ種類の文の書き方が割れる。

### 3. doc は実測基準版を 1 回宣言する

実測記述を持つ doc は、冒頭の前提の直後に実測基準版を 1 回宣言し、本文の個々の実測記述は版を
名乗らない。宣言の文は 7 つの doc（doc-3・4・5・7・8・9・10）で同一である。

**寄せ先は中央の定数ではなく、その doc 自身のリテラルである。** これが §1 との違いであり、本決定の
要点である。7 つの doc は 7 つの宣言を持ち、それぞれの書き換えがそれぞれの doc の再実測を促す。
中央の定数を参照させると、定数を動かした瞬間に 7 つの doc 全体が新しい版で実測されたことになる。

### 4. 実測註はリテラルのまま残す

コードの註と、decisions の実測註は、版表記をリテラルのまま持つ。集約しない理由は 2 つある。

- **中央の定数を参照させると、誰も測っていない版で実測したという主張が自動生成される。** 定数を
  動かした瞬間に 82 箇所ぶんが新しい版を名乗り、このプロジェクトが保っている「不可能」と
  「未測定」の区別が機構の側から壊れる。
- **リテラルの書き換えが再実測を促す強制力である。** 外すと確認の契機が消える。

**ファイル単位の宣言（§3 の形をコードにも適用すること）も採らない。** 触るファイルは 30 から 20 前後
まで減るが、1 行の書き換えが 10 個の事実を「再実測済み」に見せるので、上の 2 点目が失われる。
2026-08-12 にユーザーがこの選択肢を見たうえでリテラル維持を確定した。

**残す対象は実測註だけである。** 付随的な版表記（Context の 7 種類目）は測定を指していないので、
本節が求める再実測の対象ではない。**版差記録も本節の対象ではない**（§5 と同じ理由で動かさない）。
引き上げの作業量を数えるときは、この 3 つを混ぜない — 混ぜると、測定でないものを再実測する予定を
立てることになる。

**上げても挙動が変わっていなかった註も、確かめたうえでリテラルを新しい版へ動かす**（2026-08-12 に
TASK-152 が判断し、ユーザーが確定した。本決定を書いた時点では §3・§4 がこれを前提にしていただけで、
決めてはいなかった）。範囲表記と据え置きの 2 案を検討して却下した理由が、この形の根拠である。

- **範囲表記（「v1.48.0 以降」）は採れない。** 却下の理由は 2 段あり、**1 段目だけで足りる**。
  ①**範囲は測っていない版についての主張を含む。** TASK-152 が測ったのは v1.48.0 と v1.49.3 の
  2 版だけなので、**間の v1.49.0・v1.49.1・v1.49.2 は未実測である** — これは測定の形そのもので
  あって推測ではない。上限を閉じた「v1.48.0〜v1.49.3」にしても同じ穴が残り、本プロジェクトが
  保っている「不可能」と「未測定」の区別が §4 冒頭と同じ形で壊れる。②**上限が開いた範囲は、
  偽である疑いも濃い。** TASK-153 が、`--ref ""`／`--depends-on ""`／`-a ""` の沈黙無変更を
  v1.50.0 が反転させたと記録している（`task-builders.ts` の `parseClearableStringList`）。
  **ただし TASK-152 はこれを実測していない** — `~/.npmrc` の `min-release-age=7` が v1.50.x の
  取得そのものを弾くためで、それは v1.50.x を動作確認済み版に採らない理由と同じものである。
  **測ってある側は整合している**: `--clear-refs`／`--clear-deps`／`--clear-docs` は v1.48.0 にも
  v1.49.3 にも無く、沈黙無変更は両版で成立した。
- **据え置きは §5 が引いた線を消す。** decisions の実測註を動かさない根拠は、それが日付つきの
  「過去の判断が立っていた事実」だからである。対してコードと AGENTS の実測註は歴史ではなく、
  **いまのコードがその拒否を行う根拠**である。`MIN_VERSION` が新しい版を指しているのに註が
  古い版について述べている状態は、コードが実際に要求する版について何も述べていない。据え置くと
  コードの註が decisions の註と同じ振る舞いになり、§5 の区別が層の側から失われる。加えて
  **「確かめて無変更だった」と「確かめ忘れた」が読み手に区別できない。**
- **ユーザーが節約を見込んだ費用は、リテラルの側には無い。** 据え置きでも「変わっていない」と
  言うためには測る必要があるので、再実測の量は 3 案で同じである。動かす案が余分に払うのは
  リテラルの打ち直しだけで、それは §4 の 2 点目が求めている確認の契機そのものである。

**違いが出た箇所は、動かすのではなく版差記録にする。** TASK-152 で違いが出たのは 1 件で、それは
**§4 の 82 件ではなく §3 の doc の実測記述**だった（doc-8 §6.5、completed タスクへの `task edit` の
失敗文面）。**§4 の 82 件は全件が一致し、版差記録へ移ったものは 1 件も無い** — コードにその文面へ
依存する註は元から無く、更新アダプターは終了コードで判定する。doc-8 §6.5 は本文を版に依存しない
書き方へ改め、文面を名乗るのは新設した版差記録だけにした。**版差記録へ移した註は、以後 §4 の対象
ではなくなる**（§5 と同じ理由で動かさない）。

**測り直して主張そのものが偽だった場合は、版を動かすのではなく主張を直す。** TASK-152 は 1 件
見つけた（`interpret/type_value.rs` の「`config.yml` は `--type` の語彙を広げられない」）。**これは
v1.48.0 でも偽で**（両版で実測した）、版差ではなく誤りだったので、註を訂正して**元の主張が偽だった
ことを書き残した**。動かす前に確かめる理由はこれで 2 つになる — 版差を見つけるためと、元から
偽だった主張を見つけるためである。

どの案を採るにしても、確かめずにリテラルだけ動かすことは §4 が禁じている。

### 5. decisions は集約対象にしない

decisions の実測註 9 箇所と版差記録 5 箇所は触らない。decision は日付つきの記録であり、そこにある
「2026-08-02、この機、backlog 1.48.0」のような文は、その判断が立っていた事実である。要件を上げる
ときに書き換えると、過去の判断の根拠を改竄することになる。**decisions で直すのは要件の写しだけ**
である（下記）。

### 6. 要件の写しは参照へ置き換える

decision-7 の「最低バージョン要件」の項を**散文側の正本**とし、他の decision・doc はその値を写さず
本項を参照する。doc-4 §4・doc-5 §3・decision-2・decision-7 の Context の 4 箇所を参照へ改めた。

## Consequences

- 望ましい帰結
  - 要件を上げるときに触る箇所が **166 → 95**、ファイルが **39 → 30** になる。着手時の 189 箇所の
    うち、版差記録 13・decisions の実測註 9・付随的な版表記 2 は元から触らないので、引き上げの対象は
    165 箇所（＋`MIN_VERSION` の定義 1 で 166）・39 ファイルだった（残る 6 ファイルは日付つきの
    実測註だけを持つ decision である）。**本決定の後に文字列が残るのは 127 箇所・40 ファイル**で、
    そのうち引き上げで触るのが 94 箇所（＋`MIN_VERSION` の定義 1 で 95）・30 ファイルである。
    **この数はレビュー後に 1 件ずつ読み直して直した値である** — 初版は 122 → 100 と書いており、
    ①`screen-text.test.ts` の検査を足したのが計数の後だったため 5 箇所を数え漏らし、②付随的な版表記
    2 箇所と `update.rs` の版差記録 3 箇所を実測註に数えていた。
  - 版値の食い違いが起こりえなくなる。`MIN_VERSION` を動かすと `wire_fixtures.rs` が落ち、再記録
    しないとフロントエンドの試験が動かない。
  - 画面に偽の版を出す道が閉じる。差を述べる 1 文以外は版を持たないので、`readiness.version`
    （利用者の CLI）を誤って表示に使う余地が無い。
- 費用・制約
  - **触るファイルは 4 分の 1 しか減らない**（39 → 30）。残る 95 箇所のうち 82 が実測註で、
    これは §4 で残すと決めたものである。要件の引き上げは機械的な置換ではなく再実測を含む
    作業であり続ける。**ユーザーの当初の問い（「毎回 50 以上のファイルを修正・確認が必要なのか」）
    に対する答えは「30 ファイルまでは減るが、そこから先は再実測の量そのものである」**になる。
  - **実測註は今後増える。** 新しい挙動を実測して註を書くたびに 1 件足されるので、82 は下限である。
    ただし費用が発生するのは要件を上げた回だけで、上げない限り 1 行も触らない。
  - 利用者は「どの版の制約か」を画面で読めなくなり、doc へ行くことになる。
  - doc の実測基準版は doc 単位でしか動かせない。1 つの doc の中で一部だけ測り直した状態は、
    宣言の形では表せない（表す必要が生じたら版差記録として本文に書く）。
- 後続への影響
  - **TASK-152**（要件を v1.49.3 へ上げる）が触ったのは上の 95 箇所・30 ファイルである。内訳は

    decision-7 の正本 1・README 4。**触らなかったのは**着手時にあった版差記録 13・decisions の
    実測註 9・付随的な版表記 11・生成物の記録 2 である。
  - **版差記録は引き上げのたびに増える。** TASK-152 の後は **17 箇所**で、着手時の 13
    （doc-5 §3.4 の 4・doc-9 §5 の 1・decisions の 5・`update.rs` の 3）に 4 つ足された —
    doc-8 §6.5 の 1（失敗文面の版差）・decision-7 の 2（この引き上げの理由と v1.50.x の見送り）・
    `type_value.rs` の 1（元から偽だった主張の訂正記録）である。**次の引き上げが数えるのはこの 17
    で、13 ではない。**「触らない」の総数も 33 から 37 になる。
  - **TASK-152 へ委譲した判断は済んだ**（§4 の末尾に追記した。2026-08-12）: 挙動が変わっていな
