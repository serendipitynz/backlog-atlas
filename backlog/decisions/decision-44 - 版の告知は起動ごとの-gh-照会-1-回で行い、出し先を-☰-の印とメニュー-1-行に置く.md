## Context

decision-30 は v0.1.0 が **自己更新** を持たないと決め、**版の告知** を README と GitHub Releases の
watch に置いた。同決定の 費用・制約 の 3 つ目がその穴を自分で書いている — 「版の告知が Atlas の外に
ある。GitHub Releases を watch していない利用者には何も届かない。アプリ内の版の告知（TASK-157）が
入るまでこの穴は残る」。本決定はその TASK-157 である。

**decision-30 の 4 語をそのまま引く** — 自己更新（アプリ自身が新しい版を取得して自分の配布物を
置き換える経路）・版の告知（新しい版が出たことを利用者が知る手段。取得と入れ替えの操作は含まない）・
手動入れ替え・自プロセスの外向き通信（Atlas のプロセス自身が開く外向き接続。子プロセスの CLI が開く
ものは含まない）。**本決定が行うのは 版の告知 だけで、自己更新 は依然として持たない。**

争点語は TASK-157 の対応表で本文より先に固定した（初版 2026-08-24、告知の出し先 1 行を第 2 版で確定）。
以下で使う **利用中の版**（走っているビルド自身が持つ版。`src-tauri/Cargo.toml` の `version`）・
**公開されている版**（リリース置き場が `releases/latest` として答えるリリース 1 件の tag。draft と
prerelease は入らない）・**新しい版**（公開されている版 が 利用中の版 より真に大きい状態とその値）・
**版照会**（公開されている版 を 1 つ得るための `gh` の 1 回の起動）・**照会の縮退**（版照会 が
公開されている版 を答えなかったこと。入口は `gh` 不在・未認証・照会失敗・照会期限到達 の 4 つ）・
**リリース置き場**・**リリースページ**・**告知の出し先** はその表の語である。

### 実測 (2026-08-24、この作業機、gh 2.97.0)

- **温まった 版照会 は 0.49・0.57・0.62 秒である。** `gh api --hostname github.com
  repos/<owner>/<repo>/releases/latest --jq '.tag_name'` を 3 回。**初回だけ 6.80 秒**で、これは冷えた
  接続ぶんである。decision-19 の gh 照会期限 30 秒には冷えた回でも遠い。
- **未認証は確かに 照会の縮退 へ落ちる。** `GH_CONFIG_DIR` を空のディレクトリへ向け `GH_TOKEN` を外して
  同じ呼び出しを行うと **exit 4** で、stderr は `gh auth login` の案内である。**パブリックリポジトリでも
  `gh api` は認証を要する**ので、「公開リポジトリなら未認証でも読める」は成り立たない。
- **印 の色は 10 テーマすべてで地に対して 5.86:1 以上である。** `--info` を取り、地は `body` の背景。最小が atlas-light の 5.86、最大が rose-pine の 10.37（借り物 playwright ＋ WebKit で実物のシェルを測った。2026-08-24）。**decision-22 の 印グリフの収録条件 3:1 は族の色についての条件なので直接は掛からない**が、比べる相手として使える値としてこれを上回っている。
- **印 は ☰ の図形に触れない。** 控えは 24.625px、図形はその中央に 11.953px なので隅は 6.33px で、5px の点を隅へ寄せると 1〜6px を占めて 0.33px 空く。**5px が触れずに置ける最大である。**
- 返った値は `v0.1.0` で、利用中の版 は `0.1.0` である。**tag の先頭の `v` は版値ではない**ので、
  比較の前に落ちる必要がある（`update.rs` の `Version::parse` が既にそうする）。

### 先行する判断との関係

- **decision-14 の形をそのまま使う。** 引数は固定配列、`--hostname github.com` で `GH_HOST` に
  横取りさせない、`--jq` で応答を 1 行へ縮約して JSON パーサを持たない、起動時に `GH_PROMPT_DISABLED` と
  `GH_NO_UPDATE_NOTIFIER` を立てる。**`--paginate` は要らない** — `releases/latest` が返すのは
  ページングされない単一オブジェクトである。
- **decision-19 の期限と共有の待機をそのまま使う。** 版照会 は `subprocess` の期限付き待機を通り、
  期限は gh 照会期限 と同じ値である。**独自の待機を書かない**理由はあちらが述べたとおりで、
  あの実装が正しくなるまでにレビュー 5 ラウンドを要したことである。
- **decision-29 の解決順に載る。** 版照会 が起動するのは 外部コマンド `gh` であり、アプリ設定の
  外部コマンド指定 が最優先で効く。**`gh` を 3 本目として増やすのではなく、既にある 1 本を 2 つ目の
  用途で呼ぶ。**
- **decision-30 が数えた費用をどれも負わない。** 新規本番依存は 0 件で、自プロセスの外向き通信も
  0 本のままである（通信を行うのは `gh` の子プロセスで、認証も利用者のものが効く）。署名鍵は
  存在せず、遡れない受け皿 も要らない。**自己更新 の再検討ではない**ので、decision-30 の
  再検討の契機 3 つはどれも開いていない。
- **decision-13 に項目を足さない。** アプリ設定に 版照会 の切替も最後に照会した時刻も置かない。
  理由は Decision の 2 で述べる。
- **decision-27 §2 は 利用中の版 と 公開されている版 に掛からない。** あちらの 5 つの規則は
  Backlog CLI の 最低バージョン要件 の**表現**についてのもので（AGENTS 和英の 動作確認済み版 節が
  そう書いている）、Atlas 自身の版はその対象ではない。**§2 の理由②（版を名乗ると真であることを
  保証できない）も当たらない** — `CliReadiness` が版を持たない状態で画面へ出る文があるのがあちらの
  事情で、公開されている版 は照会が答えた値そのものであり、答えなかったときは告知が出ない。

## Decision

### 1. 版照会 は起動ごとに 1 回、利用者が頼まなくても行う

起動順序（`App.svelte` の `onMount`）へ 1 段足す。**待たない** — 起動中の誰もその答えを読まないので、
待つと最初の描画の前に IPC の往復が 1 つ増えるだけである（`refreshDirectory` と同じ形）。

**利用者の押下を入口にする案は採らない。** 押しに行く利用者は Releases を見に行ける利用者であり、
decision-30 が書いた穴（watch していない利用者に何も届かない）はその案では閉じない。**AC #1 の
「知れる」は満たしても「届く」は満たさない。**

**代償は、Atlas の起動時に子プロセスが GitHub へ 1 回問い合わせる挙動が既定になることである。**
Atlas 自身の接続は 0 本のままだが、外向きの通信が起動のたびに 1 回起きること自体は新しい。
2026-08-24 にオーナーがこれを承知のうえで選んだ。

### 2. 頻度の記録を持たず、アプリ設定に切替も置かない

**1 日に 5 回起動すれば 5 回照会する。** 最後に照会した時刻を持てば減らせるが、その値の置き場は
アプリ設定ファイルであり、**アプリ設定の項目を足すのは 3 か所の編集で、うち 2 か所は落としても
静かである**（`KNOWN_SCHEMA_VERSION`、`mergeDraft`、`normalize`。AGENTS の ツールチェーン 節）。
0.5 秒・1 回の照会を減らすために払う費用ではない。

**切替を置かない理由は別である。** 既定を切にすると穴が閉じず、既定を入にした切替は、それを探す
利用者がその存在を知っている必要がある。**設定を持たないほうが、何が起きるかを 1 つに保てる。**
自動照会そのものを嫌う利用者への答えは、いまは持たない — 下の 再検討の契機 に入口を置く。

### 3. 告知の出し先は ☰ の印 と メニュー 1 行 で、上部帯を作らない

**doc-11 §4 の閉じた表は動かさない。** 版の告知 は画面の状態を 1 つも変えない — 発行できない操作は
無く、表示は古くなく、回答を待っている問いも無い。**あの表が並べているのは操作か鮮度に効く状態で、
版の告知 はそのどれでもない。** 帯にすると、× で閉じても次の起動で戻るものが画面の最上段に住み、
最悪ケースが 5 本から 6 本へ伸びる。

置くのは次の 2 つで、**doc-7 §2.1 のメニューの側の改訂である。**

- **メニューに リリースページを開く を常設する。** 新しい版 の有無で現れたり消えたりしない —
  行の有無が状態を述べる形にすると、メニューの項目が起動ごとに違う数になる。押すと リリースページ を
  既定ブラウザで開く。
- **新しい版 があるとき、その行が版を語で述べ、☰ に 印 を付ける。** ☰ は アイコンのみのボタン
  （doc-11 §2.4）なので、印は図形の外側の塗りで示し、同じことを `aria-label` にも語で足す —
  3 配置切替の 既定印 が先に採った形である（doc-8 §2.2）。**メニューを開かなくても気づけるのは
  この印だけ**なので、これが 版の告知 の本体である。
- **行の側は 印 を持たず、版を可視の語で述べる。** あの行は可視の文言を持つ控えなので、状態を
  図形で足すと `aria-label` と可視の名前が食い違う側の問題に入る（doc-11 §2.4）。**語で述べれば
  読み上げにも目にも同じものが届く。**
- **この行を押すとメニューは閉じる。** doc-7 §2.1 は閉じるかどうかを 群 で決めており、被せ層を上げる行は
  閉じ、グリッドの行を変える行は閉じない。**この行はどちらの理由でもなく、それ自身の理由で閉じる** —
  上がる層が無いので閉じる契機 4 つのどれにも当たらず、押下 1 回で用事が済み、行き先は Atlas の外である。
  閉じないと、利用者が去った窓の上に誰も降ろしていない層が残る。**この帰結が、押下の失敗を ⑤ 通知 へ
  向ける**（doc-11 §4 の 押した層が結果より先に閉じるもの）。

### 4. リリースページ は このビルドの定数で、応答が返した URL を開かない

リリース置き場 の owner/repo はビルド時の値で、アプリ設定にも台帳にも無い。**リリースページ の URL は
その定数から組み、`releases/latest` の応答が含む URL は読まない。** 網の応答から来た文字列を
既定ブラウザへ渡す経路を作らないためで、**照会が答えるのは tag 1 つだけ**という形はここから来ている。

**開く先はリリース一覧のページで、リリース 1 件のページではない。** 行は 新しい版 が無いときにも
押せるので、そのとき開く先が「新しい版のページ」では嘘になる。

### 5. 照会の縮退 は 4 つを区別せず、⑤ 通知 にも載せない

`gh` 不在・未認証・照会失敗・照会期限到達 のどれであっても、**版の告知 が出ないだけで画面は変わらない**
（AC #5）。**4 つを画面の上で区別しない** — 帰結が同じで、利用者が取れる行動も同じである。

**doc-11 §4 の ⑤ は「押下そのものが無い起動時の失敗」を自分の届け先だと書いており、字面ではここも
そこに入る。** 入らないと決める理由は、あの 3 例（設定の読取・変更通知の購読・外部エディタの確認）が
失敗すると**利用者が持てたはずの能力が減る**のに対し、版照会 の失敗が減らすのは**利用者が見たことの
ない告知だけ**だからである。**⑤ を立てると、Atlas は「知らせようとして失敗した」ことを、知らせる
中身が無いときに述べることになる。** doc-11 §4 にこの例外を理由付きで書く。

**縮退の理由を画面へ運ばない**ので、`release_notice_read` は 新しい版 が無いことと 照会の縮退 を同じ
「告知なし」で返す。**画面が使ってはいけない値を wire に載せない**という形は decision-27 §2 が
`CliReadiness` の `ready` について先に採ったものと同じである。

## Consequences

- 望ましい帰結
  - **decision-30 が名指しした穴が閉じる。** watch していない利用者にも、次の起動で 印 が届く。
  - **decision-30 が数えた費用をどれも払わない。** 新規本番依存 0 件、自プロセスの外向き通信 0 本、
    署名鍵なし、遡れない受け皿なし。**「Atlas が外部と通信する経路は、利用者が導入・認証した CLI の
    子プロセスだけである」という説明が真のまま残る。**
  - **上部帯の閉じた表と最悪ケースが動かない。** フィルタ帯 1 行 ＋ 帯 5 本 で頭打ちのままである。
  - **アプリ設定のスキーマ版が動かない。** 設定項目を足さないので、`KNOWN_SCHEMA_VERSION` と
    `mergeDraft`・`normalize` の 3 か所はどれも触らない。
- 費用・制約
  - **起動のたびに GitHub へ 1 回問い合わせる。** 頻度を落とす記録を持たないので、起動回数がそのまま
    照会回数である。**利用者が切る手段は無い**（`gh` を PATH から外す以外に）。
  - **`gh` を持たない利用者には 版の告知 が 1 度も出ない。** decision-30 の穴はその利用者については
    閉じず、README と watch のままである。**Atlas はそのことを画面で述べない**（§5）。
  - **告知は印 1 つなので、見落としうる。** 帯を選ばなかった代償で、気づくのが遅れても失われるのは
    版を上げる時期だけである。
  - **リリースページ を押した利用者は、そこから先を手で行う。** 手動入れ替え は手動入れ替えのままで、
    decision-30 の判断は動いていない。
  - **draft と prerelease は 新しい版 にならない。** `releases/latest` がそれらを外すためで、
    公開前の版を先に知らせる道はここに無い。
- 後続への影響
  - **doc-7 §2.1 に リリースページを開く の行と、その 印 を書く。** メニューの項目の並びは
    入口 → キーボード操作一覧 → **リリースページ** → プロジェクト一覧 になる。**固定の行を
    プロジェクト一覧より前に置くのはあちらの規則どおり**で、一覧は台帳の数だけ伸びる。
  - **doc-11 §4 に、版照会 の失敗を ⑤ に載せない例外を理由付きで書く。** 表の行は増えない。
  - **doc-13 §3.1 の 4 つの版に 5 つ目は増えないが、タグの形についての検査が 1 つ増える。**
    版照会 が比べるのは `Cargo.toml` の版がバイナリへ入ったものと tag であり、**タグと 4 か所を
    突き合わせる規則がそのまま 版照会 の正しさを支える** — 突き合わせを飛ばした版が出ると、その版の
    利用者は自分より古い tag を「新しい版」と読まされうる。**加えて、素の `vMAJOR.MINOR.PATCH` 以外の
    タグをリリース workflow が落とす**（2026-08-24 に足した。doc-13 §3.1）。**§4 が「読めないタグには
    何も告知しない」と決めたことの裏側で、両方が要る** — こちらだけでは `v0.1.1+build.1` が
    「現に新しいリリースなのに、どの Atlas もそれを述べない」状態を作れてしまい、それは意図した沈黙では
    あっても利用者にとっては欠落である。**沈黙を選ぶ判断と、沈黙が起こりえないようにする検査は別の場所に
    属する**: 前者は読めない値を比べないという Atlas の側の規則で、後者はその値を出さないという配布層の
    側の規則である。
  - **AGENTS 和英に本決定を引く項を足さない。** 起動順序・メニュー・上部帯はどれも doc が正本で、
    AGENTS はそれらの写しを持たない。
  - **v0.2.0 を出す回（TASK-181）に、この経路が初めて意味を持つ。** それまで 公開されている版 は
    利用中の版 と等しく、印 は出ない。**印が出るところを見られるのは v0.2.0 の公開後である。**
- 再検討の契機
  - **自動照会そのものを嫌う報告が来たとき。** そのときはアプリ設定に切替を置く（§2 の費用を払う）。
    「設定が無い」ことへの不満だけでは開かない — 開くのは、切ることを望む利用者が現にいる場合である。
  - **起動が遅いという報告が、版照会 に帰属できたとき。** 待たない形なので最初の描画は待たされない
    はずだが、**測ったのはこの機の 1 台だけである。**
  - **prerelease を先に知らせる必要が出たとき。** `releases/latest` を別の照会に替える判断になる。
