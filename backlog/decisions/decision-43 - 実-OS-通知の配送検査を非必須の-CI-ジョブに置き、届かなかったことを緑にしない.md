## Context

doc-9 §3 は、各 Backlog ルートの管理ファイル群をファイル監視で購読し、通知を受けたらそのルートを
読み直すと定める。実装は `notify` crate で OS のファイル変更通知を購読する
(`src-tauri/src/sync.rs`)。**Atlas 自身のコードが正しいことは決定的なテストが持っている** —
管理パス判定・デバウンス規則・通知が欠けたときにルート全体の読み直しへ倒すこと。**持っていないのは
「OS が現に配送するか」である。**

それを測る 1 本 (`sync::tests::the_watch_session_delivers_a_batch_for_an_external_change`) は
`#[ignore]` で既定実行から外れており、外れている理由は主張の対象が環境の性質だからである。
**結果として、この 1 本は誰も回していなかった** — 2026-08-01 のレビューでも未実行であり、通した環境の
記録は 1 つも無い。

判断が要るのは、外してあること自体ではなく、外したままにすると次の 3 つが同時に成り立つからである。

- **`notify` はキャレットで入っている** (`notify = "8"`、実物は 8.2.0)。`cargo update` で minor が入り、
  **配送を通る唯一のテストが既定実行の外にあるなら、配送の退行は黙って通る。**
- **その 1 本の合格条件が `WatchBatch::Rescan` を含んでいた。** `Rescan` は「イベントが落ちた」か
  「watcher がエラーを述べた」を意味するので、**緑が「届いた」を述べていなかった** — Atlas の倒し方が
  正しいことを述べていただけで、それは決定的なテストが既に持っている。
- **libtest のフィルタが何にも当たらない実行は 0 で終わる** (実測: cargo 1.96.0 で
  `0 passed` は緑)。手順を「この名前を渡して回せ」と散文で書くだけでは、**名前が動いた日から緑が
  何も述べなくなる。** cargo にこれを失敗にするオプションは無い。

### 実測 (2026-08-24)

**配送検査 とは、外部の書き込みから Atlas の束の受け口 (`WatchSession::batches()`) まで実 OS 通知が
届いたことを、届かなかったことと区別して述べる 1 本のテストを明示実行することを指す。**
**「届いた」は束が `WatchBatch::Changed` として来てその中に書き換えたファイルが入っていること**を指し、
**`Rescan` はここに入らない。**

- **作業機 macOS arm64 (Darwin 25.6.0)、debug ビルド: 3 回とも届いた。** 束は
  `Changed(["…/tasks/task-1 - a.md"])`、いずれも 0.8 秒台。**既存の註が理由に挙げていた「sandbox 内では
  FSEvents が届かない」状態ではなかった** — 届くかは sandbox プロファイル次第で、この作業機の shell では
  止まらない。だから `#[ignore]` の理由は sandbox の名では書かず、「環境の性質でありコードの欠陥では
  ない」の側で書く。
- **合格条件に歯があることを変異で確かめた。** 監視ループの `record` を `record_rescan` に替えた版では
  新しい判定が落ち、戻した木で緑を見た。**入口のガードも同じく確かめた** — テスト名の定数を 1 文字
  変えた版は「検査が 1 本も走っていない」を出して 1 で終わり、戻して緑になった。
- **CI ランナーの 3 種でも届いた** (本決定を載せた PR の 1 回目の run、commit `0577257`)。
  `os-notify (macos-latest)` が `darwin/arm64` で 0.47 秒、`os-notify (windows-latest)` が `win32/x64`
  で 0.39 秒、`e2e (ubuntu-24.04)` の最後の段が `linux/x64` で 0.38 秒。**3 つとも束は 1 本の
  `Changed` で、Rescan へ倒れた run は 1 つも無い。**
- **突き合わせるのは「1 passed」であって、filtered out の数ではない。** 同じ run で macOS と Linux が
  462、Windows が 461 と報告した — crate が `#[cfg]` でプラットフォームごとに違うテスト集合を持つためで、
  **総数の差は配送について何も述べない。**
- **ジョブの費用は、キャッシュが空の 1 回目で macOS 2 分 10 秒・Windows 4 分 13 秒、温まった 2 回目で
  48 秒・1 分 40 秒である** (同じ PR の連続する 2 run)。`e2e` は 1 回目 4 分 51 秒・2 回目 5 分 0 秒で、
  **配送検査の 1 段を足したぶんは 1 回目の crate ビルドを含めて約 90 秒だった。**
  **`Swatinem/rust-cache` が効いているのはこの差である** — 2 回目に残るのは crate 自身のビルドで、
  依存の再コンパイルではない。

## Decision

1. **配送検査の入口は `pnpm run os-notify` 1 つとする** (`scripts/os-notify/run.mjs`)。CI の 3 か所も
   手作業もこれを呼ぶ。**中身は cargo の呼び出し 1 つと、走ったテストが 1 本であることの確認である** —
   2 つ目が要るのは Context の 3 点目のためで、**フィルタが空振りした実行を成功として報告しないため**に
   ある。
2. **既定実行では skip する。** `#[ignore]` を保つ。環境の性質で `cargo test` を赤くすると、コードの
   欠陥と区別が付かない。**セッションの検査は `pnpm test`・`pnpm run check`・`pnpm run lint` の 3 本の
   ままである** — decision-40 の GUI E2E と decision-42 の 規模計測 が 4 本目にならないのと同じ理由で、
   これも 4 本目にしない。
3. **明示実行では失敗させる。** 期限内に束が来ないことも、来た束が `Rescan` であることも失敗である。
   **届かなかったことを緑で述べる形を持たない。** **届かない環境で skip へ自動的に落ちる判定は持たない** —
   届かないことを届かないと述べるのがこの検査の成果だからである。
4. **CI の置き場は 3 か所とする。** `os-notify (macos-latest)`・`os-notify (windows-latest)` の新しい
   ジョブ 2 つと、`e2e (ubuntu-24.04)` の最後の 1 段。**Linux が別のジョブに乗るのは apt 一覧のためで
   あり**、理由は下の「採らなかったもの」にある。
5. **マージ要件にしない。** ruleset `main` が名指しする 3 つ (`frontend`・`rust (macos-latest)`・
   `rust (windows-latest)`) は動かさない。**FSEvents やランナー画像の更新で赤くなったものが、それを
   起こしていない PR を止めることは無い** (decision-40 §5 と同じ判断)。**代償も同じで、マージ要件でない
   検査は誰も読まなければ何も述べていない。**
6. **範囲は監視の 1 本だけとする。** 環境依存 ignored テストは 4 本ある — 監視 1、PATH 上の `backlog`
   を要する 2 本 (`commands.rs`)、認証済み `gh` と網の到達を要する 1 本 (`history.rs`)。**残る 3 本は
   「導入されたプログラムがあるか」を要求するもので、プラットフォームごとに違う機構を持たない。**
   だから本決定は覆わない。**規模計測 の 4 本は別族である** — あちらは何も主張せず数を刷るだけで、
   decision-42 が持つ。

## 採らなかったもの

- **`rust` ジョブに 1 段足す。** あれはマージ要件なので、ランナー画像の更新で無関係な PR が止まる。
  この検査は「赤くなれること」に意味がある側なので、止める力を持つ場所に置けない。
- **`os-notify` の matrix に Linux を入れる。** Linux では WebView の開発パッケージを apt で入れるまで
  crate がリンクできず、**その一覧は現に 3 か所へ写されている** (doc-13 §3.4 が数の正本)。4 か所目は
  decision-33 §3 が断り、decision-40 が改めて断った。**`e2e` が 3 か所目を払っていることは、
  4 か所目が無料になったという意味ではない。**
- **手順を散文で記録し、実機で 1 度回して終わりにする。** 記録が一度きりの snapshot になり、`notify` が
  上がっても誰も測り直さない。**オーナーが CI を選んだ** (2026-08-24)。
- **`Rescan` を合格に残す。** Atlas の倒し方が正しいことは決定的なテストが持っており、この 1 本が
  持てるのは配送だけである。**両方を 1 つの緑にまとめると、緑がどちらを述べたのか読めない。**
- **走ったテスト数の確認を CI の YAML に書く。** 3 か所へ同じ判定を写すことになる。入口を 1 つにすれば
  1 か所である。

## Consequences

- **マージ要件でない check 名が 2 つ増えた** (`e2e (ubuntu-24.04)` に続いて 3 つ目・4 つ目)。**読む人が
  要る。**
- **`e2e (ubuntu-24.04)` の赤に原因が 2 つになった。** どちらであるかは落ちた段が名乗る。段を並べる順は
  E2E が先で、配送検査が最後である。
- **`os-notify` は PR ごとに crate を 2 プラットフォームでコンパイルする。** `Swatinem/rust-cache` の
  キーはジョブごとなので、`rust` ジョブのキャッシュは共有されない。**空のキャッシュで払った時間は
  上の 実測 にある。**
- **`pnpm run` の経路が 3 本目になった** (`e2e`・`scale`・`os-notify`)。**どれもセッションの検査では
  ない。**
- **テスト名を変える回は `scripts/os-notify/run.mjs` の定数も変える。** 変え忘れは緑にならない —
  それがガードの目的である。
- **`notify` の版を上げる回は、この 3 か所が最初に配送について述べる。**

## 後続への影響

- **環境依存 ignored の残る 3 本は同じ問いを持つが、本決定はそれを答えていない。TASK-200 が引き取る。**
  問いは「配送されるか」ではなく「そのプログラムが導入されているかを CI が用意できるか」である
  (`e2e` ジョブは既に `backlog` を導入しており、`gh` はランナーに載っている)。**本決定の Decision 6 を
  「3 本も同じ形で足せる」と読まない** — 足せるかどうかは測っていない。
- **decision-40 の「Linux のジョブが 1 つできたことは、あちらの選択肢を 1 つ増やしている」がここで
  使われた。** 増えた選択肢とは、apt 一覧を写さずに Linux で crate をビルドできる場所である。
- **マージ要件にするなら ruleset へ `os-notify (macos-latest)`・`os-notify (windows-latest)` の文字列を
  足す** (decision-33 と decision-40 の Consequences と同じ結びつき)。**ジョブ名を変える回はその 2 つの
  文字列も動く**ので、ruleset を見る。
- **`#[ignore]` を新しく付ける回は、それを回す経路も同じ回に決める。** 4 本のうち 3 本が誰にも回されない
  まま残った理由は、註に明示実行のコマンドを書いたことで手順を書いたと読めたことである。**コマンドを
  書いた註は、それを走らせる人を作らない。**
