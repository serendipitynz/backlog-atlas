## Context

TASK-32（doc-9「同一 Backlog ルート更新時の競合検出と再読み込み」）は、ファイル監視・
更新前競合検出・再読込を実装する。doc-9 §3 は外部変更の継続検出を「Backlog ルートの
ファイル変化を OS の変更通知で継続監視する」と定め、doc-9 §7 が「監視の実装手段
（Rust のファイル監視 crate 等）は実装時に、決め打ちの新規本番依存を入れる前に選定
理由を確認する（AGENTS）」と、本 ADR を明示的に要求している。判断は 2026-07-25 の
TASK-32 着手時に、AGENTS「Dependencies」の導入ゲートに従い着手前にユーザーへ確認した
うえで行った。

用語は doc-9 §1 と doc-1 に従い、本 ADR で新語は導入しない（**ファイル監視**・
**外部変更**・**読取版指標**・**デバウンス**・**best-effort** はいずれも doc-9 §1 の
定義を用いる）。**採用時に比較した候補**は decision-10 と同義とする（採用時に比較した
候補とは、その依存を採用した時点で実際に俎上へ載せ、比較のうえ却下した選択肢を指す）。

doc-9 §3/§5 が監視に課す要件は次である。

- OS の変更通知で継続監視する（定期走査ではなく、変更通知を購読する）。
- 監視は読み取り専用の観測であり、ファイルを書き換えない（doc-9 §3、AC #5）。
- 通知は連続・重複しやすいため、短い時間窓で束ねる（デバウンス、AC #1）。
- Atlas はデスクトップアプリ（decision-1、Tauri）であり、macOS・Linux・Windows で
  同一に動く必要がある。監視の下回りは各 OS で異なる（FSEvents / inotify /
  ReadDirectoryChangesW）。

評価軸は次の四つとした。

- OS の変更通知で継続監視でき、doc-9 §3 の継続検出（best-effort 観測）に足るか。
- macOS・Linux・Windows を単一 API で扱えるか。
- デバウンス（AC #1）を扱えるか。扱えるとして、AGENTS の依存最小方針に沿うか。
- 保守されているか、導入範囲を局所に閉じられるか。

## Decision

**`notify` 8.2.0**（CC0-1.0）を採用する。FSEvents（macOS）/ inotify（Linux）/
ReadDirectoryChangesW（Windows）を単一の API の背後に置くクロスプラットフォームの
ファイル監視 crate である。導入範囲は `sync` モジュールの具象ウォッチャ
（`WatchSession`）に限定する。読取版指標・更新前競合検出・再読込・デバウンスのコアは
notify に依存せず、実ファイルなしで単体テストできる状態を保つ。

デバウンスは自作の純粋ロジック（`Debouncer`）で実装し、`notify-debouncer-full` は
採らない。これにより新規本番依存を notify 1 本に抑え、束ね規則を時刻注入で単体テスト
できるようにする。監視はルートの再帰監視に管理ファイル判定のフィルタを重ねて行い、
ファイルへの書き込みは一切しない（読み取り専用、AC #5）。

### 採用理由

- OS の変更通知（FSEvents / inotify / ReadDirectoryChangesW）を単一 API で扱える。
  doc-9 §3 の「OS の変更通知で継続監視」を、定期 stat のポーリングによらず満たす。
- Rust のファイル監視のデファクト標準であり（cargo-watch・rust-analyzer 等が採用）、
  クロスプラットフォームの下回りを本 crate が担うため、OS 別コードを Atlas 側に持たない。
- 具象ウォッチャ（`WatchSession`）に閉じ込められ、指標・競合・再読込・デバウンスの
  コアは notify 非依存で単体テストできる。これは読み取り層の `ScanSource`、更新層の
  `BacklogCli` と同じ境界の引き方である。

### 却下した候補と却下理由

| 候補 | 却下理由 |
|---|---|
| 定期 stat ポーリング（依存ゼロ） | 依存最小方針には最も適合するが、OS の変更通知を使わず定期走査になるため doc-9 §3 の「OS の変更通知で継続監視」と乖離する。走査間隔ぶんの検出遅延と、無変更時も走査し続ける CPU コストを負う。依存 1 本を避ける利益より、要件との乖離の害が大きい。 |
| `notify` ＋ `notify-debouncer-full` | デバウンス済みイベントを提供する公式コンパニオンだが、本番依存が 2 本になる。安定版が 0.x 系で notify 8 との版整合を別途確認する必要もある。デバウンスは短い純粋ロジックで自作でき、AC #1 を時刻注入でユニットテスト可能に保てるため、依存最小方針（AGENTS）に沿って自作を選び、これを却下した。 |
| `inotify` / `fsevent-sys` 等のプラットフォーム個別 crate 直叩き | 各 OS のバックエンドを直接叩くと、クロスプラットフォーム吸収を Atlas 側で再実装することになる。notify が既に担う層の重複であり、保守対象を増やすため却下した。 |
| `notify` 9.0.0-rc | 現時点でリリース候補（プレリリース）である。安定版 8.2.0 が存在する以上、本番依存に RC を選ぶ理由が無い。9 系が安定化したら、監視挙動を確認して更新する余地は残す。 |

## Consequences

- 望ましい帰結
  - OS の変更通知でファイル監視でき、doc-9 §3 の継続検出（外部変更の継続検出）を、
    クロスプラットフォームに満たせる。
  - 監視の具象を `WatchSession` に閉じたことで、読取版指標・更新前競合検出・再読込・
    デバウンスのコアは notify 非依存のまま単体テストできる。
- 費用・制約
  - 本番依存が 1 本増える（推移的にプラットフォーム別バックエンド `fsevent-sys`〈macOS〉・
    `inotify`〈Linux〉・`kqueue`〈BSD〉と `notify-types` を伴う）。導入範囲を `sync` の
    `WatchSession` に閉じることで影響を局所化している。
  - 監視は best-effort である。OS 通知の取りこぼし・遅延はありうるが、これは doc-9 §4.1 が
    固定した保証水準と整合し、更新成功後の能動再読込（doc-5 §6）が監視の取りこぼしを
    補う二重化になっている。
  - 監視は読み取り専用でファイルを書かない（AC #5）。競合による情報喪失の唯一の経路は
    CLI の read-modify-write に限られ（doc-9 §4.1）、本依存はそこに関与しない。
- 後続への影響
  - TASK-33（Tauri コマンド境界）が `WatchSession` のデバウンス済みバッチを購読し、
    スイムレーン・詳細の再読込（doc-7・doc-8）へ配線する。本 ADR はライブラリ層の
    監視までを定め、UI への配線は TASK-33 の範囲とする。
  - 将来のブランチ切替（decision-3）は監視ではなく再読込契機として扱い、`SyncState` の
    同一 reload 経路に載せる（doc-9 AC #6）。監視の追加は不要である。
  - notify の版が上がった際は、監視挙動を動作確認して更新する（読み取り・更新の
    サポート範囲の確認〈decision-7〉と同様の運用）。
