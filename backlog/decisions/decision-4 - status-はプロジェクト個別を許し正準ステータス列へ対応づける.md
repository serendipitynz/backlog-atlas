## Context

プロジェクトごとに異なる status を許すか、初期版で共通の To Do / In Progress /
In Review / Done を要求するかを決める（TASK-5 に依存、TASK-7）。スイムレーンの列は
この結果に依存する。用語を先に固定する。

- **プロジェクト固有 status** … 各 Backlog ルートの config.yml が statuses に定義する、
  そのプロジェクト内でのみ有効な status 値。プロジェクトごとに異なりうる。
- **正準ステータス列** … スイムレーンが横断表示で常に持つ固定 4 列
  To Do / In Progress / In Review / Done。
- **列対応規則** … 各プロジェクト固有 status を正準ステータス列のいずれか 1 列へ
  対応づける規則。
- **未分類 status** … 列対応規則でどの正準ステータス列にも対応づかなかった status 値。
  2026-08-04 に「未対応 status」から改称した（TASK-70。status の値そのものは欠けていない
  ため。改称の範囲とコード識別子 `unmapped` を据え置く理由は doc-7 §2.2）。

前提は decision-2・doc-4。読み取り層は各 Backlog ルートの config.yml を解決基点とし、
status 定義をそこから得て、タスクの status をその定義で正規化する（doc-4 の 2 章・
3.1）。つまり status 定義の所在は既に「プロジェクトごとの config.yml」に置かれている。

実測。初期対象 2 プロジェクトの config.yml を確認した。`backlog-atlas` は
statuses が To Do / In Progress / In Review / Done。`geomyth` は現時点で Backlog ルート
（config.yml）が未初期化で、statuses は未定である。すなわち Atlas は、statuses が
別々でありうる、さらに未初期化でありうる複数ルートを、起動時に前提を置けないまま
束ねる必要がある。

- 共通 status を要求する案は、全プロジェクトの config.yml を Atlas が指定する 4 値へ
  一致させることを各プロジェクトへ強いる。これは「タスクの正本は各プロジェクトに
  残し、Atlas は集約する側」という doc-2 の境界に反し、config.yml をプロジェクトの
  正本として読む doc-4 とも衝突する。geomyth のように未初期化・将来別 status を
  選ぶ余地も奪う。
- 一方、スイムレーンの列はプロジェクト横断で安定していないと、行（プロジェクト）を
  またいだ優先順位判断（doc-1 のスイムレーンの目的）ができない。列は固定したい。

この 2 要求は、「status 値の定義はプロジェクト個別に許し、横断表示の列は正準へ
対応づける」ことで両立する。

## Decision

status は**プロジェクト個別を許容**する。各 Backlog ルートの config.yml が定義する
プロジェクト固有 status をそのまま読み、Atlas は共通 status を強制しない。横断表示
では、**列対応規則**により各プロジェクト固有 status を**正準ステータス列**
（To Do / In Progress / In Review / Done）のいずれか 1 列へ対応づける。

列対応規則。

- 既定は名称一致（大文字小文字と前後空白を無視）で正準ステータス列へ対応づける。
  Backlog.md の既定 4 status はこれで一致する。
- 別名の対応（例: `Doing`→In Progress、`Review`→In Review、`Closed`/`Cancelled`→Done）は、
  プロジェクト台帳（TASK-4）のエントリ属性として持つ任意の別名表で補える。既定で
  空とし、必要なプロジェクトだけ設定する。台帳側に置くのは、対象 Markdown を
  書き換えず Atlas 側の解釈として持つためである（doc-2 の境界）。
- どの正準ステータス列にも対応づかない status は**未分類 status**とし、破棄しない。

未分類 status の扱い。

- スイムレーンでは、未分類 status のタスクをいずれかの正準列へ紛れ込ませない。
  行（プロジェクト）内に「未分類」の区画を設けて可視化し、値（元の status 文字列）を
  そのまま示す。これは doc-4 の縮退表示（想定外スキーマ＝未知 status 値）の適用に
  当たり、判別できたフィールドは活かし、列への対応だけを未確定として印を付ける。
- config.yml に定義済みだが正準へ対応づかない status（プロジェクトが独自 status を
  正式運用する場合）と、config.yml にすら無い status（タスク frontmatter だけに
  現れた想定外値）は、どちらも未分類 status として同じ区画に出しつつ、後者は doc-4 の
  「想定外スキーマ」としてより強い縮退印を付ける。

## Consequences

- 望ましい帰結
  - 各プロジェクトの config.yml を正本として読む doc-4 と、正本は各プロジェクトに
    残す doc-2 の境界を保てる。geomyth の未初期化・将来の独自 status も許容できる。
  - 正準ステータス列を固定するため、プロジェクト横断の優先順位判断が列単位で成立する。
- 費用・制約
  - 列対応規則と別名表という解釈層を Atlas が持つ。別名の設定はプロジェクトごとに
    利用者が必要に応じて行う。
  - 未分類 status を出す区画をスイムレーンに設ける必要がある（列の骨格に加えた区画）。
- 後続への影響
  - スイムレーン画面（TASK-11）の列は正準ステータス列の 4 列＋行内の未分類区画で
    設計する。列対応規則・別名表・未分類区画の見せ方は TASK-11 の入力とする。
  - 別名表は台帳エントリ（TASK-4）の任意属性として置く。
  - 未分類 status の縮退表示は doc-4 の縮退表示規則に従う。
