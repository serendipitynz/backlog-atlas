## Context

decision-7 は sidecar 同梱を初期版で採らず、**同梱検討契機**（PATH 上 backlog 前提から
sidecar 同梱の検討へ移る時点・条件）まで先送りした。その第 1「第三者配布に踏み出すとき」は
TASK-102 の GitHub リポジトリのパブリック化と v0.1.0 公開で到来する（TASK-99）。

**この契機は 2 つの条件の連言である。**前半「開発者＝利用者以外へ配布し」は TASK-102 で
到来するが、後半「利用者に backlog の個別導入を求めない体験が要るとき」は到来する事実では
なく、**選ぶかどうかが本決定そのもの**である。契機の到来は「同梱せよ」ではなく「判断せよ」を
意味する。

判断のために 2026-08-12 に実測した。

- **同梱するなら配布物へ入る単一実行ファイルの大きさ**（`backlog.md-<platform>-<arch>`
  サブパッケージ 1.50.1 の展開後）。macOS arm64 67.4 MB / macOS x64 72.8 MB /
  Linux x64 96.2 MB / Linux arm64 96.2 MB / Windows x64 100.1 MB / Windows arm64 97.1 MB。
  中身は `package/backlog`（Windows は `package/backlog.exe`）の単一実行ファイル 1 つで、
  Tauri の `externalBin` が求める形にそのまま合う。
- **Atlas 本体**は `.app` が 14 MB、aarch64 dmg が 9.7 MB（`pnpm tauri build` の出力の実測）。
  同梱すると macOS で 14 → 81 MB となり、**配布物が約 5.8 倍**になる。
- ライセンスは MIT で、サブパッケージにも LICENSE が入っている。再配布そのものは妨げられない。
- **読み取りは CLI 不在でも成立する**（decision-2）。`backlog` が見つからない場合は更新機能を
  無効化して読み取り専用で起動する経路を decision-7 が既に定めており、実装済みである
  （`update.rs` の `probe`／`CliStatus`）。導入前でも画面は成立する。
- **Windows の導入摩擦は decision-16 が既に埋めている。** npm が `backlog.exe` を PATH へ
  置かない環境でも、npm が置いた shim の所在からプラットフォーム別実行ファイルへ到達する
  段を実行ファイル解決の順序が持つ。同梱が解こうとしていた摩擦のうち、実際に起きて
  いたものはここで解けている。

> **2026-08-13 の訂正（TASK-156、decision-29）。判断は据え置き、事実の側を直す。**
> 本節の「利用者の PATH 上の `backlog`」は、2 つの別の状態を区別せずに書かれていた —
> 利用者のログインシェルの PATH に `backlog` がある状態（シェル側 PATH 前提）と、Atlas の
> プロセスが継承した PATH にある状態（プロセス側 PATH 前提）である。実行ファイル解決の順序
> 3 段目が成功する条件は後者だが、**本決定が費用と便益を測った土台は前者だった。**
> Finder・Dock から起動した `.app` では後者が破れることが実機で出ている（decision-29 の
> GUI 継承 PATH）。
>
> したがって **下の理由 2「同梱は解けていない摩擦を解かない」は、そのままでは維持できない** —
> 同梱ならこの破れを構造的に消せるからである。それでも**同梱は採らない**。理由は decision-29 が
> 述べる: 同じ原因で `git` と `gh` も落ちるので対策の範囲が欠陥の範囲に足りず、`gh` は認証状態が
> 利用者の設定にあるため同梱で代替できず、下の理由 3（版の整合）はむしろ悪化する — 当の利用者は
> 現に `backlog` を導入しているので、2 つの CLI が同じルートを触ることが確定するためである。
> 対策は decision-29 の 外部コマンド指定 が持つ。

## Decision

**第三者配布に踏み出しても sidecar 同梱を採らない。**開発時・配布時とも利用者の PATH 上の
`backlog` を用いる前提を保つ。decision-7 の同梱検討契機 第 1 は到来したが、その後半
（利用者に個別導入を求めない体験が要る）を**選ばない**という判断である。

理由は 3 つで、いずれも上の実測に基づく。

1. **費用が便益に見合わない。** 同梱は配布物を約 5.8 倍にする。得られるのは「利用者が
   `npm install -g backlog.md` を 1 回打たなくてよい」ことで、その利用者は Backlog.md の
   管理ファイルを既に持っている者である（Atlas は Backlog ルートを登録して使う。doc-3）。
   CLI を導入していない利用者が Atlas だけを先に入れる筋道は薄い。
2. **同梱は解けていない摩擦を解かない。** 実際に起きた導入摩擦は Windows の
   `backlog.exe` 不在（TASK-60）で、decision-16 が実行ファイル解決の順序で解いている。
   残る摩擦は「CLI を入れる操作そのもの」だが、読み取り専用起動が入口として成立している
   ため、導入前に画面が何も出ないという状態にはならない。
3. **同梱は版の整合を新しい不整合面へ変える。** 読み取りはファイル形式に依存する
   （decision-2）。同梱すると、Atlas が呼ぶ CLI と利用者自身が同じルートに対して打つ CLI が
   別の版になり得る。管理ファイルの書式は v1.48.0 と v1.50.1 で同一だと確かめたが
   （TASK-99 の実測）、それは現時点の事実であって、同梱は**その一致を配布のたびに
   確かめる義務**を新しく作る。同梱しなければ、利用者のルートを触る CLI は 1 つである。

**上限は固定しない**という decision-7 の姿勢は変えない。同梱しない以上、利用者の CLI の版は
利用者が決める。

### 再検討の契機

decision-7 の同梱検討契機 第 2・第 3 は生きている。次のいずれかが生じたら本決定を見直す。

- **バージョン整合を配布側で固定したいとき**: 利用者環境の版差が動作保証を難しくし、
  動作確認済み版を配布物に固定したくなったとき。
- **CLI 前提の導入摩擦が実利用を妨げるとき**: PATH 上に backlog が無い利用者が増え、
  導入の手間が採用の障壁になったとき。

第 1 は本決定で判断済みなので、**同じ契機を理由に再び判断を開かない**。第三者配布は既に
始まっており、それ自体は新しい事実ではなくなる。

## Consequences

- 望ましい帰結
  - 配布物が Atlas 自身の大きさに留まる（macOS で `.app` 14 MB）。
  - 6 プラットフォームぶんの CLI 実行ファイルの取得・更新追随・ライセンス表示を
    リリースワークフロー（TASK-101）が負わない。バンドル構成は `externalBin` を持たない。
  - 利用者のルートを触る Backlog CLI が 1 つに保たれ、同梱版と利用者版の書式期待の
    ずれという不整合面が生まれない。
- 費用・制約
  - 利用者は PATH に最低バージョン要件を満たす `backlog` を用意する必要がある。README が
    導入要件と、CLI 不在時に読み取り専用で起動することを述べる（TASK-99）。**その PATH が
    GUI 起動のプロセスへ届くとは限らない**（上の訂正）。届かない環境の利用者は decision-29 の
    外部コマンド指定 で直す。
  - CLI 不在の利用者は更新操作を行えない。画面は縮退した状態で立ち上がる。
- 後続への影響
  - **TASK-101**（リリースワークフロー）は `externalBin` の受け皿を用意しない。
  - **TASK-97・TASK-90**（README）は本決定を導入要件として書く。
  - 実行ファイル解決の順序（decision-16）は 3 段のまま。同梱バイナリ解決の段を足さない。
  - 再検討が起きた場合も、doc-5 の実行ファイル解決だけを差し替えれば済む構造は
    decision-7 のとおり保たれる（操作写像・作業ディレクトリ・引数配列渡しは不変）。
