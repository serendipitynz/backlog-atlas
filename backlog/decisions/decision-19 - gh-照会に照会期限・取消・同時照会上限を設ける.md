## Context

decision-14 は、コミット・PR 関連解決（doc-6 §6）の GitHub 分を `gh api` の呼び出しで実装する
と定めた。その Consequences は 2 つの制約を明記している。**呼び出しに期限を設けていない**こと
と、**Pull Request ごとに 1 回 `gh` を起動し、前の 1 件が終わるまで次を始めない**ことである。
本決定はその 2 つを改める（TASK-87、`_sandbox` の実装報告書 指摘 4、推奨順 4）。用語を先に
固定する。

- **gh 照会期限** … 1 回の `gh api` 起動について、Atlas が応答を待つ上限の長さ。1 回の履歴読取が
  複数の Pull Request を照会する場合、期限は起動 1 回ごとに掛かる。
- **照会期限到達** … gh 照会期限に達したため Atlas が `gh` を終了させ、その Pull Request の
  コミット集合を得ないまま照会を終えたこと。doc-8 §5 の参照失敗の原因として、起動不能・
  参照不正・照会失敗と並ぶ 4 つ目になる。
- **読取識別子** … 1 回の履歴読取呼出しを他の呼出しと区別する値。画面が採番し、読取の要求と
  取消の要求の両方に載せる。`src/lib/history-read.ts` が既に持つ呼出しトークン（画面状態の
  新旧判定に使う値）と同じ対象であり、別に採番しない。
- **履歴読取の取消** … 画面が、まだ結果を待っている履歴読取について「この結果はもう表示
  しない」をバックエンドへ伝え、走っている `gh` を終了させる要求。読取識別子で対象を指す。
- **見捨てられた照会** … 画面がもう表示しないと決めた履歴読取のために、まだ走り続けている
  `gh` の子プロセス。
- **同時照会上限** … 1 回の履歴読取の中で、同時に走ってよい `gh` 子プロセスの個数の上限。
- **直列照会** … 抽出した Pull Request を 1 件ずつ順に照会し、前の照会が終わるまで次を始めない
  実行の形。`history::resolve_relations` の現在の形がこれである。

現状で起きることは 3 つに分かれる。

**待機に上限が無い。** `github_pull_request_commits` は `Command::output()` で `gh` の終了を待つ。
通信または `gh` が終わらなければ、その履歴読取は完了しない。

**見捨てられた照会が残る。** `history-read.ts` のローダは呼出しトークンで古い応答を画面状態へ
保存しないが、バックエンドへ伝える経路が無い。タスクを切り替えても、詳細を閉じても、
再取得を押しても、古い呼出しの `gh` は走り続ける。再取得は新しい照会を増やすだけで、
古い照会を止めない。

**直列照会が待ち時間を件数に比例させる。** 複数の Pull Request を References に持つタスクでは、
前の 1 件が終わるまで次を取れない。decision-14 は「1 タスクの Pull Request URL は通常 1〜2 件
であり、プロセス起動の費用は許容する。件数が増える運用が現れたら見直す」と書いたが、見直しの
契機は件数ではなく期限の導入で来た — 期限を入れると、直列のままでは 1 回の履歴読取が最悪
「PR 件数 × gh 照会期限」だけ画面を待たせることになる。

期限を決めるにあたって効く事実が 3 つある。

1. **decision-18 が期限付き待機の形をそのまま与える。** `Reapable` トレイト越しの `poll_until`
   （`try_wait` の反復）と、強制終了後の回収・配管の読み切りに掛ける後始末猶予である。
   これは PR #43 のレビュー 5 ラウンドで、期限の外側に残っていた無条件の待ちを 2 つ潰した
   あとの形であり、`gh` 側に同じものを書き起こせば同じ穴を 2 度目に掘ることになる。
2. **`gh api` の実測は 0.48〜0.73 秒である**（2026-08-02、この機・認証済み・
   `gh api --hostname github.com --paginate --jq '.[].sha' repos/<owner>/<repo>/pulls/<n>/commits`。
   serendipitynz/backlog-atlas の PR #41〜#43 と tauri-apps/tauri の PR #15788〜#15790 の
   計 6 件、いずれもコミット 1〜10 件で 1 ページ）。GitHub は PR のコミット一覧を 1 ページ
   100 件・上限 250 件に切るので、`--paginate` の往復は最大 3 回である。
3. **decision-14 が「タイムアウトを設けていない」理由として書いた「`std` だけでは新規依存
   なしに子プロセスを時間付きで待てない」は偽である。** 2026-08-02 に decision-18 が訂正済みで、
   真であるのは「std に時間付き待機のプリミティブは無い」までである。本決定はその訂正を
   `gh` 側の実装で回収する立場にある。

## Decision

**gh 照会期限を 30 秒とし、`gh` の 1 回の起動ごとに掛ける。** decision-18 が Backlog CLI に
定めた CLI 終了期限と同じ値である。同値にした理由は 2 つで、実測 0.73 秒の約 40 倍であり
遅い回線でも正常な照会が到達しないこと、および「Atlas が外部プログラムを待つ上限は 30 秒」
の 1 文で両方を説明でき、根拠を 2 通り書かずに済むことである。アプリ設定では変えない
（decision-18 と同じ扱い）。

**照会期限到達を `LookupFailure` の 4 つ目の値 `TimedOut` として画面まで運ぶ。** decision-14 が
原因を 3 つに畳んだ理由は「照会が走って失敗した場合の原因（認証・権限・PR の不在・
ネットワーク）は終了状態からは分かれない」ことだが、照会期限到達は Atlas 自身が起こした
事象なので分かれる。doc-8 §5 が求める「その原因が解消できるかどうか」の答えも他の 3 つと
違う — 起動不能は `gh` の導入で、参照不正は References の修正で解消し、照会失敗は解消経路を
確定できないのに対し、照会期限到達は再取得で結果が変わり得る。

**履歴読取の取消を、読取識別子を鍵とする専用コマンドで受ける。** 画面は読取識別子を採番して
`task_history_read` に載せ、`task_history_cancel` に同じ値を載せて取り消す。画面が取消を送る
のは 2 つの場合で、同じ画面が次の履歴読取を始める直前と、タスク詳細を閉じたときである。
**加えてバックエンドは、同じ (slug, TASK-ID) について新しい履歴読取が始まった時点で、その
鍵の古い読取を取り消す。** 前者だけでは、画面側が取消を送らない経路（今後足す画面、例外で
抜けた経路）が見捨てられた照会を作り、それを検出する手段が無い。後者だけでは、詳細を閉じた
場合に新しい読取が始まらないので古い `gh` が残る。2 つは別の場合を塞ぐので両方を置く。

取消が掛かるのは `gh` の照会である。コミット検索（`git log`）は通信を伴わずローカルで完結
するため期限も取消も持たせないが、取消は照会を始める前にも確かめ、既に取り消されている
読取のために `gh` を 1 つも起動しない。

**同時照会上限を 2 とし、直列照会をやめる。** 1 タスクの Pull Request が通常 1〜2 件である
（decision-14）以上、2 で通常の運用は上限に当たらず、待ち時間が件数に比例しなくなる。
3 件以上を持つタスクでは 2 件ずつ進み、最悪の待ち時間は「⌈PR 件数 ÷ 2⌉ × 30 秒」になる。
上限を置くのは、References の PR 件数がタスクの内容で決まる値であり、上限が無ければ
1 タスクが同時に開くプロセスと TCP 接続の数を Atlas が言えなくなるためである。

**decision-18 の期限付き待機を共有モジュールへ移し、`backlog` と `gh` が同じ実装を使う。**
`update.rs` に閉じている `Reapable`・`poll_until`・`wait_until`・配管の読み切りを
`subprocess` モジュールへ移し、両方の呼び出し元がそれを使う。書き起こさない理由は、
その実装が「掲げた期限の外側に無条件の待ちを残さない」ためにレビュー 5 ラウンドを要した
ものであり、2 つ目の写しは同じ穴を独立に持ち得るからである。

## Consequences

- 望ましい帰結
  - 応答しない `gh` が履歴読取を止めたままにしない。最悪でも「⌈PR 件数 ÷ 2⌉ × 30 秒 +
    後始末猶予」で画面へ結果が戻る。
  - 見捨てられた照会が残らない。タスク切替・再取得・詳細を閉じる操作のいずれでも、
    もう表示しない読取の `gh` は終了する。
  - 照会期限到達が他の参照失敗と区別して出るので、画面は「解消経路を約束できない照会失敗」と
    「待てば・再取得すれば変わり得る期限到達」を同じ文で説明せずに済む（doc-8 §5）。
  - 複数の Pull Request を持つタスクで、待ち時間が件数に比例しなくなる。
- 費用・制約
  - `LookupFailure` に値が 1 つ増えるので、`wire.ts` の union・`wire_tokens.json` の
    トークン集合・`detail.ts` の解消可否の文言がすべて連動する（AGENTS のテスト節）。
  - 取消コマンドが 1 本増え、画面はそれを呼ぶ責務を負う。呼び忘れは (slug, TASK-ID) の
    引き継ぎが拾うが、詳細を閉じた場合だけは引き継ぎが働かないので取消が唯一の手段になる。
  - **強制終了が `gh` の孫プロセスへ届くかどうかは測っていない。** decision-18 が `backlog`
    について残したのと同じ未測定事項であり、届かない場合、期限到達後も孫が走り得る。
    残らないとは書かない。
  - 同時に 2 つの `gh` が走るので、認証済みのレート制限（5,000 req/h）に対する消費が
    瞬間的に 2 倍になる。1 タスクの照会が数件である以上、制限には遠い。
  - 同時照会上限を 2 に固定したので、PR を多数持つタスクは 2 件ずつ進む。上限を設定で
    変えられるようにはしない（decision-18 が CLI 終了期限について採った扱いと同じで、
    設定項目はスキーマ版の管理対象になる）。
- 後続への影響
  - GitHub 以外の remote ホスト種別を足すときは、その参照手段も gh 照会期限・履歴読取の
    取消・同時照会上限の 3 つに載せる。`PrCommitSource` の実装が期限と取消を受け取る形に
    なっているので、載せずに足すことはできない。
  - decision-14 の Consequences のうち「呼び出しにタイムアウトを設けていない」と
    「PR ごとに 1 回 `gh` を起動する（直列）」の 2 項は本決定で改めた。両項にその旨を
    注記する。ロックを持たずに `gh` を待つ 2 段割りは本決定でも維持する。
