## Context

Tauri コマンドはすべて `#[tauri::command(async)]` であり、本体は WebView の描画スレッドから
外れて走る。外れたことで主スレッドが黙って与えていた直列化が失われるため、コマンド境界
（`commands.rs`）はアプリ全体に 1 個の mutex を置いてそれを取り戻していた。台帳を変更する
コマンドと、台帳エントリを読んだあと workspace に作用するコマンドが、**処理全体で**この 1 個を
保持する。`update_apply` はこれを取得したあと、CLI 版確認・更新実行・更新後の再読込まで
その下で行い、`SystemBacklog::run` は `Command::output()` で子プロセスの終了を期限も取消も
無く待つ（TASK-85、`_sandbox` の実装報告書 指摘 1、推奨順 2）。用語を先に固定する。

- **設定ファイルロック** … Atlas 自身が所有する台帳ファイル `projects.toml`（doc-3 §2.1）と
  アプリ設定ファイル `settings.toml`（decision-13）について、読み込み→変更→保存の一続きを
  直列化する排他。ファイル操作の間だけ保持し、子プロセスの終了を待つ間は保持しない。
- **プロジェクト単位ロック** … 1 つの登録済みプロジェクトの台帳エントリ・開いている
  セッション（モデルと読取時版）・監視の登録の組合せを 1 単位として直列化する、slug ごとに
  1 つ持つ排他。
- **CLI 終了期限** … Backlog CLI の 1 回の起動について、終了を待つのをやめて子プロセスを
  強制終了するまでに許す経過時間。1 画面操作が複数回の起動に分かれる場合、期限は起動
  1 回ごとに掛かる。
- **後始末猶予** … 子プロセスの終了を待つのをやめたあと、その後始末に使ってよい上限時間。
  後始末は 2 つある。①**強制終了した子プロセスの回収** — `Child::wait` はプロセスが終わるまで
  戻らず、強制終了が効かなかった場合そのプロセスは終わらないかもしれない。②**配管の読み切り**
  — パイプが終端に達するのは書込み側が 1 つ残らず閉じたときなので、子プロセスを終了させても
  終端が来るとは限らない（配管を継承した子孫プロセスが持ち続ける）。どちらも上限を置かないと、
  CLI 終了期限で取り除いた無期限の待ちが後始末の側から戻る。
- **期限到達** … CLI 終了期限に達したため子プロセスを強制終了し、その更新を不成立として
  返した結末。doc-5 §5 の失敗種別として、非ゼロ終了・起動失敗と並ぶ 3 つ目になる。
- **要再読込** … 更新が失敗したあと、ディスク上の管理ファイルが呼び出し前と同じだと Atlas が
  言えない状態。再読込しなければ画面が実体と食い違う。

現状で起きることは 2 つに分かれる。

**1 個の mutex が全プロジェクトを待たせる。** `backlog` が停止するか長時間終了しないと、
更新対象とは別のプロジェクトの監視再読込・開閉・手動再取得・更新も、台帳の読取・登録・
更新・登録解除も、アプリ設定の読取・保存も完了しない。`(async)` が空けるのは WebView
スレッドだけで、backend のロックは解放しない。同じ論点は `gh` について既に認識されており、
`task_history_read` は必要な References を取り出すまででロックを落としてから `git`・`gh` を
実行する形になっている。`backlog` では同じ回避をしていない。

**子プロセスの待機に上限が無い。** `Command::output()` は子プロセスが終了するまで戻らない。
応答しない CLI に当たった場合、その 1 回の呼び出しがバックエンドを永久に止める。

期限を設けるにあたって効く事実が 3 つある。

1. **標準ライブラリだけで期限付き待機を組める。** `std::process::Child::try_wait` は Rust
   1.18.0 から stable であり（rustc 1.96.0 の `library/std/src/process.rs` で確認）、これを
   短い間隔で反復すれば新規依存なしに期限付き待機になる。**decision-14 が「`std` だけでは
   新規依存なしに子プロセスを時間付きで待てない」と書いたのは誤りである** — 真であるのは
   「std に**時間付き待機のプリミティブ**は無い」までで、`try_wait` の反復で組めることまでは
   否定できない。これは「不可能」と「未測定」「未着手」を書き分ける規則（doc-10 §1、TASK-58）
   の再発なので、decision-14 の当該記述は本決定と同じ変更で訂正する。
2. **強制終了は子プロセス側の後始末を走らせない。** `Child::kill` は Unix で `SIGKILL`、
   Windows で `TerminateProcess` を用いる（rustc 1.96.0 の `sys/process/unix/unix.rs` と
   `sys/process/windows.rs` で確認）。どちらも捕捉できないので、強制終了された `backlog` が
   管理ファイルを書いている途中だった場合、中途の内容がディスクに残り得る。**孫プロセスは
   終了しない**（Backlog CLI が孫プロセスを作るかどうかは**未測定**である）。
3. **実測した所要時間は期限より 2 桁小さい。** 2026-08-02 に macOS で、本リポジトリの
   Backlog ルート（タスク 110 件）の写しに対して測った値は、`backlog --version` が初回 258 ms・
   定常 117〜120 ms、`backlog task list --plain` が初回 1037 ms・定常 272〜288 ms、
   `backlog task edit -s` が 189〜240 ms である。

## Decision

**1. 排他をプロジェクト単位へ分ける。** アプリ全体に 1 個だった mutex を、設定ファイル
ロック（台帳用・アプリ設定用の 2 本）とプロジェクト単位ロック（slug ごとに 1 本）に置き換える。

- 設定ファイルロックは、**読み込み→変更→保存の一続きだけ**を直列化する。子プロセスの
  終了を待つ間は保持しない。**純粋な読取は取らない** — decision-17 の一時ファイル置換に
  より、読み手が中途の内容を見ることはなく、得られるのは必ず置換前か置換後のどちらか
  丸ごとだからである（1 個の mutex を読取にも掛けていた元の理由「半端なバイト列を破損と
  読んでしまう」は、decision-17 が入った時点で成り立たなくなっている）。台帳用と設定用の
  2 本を**同時に保持しない** — 順序を決めずに入れ子にできる 2 本は循環の余地を残すので、
  入れ子そのものを禁じる。
- プロジェクト単位ロックは、台帳エントリを読んでからそのプロジェクトのセッションに
  作用し終えるまで保持する。CLI の実行はこの下で行う。**別の slug のロックは独立**なので、
  1 件の更新が別プロジェクトの読取・開閉・監視再読込を待たせない。
- ロック順は **プロジェクト単位ロック → 設定ファイルロック** に固定する。逆順を作ると、
  台帳を書いてからセッションを閉じるコマンドと、エントリを読んでからセッションに作用する
  コマンドの間で循環する。
- 複数プロジェクトを対象とするコマンド（起動時の全ルート読取）は、slug ごとに取得と解放を
  繰り返す。複数のプロジェクト単位ロックを同時に保持しない。
- プロジェクト単位ロックは、一度作ったら**プロセスが終わるまで捨てない**。登録解除で
  捨てると、そのロックを待っている実行中の呼び出しがある間に次の呼び出しが新しいロックを
  作り、同じ slug に対して 2 本のロックが同時に有効になる。捨てないことによる保持量は
  1 回の実行中に現れた slug の数に限られる。

**2. Backlog CLI の 1 回の起動に CLI 終了期限を設ける。** 値は **30 秒**とし、定数として持つ
（アプリ設定では変えられない）。子プロセスは標準入出力を配管して起動し、標準出力と標準
エラーはそれぞれ専用のスレッドで読み出す。終了は `try_wait` の反復で確認し、期限に達したら
`Child::kill` で強制終了して回収し、期限到達として返す。版確認（`backlog --version`）にも
同じ期限が掛かる。

**後始末にも上限を置く（後始末猶予 1 秒）。** 期限に達した後に残る 2 つの待ちも、そのままでは
無期限であり、期限で取り除いた待ちをそっくり戻してしまう。

- **回収**: 強制終了した子プロセスは回収する（ゾンビを残さないため）。ただし `Child::wait` の
  ような無条件のブロックは使わず、後始末猶予まで反復確認するに留める。**強制終了が効くとは
  限らない**（結果を捨てないので、効かなかったことは失敗理由に出る）ため、無条件に待つと
  「終わらないかもしれないプロセス」を待ち続けることになる。猶予を過ぎたら回収せずに戻り、
  そのことを失敗理由に書く。
- **読み切り**: 子プロセスが自分で終了した場合は、読めた分を後始末猶予まで待って取り、
  猶予を過ぎたら読めている分だけを返す。期限到達で強制終了した場合は読み出しを**まったく
  待たない** — 返すのは期限に達した事実だけで、説明すべき CLI の判断は存在しない。
  読み出しスレッドは止めずに放置する（書込み側が詰まらないよう読み続ける一方、呼び出し側が
  去った後は読んだ内容を蓄えない）。

**1 回の起動が Atlas を止める時間の上限は「CLI 終了期限 ＋ 後始末猶予」、正常終了した場合は
「子プロセスの所要時間 ＋ 後始末猶予」である。** ここに無条件のブロッキング待機は 1 つも無い。

**3. 期限到達を doc-5 §5 の 3 つ目の失敗種別にする。** 期限到達は必ず**要再読込**である。
これに伴い、失敗が要再読込かどうかを運ぶ wire 上のフィールドは、意味に合わせて
`partial` から `reloadRequired` へ改称する。要再読込となるのは次の 2 つである。

- 1 画面操作の 2 回目以降の呼び出しでの失敗（先行する呼び出しが既に書いている＝部分適用）。
- 期限到達（強制終了した呼び出しが書いたかどうか分からない）。

## 検討した代替案

| 案 | 退けた理由 |
|---|---|
| 1 個の mutex のまま、`update_apply` だけ CLI 実行中にロックを落とす | 落とした窓の間に `ledger_update` がそのプロジェクトを移動でき、doc-9 §4 が守る「台帳エントリ・モデル・読取時版の組合せ」がまさに壊れる。この組合せを守ることが 1 個の mutex を置いた理由なので、それを外すだけの案は元の危険を戻す |
| 期限付き待機に `wait-timeout` クレートを導入する | AGENTS の依存ゲート（新規本番依存は選定理由と導入範囲の確認を要する）に掛かる一方、`try_wait` の反復で同じことが標準ライブラリだけで書ける。最小依存の方針に対して見合わない |
| CLI 終了期限をアプリ設定で可変にする | 可変を必要とする実例が現時点で無い。設定項目の追加は decision-13 によりスキーマ版の管理対象になり、`KNOWN_SCHEMA_VERSION`・`mergeDraft`・`normalize`・wire 型・設定画面まで連動する。必要が現れてから足すほうが安い |
| 期限を 1 画面操作の全体に掛ける | 1 回の起動ごとに掛けるほうが、どの呼び出しが応答しなかったかを失敗理由に書ける。操作全体に掛けると、最後の呼び出しが遅いだけで先頭から数えた累計が期限に当たり、原因の呼び出しを名指しできない |
| 期限到達を非ゼロ終了として報告する | 偽である。終了コードは観測していない（強制終了したのは Atlas 自身である）し、非ゼロ終了は「CLI が判断を返した」ことを含意するので、利用者が stderr を読んで原因を直せるという前提も成り立たない |
| 期限到達でも要再読込としない | 強制終了した呼び出しが管理ファイルを書いたかどうかは分からない（上の Context 2）。再読込を省くと、画面がディスクと食い違ったまま残る。doc-9 §3 は監視を保証された経路として扱っていないので、監視が拾うことを当てにできない |

## Consequences

- 望ましい帰結
  - 1 件の更新が停止しても、別プロジェクトの読取・開閉・監視再読込と、台帳・アプリ設定の
    読取・保存は完了する。利用者から見て、止まるのは対象プロジェクトだけになる。
  - 応答しない CLI に当たっても、バックエンドが止まるのは 1 回の起動あたり最長 31 秒
    （CLI 終了期限 30 秒 ＋ 後始末猶予 1 秒）で終わり、失敗として画面に届く。実測
    （Context 3）の定常最悪 288 ms に対して約 100 倍、初回込みの最悪 1037 ms に対して
    約 30 倍なので、遅いだけの正常な呼び出しでは発火しない。
  - 新規クレートが増えない。ビルド時間・監査対象・供給網の面が変わらない。
- 費用・制約
  - **期限到達は中途の管理ファイルを残し得る。** 強制終了は捕捉できず（Context 2）、Atlas は
    CLI をまたぐロールバックを持たない（doc-5 §5）。掲げる保証は「期限到達を要再読込として
    扱い、再読込で現状を画面へ写す」ことだけで、管理ファイルが無傷であることは掲げない。
  - **プロセスは残り得る。** 強制終了は対象の子プロセスだけに届き、しかも**効くとは限らない**
    （効かなければ失敗理由にそう出る）。Backlog CLI が孫プロセスを作るかどうかは未測定なので、
    残らないとは書かない。残ったプロセスが配管を保持している場合、**Atlas はそれを待たない**
    （後始末猶予まで）。したがって、その出力の末尾は失われ得るし、回収できなかった子プロセスは
    ゾンビとして Atlas の終了まで残り得る。掲げる保証は「上限内に戻ること」であって、
    「プロセスが消えること」でも「出力が全部揃うこと」でもない — 判断は終了コードであり
    （doc-5 §5）、出力はその理由文に過ぎず、そしてどちらも無期限に待つ理由にはならないからである。
  - 終了の確認が反復であるため、子プロセスが終わってから Atlas がそれに気づくまでに、
    反復の間隔ぶんの遅れが入る。間隔は 20 ミリ秒とし、上の実測（最短 117 ms）に対して
    有意にならない値に置く。
  - `partial` → `reloadRequired` の改称は wire 型の変更なので、`wire.ts`・記録した
    wire fixture・トークン集合・失敗文言まで連動する。旧名で保存された画面状態は無い
    （wire 型は毎回の呼び出しで作られる値であり永続しない）ので、移行は要らない。
  - **decision-14 の Consequences を訂正する。** 「`std` だけでは新規依存なしに子プロセスを
    時間付きで待てない」は偽であり（Context 1）、`gh` に期限が無いのは不可能だからではなく
    TASK-87 が扱う未着手事項である。同じ変更で書き直す。`gh` を待つ間ロックを持たない
    という判断そのものは本決定でも維持する（プロジェクト単位ロックに分けたあとも、
    ネットワーク待ちを 1 プロジェクトのロックの下で行う理由は無い）。
  - `_sandbox` の実装報告書 指摘 1 が挙げた 4 条件のうち、本決定は 3 つ（台帳と workspace の
    mutex 分離、同一プロジェクトの組合せの保護、子プロセスへの終了期限）を定める。残る
    1 つ（停止する偽 CLI を使った試験）は実装側の受入条件であり、決定事項ではない。
- 後続への影響
  - **TASK-87（`gh` 照会に終了期限・取消・同時実行上限を設ける）** は、本決定の期限付き
    待機の形をそのまま引ける。`gh` 側は取消と同時実行上限も要るので、本決定は期限だけを
    定め、取消の経路は TASK-87 が決める。
  - **TASK-99（Backlog CLI の sidecar 同梱）** で実行ファイルが変わっても、期限は
    `BacklogCli` の実装の内側にあるので、順序の差し替えだけで済む点は変わらない。
  - Atlas が新しく子プロセスを起動する経路を足すときは、期限を持たせるかどうかを
    その場で決める。持たせない場合、決定に「なぜ持たせないか」を真である理由で書く。
