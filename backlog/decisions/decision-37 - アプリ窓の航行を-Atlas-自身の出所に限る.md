## Context

doc-8 §9.3 は 本文リンク について「アプリ窓は Atlas から離れない」を成立させたが、**その手段は
`href` を置かないことだった**ので、本文がリンクを 1 つも持たなくても成り立つ経路には届いていない。
同節はそれを明記して先送りしている（「窓が離れる経路を engine の側で一括して塞ぐかどうかは、
本節では決めていない」）。TASK-146 がその残りである。

**重いのは、起きたときに戻れないからである。** Atlas は 戻る控え を 1 つも持たない。離れた先から
主画面へ帰る手段は engine のものだけになり、**その engine のものが一様でないことが測定で分かった**
（下記）。

語と指示対象は TASK-146 の対応表 初版で本文より先に固定した。以下で使う **航行の試み**（窓の最上位
文書を別の文書へ置き換える要求が engine の許否判断へ届くこと 1 件。許されたかは含まない）・
**窓が離れる**（その試みが許され、窓が Atlas の画面を表示していない状態）・**経路**（利用者の 1 続きの
操作が 航行の試み を生み、許されて 窓が離れる に至る道筋 1 本）・**引きずり込み**（窓の外で始まった
引きずりを窓の上で放す操作）・**窓内の引きずり**（開始も終了も webview の内側にある引きずり）・
**航行ゲート**（航行の試み 1 件が必ず通る許否判断の 1 か所）・**横取り**（wry が drop 事象を engine の
既定処理より先に受け取り、既定処理を起こさせないこと）・**戻る控え**（Atlas 自身が画面に置く「1 つ前へ
戻る」操作の控え。engine の文脈メニューが持つものは含まない）はその表の語である。

### 塞ぐより先に測った

**測定器は 航行ゲート に置いた**（許否を 1 つも変えず、試みられた URL だけを記録する形）。**目視だけに
しなかった理由は、目視が区別できないものがあるからである** — 画面が変わらないことは「試みが無かった」
とも「試みを engine が断った」とも読め、後者なら engine か URL が変われば通る。

**2026-08-18、macOS の実機で 6 つの操作を 1 回ずつ行った。** 結果は 航行の試み 3 件で、**3 件とも
引きずり込み だった。** **数えるのは実施した操作であって、依頼した操作ではない** — 依頼は 5 つで、
そのうち「ファイルを引きずり込む」をオーナーが `.png` と `.md` の 2 回に分けて行ったので、実施は 6 つに
なった。**分けたほうが正しい**（下表のとおり、帰る手段が 2 つで違った）。

| 操作 | 航行の試み | 窓が離れたか | 帰る手段 |
|---|---|---|---|
| ブラウザのアドレスバーから URL を窓へ引きずり込む | 1 件（`https` の URL） | 離れた | 文脈メニューの戻るで帰れた |
| Finder から `.png` を窓へ引きずり込む | 1 件（`file:` の URL） | 離れた（画像が開いた） | **文脈メニューに戻るが無い。**⌘← では帰れた |
| Finder から `.md` を窓へ引きずり込む | 1 件（`file:` の URL） | 離れた | 文脈メニューの戻るで帰れた |
| 添付画像 をつまんで同じ窓の別の場所へ放す | **0 件** | 離れない | — |
| タスクカードを 受け先 でない場所へ放す | **0 件** | 離れない | — |
| 本文の選択文字をつまんで窓の別の場所へ放す | **0 件** | 離れない | — |

**窓内の引きずり の 3 つは「試み自体が生じない」** であって「試みを断られた」ではない。測定器を
置いたのはこの差を言えるようにするためで、**初期読み込みの 1 件が必ず記録されるので、0 件が
「測定器が動いていない」ではないことも同時に言える。**

**なぜ生じないかは、1 つだけコードで言える。** タスクカードが `dragstart` で載せるのは
`text/plain` の 横断タスクID 1 つであり（doc-7 §4.2）、**engine が読み込み要求に変えられる値ではない。**
残る 2 つ — 添付画像 と 選択文字 — について「engine の既定処理が窓内で始まった引きずりを読み込み
要求に変えない」と述べることはできるが、**それは読みであって、測ったのは 0 件のほうである。**
**この 3 つを塞ぐ実装は入れていない**（塞ぐものが無い）。下の Decision 1 の ゲート は出所で決めるので、
**将来この 3 つのどれかが航行を生むようになっても、そこで止まる。**

**経路が開いているのは TASK-81 の `dragDropEnabled: false`（decision-34）以降である。** wry 0.55.1 は
drag-drop handler が登録されたときだけ engine から drop を 横取り し、`tauri-runtime-wry` 2.11.4 は
その flag が真のときだけ登録する。外れているいまは 3 engine とも既定の drop 処理が走り、**どれも
落とされた URL・ファイルを「読み込むもの」として扱う**（macOS は `super` へ委譲、Windows は
`SetAllowExternalDrop(false)` が呼ばれない、Linux は drop の signal を繋がない）。**つまり v0.1.0 まで
塞がっていたのは偶然であって、その偶然は戻す種類のものではない** — decision-34 がその flag の
load-bearing な理由を持つ。

**航行を拒む既定は框架の側に 1 つも無い。** wry は navigation handler が無ければ全許可、tauri の既定の
航行ゲート も plugin へ委ねるだけである。**CSP はこれを止めない** — decision-28 の 9 行は最上位の航行を
対象にしておらず、`form-action 'none'` が閉じるのは form 経由の 1 つだけである。

## Decision

### 1. 航行ゲート で、Atlas 自身の出所へ向かう航行だけを許す

**それ以外の 航行の試み は拒む。** Atlas は単一文書のアプリで、自分から航行することが 1 度も無い
（本文リンク は 既定ブラウザ起動 へ渡す。doc-8 §9.3）ので、**自分の出所以外への航行は例外なく
利用者が意図していないものである。**

**拒んだことを画面に出さない。** 出す文は「あなたが落としたものは開かない」以上のことを言えず、
利用者から見た結果は 窓内の引きずり の 3 つ（何も起きない）と同じである。**doc-11 §5 の 保留理由 でも
ない** — 差し控えている操作が画面に無い。

### 2. 出所は名指しせず、最初の航行から学ぶ

**窓が最初に行う航行は、アプリが自分を読み込む 1 件である** — 存在しない窓には何も落とせない。
したがって最初に ゲート を通る URL がその出所そのものである。

**名指しを採らない理由は、名指しが 3 つになるからである。** 出所は macOS・Linux で
`tauri://localhost`、Windows で `http://tauri.localhost`、開発中は `tauri.conf.json` の `devUrl` であり、
**書けばこの 3 つを 4 か所目として持ち、2 つの platform 慣習と 1 つの設定に追従させ続けることになる。**

### 3. 比べるのは URL 全体ではなく scheme・host・port の 3 つ

再読込も、開発サーバが付ける query も同じ文書である。**`Url::origin` は使えない** —
`tauri://localhost` のような特殊でない scheme では opaque origin を返し、**opaque origin は互いに等しく
ならない**ので、アプリ自身の再読込が拒まれる。

### 4. 窓の生成は `tauri.conf.json` に残す

TASK-146 の起票は「窓を Rust 側で作れば `on_navigation` で航行を拒める」と見当を書いていたが、
**その移動は要らなかった。** tauri 2.11.5 の既定の 航行ゲート は、窓をどう作ったかによらず plugin の
`on_navigation` を必ず通す。**したがって plugin 1 つで届き、窓の宣言・大きさ・装飾の設定は
`tauri.conf.json` の 1 か所に残る。**

## Consequences

- **doc-8 §9.3 の「決めていない」の項を、本 decision を指す形へ改めた。** 同節が閉じたのは
  「Atlas がリンクとして描いたもの」に限るという範囲の記述はそのままである — 範囲は変わっておらず、
  **残りをどこが引き取ったかが決まった**のが変わった点である。
- **AC #4（戻れるかの判断）はこう決めた: 戻る控え を足さない。** 航行が起きなくなったので戻る先が
  無い。**engine の戻るに頼る形を採らなかった理由は測定にある** — `.png` を落としたときの文脈
  メニューには戻るが無く、⌘← を知っている利用者だけが帰れた。**「engine が戻るを持っている」は
  一様に真ではない**ので、それを前提にした設計は書けない。
- **拒否が沈黙なので、経路が塞がっていることは画面から分からない。** 押さえるのは
  `src-tauri/src/navigation.rs` の単体試験で、**scheme・host・port・最初の航行の 4 つを別々に壊すと
  それぞれ別の試験が落ちる**ことを確かめてある（`http` と `https` を同じ host で比べる形は port の
  既定値 80・443 の差で落ちてしまい scheme を押さえないので、port を持たない custom protocol 同士で
  比べている）。
- **同じ形の穴は残っていない、とは書かない。** 測ったのは macOS の 6 操作であり、engine の既定処理が
  他に何を航行として扱うかは網羅していない。**ゲートは操作を数えずに出所で決めるので、数え漏らした
  操作があってもそこで止まる** — これが操作ごとに塞ぐ形を採らなかった理由でもある。
- **Windows・Linux は未測定である。** 経路の在否も、ゲートが同じように効くことも、macOS でしか
  測っていない。**ゲートは 3 engine が共通に通る tauri 側の 1 か所にあるので同じに効くはずだが、
  これは読みであって実測ではない。**
