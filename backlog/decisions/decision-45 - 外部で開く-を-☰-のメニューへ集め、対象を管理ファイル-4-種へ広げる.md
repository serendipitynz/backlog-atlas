争点語は TASK-83 の対応表で本文より先に固定した（初版 2026-08-25）。以下で使う

1. **doc-8 §7 の区画は パスと再読込 だけを残し、起動はメニューが独占する。**
2. **名前付きエディタ は既存の 2 経路を置き換えず、同じ群に併存する。**

### 先行する判断との関係

- **decision-29 の 外部コマンド解決の順序 は動かない。** あちらが順序を定めているのは 起動指定 —

  **両者は同じ群の別の行として併存する**ので、「アプリ設定が最優先」は 起動指定 の行の中でそのまま効く。
  **名前付きエディタ をアプリ設定で上書きする手段は置かない** — 上書きしたい利用者の手段が
  起動指定 の行そのものである。
- **decision-15 は名前付きエディタに掛からない。** あちらが `ShellExecuteW` を選んだのは
  OS の関連付け起動 の Windows 実装についてで、その行は残るので判断も残る。**名前付きエディタ は
  プログラムを名指すので関連付けを引かない。**
- **decision-13 に項目を 1 つ足す。** 注意の抑止 がそれで、`KNOWN_SCHEMA_VERSION` は 6 から 7 へ上がる。

- **decision-25 の 既定ブラウザ起動 とは別の経路のままである。** あちらが渡すのは利用者が本文に書いた

- **decision-37 の 窓の航行ゲート に触れない。** 起動するのは別プロセスであって、Atlas の窓は航行しない。
- **decision-42 の 再構築単位 に触れない。** 外部エディタの保存が届く経路は doc-9 の監視のままである。

## Decision

### 1. 対象は 選択中の管理ファイル 1 件で、対象未選択 では理由付きで保留する

**外部で開く が渡すのは 1 件である。** 定まる経路は 4 つで、タスク詳細が開いているタスク
（doc-8 §2.1 のどの配置でも同じ）・プロジェクト詳細の 選択中の文書（doc-10 §5）・選択中のマイルストーン
（doc-10 §6）・選択中の決定事項（doc-10 §10）である。**画面ではなく対象で定まる** — スイムレーンだけが
出ている状態と、プロジェクト詳細で区画を開いただけの状態は、どちらも 対象未選択 である。

**対象未選択 のとき行は消えず、理由付きで保留する**（doc-11 §5）。消す案は採らない — 行の有無が状態を
述べる形になり、decision-44 §3 が リリースページを開く について退けたのと同じ形である。**保留理由が
述べるのは「開く相手が無い」であって「開けない」ではない** — 開けない状態（ファイルが読み取り結果から
消えた）は別の理由を持つ。

**プロジェクト詳細の側は、開いている区画が答える。** 3 つの選択は **区画切替 では消えない**ので、
**「選択されているもの」を並べて先頭を採ると、マイルストーンを見ている利用者に文書が渡る。**
概要 と 新規タスク はファイルを選ばないので 対象未選択 である。

**この規則が要るのは上の 1 つの事実だけで、何が選択を落とすかの数え上げは持たない。** 初版は「落ちるのは
ルートの移動と明示の解除だけ」と添えていたが、**明示の解除は TASK-121 で無くなっており、再読み込みで対象が
消えたときも落ちる**（doc-10 §5 の 4 事象の 4 つ目）。**PR #157 の 2R [P3] がこれを捕まえた — [P1] と同じ型の
誤りを、その [P1] を直す文の中でもう一度やった。** 数え上げを持たない形にしたのは、同じことを 3 度やらない
ためである。

**初版はここを「対象が 2 件以上になる状態を作らない。タスク詳細とプロジェクト詳細は同時に立たないので、
4 経路のうち高々 1 つが答える」と書いていた。** 前半は偽で、後半は 2 画面の間についてだけ真だった —
**プロジェクト詳細の内側では 3 つが同時に設定されうる。** 誤りは 2 つの形で残っていた: この節が「選ぶ規則を
持たない」と述べ、実装の註が「3 区画は同時に開かないので高々 1 つ」と主張していた。**どちらも測っていない。**
**PR #157 の 1R [P1] が捕まえた**（レビュワーが操作列を書いた: 文書を選ぶ → マイルストーン区画へ移る →
選ぶ → 外部で開く で、渡るのは文書）。

**規則は「開いている区画のもの」1 本で、これは測れる。** 押す前に何を開くかを読める場所は 表示パス で
（doc-10 §5）、それが画面に出ているのは開いている区画の選択についてだけである。**したがってこの規則は
doc-8 §7 の 押す前に読めていなければならない の帰結であって、新しい判断ではない。**

### 2. 置き場は ☰ のメニューの 外部で開く で、doc-7 §2.1 の粒度の規則からの意図的な逸脱である

doc-7 §2.1 は **1 プロジェクトに閉じた操作**を共通入口から締め出しており、外部で開く は
**管理ファイル 1 件に閉じた操作**なのでそれより狭い。**それでもメニューへ置く。**

理由は、対象が 2 画面の 4 区画にまたがることである。**区画ごとに置くと、同じ 7 行の群が 4 か所に出る** —
行の集合・frontmatter の注意・注意の抑止 のどれもが 4 つの写しを持つことになり、写しは黙って古びる。
**メニューは、その 4 区画のどれを見ているときにも同じ 1 か所である。**

**doc-10 §2 が記録した逸脱と同型で、向きが逆である。** あちらは全プロジェクトに効く入口を 1 プロジェクトの
画面へ置いた。こちらは 1 ファイルに閉じた操作を全プロジェクトの入口へ置く。**どちらも「置かない案では
可視の入口が無くなる」ことが理由である。**

**逸脱で足すのは群 1 つだけで、他の 1 プロジェクトに閉じた操作は依然としてメニューに置かない。**

### 3. サブメニューは 被せ層 を 2 枚にしない

doc-7 §2.1 の **被せ層は同時に 1 枚だけ** は動かさない。**サブメニューは親の行に係留され、親と同時に
降りる入れ子の層なので、親と合わせて 1 枚と数える。**

数え方をこう定めるのは、あの規則が守っているものが **Escape と外側の押下が何に効くか利用者が一意に
読めること** だからである。入れ子はそれを壊さない — 出口の梯子が定まっていれば、押した 1 回が
何を降ろすかは常に 1 つに決まる。**サブメニューはメニューの一覧の外に置く。** 一覧はスクロールを持ち（doc-7 §2.1）、**スクロール容器は
自分の外へ出た子孫を両軸で切る。** **2026-08-25 の実機でこれが起きた** — オーナーの `pnpm tauri dev` で
サブメニューは描かれているのに見えず、押しても何も起きないように見えた。**矩形は正しい値のまま当たり判定
だけが失われる**（借り物 playwright の実測: `overflow-y: auto` をパネルへ戻すと、矩形が同一のまま
`elementFromPoint` が届かない。WebKit・Chromium とも）。**したがって矩形を測る試験でも捕まらず、
jsdom は算出スタイルを持たないのでコンポーネント試験が持てるのは入れ子の関係だけである。**

**面はパネルと同じものを取る** — 地・枠・角・影・字・余白。**サブメニューは別の層ではなく同じ 被せ層 の
一部なので**（下の 梯子）、値を新しく選ぶ理由が無い。**2026-08-25 の実機で、影が無いことをオーナーが
指摘した** — 影が無いと、手前に浮いた面ではなくパネルの地の続きに見える。**併せて、初版が実在しない
トークン 2 つ（`--border`・`--warn`）を書いていたことが分かった**: 無効値なので `border` の宣言ごと落ち、
枠が 1 本も出ていなかった。**木の中でトークン名を外していたのはこの 2 つだけである**（実測。他の
未解決名はすべて inline `style` で与えているもの）。**機械の検査は無い** — `var(--…)` の解決を確かめる
走査は木の全体に掛かるので、足すなら別のタスクである。

**梯子は 3 段である**: Escape はサブメニューだけを降ろす、
外側の押下は両方を降ろす、親の行の再押下はサブメニューだけを降ろす。**別の被せ層を上げる操作は
両方を降ろす**（§2.1 の「層を上げる経路は、前の層が残っていればそれを降ろす」がそのまま効く）。

**メニュー内展開の案は採らない。** 外部で開く の行を押すと同じパネルの中に 7 行が現れる形で、
層は 1 枚のままになる。**退ける理由は §2.1 自身が持っている** — あの節は「項目の縦の位置が開くたびに
変わらないこと」を定めており、展開はその下にある プロジェクト一覧 を 7 行ぶん押し下げる。
**加えてパネルの高さは 24rem 幅の上限しか持たないので、台帳のエントリが多い環境では展開したパネルが
窓の高さを超える。**

### 4. 行の集合はプラットフォームで決まり、導入の有無を探索しない

**行の集合を決めるのはプラットフォームだけである。** 集合は次のとおりで、**この表が正本である。**

| 行 | macOS | Windows | Linux |
|---|---|---|---|
| Visual Studio Code で開く | ○ | ○ | ○ |
| Zed で開く | ○ | ○ | ○ |
| CotEditor で開く | ○ | — | — |
| Notepad++ で開く | — | ○ | — |
| 起動指定 で開く（アプリ設定／`$VISUAL`／`$EDITOR`） | ○ | ○ | ○ |
| OS の関連付けで開く | ○ | ○ | ○ |
| ファイルマネージャで示す | ○ | ○ | — |
| 端末で開く | ○ | ○ | — |

**導入されているかを探索しない。** 探索する案は、macOS・Windows・Linux で手段が全く別物
（LaunchServices・レジストリ・PATH）になり、3 プラットフォーム分の実測を本決定に負わせる。
**探索しないことの代償は、押して初めて分かることである** — その代償は 失敗が必ず述べられること
で受ける（§7）。

**入っているものだけ並べる案も採らない。** 行の有無が状態を述べる形になり、§1 が 対象未選択 について
述べたのと同じ理由で退ける。

**起動の形は行ごとに違い、`Platform` の網羅 `match` が持つ。** プラットフォーム分岐を `cfg` ではなく
値にする（m-1 TASK-44）ので、どのプラットフォームの表も他のホストから試験できる。

- **macOS の 5 行はどれも `open` を通す** — `open -a <アプリ名> <パス>`、`open -R <パス>`、
  `open -a Terminal <フォルダ>`。**PATH を要さない**ので、`code` をシェルへ入れていない利用者にも効く。
- **Windows と Linux の 名前付きエディタ は PATH のプログラムを名指す。** 入っていなければ
  spawn がその場で失敗し、プログラム名が付いた理由が返る。
- **Windows の 所在に効く 2 操作 は `explorer.exe /select,<パス>` と `wt.exe -d <フォルダ>` である。**
  `/select,` はコンマを含む 1 つの argv 要素であり、シェル文字列ではない（AGENTS）。

### 5. 観測するのは手渡して終わるプログラムだけである

`Launcher::spawn_observed` は 既定ブラウザ起動 だけのものだったが、**本決定はそれを
「手渡して終わるプログラム」の規則へ言い直す。**

- **観測する**: `open`（macOS の 5 行すべて）。手渡した直後に終了するので、終了状態が
  「渡せた」と「その名前のアプリが無い」を分ける唯一の値である。
- **観測しない**: 起動指定（エディタ自身が走り続ける。`vim` を待つと呼び出しが返らない）、
  OS の関連付け起動、Windows・Linux の 名前付きエディタ（同じくエディタ自身）、
  `explorer.exe`（**成功しても 1 で終わる**ので、終了状態は何も述べない）、`wt.exe`。

**この区別は行の性質であって、プラットフォームの性質ではない。** 表の 1 列として持つ。

### 6. frontmatter の注意 は層で述べ、注意の抑止 をアプリ設定へ置く

**述べる 2 点は doc-8 §7 のものと同じで、置き場と出し方だけが動く** — 開くのは frontmatter を含む
管理ファイルそのものであること、編集した結果は Backlog CLI のスキーマ保護を通らないこと。
**「タスクの」ではなく「管理ファイルの」と述べる**（対象が 4 種になったので、タスクだけを名指すと
文書を開く利用者には偽になる）。

- **出すのは 名前付きエディタ・起動指定・OS の関連付け の 3 種の行を押したときだけである。**
  所在に効く 2 操作 は編集の手段を渡さないので、この注意を持たない。
- **層に 注意の抑止 の刻みを置く。** 入れて進むと、以後この注意は出ない。**アプリ設定の項目で、
  設定画面から戻せる** — 戻せない指定を刻み 1 つで与えない。
- **抑止されている間は層が立たず、押下がそのまま起動になる。**

**層は、それを立てた対象が替わったら失効する**（doc-11 §15 ④）。**判定は「対象が同じか」だけでは足りない** —
未保存入力があるあいだパネルは読み取り結果から消えたファイルを描き続けるのでパスは変わらず、替わるのは
群そのものが保留になることのほうである。**着手回の実装は初版でこれを落としており、コンポーネント試験が
捕まえた。**

**未保存入力 の問いが読むのは、その対象自身の 未保存入力 である。** プロジェクト詳細は 4 区画の入力を
1 つの旗で束ねており（画面を離れるときはそれで正しい。doc-8 §6.3）、**概要 に打った名前は `projects.toml`
への入力なので、文書を外部で開くことと関係が無い。** doc-8 §6.4 が避けようとしているのは**同じファイルの
二重編集**であって、同じ画面で何かを打ったことではない。**これも PR #157 の 1R [P2] が捕まえた** —
初版は画面の旗をそのまま読んでいた。

**抑止が書けなかったら述べる。** アプリ設定ファイルは未知の上位 `schema_version` で読み取り専用へ縮退する
（decision-13）ので、この書き込みは拒否されうる。**黙って落とすと、利用者が刻んだ指定は効かないまま、
次の押下で注意が立つときになって初めて食い違いが現れる** — 行為から切り離された時点で、しかも
「効かなかった」ではなく「また出た」という形で。**述べ先は ⑤ 通知 で、理由は起動の失敗と同じである**
（層は答えより先に降りている）。**それでも起動は行う** — 押されたのは 進む であり、併せて頼まれた指定を
記録できなかったことは、開く相手を渡さない理由にならない。**PR #157 の 1R [P2] の 2 件目である。**

**doc-11 §12 の 実行前確認 は残り、この層とは別の問いである。** あちらが問うのは 未保存入力 の
二重取り込み（doc-8 §6.4）で、**抑止できない** — 抑止できる注意にすると、その注意が要る 1 回だけ
出ないという状態を作れてしまう。**両方が当たるときは層 1 枚が 2 点を述べる**（doc-11 §7 の
「同じ事柄を 2 通りに述べない」ではなく、**別の 2 点を 1 枚で述べる**）。**進むの答えは 1 つで、
刻みが効くのは frontmatter の注意 の側だけである。**

### 7. 失敗は ⑤ 通知 で、成功は何も述べない

**押下の失敗は ⑤ 通知 である**（doc-11 §4 の 3 つ目の型）。メニューは押下で自分を閉じるので、
結果が返る前に押した層が無い — decision-44 §3 が リリースページを開く について同じ帰結を出している。

**成功は何も述べない。** doc-8 §7 の区画は 起動した事実 を述べていたが、**その置き場が無くなる**
（区画にはもう起動の控えが無い）。**帯を 1 本立てる案は採らない** — doc-11 §4 が「画面が既に見せて
いる成功に帯を立てない」と定めており、成功したときに前へ出るのは起動されたプログラムそのものである。
**代償は、何も起きなかったように見える起動が 1 種類だけ残ることである** — 端末エディタを 起動指定 に
持つ利用者で、GUI プロセスから起動した端末エディタは描く端末を持たずに終了する。**その行は
その旨の註を持ち続ける**（doc-8 §7 が既に持っているもの）。

### 8. doc-8 §7 の区画は 管理ファイルのパス と 再読込 だけを残す

**残す 2 つはどちらも doc-8 §7 自身の要件である。**

- **管理ファイルのパス** — 「何を開こうとしているのかは、開く前に読めていなければならない」。
  **起動の控えがメニューへ移っても、押す前に読む場所はここである。**
- **継続検出 が止まっている間の 再読込** — 「戻ってきたときに読み直せる」。**画面を離れずに反映まで
  到達できること**が要件で、メニューはその到達先を持たない。

**注意文 2 種（frontmatter の注意・継続検出停止の註）は区画から出て、層と行の註へ移る。**
**未保存入力の警告文も区画から出る** — 実行前確認 の中で述べられる。

**文書・マイルストーン・決定事項 の側に対応する区画を作らない。** doc-10 §5 の 表示パス が既に
パスを述べており（§6・§10 も同じ列に出す）、押す前に何を開くかを読む場所はそこである。

**ただし 再読込 のほうは、あちらに置き場が無い。** doc-10 §3 のヘッダ行は プロジェクト名・slug・件数・
スイムレーンへの往復・☰ を持つだけで、**プロジェクト詳細画面はいま 再読込 を 1 つも持たない**（確認した）。
doc-8 §7 の「戻ってきたときに読み直せる」は 4 種すべてに掛かるので、**そのヘッダ行へ 再読込 を 1 つ足す。**

**サブメニューの側には置かない。** 置くと同じ操作が 3 か所（レーンヘッダ行・タスク詳細の区画・
サブメニュー）になり、しかもサブメニューの 1 つだけが「どのルートか」を対象から導くことになる。
**画面ごとに 1 つという形は既にあるもので**（doc-7 §2.3 のレーンヘッダ行が 1 つ、doc-8 §7 の区画が 1 つ）、
足す 1 つはその 3 つ目である。

### 9. 継続検出停止の註 はサブメニューが持ち、起動の差し控え は無くなる

**着手回が見つけた欠落である。** doc-8 §7 は 継続検出 が止まっている間「開く前に伝える」ことを
要件にしており、区画がそれを常に描いていた。**§6 の層はその文の置き場になれない** — 抑止されると
出なくなるので、抑止した利用者には要件が満たされない。

**註はサブメニューが持つ。** 継続検出 が止まっている間、編集の手段を渡す行の上に 1 行として出す。
**開いた時点の状態から描くので、押す前に必ず読める位置にある。**

**doc-11 §12 が「本節を通らない」ものとして数えていた 起動の差し控え は無くなる。** あれは、
区画が描かれた後に監視が失敗した場合に、1 度目の押下を起動に使わず註を出すことに費やす仕組みだった。
**サブメニューは押下で開き数秒だけ立つので、註は現在の状態から描かれる** — 区画がパネルの寿命ぶん
古びうるのに対し、こちらが古びうるのはサブメニューを開いてから行を押すまでの間だけである。

**代償はその間の 1 回である。** その窓の中で監視が死ぬと、利用者は註を読まずに起動する。
**失うのは 1 押下ぶんの保護で、気づく経路は残る** — 監視が止まったことはスイムレーンの帯が述べる
（doc-9 §3.1、doc-7 §5.3）。**差し控えを保つ案は、サブメニューの 1 行を「押しても起動しない行」に
することを意味し**、それは §12 が二度押しについて退けた形（同じ座標の 2 打で確定に届く）の裏返しで、
同じ座標の 2 打のうち 1 打目が黙って捨てられる形になる。


## Consequences

- 望ましい帰結
  - **4 種の 管理ファイル が同じ 1 つの経路で外部へ出る。** これまで外部エディタへ渡せたのは
    タスクだけで、文書・マイルストーン・決定事項 は Atlas の中でしか開けなかった。**決定事項は
    Atlas が本文を書く手段を持たない種類**（AGENTS の 更新 節。CLI に本文を書く手段が無い）なので、
    **本決定はその 1 種類について「書く手段が画面から到達できる」を初めて成立させる。**
  - **行の集合・注意・抑止 が 1 か所になる。** 区画ごとに置く案が持っていた 4 つの写しは生じない。
  - **押す前に何が起動するかを読める行が増える。** 名前付きエディタ の行は製品名を名乗るので、
    OS の関連付け起動 が「何が開くか押すまで分からない」という性質を持っていたのに対し、
    こちらは名前が答える。
  - **doc-11 §4 の上部帯の閉じた表が動かない。** 増えるのは ⑤ の届け先 1 つで、帯の種別は増えない。
- 費用・制約
  - **導入されていないエディタの行を押すと失敗する。** 探索しないことの代償で、押す前に分かる手段は
    無い（§4）。**失敗は必ず述べられる**が、それは押した後である。
  - **macOS の 5 行は最大 1.2 秒待つ。** `open` を観測するので、失敗する場合の呼び出しはその窓ぶん
    掛かる（既定ブラウザ起動 が既に払っている費用と同じもの）。**成功する場合は待たない。**
  - **Windows・Linux の 名前付きエディタ は PATH に依存する。** 導入済みでも PATH に無ければ
    失敗し、Atlas はその 2 つを区別できない。**macOS だけが PATH を要さない**という非対称が残る。
  - **Linux には 所在に効く 2 操作 が無い。** デスクトップ環境ごとにファイルマネージャも端末も違い、
    単一の呼び出しが決まらないためである（§4）。**Atlas はそのことを画面で述べない** — 出ない行に
    理由を添える場所が無く、他のプラットフォームにある行が無いことに利用者が気づく経路も無い。
  - **アプリ設定のスキーマ版が 6 から 7 へ上がる。** 注意の抑止 を足すので、`KNOWN_SCHEMA_VERSION` と
    `mergeDraft`・`normalize` の 3 か所を触る。**旧いビルドは新しいファイルを読み取り専用へ縮退させる。**
  - **成功を述べる場所が無くなる。** 端末エディタが描かずに終了した場合、画面には何も出ない
    （§7）。**行の註がその可能性を述べるだけである。**
  - **サブメニューという形が 1 つ増える。** メニューの中に層を入れ子にする実装はこれが最初で、
    出口の梯子 3 段を持つのもここだけである。
- 後続への影響
  - **doc-8 §7 を書き換える。** 起動の 2 経路・開く前の注意表示・未保存入力の警告 は区画から出て、
    残るのは 管理ファイルのパス と 再読込 である。**外部エディタ経路 という語は残り、指示対象が
    「タスクの管理ファイルを開く経路」から「管理ファイル 4 種を外部へ渡す経路」へ広がる。**
  - **doc-7 §2.1 に 外部で開く の 群 を足す。** 群 は `layer`・`rows`・`external` の 3 つに
    **4 つ目**が加わる。**項目の並びは 外部で開く → 入口 → キーボード操作一覧 → リリースページ →
    プロジェクト一覧** で、オーナーの図のとおり先頭である。**サブメニューの数え方と出口の梯子も
    同じ節へ書く。**
  - **doc-10 §3 のヘッダ行に 再読込 を 1 つ足す**（§8）。**§5・§6・§10 の 表示パス は動かない。**
  - **doc-11 に、注意の抑止 を持つ層の形を書く**（§15 として足した）。§12 の 実行前確認 とは別の層で、
    **抑止できる注意と抑止できない問いの別**がその節の中身である。**§12 の「本節を通らないもの」は
    3 つから 2 つへ減る**（§9）。
  - **decision-13 の項目一覧に 注意の抑止 が入る。** decision-13 の本文は項目を数え上げていないので
    改訂は要らないが、`settings.rs` の頭註と鍵集合の試験は動く。
  - **TASK-83 の実 印。** Windows と Linux の起動の形は本決定を書いた機（macOS）で測れないので、
    **実機での確認が要る**（オーナーの Windows 実機と WSL Ubuntu 24）。**macOS の 5 行は本タスクで
    測る。**
- 再検討の契機
  - **名前付きエディタ を足す要望が来たとき。** 表に 1 行足すだけで済む形にしてあるが、
    **足すたびに 3 プラットフォーム分の起動の形を決めることになる**ので、集合を無制限に伸ばすなら
    探索（§4 で退けた案）へ戻る判断になる。
  - **Windows・Linux で PATH 依存が現に問題になったとき。** そのとき初めて、そのプラットフォームの
    探索手段を測る。**macOS が要らないのは `open -a` があるからで、他の 2 つに同じものは無い。**
  - **Linux の 所在に効く 2 操作 を求める報告が来たとき。** `xdg-open` でフォルダを開く案は
    ファイルを選択状態にできないので、**「示す」を満たさないまま行が増える**。求められているのが
    フォルダを開くことなら doc-3 §2.1 の 場所を開く と同じ形で足せる。
  - **サブメニューが 2 段目を要求されたとき。** 出口の梯子は 3 段で定めてあり、段数が増えると
    「押した 1 回が何を降ろすか」の一意性を測り直すことになる。
