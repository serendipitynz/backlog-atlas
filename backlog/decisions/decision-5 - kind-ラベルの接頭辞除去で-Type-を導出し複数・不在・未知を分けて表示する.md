## Context

`kind:feature` / `kind:bug` / `kind:research` / `kind:writing` / `kind:maintenance`
などの kind ラベルを Type として通常ラベルから分離する規則と、未定義値・複数 kind・
kind 無しの表示方法を決める（TASK-5 に依存、TASK-8）。

前提は doc-4。doc-4 は既に「labels を `kind:` 接頭辞の有無で kind ラベルと通常
ラベルへ分ける分離を読み取り層で行う」ことと「Type の値そのものの導出規則
（kind→Type 名、複数 kind、不明値）は TASK-8 で確定する」ことを固定した（doc-4 の
3.3）。本決定はその導出規則と表示方法を確定する。分離の場（読み取り層）は再決定
しない。用語を先に固定する。

- **Type 値** … kind ラベル `kind:X` から接頭辞 `kind:` を除いた残り X（feature・bug
  など）。Type の表示値。
- **複数 kind** … 1 タスクの labels に kind ラベルが 2 つ以上存在する事象。
- **kind 無し** … 1 タスクの labels に kind ラベルが 1 つも存在しない事象。
- **未知 Type** … 導出した Type 値が既知 Type 集合に含まれない事象。
- **既知 Type 集合** … Atlas が表示上の色・並び等を用意しておく Type 値の集合。
  初期版は doc-2 が列挙した feature / bug / research / writing / maintenance とする
  （decision-20 が enhancement / task / chore / docs / spike を足して 10 語にした）。

導出を「接頭辞 `kind:` の機械的除去」に置く根拠。kind ラベルの語彙（feature・bug 等）
は各プロジェクトが付けるもので、Atlas が固定した対応表へ写す方式にすると、
プロジェクトが新しい kind（例 `kind:spike`）を導入するたびに Atlas の対応表更新が
必要になり、正本は各プロジェクトという doc-2 の境界に反する。接頭辞除去なら、
未知の kind も Type 値として素直に運べ、既知/未知の区別は表示側で吸収できる。

## Decision

Type 値の導出は、kind ラベル `kind:X` の**接頭辞 `kind:` を除去した残り X** を
Type 値とする（大文字小文字は保持、前後空白は除く）。分離自体は読み取り層で行う
（doc-4 の 3.3 を再確認）。通常ラベル一覧には kind ラベルを混ぜない。

> **2026-08-02 の注記（decision-20、TASK-110）**: 本節が Type 値の導出元を kind ラベル 1 つに
> 限った点は decision-20 が改めた。Backlog CLI v1.48.0 が frontmatter へ書く `type:`
> （type フィールド）も導出元になり、両方の値を併記する。接頭辞除去の規則そのものと、
> 既知 Type 集合の役割は変えていない（集合の中身は decision-20 が 10 語へ広げた）。
>
> **下の境界事象のうち 2 つは、表示の中身ではなく発火条件が変わった。** 「複数 kind」と
> 「kind 無し」はどちらも labels の kind ラベルの個数で条件を書いているが、導出元が 2 つに
> なるとその個数は表示すべき Type 値の個数と一致しない。`labels: []` に `type: bug` を持つ
> タスクは「kind 無し」に当たるが Type 値を 1 つ持ち、`kind:bug` に `type: feature` を持つ
> タスクは「複数 kind」に当たらないのに Type 値を 2 つ持つ。decision-20 は条件を Type 値の側で
> 言い直し、**複数 Type 値**（Type 値が 2 つ以上。導出元は問わない）と **Type 候補なし**
> （どちらの導出元からも Type 候補を得ない）を発火条件とする。併記する・「Type 未設定」と
> 出す、という表示の中身は本節のままである。「未知 Type」は元から Type 値の側で条件を
> 書いているので変わらない。
>
> 表示そのものが変わるのは 1 点だけで、大文字小文字の違いしかない Type 候補
> （`kind:bug` と `kind:Bug`）は decision-20 以降 1 つに畳まれる。

境界事象の表示。

- **複数 kind**（kind ラベルが 2 つ以上。decision-20 以降の条件は**複数 Type 値** =
  Type 値が 2 つ以上）: どれか 1 つへ丸めず、導出した Type 値を
  すべて併記する。Type は 0 個以上の値の並びとして扱う（単一値に固定しない）。
  併記順は labels の出現順を保つ（decision-20 以降は Type 候補の順で、kind ラベル由来が先）。
- **kind 無し**（kind ラベルが 0 個。decision-20 以降の条件は**Type 候補なし** =
  どちらの導出元からも Type 候補を得ない）: Type を「未設定」として表示する。空にせず、
  Type が付いていないことを明示する（通常ラベルの有無とは独立）。
- **未知 Type**（Type 値が既知 Type 集合に無い）: 値を破棄せず、その Type 値を
  そのまま表示しつつ、既知 Type 集合に無いことが分かる印を付ける（既定の中立表示に
  フォールバックする）。プロジェクトが独自 kind を導入しても表示自体は成立する。

未設定・未知は、doc-4 の不整合表示と同じ方針（判別できた事実は活かし、不足・想定外は
明示する）に沿う。ただし kind 無し（decision-20 以降は Type 候補なし）はタスクの欠陥ではなく正当な状態でもあるため、
不整合の「不足」ではなく「Type 未設定」という通常の表示状態として扱い、解析エラーの
印とは区別する。

## Consequences

- 望ましい帰結
  - 接頭辞除去のみで導出するため、プロジェクトが新しい kind を導入しても Atlas 側の
    対応表更新なしに Type 値として運べる。正本は各プロジェクトという境界を保てる。
  - 複数 kind を丸めず併記するため、`kind:research` かつ `kind:writing` のような
    タスクの分類情報を失わない。
- 費用・制約
  - Type は単一値でなく値の並びになる。タスク詳細・スイクレーン等の表示は Type を
    0 個以上として描く必要がある。
  - 既知 Type 集合（色・並びを用意する対象）を Atlas 側に持つ。未知 Type は中立表示に
    フォールバックする。
- 後続への影響
  - タスク詳細画面（TASK-12）は Type を値の並びとして表示し、未設定・未知の印を
    描く。既知 Type 集合の見せ方（色・アイコン）も TASK-12 の入力とする。
  - スイムレーン（TASK-11）で Type によるフィルタ・強調を行う場合、複数 Type と
    未設定を含めた対象の扱いを本規則に合わせる。
  - 読み取り層（doc-4）は分離済みの Type 値の並びと通常ラベルを保持する実装とする。
