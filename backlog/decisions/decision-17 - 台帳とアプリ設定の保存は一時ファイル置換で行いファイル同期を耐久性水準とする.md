## Context

Atlas が自分で書くファイルは 2 つある。台帳ファイル `projects.toml`（doc-3 §2）と
アプリ設定ファイル `settings.toml`（decision-13）で、どちらも OS のアプリ設定ディレクトリに
同居する。両方とも保存先へ直接 `std::fs::write` していた（TASK-84、`_sandbox` の実装報告書
指摘 2、推奨順 1）。用語を先に固定する。

- **原子的でない保存** … 保存途中の失敗を読者から隠したまま、新旧どちらでもない内容が
  保存先に残り得る書込み方法（報告書 指摘 2 の定義）。`std::fs::write` は保存先を切り詰めて
  から書くので、これにあたる。
- **一時ファイル置換** … 保存先と同じディレクトリに作った一時ファイルへ内容を全量書いてから、
  保存先の名前へ `rename` で置き換える書込み手順。
- **耐久性水準** … 保存が済んだと言うために、書いた内容がどの記憶階層まで届いていることを
  要求するかを定めた段階。①プロセスのバッファを出て OS のページキャッシュへ届く
  ②記憶デバイスへ届く（**ファイル同期**）③置換したという事実自体も記憶デバイスへ届く
  （**親ディレクトリ同期**）の 3 段。
- **保存境界** … 一時ファイル置換を構成するファイルシステム操作を 1 つの trait にまとめ、
  実装を差し替えられるようにした継ぎ目。**保存の段**は、その操作それぞれの名前を、
  失敗の注入先として指定できる値にしたもの。

原子的でない保存が残す被害は 2 ファイルで非対称である。`projects.toml` が壊れると
`LoadedLedger::load` が台帳全体をエラーにするので、**登録済みの全プロジェクトが開けない**。
`settings.toml` が壊れた場合は decision-13 の縮退により既定値で起動できるが、保存済みの
表示テーマ・カード情報量・監視設定・外部エディタ指定・`backlog_cli` は失われたように見える。
プロセス内 mutex は同時読み書きを防ぐが、プロセス終了や OS レベルの書込み失敗から
既存ファイルを守らない（それは TASK-85 が扱う別の層である）。

耐久性水準を選ぶにあたって効く事実が 3 つある。

1. `rename` は保存先の名前を原子的に差し替える。標準ライブラリの `fs::rename` は Unix の
   `rename(2)` と Windows の `MoveFileEx`（`MOVEFILE_REPLACE_EXISTING`）に載っており、
   **同一ファイルシステム上でなければならない**。一時ファイルを保存先と同じディレクトリに
   作るのはこのためで、OS の一時ディレクトリでは満たせない。
2. **親ディレクトリ同期が Windows で成立するかは測れていない。** Unix はディレクトリを開いて
   同期できる（2026-08-02 に macOS で `File::open(dir)?.sync_all()` の成功を実測）。Windows でも
   `std::os::windows::fs::OpenOptionsExt::custom_flags` に `FILE_FLAG_BACKUP_SEMANTICS` を渡せば
   標準ライブラリだけでディレクトリを開ける。**測れていないのはその先**で、ディレクトリの
   ハンドルに対する `FlushFileBuffers`（`File::sync_all` の Windows 実装）が通るかどうかを、
   この環境は Windows 実機を持たないため確かめられない。**したがって「Windows では不可能」とは
   書かない** — 測っていない理由を非提供の根拠にしたのが doc-10 §1 に「提供しない操作区画の
   理由は真であるものを書く」を足させた誤りである（TASK-58）。
3. **ファイル同期は macOS で既に最も強い形になっている。** Apple の `fsync(2)` はデバイスへの
   書き出しを保証せず `F_FULLFSYNC` を使えと述べるが、Rust の `File::sync_all` は Apple 向けに
   `fcntl(F_FULLFSYNC)` を呼ぶ（rustc 1.96.0 の標準ライブラリ実装 `sys/fs/unix.rs` の `fsync` で
   確認）。つまり本決定が行うファイル同期は、生の `fsync` より強い。

## Decision

台帳ファイルとアプリ設定ファイルの保存を、次のとおり行う。

**1. 一時ファイル置換で書く。** 保存先と同じディレクトリに、保存先のファイル名から導いた
別名の一時ファイルを作り、内容を全量書き、ファイル同期を行い、閉じてから、保存先の名前へ
`rename` で置き換える。一時ファイルは他の書き手のものを掴まないよう、既存を許さない作成
（`create_new`）で作る。

**2. 耐久性水準はファイル同期までとし、親ディレクトリ同期は行わない。**

**掲げる保証**は、**書込み途中の失敗が保存先に中途の内容を残さない**ことである。容量不足・
書込みエラー・プロセス強制終了のいずれで止まっても、保存先の名前が指すのは旧内容の全体か
新内容の全体で、その名前を読んだ者が途中の TOML を見ることはない（`rename` の原子性）。
これは実装と試験が立証する範囲であり、TASK-84 が消そうとしている損害そのものである。

**掲げない保証**は、電源断・OS 障害の後に何が残るかである。`rename` によるディレクトリ
エントリの変更を記憶デバイスへ書き出させていないので、その先はファイルシステム自身の
クラッシュ時の規則に委ねられる。ジャーナリングファイルシステムでは置換が原子的に扱われるのが
通例だが、**本決定はそれを保証として掲げないし、この実装も試験もそれを立証しない**。
「電源断では直近 1 回の保存が失われるだけで旧ファイルは無傷」と書けば、実装が持たない
保証を約束することになる。

この水準を選ぶ理由は 2 つ。

- 親ディレクトリ同期が上乗せするのは `rename` 自体の耐久性だけで、**掲げる保証**の側は
  それが無くても成立する。動作中の読者が中途の内容を見ないことは `rename` の原子性が
  与えるものであり、ディレクトリエントリの永続化とは別の事柄である。
- Context 2 のとおり、Windows でディレクトリのハンドルに `FlushFileBuffers` が通るかを
  この環境では測れない。通らなければ水準は Windows だけ低いまま残り、通ることを確かめるには
  Windows 実機を要する受入条件が増える。m-1 TASK-44 以降この種の分岐は値にして両ホストから
  検査できる形にしてきたが、ディレクトリ同期の成否はホストの実挙動そのものなので、その形に
  できない。**この理由は「不可能だから」ではなく「未測定だから」である** — 実機で測れる機会が
  来たら、水準を上げる判断はやり直せる。

**ファイル同期を省かない**理由も記録する。同期を省いて `rename` だけを行うと、ファイルの
内容より先に `rename` が永続化され得る。そのとき電源断後に残り得るのは、保存先の名前が指す
中身の無いファイル、すなわち原子的でない保存そのものである。掲げない保証の側にも下限は要る、
ということである。省けるのは保存 1 回につき 1 呼び出しで、両ファイルとも小さく、保存は
利用者の操作に対して 1 回しか起きない。

**3. 保存境界を置き、保存の段を値にする。** ディレクトリ作成・一時ファイル作成・書込み・
ファイル同期・`rename` の 5 段を 1 つの trait にまとめ、実物は標準ライブラリを呼ぶ。
試験用の実装は指定した 1 段だけを失敗させ、残りは実物へ委ねる。これにより「失敗時に旧ファイルが
変わらない」「成功時に新ファイル全体だけが見える」を、実ディスク障害を起こさずに主張できる。
段を `cfg` でも文字列でもなく値にするのは、どの段を失敗させるかを試験が名指せるようにするため。

**4. どの段で失敗しても、保存先には触れない。** 失敗したら一時ファイルを片付けてから失敗を
返す。片付けに失敗しても元の失敗を上書きしない（残る一時ファイルは何も指しておらず、
次の保存は別名を作る）。

**5. 適用範囲は Atlas 自身が書く 2 ファイルだけ。** 対象プロジェクトの Backlog 管理ファイルは
decision-2 により Backlog CLI が書くので、本決定の対象ではない。読み取り層・履歴層は何も
書かない。

## Consequences

- 望ましい帰結
  - 書込み途中の失敗が保存先に残らないので、台帳の破損で登録済み全プロジェクトが開けなくなる
    経路と、設定の破損で既定値起動になる経路が、どちらも消える。
  - 「失敗時に旧ファイルが変わらない」「成功時に新ファイル全体だけが見える」が、実ディスク障害を
    起こさずに試験で固定できる。保存境界が無ければ、この 2 つは主張したまま検査されない。
  - 台帳と設定が同じ 1 つの手順を通るので、片方だけが直る形にならない。
- 費用・制約
  - 保存 1 回あたりファイルシステム呼び出しが増える（作成・書込み・同期・`rename`）。両ファイルとも
    小さく、保存は利用者の操作に対して 1 回しか起きないので、体感に出る量ではない。
  - `rename` による置換は、保存先が持っていた権限と所有を一時ファイルのものへ置き換える。
    どちらも Atlas 自身のアプリ設定ディレクトリにあり、作成時の既定（プロセスの umask 由来）で
    書かれてきたファイルなので、失われる設定は無い。
  - プロセスが段の途中で強制終了すると、一時ファイルがディレクトリに残る。何も指していない
    ファイルであり、次の保存は別名を作るので、動作には影響しない。掃除は行わない。
  - 電源断・OS 障害の後に何が残るかは、本決定の掲げる保証の外にある。`rename` の
    ディレクトリエントリを永続化していないので、結果はファイルシステムのクラッシュ時の
    規則しだいであり、この実装も試験もそれを立証しない。**掲げるのは書込み途中の失敗に
    対する保証だけ**である。
  - Windows でディレクトリ同期が成立するかが未測定のまま残る。実機で測れる機会が来たら、
    水準を上げる判断はやり直せる（そのときは本決定を改訂する）。
- 後続への影響
  - doc-3 に §2.3「書き込み（一時ファイル置換）」を足し、decision-13 の「後続への影響」から
    本決定を参照する。どちらも置き場・形式・縮退は定めていたが、書込みの手順は定めて
    いなかった。その空白がここで埋まる。
  - TASK-85（共通 mutex の分割）はプロセス内の同時実行を扱う。本決定はプロセス外の失敗を
    扱うので、どちらも他方を不要にしない。
  - Atlas が自分で書くファイルが将来増えた場合は、同じ保存境界を通す。増やす側が
    `std::fs::write` を直接呼ぶと、本決定の外に出る。
