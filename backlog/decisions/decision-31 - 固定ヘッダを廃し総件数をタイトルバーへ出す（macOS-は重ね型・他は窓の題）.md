## Context

TASK-82 は、スイムレーンのメニューをアプリのタイトルバーへ統合できるかを判断する。**起票の本文は
手段を 1 つだけ想定していた** — `decorations: false` にして自前のタイトルバーを描き、3 環境ぶんの
ウィンドウ操作を自前で持つ、である。実測すると**手段は 3 つあり、費用はその選び方でまったく違う**。
この decision が記録するのは、その 3 つを分けたうえでの採否である。

語と指示対象は `_sandbox/handoff/referent-table/referent-table-task-82.md` 初版で本文より先に
固定した。以下で使う **帯への統合**（固定ヘッダの 3 つを OS のタイトルバーの帯へ移し、固定ヘッダの
行を無くすこと）・**重ね型**（装飾を OS に残したままタイトルバーを透明にし、その帯をアプリが
描く形）・**自前装飾**（OS に窓装飾を描かせず、窓を操作する控えをアプリが描く形）・**信号機帯**
（macOS の窓が 3 ボタンのために使う左端の領域）・**取り戻す高さ**（帯への統合によって内容が
使えるようになる窓の高さ）・**失う窓操作**（統合後にその OS の標準の手段では行えなくなる窓の
操作）・**帯の語**（統合後の帯が信号機帯の右に出す 1 つの語）はその表の語である。

**ユーザーが 2026-08-15 に UI モックを出し（`_sandbox/assets/TASK-82.png`）、同日に内容の置き場を
確定した。** モックは帯にアプリ名と総件数と ☰ を並べているが、**確定した置き場は ☰ を帯に置かず
フィルタ帯へ降ろすもので**、これがこの判断の形を変えた — **帯に押せるものが 1 つも無くなると、
帯全体をつかんで動かせばよく、Windows・Linux で自前装飾を採らずに済む経路（窓の題）が成立する。**

### 実測基準版

実測は macOS 26.5.2 (Build 25F84)・backingScaleFactor 1.0 の機械で、2026-08-15 に行った。
ライブラリ側の版は tauri 2.11.5・tauri-utils 2.9.3・tauri-runtime-wry 2.11.4・tao 0.35.3・
wry 0.55.1 である。**Windows・Linux は実機で測っていない** — 下の該当項はソースから読み取った
事実であって実測ではなく、その別は各項が名乗る。

### 実測 (2026-08-15)

数は AppKit を直に測った値と、本物のヘッダを WebKit へ載せて測った値の 2 系統である。

- **取り戻す高さは 32.0 pt である。** `NSWindow.frameRect(forContentRect:styleMask:)` に
  1200×800 の内容と `[.titled, .closable, .miniaturizable, .resizable]` を渡すと frame が
  1200×832 を返す。
- **信号機帯の右端は 69 pt、高さは窓上端から 9〜23 pt である。** `standardWindowButton` の 3 つは
  14×14 pt で x=9・32・55 に並ぶ。帯の左に空けるのはこの 69 pt に間隔を足した幅である。
- **固定ヘッダは 46.83 px、フィルタ帯は 36.16 px、グリッドは y=82.98 px から始まる。**
  WebKit・1200×800・地 110%（doc-11 §2.2）で、`_sandbox/app-check/` のハーネスに本物の
  `App.svelte` を載せて測った。**固定ヘッダの高さは ☰ の 28.02 px と上下 8.8 px で決まっている。**
- **帯の左を 78 px 空けても 1200 px 幅では溢れない**（`scrollWidth` 1200 = `clientWidth` 1200）。
  画面名・総件数・☰ を並べたままの本物のヘッダで測った値なので、**☰ を降ろした後の帯はこれより
  余裕がある。**
- **重ね型は設定値 1 つの差である。** tauri は macOS の窓を**既に** `fullSizeContentView` で
  作っており（`tauri-runtime-wry` の `title_bar_style`。`TitleBarStyle::Visible` でも
  `with_fullsize_content_view(true)` を通す。devtools でコンテンツが押し出される問題の回避策）、
  `Overlay` が変えるのは `titlebarAppearsTransparent` だけである。同じ窓を Swift で組んで測ると、
  `fullSizeContentView` のある窓は frame と内容が同じ 1200×800 で、`contentLayoutRect` だけが
  1200×768（= 800 − 32）を返す。
- **信号機帯の位置は設定から動かせる。** `trafficLightPosition` は `titleBarStyle: Overlay` と
  `decorations: true` の両方を要る（`tauri-utils` の註）。
- **要る権限は 2 つで、どちらも `core:default` に入っていない。** `core:window` の既定集合が持つのは
  `allow-title`（取得）と `allow-internal-toggle-maximize` までで、`allow-start-dragging` と
  `allow-set-title` は含まれない（tauri の `permissions/window/autogenerated/reference.md`）。

ソースから読み取った事実（**実機未測定**）:

- **重ね型は macOS 専用である。** `TitleBarStyle` は macOS のみに効く型で、`title_bar_style` の
  実装自体が `#[cfg(target_os = "macos")]` に囲まれている。Windows・Linux で帯をアプリが描くには
  自前装飾しかない。
- **自前装飾でも縁つかみ変形は残る。** tao は装飾なし・変形可・非最大化・非全画面の窓について
  `WM_NCHITTEST` を自前判定し（Windows 側）、GTK 側も同じ `hit_test` に `begin_resize_drag` を
  繋いでいる（X11・Wayland の両経路）。**Windows の style からは `WS_CAPTION`・`WS_SYSMENU`・
  `WS_SIZEBOX` が外れない** — 装飾なしは `WM_NCCALCSIZE` で内容領域を窓いっぱいへ広げる形で
  実現されている。
- **移動とダブルクリック最大化は tauri が 3 OS ぶん持っている。** `data-tauri-drag-region` の
  スクリプトが `start_dragging` と `internal_toggle_maximize` を呼び分け、macOS だけは
  `mouseup` で最大化する（カーソルが動いたら取り消せる OS の作法に合わせるため）。
- **信号機帯の inset は webview の親ビューの `drawRect` ごとに再適用される**（`wry` の
  `WryWebViewParent`）ので、一度きりの設定ではない。**全画面の出入りで消えないことはこれから読める
  だけで、測っていない** — 下の 未測定 に置いてある。
- **自前装飾で失うもの。** Windows は最小化・最大化・閉じるの控えと、**Win11 の配置候補**
  （最大化ボタンへのホバーで出るもの。`HTMAXBUTTON` を返す手段が Tauri に無い）。Linux は WM の枠と
  その右クリック窓メニュー、**変形中のカーソル**、影と角丸（`shadow` は Linux 未対応）。
  **Linux の縁のホバー時のカーソルは失わない** — tao は装飾なし・変形可・非最大化の窓について
  `motion-notify` で縁を判定し、`to_cursor_str` のカーソルを出す。**tao の FIXME が言っているのは
  `begin_resize_drag` を呼んだ後のカーソルだけである。** 初版はこれを「変形カーソルの表示を失う」と
  書いていたが、FIXME はそこまで支えていなかった。

## Decision

**帯への統合を採る。手段は OS ごとに分け、自前装飾はどこでも採らない。**

1. **固定ヘッダの行を無くす。** 3 つの行き先は、**画面名は廃止**・**総件数はタイトルバー**・
   **☰ はその画面の最上段の帯の右端**である。スイムレーンではフィルタ帯（doc-7 §5.2）、
   プロジェクト詳細では doc-10 §3 のヘッダ行がその帯にあたる。
2. **総件数の出し方は macOS が重ね型、Windows・Linux が窓の題とする。**（**2026-08-15 に改訂した。
   下の「Linux の改訂」を先に読むこと** — **Linux の窓の題は画面に反映されないと実測で分かり、総件数を
   出さないことになった。** 画面へ総件数を出す経路として本項が残るのは macOS の帯と Windows の題の 2 つで
   ある。）macOS は
   `titleBarStyle: "Overlay"` ＋ `hiddenTitle` で帯をアプリが描き、Windows・Linux は窓の題そのものを
   `Backlog Atlas — 表示 X / Y 件 ・ N / M プロジェクト` の形で書き替える。**この分岐は `cfg` ではなく
   値で持つ**（m-1 TASK-44 が確立した規則）。
3. **帯の語はアプリ名とする。** プロジェクト詳細では**題はアプリ名だけ**にする — 総件数はグリッドを
   述べる 2 つの比であり、doc-7 §2.1 が既にスイムレーン限定と定めている。**画面の身元は
   プロジェクト詳細のパンくずが「現在地」として名乗るので、画面名の廃止で失う情報は無い。**
4. **プロジェクト詳細の 戻る 控えを `arrow-left` のアイコンのみのボタンにする。** これは
   **doc-11 §2.4 の 語の中の記号（`← スイムレーン`。原文は doc-12 §8）からの意図的な逸脱である** —
   同項は「記号だけを図形へ抜き出すと語が変わる」として替えないと定めており、ここで変わる語は
   承知のうえで変える。図形は arrow 族（移動）に入り、doc-7 §2.3 の 行末の入口 `arrow-right` と
   対になる。**行き先の語は `aria-label` が持つ。**
5. **この decision では実装しない。doc の改訂も実装タスクが同じ PR で行う。** doc は現に画面が
   どうであるかを述べる文書なので、実装より先に改訂すると存在しない画面を述べることになる。
   **改訂する範囲はこの decision が名指しし（下記）、実装タスクの受入条件がそれを求める。**

## Consequences

- **失う窓操作は 3 OS とも 0 である**（下の 未測定 の項が、これがまだ読みであって実測でないことを
  述べている）。これが自前装飾を退けた理由そのものである — 自前装飾は Win11 の配置候補と Linux の
  窓メニュー・変形中のカーソル・影を失い、**そのうえ固定ヘッダが OS の窓操作を持つ形になって
  doc-7 §2.1 の「固定ヘッダに常設する操作はメニューだけ」「粒度の違う操作を同じ場所に混ぜない」と
  正面から衝突する。**
- **取り戻す高さは macOS で 32.0 pt、Windows・Linux で 0 である**（題は OS の帯に書くだけなので窓の
  高さは変わらない）。**固定ヘッダの 46.83 px はどの OS でも内容へ返る。** **この 2 つは足せない** —
  macOS では帯そのものが 32.0 pt のところへ載るので、返るのは 46.83 px であって 78.8 px ではない。
- **フィルタ帯の ☰ は帯の 1 行の高さ（`--bar-control`）を取る。** 現行の ☰ は 28.02 px に上下 8.8 px を
  持ち、**36.16 px の帯にはその寸法では入らない** — 移設は横幅の話だけではなく、doc-7 §5.2 が帯を
  1 行に保つと定めている以上、控えの寸法がそちらへ合わせる。
- **改訂される契約は、当初 5 つと数えたが足りていなかった。** 数え直した改訂先は doc-7 §2（積み順）・
  §2.1（固定ヘッダの節そのもの。常設の入口の置き場が画面ごとの最上段の帯へ移る）・§2.3 の図（`[固定ヘッダ]`
  の行を刷っている）・§5.2（フィルタ帯が常設の入口を持つ／総計の置き場が「画面名の横だけ」と述べている）、
  doc-10 §2（全プロジェクトに効く設定の入口の置き場・出口の語）・§3（ヘッダ行の右端）・末尾の参照、
  doc-11 §2.4（語の中の記号 の逸脱の記録）・§4 の ⑥ の文（「固定ヘッダのメニューへ寄せた」）、
  doc-3 §4（入口を粒度で分ける段が固定ヘッダを名指ししている）、**decision-13 の 後続への影響**（アプリ設定を
  固定ヘッダの設定から開くと述べている）、そして doc-12 §8 の原文からの逸脱の記録。
  **decision の本文が改訂に入ることには前例がある** — doc-7 §2.2 の 語と識別子 の項が、未分類系の改称が
  decision-4・decision-6 に及び、完了済みタスクの記録には及ばないと記録している。
  **列挙は網羅の保証にならないので、実装タスクの受入条件は列挙ではなく条件で書いた** — 「`backlog/docs/`
  と `backlog/decisions/` に現在形で 固定ヘッダ・画面名・「← スイムレーン」を述べる文が残っていない」を
  grep で数え直す形である。**上の列挙はその出発点であって、上限ではない。**
- **その grep から除くものは 3 種で、そこは触ってはならない。** 過去の状態の記録としてそう書いてある箇所、
  **本 decision 自身の本文**（この変更を定めている文書なので、固定ヘッダを現在形で述べるのが正しい）、
  そして **doc-12 の転記**（doc-12 §1 が「原文の値のまま写す」と定めている。ここを直すと、doc-11 §2.4 が
  語の中の記号 の原文として doc-12 §8 を引く鎖が切れる）。**除外を書いておかないと、grep の当たりの
  大半が「触ってはならないもの」になり、その中に混ざった本物の 1 件が雑音として見落とされる。**
- **☰ が 1 プロジェクトの帯に載ることは、doc-7 §2.1 の粒度の規則からの意図的な逸脱である。** §2.1 は
  1 プロジェクトに閉じた操作を固定ヘッダから締め出しており、その鏡である「全プロジェクトに効く入口を
  1 プロジェクトの帯へ置く」も同じ規則が退ける形になる（doc-10 §2 は全プロジェクトに効く設定を本画面に
  置かないと述べている）。**それでも置くのは、doc-7 §2.1 が「ショートカットだけが入口の操作を作らない」と
  定めているためである** — ☰ を置かない案では、プロジェクト詳細に居る間、設定・キーボード操作一覧・
  プロジェクトを登録に可視の入口が無くなる。**ユーザーはその案を検討したうえで置く側を選んだ**
  （2026-08-15）。**逸脱の記録は doc-10 §2 が持つ。**
- **追加する権限は 2 つに限る。** `core:window:allow-start-dragging`（macOS の帯をつかむ）と
  `core:window:allow-set-title`（Windows・Linux の題を書く）。decision-28 が CSP について採った
  「画面が動く最小」と同じ考え方で、窓を操作する控えを持たない以上、最小化・最大化・閉じるの権限は
  足さない。
- **TASK-149（窓の大きさを再起動後も引き継ぐ）の手段選定はこの判断に制約されない。** 対応順が
  #10 をこの行の後ろに置いていたのは、統合が自前装飾を要求するなら窓装飾を自前で持つ前提で手段を
  選ばねばならないからである。**自前装飾を採らないので、窓装飾は 3 OS とも OS のままである。**
- **失う窓操作が 0 だというのは、ソースから読んだ帰結であって実測ではない。** 測ったのは寸法だけで、
  **どの窓操作もまだ動かしていない。** 未測定のまま残るのは次の 5 つで、**実装タスクの受入条件が
  これを引き取る**。
  - Windows・Linux の実機確認（題がそれぞれのタイトルバーでどう省略されるかを含む）。
  - macOS で重ね型の帯をつかんで窓が動くこと、ダブルクリックで拡大すること。
  - macOS で全画面へ出入りしたときに信号機帯の inset が保たれること（`drawRect` ごとの再適用から
    読めるだけである）。
  - **macOS の全画面中の帯の見え方** — 信号機が隠れる間、左に空けた 78 px が何も避けていない状態に
    なる。初版はこれを数え落としていた。
  - macOS で窓の題が中央寄せになること（重ね型では題を隠すので画面には効かないが、窓の題自体は
    Mission Control や窓の一覧に出る）。

## Linux の改訂 (2026-08-15)

**上の 2 が Linux について定めた「窓の題そのものを書き替える」は、実測でこの目的を果たさないと分かった。**
本節はその改訂であり、上の判断のうち Linux に関する部分だけを置き換える。macOS と Windows は変えない。
語は `_sandbox/handoff/referent-table/referent-table-task-176-linux.md` 初版で本文より先に固定した。

### 実測 (2026-08-15、オーナーの Linux 実機。GNOME・Wayland セッション)

- `plugin:window|set_title` は**拒否されない**。直後の `plugin:window|title` は**書いた値を返す**。
  したがって権限の問題ではなく、GTK は新しい題を保持している。
- **それでも窓の装飾に出る題は変わらない。** 利用者から見て総件数はどこにも出ない。
- **Atlas 側で直せる層ではない** — アプリは記録どおりの呼び出しを行い、値はウィンドウオブジェクトに入っている。
  どの層が描き替えていないかは**測っていない**（この判断には要らない）。

### 決定

**Linux では総件数を出さない。** 窓の題は従来どおり書くが（無害で、題を読む窓一覧には効く）、**画面に総件数が
出ないことを受け入れる。** 上の 2 が Linux について定めた「窓の題で出す」は、この環境では目的を果たさないと
実測で分かったので、**果たす手段を探すのではなく、出さないことを記録する。**

**この結論は、帯を描く案を実装して実物を見たうえで採った**（2026-08-15、オーナー）。**内容上の帯**（OS の
装飾の下、内容領域の最上段にアプリが置く帯）を Linux に描かせ、実機で確認した結果、次の 2 つで退けた。

- **アプリ名が 1 行おきに 2 度出る。** OS の装飾が既に「Backlog Atlas」を刷っているので、その直下の帯が同じ語を
  繰り返す。**重ね型ではこれが起きない** — あちらは装飾そのものが透明で、帯が題の置き場を兼ねる。**帯の語を
  アプリ名とする上の 3 は、重ねない置き場へは移らなかった。**
- **内容の高さを 32px 払う。** 重ね型は装飾の高さに載るので内容を使わないが、内容上の帯は使う。**払った先が
  重複した語では割に合わない。**

**総件数をフィルタ帯へ出す案も退けた**（同日）。数を刷る場所が環境で変わる。

### 帰結

- **Linux の利用者は 2 つの比を受け取らない。** 行ごとの内訳はレーンヘッダ行に残るので、**失うのは全体の 2 つの
  比だけである。**
- **「帯を描くか」と「重ねるか」は 1 つの値のままでよい**（`OVERLAY_TITLE_BAR`）。Linux が帯を持つ案の下では
  別の問いだったが、持たないなら同じ問いに戻る。
- **書き込みの適用確認は持たない。** 題を書いた後に読み戻して届いていなければ述べる機構は、**この不具合を
  検出できない**（GTK は題を受け取っているので「適用済み」と答える）。仮に検出できたとしても、**述べる先は
  オーナーが承知のうえで採った状態**であり、起動のたびに帯が立つのは決着済みの判断についての雑音である。
  **拒否されたときの通知は残す**: Windows で題が書けなければ総件数はどこにも出ない。
- **macOS と Windows の実機確認は済んでいる**（2026-08-15）。macOS は帯をつかんで窓が動き、ダブルクリックで
  拡大し、信号機の下に文字が潜らない。Windows は題に総件数が出る。
- **上の Consequences の「取り戻す高さは Windows・Linux で 0」は正しいままである** — Linux は帯を持たないので、
  固定ヘッダの 46.83 px がそのまま内容へ返る。該当行に入れた註は取り消した。
