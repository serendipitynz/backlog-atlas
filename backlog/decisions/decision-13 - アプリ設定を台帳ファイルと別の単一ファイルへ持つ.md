## Context

画面設計案（doc-1 追補で定義。以下 設計案。引用する事実は doc-12 §2.2 に転記してある）の 01
「スイムレーン全景」が設定モーダルを置き、02・04 が「選択はアプリ設定に保存し、
再起動後も保つ」ことを設計の要件として挙げている。現時点の Atlas は、再起動をまたいで
残る記録として台帳ファイル（doc-3 §2.1、`app_config_dir()/projects.toml`）だけを持ち、
画面の既定値はどれも保持していない。本 ADR は、その記録をどこへ置くかを決める。

用語は doc-1・doc-3 に従い、本 ADR は次の 2 語を導入する。

- **アプリ設定** … 台帳エントリに属さない画面表示と操作の既定値を保持する記録を指す。
- **アプリ設定ファイル** … アプリ設定を永続化する単一ファイルを指す。

保持する必要のある既定値は次である。いずれも「どのプロジェクトを読むか」ではなく
「読んだものをどう見せ、どう操作するか」に属し、特定の台帳エントリに紐づかない。

| 項目 | 規定する文書 |
|---|---|
| 表示テーマ（decision-12） | doc-11 §2.1 |
| カード情報量（S / M / L） | doc-7 §3 |
| 既定の保存区分（フィルタの初期値） | doc-7 §5.2 |
| 既定の詳細配置（併置サイドバー／中央モーダル／全面シングルビュー） | doc-8 §2.2 |
| ファイル監視で外部変更を取り込むか | doc-9 §3.1 |
| 外部エディタ指定（`$VISUAL`／`$EDITOR` を上書きする起動指定） | doc-8 §7 |
| 既定の並び順（セル内のカードの並び） | doc-7 §5.4 |

**2026-08-10 追記（TASK-132）**: 表の最終行（既定の並び順）を足した。本 ADR の Consequences が
定めるとおり項目の追加はスキーマ版の管理対象なので、`schema_version` を 2 → 3 へ上げた。上げないと、
この項目を知らない旧ビルドが新しいファイルを自分の版として読み、serde が未知キーを捨てたうえで
次の保存が値を消す。**並び順を下の「アプリ設定を持たない値」へ入れなかった理由**は、あちらを外した
根拠が「次回起動時に前回どけたものが消えたままだと、登録したはずのプロジェクトが失われたように
読める」ことであり、並び順はカードを 1 枚も画面から失わせないためである。書き戻しは
既定の詳細配置（doc-8 §2.2）と同じ形で、帯で選んだ時点でそれが既定になる。

画面設計案 01 の設定モーダルが挙げる「起動時に全ルートを読み直す」は、項目に含めない。
ドメインモデルを永続化するキャッシュを持たない構成では、起動時の読み取りを切った状態に
指示対象が無いためである（doc-9 §3.2）。

置き場所の候補は三つあった。

- **台帳ファイルへ同居**（`projects.toml` に `[settings]` テーブルを足す）。
- **アプリ設定ディレクトリの別ファイル**。
- **webview のストレージ**（`localStorage` 等）。

## Decision

**アプリ設定は、台帳ファイルと同じアプリ設定ディレクトリに置く別の単一ファイル
（`app_config_dir()/settings.toml`）へ持つ。台帳ファイルへ同居させない。**

- **同居させない理由**: 台帳ファイルは `schema_version` が未知の上位版のとき、
  上書きで破壊しないよう読み取り専用へ縮退する（doc-3 §2.2）。同居させると、その縮退が
  表示テーマやカード情報量の保存まで巻き込み、「台帳を編集できないビルドでは配色も
  変えられない」という関係のない結合が生まれる。台帳は読み取り対象の定義であり、
  アプリ設定は見せ方の既定値で、片方の版が上がっても他方を書けなくする理由がない。
- **webview のストレージを使わない理由**: 保存場所が OS と webview 実装に依存し、
  アプリ設定ディレクトリの外へ出る。台帳と同じディレクトリに置けば、利用者が場所を
  把握でき、退避も一箇所で済む。
- **形式**: TOML。理由は doc-3 §2.2 と同じ（手編集しやすく、Rust の serde で素直に
  読み書きできる）。読み書きは decision-9 で採用済みの `toml` crate で行い、本 ADR で
  新規依存を増やさない。
- **スキーマ版と縮退**: 台帳ファイルと同じく `schema_version` を持つ。未知の上位版は
  読み取り専用へ縮退し、既定値で動かしたうえで上書き保存しない。ファイルが無い・
  壊れている場合は既定値で起動し、その旨を告げてから、次の保存で作り直す。
  設定が読めないことを理由に画面を止めない（設定は表示の既定値であり、読み取りの
  前提ではない）。
- **アプリ設定を持たない値**: 列折畳み（doc-7 §2.2）・行折畳み・行非表示（doc-7 §5.1）は画面の一時状態
  として扱い、本ファイルへ保存しない。折畳みと非表示は「今この作業で邪魔なものを
  どける」操作であり、次回起動時に前回どけたものが消えたままだと、行非表示の
  「件数も読めない」性質と相まって、登録したはずのプロジェクトが失われたように読める。

## Consequences

- 望ましい帰結
  - 台帳の読み取り専用縮退（doc-3 §2.2）が、表示の既定値の保存を巻き込まない。
  - 設定と台帳が同じディレクトリに揃い、退避・移行の対象が一箇所で説明できる。
  - 新規依存が要らない（decision-9 の `toml` crate の適用範囲を広げるだけ）。
- 費用・制約
  - アプリ設定ディレクトリに読み書きするファイルが 2 つになり、版検査と縮退の経路も
    2 系統になる。両者で縮退の規則を揃えて保つ必要がある。
  - 項目の追加はスキーマ版の管理対象になる。項目を規定する文書（上表）と、
    ファイルのスキーマの二箇所を揃える必要がある。
- 後続への影響
  - アプリ設定ファイルの読み書きと設定画面は TASK-46。表示テーマ（TASK-47）・
    カード情報量（TASK-49）・既定の詳細配置（TASK-54）は、この基盤の上に載る。
  - 台帳操作とアプリ設定操作は入口が別になる。台帳エントリの編集はプロジェクト詳細画面
    （doc-10）、アプリ設定は固定ヘッダの設定（doc-7 §2.1）から開く。
  - アプリ設定ファイルを**どう書くか**は decision-17 が定める（台帳ファイルと同じ
    一時ファイルによる置換で、耐久性水準はファイル同期まで）。本 ADR が定めたのは置き場・
    形式・縮退の規則で、書込みの手順は定めていなかった。上の「両者で縮退の規則を揃えて
    保つ必要がある」は書込みの側にも及ぶので、2 ファイルは同じ手順を通る。
