## Context

2026-08-11 のユーザーの要求（TASK-149）である。**窓の大きさ を、アプリを終了して起動し直した後も
引き継ぐ。** 契約の欠落であり、窓の大きさを保持の対象として扱った doc・decision は本 ADR まで無かった
— 「窓幅」は doc-7 §2.1 のメニュー幅上限と doc-8 §2.2 の主列幅が計算に使う入力値としてだけ現れる。
`src-tauri/tauri.conf.json` は `width: 1200`・`height: 800`・`minWidth: 640`・`minHeight: 480` を持ち、
毎回 1200×800 で開いていた。**最小寸法**（`minWidth`・`minHeight` の 2 値）は TASK-145 が doc-11 §13 の
規則を成り立たせるために入れた値である。

本 ADR は 2 語を導入する。

- **窓の引継ぎ状態** … アプリの終了時に記録し、次回起動時に窓へ戻す値の組を指す。
- **窓状態ファイル** … 窓の引継ぎ状態 を保持する `app_config_dir()` 直下の単一ファイルを指す。

### 手段は 2 つあり、依存ゲートに触れた

AGENTS の Dependencies 節が求める確認（新規本番依存の選定理由と導入範囲）に触れる分岐だったので、
**ユーザーが 2026-08-18 に選定した。** 候補は 2 つである。

- **Tauri 公式の `tauri-plugin-window-state` を入れる。**
- **アプリ設定ファイル（decision-13）の項目として Atlas 自身が読み書きする。**

**decision-31 が自前装飾を採らないと決めたことで、この選定は窓装飾の判断から解放されていた** —
窓装飾は 3 OS とも OS のままなので、どちらの手段も窓の描き方に制約されない。

### 追加前に測ったこと

crate 2.4.1 の実物と、この tree の依存解決を測った（2026-08-18）。

- **足す crate は 1 つだけである。** `cargo metadata --filter-platform` をリリースの 5 トリプルに
  流した和集合が 352 → 353 で、増えるのは `tauri-plugin-window-state` 自身のみ、減るものは無い。
  依存 6 つ（`serde`・`serde_json`・`tauri`・`log`・`thiserror`・`bitflags`、build 側の
  `tauri-plugin`）は**すべて `Cargo.lock` に既に在った。**
- **新しいベンダーではない。** `tauri-apps/plugins-workspace` の公式プラグインで、
  既に在る `tauri-plugin-dialog`（doc-3 §4.1）と同じ出どころである。ライセンスは
  `Apache-2.0 OR MIT` で、配布物が両方の本文を同梱するので `scripts/spdx/` は増えない。
- **ディスクへの書込みは終了時の 1 回だけである。** `WindowEvent::Resized` はメモリ上の控えを
  更新するだけで、`RunEvent::Exit` で 1 度書く。
- **復元は 最小寸法 と比べない。** `restore_state` は記録した大きさをそのまま `set_size` へ渡す。
- **書込みは `std::fs::write` である** — 一時ファイル置換（decision-17）ではない。

## Decision

### 1. 窓の引継ぎ状態 は 窓状態ファイル へ持ち、そのファイルはプラグインが書く

`tauri-plugin-window-state` を本番依存として導入する。窓状態ファイル は
`app_config_dir()/.window-state.json` であり、**台帳ファイル・アプリ設定ファイルと同じ
ディレクトリに並ぶ 3 つ目のファイル**である（doc-3 §2.1 を改訂した）。形式は JSON で、
`schema_version` を持たない。

### 2. アプリ設定ファイルへ持たない

**decision-13 のファイルは、未知の上位版の `schema_version` を読むと読み取り専用へ縮退し、
以後の保存をすべて拒否する。** 窓の引継ぎ状態 をそこへ置くと、その縮退が窓の大きさの保持まで
巻き込む — **これは decision-13 が台帳ファイルへの同居を退けたときの理由そのものが 1 段下で
再現する形である**（「台帳を編集できないビルドでは配色も変えられない」）。片方の版が上がっても
他方を書けなくしない、というのが decision-13 の判断であり、本 ADR はそれをこの値にも適用する。

**書込み経路の重さも同じ向きを指す。** アプリ設定の保存は毎回「ディスクの版を読み直す →
一時ファイル置換」であり（`settings::save_with`）、窓の大きさが変わるたびに通す経路ではない。
終了時に 1 度だけ書くなら通せるが、**アプリ設定を利用者の操作以外の契機で書く初めての形**になり、
設定画面が設定値ひとまとまりをファイル全体として書き出す性質（`mergeDraft` が落とした項目は
ディスクから消える）と 2 人の書き手を持つことになる。

**却下したのは置き場であって、TASK-148 との関係ではない。** 折畳み 2 種と行非表示（decision-13 の
「アプリ設定を持たない値」）の改訂は別機構になるので、TASK-148 は本 ADR と合併しない。

### 3. 引き継ぐのは 窓の大きさ と 最大化されているか の 2 つだけ

**窓の引継ぎ状態 は `StateFlags::SIZE` と `StateFlags::MAXIMIZED` の 2 つである**（正本は
`src-tauri/src/window_state.rs` の `CARRIED`）。プラグイン自身の既定は `all()` なので、これは
狭める指定である。

- **窓の位置 は入れない。** ユーザーが述べたのは大きさであり、2026-08-18 の確認でも範囲外に置いた。
- **`VISIBLE`・`DECORATIONS`・`FULLSCREEN` も入れない。** Atlas はこの 3 つを実行中に一度も変えないので、
  記録すると、手で編集した 窓状態ファイル がアプリのどの操作でも作れない状態で起動させうる。
- **`MAXIMIZED` は入れる。** プラグインの resize ハンドラは最大化中は控えを更新しないので、
  `SIZE` だけだと**最大化したまま終了して、次回は最大化前の大きさで開く。**
- **この 2 つを広げるときは本節を改訂する。** 数を増やすことは、上の 2 つの理由を取り下げることである。

### 4. 最小寸法の下限適用 は Atlas が行い、リサイズの通知を受けて物理ピクセルで判定する

**最小寸法の下限適用** とは、通知された窓の大きさが 最小寸法 を下回るとき、最小寸法 以上になる最小の
物理寸法へ resize し直す処理を指す。**プラグインは比較を行わないので、Atlas が行う** — 実装は
`window_state::raised_to_minimum` で、Atlas 自身のプラグインが窓ごとに `WindowEvent::Resized` を
見て呼ぶ。

- **プラグインも macOS も、復元した大きさを 最小寸法 と比べない。** 前者は crate 2.4.1 の
  `restore_state` を読んで（記録した値をそのまま `set_size` へ渡す）、**後者は 2026-08-18 に実機で
  測った** — 400×300 の記録で窓が 400×300 で立った。**Windows・Linux は未測定である。** 不可能と
  判定したのではなく測っていない。下限適用を置けば、その 2 つがどう答えても AC #3 は成り立つ。
- **読む時点はリサイズの通知でなければならない**（2026-08-18 実測）。プラグインの復元は自分の
  `window_created` フックで走るが、**`set_size` は `inner_size()` に即時反映されない** — Atlas 側の
  フックがその次に走った時点で `inner_size()` はまだ復元前の 1200×800 を返し、復元後の値を運ぶ
  `Resized(400×300)` はその後に届いた。**したがって 1 回読む形は、2 つの `.plugin(..)` をどちらの順に
  並べても何も補正しない。** `Builder::setup` はさらに前である — tauri は
  `tauri.conf.json` が宣言する窓を建ててから setup の closure を走らせ（tauri 2.11.5 の `app::setup`）、
  プラグインのフックは `run_on_main_thread` でイベントループへ載る。
  **この 2 つは順に試して測って否定した形であり、後から読む者が同じ道を通らないために書いてある。**
- **フック内の 1 回読みは、listener と併置してある。** Windows は同期でリサイズする —
  `SetWindowPos` は `WM_SIZE` を post ではなく send する — ので、あちらでは復元の `Resized` が
  プラグイン自身のフックの実行中に届き、こちらの listener がまだ無い時点を通りうる。
  **一方が macOS を、他方が Windows を覆う。** 冗長ではない。
- **判定と resize は物理ピクセルで行う。** resize は物理ピクセルの整数単位でしか与えられないので、
  拡大率が 2 進小数でないとき、論理の 最小寸法 には「自分自身として読み戻る物理寸法」が無い —
  Windows の 130%（`LogPixels` 125、拡大率 `125/96`）では 640 論理が
  `round(833.33) = 833` 物理になり（`dpi` 0.1.2 は四捨五入する）、833 物理は 639.744 論理に戻る。
  **論理で比べると、下限適用は通知ごとに同じ 833 を求め続け、満たした状態に到達しない。**
  物理ピクセルの整数で比べると、求める寸法が次に渡される寸法そのものなので、どの拡大率でも 1 回で
  到達する。**この形は PR #138 の [P2] の指摘で入った**（初版は論理で比べていた）。
- **物理へ移すときは切り上げる。** 下限だからである — 四捨五入では 130% の下限が 833 物理
  ＝ 639.744 論理になり、AC #3 が述べる下限を割る。切り上げれば 834 物理 ＝ 640.512 論理で上回る。
  費用は利用者が求めていない幅 1 物理ピクセルまでである。
- **記録は物理ピクセル、最小寸法 は論理ピクセルである** — プラグインの `WindowState` は
  `WindowEvent::Resized` が渡す `PhysicalSize` を持ち、`tauri.conf.json` の `minWidth`/`minHeight` は
  論理ピクセル（tauri-utils 2.9.3 がフィールドにそう書いている）。**したがって同じ記録が、
  拡大率の違う画面では別の論理寸法になる** — 1x の画面で既定の 1200×800 だった窓は 1200×800 物理を
  記録し、2x の画面で開くとそれは 600×400 論理になって 最小寸法 を割る。**これは 2 つの crate を
  読んで導いた経路で、2 枚の画面で測ったものではない。**

### 5. 窓状態ファイル は 一時ファイル置換 を通らない

**decision-17 と doc-3 §2.3 が課す 一時ファイル置換 は、Atlas 自身が書く 2 つのファイルに掛かる規則
であり、窓状態ファイル には及ばない。** プラグインは `std::fs::write` で書く。**掲げる保証を
下げたのではなく、失うものが違う** — 書込み途中で失敗して中途の JSON が残ると、次回起動時に
プラグインがそれを読めず既定値へ落ちる。**失われるのは記憶していた 窓の引継ぎ状態 1 回分だけで、
読めなくなるものは無い。** 台帳ファイルの側で 一時ファイル置換 が要るのは、中途の TOML が
「登録済みの全プロジェクトが開けない」を招くからである（doc-3 §2.3）。

**窓状態ファイル を自分で書けば規則を揃えられるが、それは 1 つの値のために復元機構を
自前で持ち直すことである。** 依存ゲートで公式プラグインを選んだ意味が無くなる。

## Consequences

- 望ましい帰結
  - アプリ設定ファイルの読み取り専用縮退が、窓の大きさの保持を巻き込まない。
  - 新しいベンダーが増えず、build に足す crate は 1 つだけである（追加前に実測した）。
  - 復元が最小寸法を下回らないことが、OS ごとの未測定の挙動に依存しない。
- 費用・制約
  - **`app_config_dir()` に Atlas のプロセスが書くファイルが 3 つになった。** 一時ファイル置換 を
    通るのはそのうち 2 つだけで、版検査を持つのも 2 つだけである。doc-3 §2.1・§2.3 の「2 つ」と
    述べていた文は、この違いを書き分ける形へ改めた。
  - **窓状態ファイル は 設定モーダル の ファイルの場所 区画に出さない**（2 行のまま）。あの区画が
    述べるのは、利用者が手で編集する対象の在処である（doc-3 §2.1・§2.2）— 窓状態ファイル は
    その対象ではない。
  - プラグインの版が上がると復元の挙動が変わりうる。上の「追加前に測ったこと」は crate 2.4.1 の
    実測であり、**版を上げる回は §4 が依存している 4 点を測り直す** — 復元が 最小寸法 と比べないこと、
    記録を物理ピクセルで持つこと、復元が `window_created` フックで走ること、そして
    `WindowEvent::Resized` が復元後の値を運ぶこと。**`dpi` の版を上げる回は 5 点目**（`u32` への変換が
    四捨五入であること）で、これは切り上げの根拠になっている。
- 後続への影響
  - **TASK-148（折畳み 2 種と行非表示）は本 ADR と合併しない**（§2 の最後）。あちらは decision-13 の
    「アプリ設定を持たない値」の改訂で、機構が別である。
  - **窓の位置 を後から引き継ぐことになったら、§3 を改訂して `StateFlags::POSITION` を足す。**
    プラグインは、保存した位置がどのモニタとも交差しないときは位置を戻さず OS に任せるので、
    「前回より小さい画面で起動して窓が画面外に出る」経路はプラグイン側で塞がっている（crate 2.4.1 実測）。
  - **リリースの資産を増やす回は、第三者通知の対象トリプルを数え直す**という既存の項が、本 ADR でも
    効く — `THIRD-PARTY-LICENSES.txt` は本 ADR の依存追加で再生成した。
