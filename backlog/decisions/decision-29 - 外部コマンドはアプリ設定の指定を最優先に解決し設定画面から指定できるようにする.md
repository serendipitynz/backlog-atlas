## Context

TASK-98 の実機確認で、**同じビルドが起動のしかたで挙動を変えた**（2026-08-13、macOS）。
Finder・Dock から起動した `.app` は Backlog CLI を解決できず更新を発行できないのに、
同時刻の同じマシンのターミナルでは `backlog --version` が 1.49.3 を返す（TASK-156）。
用語を先に固定する。

- **外部コマンド** … Atlas が起動する実行ファイルのうち、Atlas の配布物に含まれず利用者の
  環境に導入されているもの。`backlog`・`git`・`gh`・外部エディタの 4 つである。
- **外部コマンド指定** … アプリ設定（decision-13）が外部コマンド 1 つについて持つ、その
  実行ファイルの絶対パス。
- **外部コマンド解決の順序** … 外部コマンド 1 つについて、外部コマンド指定を最優先に置き、
  無ければその外部コマンド固有の自動解決へ進む規則列。
- **解決結果の表示** … 設定画面が外部コマンドごとに、その実行ファイルが起動できたかどうかを
  示す印と、現に解決されている実行ファイル・その出どころ。
- **GUI 継承 PATH** … Finder・Dock から起動した Atlas のプロセスが継承する PATH の値。
- **導入済みで不可視** … 利用者のログインシェルでは外部コマンドが動くのに、Atlas の
  プロセスからは解決できない事態。

原因は PATH の継承である。実測（macOS、2026-08-13）では GUI 継承 PATH は
`launchctl getenv PATH` が返す 11 ディレクトリで、`backlog` の実体がある fnm の
multishell ディレクトリを含まない。したがって decision-16 の実行ファイル解決の順序 3 段目
（bare name を OS に解決させる）が空振りする。

**3 OS で実測した（2026-08-13）。macOS 固有ではない。**

| OS | GUI 起動 | 結果 |
|---|---|---|
| macOS | Finder / Dock の `.app` | `backlog` を解決できない（`git`・`gh` はこのマシンの launchd PATH が customize 済みで届いた） |
| Windows | 実機 | 3 つとも解決した。`backlog` は decision-16 順序 2（npm の配置）で解決 |
| Linux | `.deb` が入れた `.desktop` をアプリセンターから | `backlog`・`gh` を解決できない。`git` は解決した |

**Linux の実測が、この事態の機構を最もはっきり示している。** 同じビルド・同じマシンで、
`pnpm tauri dev`（シェルの子プロセス）では `backlog` が解決し、`.desktop` からの起動
（デスクトップセッションの子プロセス）では解決しない。**しかも 3 行が導入経路で割れた** —
apt 導入の `git`（`/usr/bin`）は解決し、fnm ＋ `npm -g` 導入の `backlog`・`gh` は解決しない。
**PATH が空なのではなく、バージョン管理ツールが置いた場所だけが入っていない。**
Ubuntu 24 の既定は Wayland で、セッションの環境は systemd user session から来るため、
`~/.bashrc` にしか書かれない fnm の設定は届かない。**したがってこれは Atlas 固有の事象ではなく、
バージョン管理ツールで node を入れた利用者に一般に起きる。**

**この事態は 2 つの前提の取り違えを露わにした。** decision-26 は「利用者の PATH 上の
`backlog` を用いる前提を保つ」と書いたが、その「PATH 上」は 2 つの別の状態を指しうる。
利用者のログインシェルの PATH に `backlog` がある状態（**シェル側 PATH 前提**）と、
Atlas のプロセスが継承した PATH に `backlog` がある状態（**プロセス側 PATH 前提**）である。
順序 3 段目が成功する条件は後者だが、decision-26 が費用と便益を測った土台は前者だった。

**欠陥は `backlog` に留まらない。** 名前だけを `Command::new` へ渡している外部コマンドは
4 つある（実測。`update.rs` の `backlog`、`history.rs` の `git`・`gh`、`ledger.rs` の
`git`、`editor.rs` の `VISUAL`/`EDITOR`）。うち 2 つは失敗が利用者に見えない。

- **`git`**: doc-3 §3.2 の Git remote 有無属性判定は、起動できない `git` を「remote 無し」
  として記録する。登録した全プロジェクトが remote 無しになり、doc-6 §6 の関連解決が
  エラーではなく「対象なし」として落ちる。
- **`gh`**: 関連解決だけが落ちる。

**外部エディタでは、この原因はすでに認識され解かれていた。** doc-8 §7 の起動指定の解決順は
アプリ設定を `$VISUAL`／`$EDITOR` より上に置き、その理由を「環境変数がデスクトップアプリの
プロセスへ届かない起動経路（Finder・ランチャーからの起動）があり、環境変数だけでは指定手段が
無い利用者が生じるため」と書いている。**本決定は新しい原則ではなく、そこにある原則を残り 3 つ
へ広げるものである。**

decision-16 も回復手段を用意していた。順序 1 段目のアプリ設定 `backlog_cli` がそれで、
「外れた場合の回復手段が 1 段目である」と明記している。ただし設定画面へ出すのは
「UI 全面改修（TASK-61〜79）が進行中で、TASK-75 の後に判断できる」として保留していた。
**その保留理由は消えている**（TASK-61〜79・75 は消化済み）。

### 却下した対比案

- **sidecar 同梱**（decision-7 の同梱検討契機、decision-26 の再検討）。**採らない。**
  同梱は `backlog` の 導入済みで不可視 を構造的に消すが、**欠陥の範囲と対策の範囲が
  合わない** — `git` と `gh` は同じ原因で落ちたままで、`gh` は認証状態が利用者の設定に
  あるため同梱で代替できない。加えて decision-26 の理由 3（版の整合）は本件で悪化する:
  TASK-156 の利用者は現に `backlog` を導入しているので、「利用者の CLI と同梱 CLI が
  同じルートを触る」は仮定ではなく確定になる。費用（配布物が約 5.8 倍）は変わらない。
  **ただし decision-26 の理由 2「同梱は解けていない摩擦を解かない」は、本件の事実の前では
  そのまま維持できない** — シェル側 PATH 前提だけを見て書かれたためである。この訂正は
  decision-26 の Context へ記録し、判断そのものは据え置く。
- **起動時の PATH 回復**（ログインシェルを 1 回起こして PATH を読み、プロセスへ入れ直す）。
  **採らない**（2026-08-13、ユーザーの判断）。4 つを一度に直す唯一の手だが、decision-16 が
  「シェルを経由する必要は無い」として避けた性質に隣接し、外部コマンド指定と違って
  利用者から見えない。**見える指定手段を先に置く。**

## Decision

**外部コマンド 4 つを、外部コマンド解決の順序で決める。** 外部コマンド指定を最優先に置き、
無ければその外部コマンド固有の自動解決へ進む。自動解決の中身は外部コマンドごとに違い、
本決定はそれを揃えない。

| 外部コマンド | 順序 | 自動解決 |
|---|---|---|
| `backlog` | 3 段 | decision-16 のまま（Windows の npm サブパッケージ経由 → bare name） |
| `git` | 2 段 | bare name |
| `gh` | 2 段 | bare name |
| 外部エディタ | 3 段 | doc-8 §7 のまま（`$VISUAL` → `$EDITOR`） |

**外部コマンド指定はアプリ設定に置き、設定画面から編集できるようにする。**
`backlog_cli` の保留を解き、`git_cli`・`gh_cli` を新設する。3 つとも decision-16 が
`backlog_cli` に定めた読み方を引き継ぐ — **値があれば存在検査をせずそのまま使い、自動解決へ
落とさない。** 落とすと綴り誤りが「なぜか別のものが動く」形で隠れる。
**空白のみの値は未設定として読む**（利用者が欄を空にしたという意思を、毎回の起動失敗へ
変えないため）。アプリ設定のスキーマ版は 3 から 4 へ上げる（decision-13）。

**設定画面は解決結果の表示を持つ。** 外部コマンドごとに、`--version` が起動したかどうかを
行の先頭の印で示し、実行ファイルと出どころは行の `?` の中へ入れる。**起動したかどうかを示すのが
要点である** — 「`git`、PATH から解決」という表示は、PATH に在るときと無いときで同じに読めるので、
解決だけを示す表示は利用者が来た問いに答えない。

**3 つとも載せる。`backlog` を含む**（2026-08-13 のユーザーの目視で確定。下の「判断を変えた点」）。

**解決できないときは、その行のコマンド名を不整合の族の色で描く。** これは上部帯 ②（CLI 縮退）が
借りているのと同じ色を、同じ理由で借りるものである（decision-22。族は色を選ぶ単位であって事象の
分類ではなく、外部コマンドが起動できないことと管理ファイル 1 件の不整合が同じ対象へ同時に付く
ことはない）。**印は doc-11 §2.4 の状態の印**で、押せる控えの外に置き、包む要素が語を持つ。

### 判断を変えた点（2026-08-13、実機の目視）

本決定は当初「`backlog` は解決結果の表示に載せない。1 つのプログラムについて 2 つの答えを
同じ画面へ出すと食い違う」としていた。**実機で見ると、これは食い違いを避けるどころか、
利用者の問いに答えない画面になっていた** — `backlog` が解決できているときは縮退帯が立たないので、
**設定画面には `backlog` について何も出ない。** 代わりに置いていた「Backlog CLI の状態は画面上部の
帯が示します」という 1 文は、帯が立っていないときに何も指していなかった。

**訂正の中身は「2 つの答え」という見立てのほうである。** この表示と縮退帯は同じ問いに 2 通り
答えているのではない。**この表示が答えるのは「起動したか」** で、**縮退帯が答えるのは
「最低バージョン要件を満たすか」** である。要件未満の CLI は問題なく起動するので、表示が
「起動した」と述べ、帯が同時に「発行できない」と述べるのは、食い違いではなく 2 つの真である。
`backlog` の行が示す実行ファイルは `SystemBacklog` の解決そのもの（doc-5 §4 の 3 段）を引くので、
実際に更新が走る実行ファイルと必ず一致する。

**解決結果の出どころは 3 値になる** — 外部コマンド指定・npm の配置からの解決・PATH からの解決。
3 つ目までが要るのは `backlog` を載せたためで、decision-16 順序 2 は他のどの外部コマンドにも
起こらない。`PATH から解決` に畳まないのは、利用者の問いに対する答えが違うからである
（OS が見つけた、のか、Atlas が npm の配置を辿った、のか）。

## Consequences

- 望ましい帰結
  - 導入済みで不可視 に陥った利用者が、アプリの中で直せる。README のとおりに導入した
    利用者が更新を発行できないまま打つ手を持たない、という状態が解ける（TASK-156）。
  - `git` の解決失敗が「remote 無し」として静かに記録される経路に、利用者から到達できる
    回復手段が付く。
  - 外部コマンド 4 つの解決が 1 つの形で述べられ、5 つ目を足すときに何を決めればよいかが
    決まっている。
  - 配布物は Atlas 自身の大きさに留まる（decision-26 の帰結を保つ）。
- 費用・制約
  - 利用者は、GUI 起動で PATH が届かない環境では 3 つの絶対パスを自分で入れる必要がある。
    自動では直らない — 起動時の PATH 回復を採らなかったことの直接の費用である。
  - 設定画面を開くたびに 3 つの `--version` を起こす（各 5 秒上限）。
  - アプリ設定のスキーマ版が 4 になり、版 3 を書く旧ビルドは新しいファイルを読み取り専用へ
    縮退させる（decision-13 のとおり）。
- 後続への影響
  - doc-5 §4 の実行ファイル解決の順序は 3 段のまま。本決定はその上位概念を置くだけで、
    段を足さない。
  - doc-6 は `git`・`gh` の解決を本決定に従って述べる。
  - decision-16 の「`backlog_cli` は設定画面に出さない」は本決定が解く。
  - decision-26 は据え置き。理由 2 の訂正だけが入る。**sidecar 同梱を再び開くのは
    decision-7 の残る 2 契機によるのであって、本件を理由にはしない** — 本件の対策は
    ここで決まった。
