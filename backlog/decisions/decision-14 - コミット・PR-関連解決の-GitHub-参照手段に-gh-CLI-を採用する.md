## Context

TASK-43（doc-6「タスクID からの Git・Pull Request 履歴参照」）は、コミット・PR 関連解決の
参照手段を実装する。doc-6 §6 は「remote ホスト種別ごとの参照手段（ホストの API 等）を
用いる」と構造だけを固定し、各ホストの具体（認証の要否・レート・オフライン時の挙動）は
種別ごとの後追加として送りにした。TASK-30 は `PrCommitSource` trait の形だけを実装し、
GitHub の実体を空けている。本 ADR は、その GitHub 分を何で実装するかを決める。

用語は doc-6 §1・doc-8 §5 に従う。本 ADR で導入する新語は **突き合わせ不能** の 1 語で、
初出は「Decision」節に置く。**採用時に比較した候補** は decision-10・decision-11 と同義
とする（その依存を採用した時点で実際に俎上へ載せ、比較のうえ却下した選択肢を指す）。

**GitHub の参照手段** とは、doc-6 §6 の参照手段のうち GitHub 分、すなわち Pull Request に
属するコミット SHA 集合を得る手段を指す。これに課される要件は次である。

- PR 座標（owner/repo/number）からコミット SHA 集合を得られること。doc-6 §6 は PR ごとに
  その PR 自身の座標で照会することを求めており、プロジェクトの remote とは限らない。
- 固定サブコマンドと引数配列で実行し、シェル文字列へ連結しないこと（doc-2・AGENTS）。
- 読み取り専用であること。Git リポジトリも管理ファイルも書き換えない（doc-6 §2）。
- 参照不能（ネットワーク・認証・オフライン）を、解決済みだが共有コミットが無い状態と
  区別して返せること（doc-6 §6・doc-8 §5）。
- 対象リポジトリが private でも解決できること。Atlas が扱うプロジェクトは個人・社内の
  非公開リポジトリを含む。

判断は 2026-07-31 の TASK-43 着手時に、AGENTS「Dependencies」の導入ゲートに従い、
着手前にユーザーへ候補・選定理由・導入範囲を提示して承認を得たうえで行った。

評価軸は次の四つとした。

- 上記の要件、とりわけ private リポジトリの解決と参照不能の区別を満たせるか。
- 新規本番依存をどれだけ増やすか（AGENTS の依存最小方針）。
- GitHub の認証情報を Atlas が保持することになるか。
- 導入範囲を局所に閉じられるか。

## Decision

**GitHub CLI（`gh`）の `gh api` 呼び出し** を GitHub の参照手段として採用する。呼び出しは
`gh api --hostname github.com --paginate --jq '.[].sha' repos/<owner>/<repo>/pulls/<number>/commits`
を固定引数配列で実行する形に固定する。

decision-7 が `backlog` について定めたのと同じく、**PATH 上の `gh` を前提とする**。すなわち
`gh` は実行時に利用者の PATH 上に在るものとして呼び、アプリ配布物へ同梱せず、クレートと
してビルドへも入れない。導入範囲は `history` モジュールの `HostReferences`（`PrCommitSource`
の本番実装）1 箇所に閉じる。関連解決のゲート判定とローカル⇄remote のコミット突き合わせは
`PrCommitSource` の注入で切り離してあり、ネットワークなしで単体テストできる状態を保つ。

各引数の役割は次のとおりで、いずれも要件から来ている。

- `--hostname github.com` … 利用者の `GH_HOST` が enterprise ホストを指していても、
  github.com の PR を別ホストへ照会させないための固定。
- `--paginate` … PR のコミット一覧はページングされる（1 ページ 100 件、GitHub 側の上限は
  250 件）。全ページを歩かないとコミット集合が欠ける。
- `--jq '.[].sha'` … 応答を `gh` の中で SHA 1 行 1 件へ縮約する。JSON パーサを Atlas 側に
  持たずに済む。出力行は 16 進 7 文字以上のものだけを SHA として採り、それ以外の行は捨てる。
- owner/repo は GitHub の名前として扱える文字（ASCII 英数と `-` `_` `.`）に限り、`.` と `..`
  は拒む。この 2 つはタスクの References URL 由来の値であり、API パスへ埋める前に検査する。

`gh` の起動時は `GH_PROMPT_DISABLED` と `GH_NO_UPDATE_NOTIFIER` を立てる。応答する端末が
無い場所で対話プロンプトに止まらないため、および更新通知が、失敗理由として画面へ出す
stderr に混ざらないためである。

**突き合わせ不能** とは、ローカルコミット一覧が得られていないため Pull Request のコミット
集合と突き合わせる相手が無く、関連 PR の件数を言えない状態を指す。Git 対象不在・Git 読取
不能のときに生じる。この状態では参照手段を呼ばず、関連解決の結果を空で返す。空の結果を
「関連が無い」と読ませないため、画面は件数ではなく突き合わせ不能である旨を出す。

### 採用理由

- **private リポジトリと認証を追加設計なしで満たす。** `gh` は利用者が既に `gh auth login`
  で確立した認証を持つ。Atlas は GitHub トークンを一切保持せず、アプリ設定にも環境変数にも
  トークンの入手経路を新設しない。レート制限も認証済みのものが効く。
- **新規クレートが 0 本である。** `reqwest` は `tauri` 経由で既にビルド木にあるが、有効な
  feature は `json` と `stream` だけで TLS バックエンドを持たない（`Cargo.lock` に rustls・
  native-tls・openssl のいずれも無い）。自前で HTTPS を叩くには TLS スタック一式が新規に
  増える。`gh` 経路はそれを増やさない。
- **既存の実行方針をそのまま使える。** Atlas は `backlog`（doc-5）と `git`（doc-6）を、固定
  サブコマンドと引数配列で、シェル非連結に実行する構造を既に持つ。`gh` はその 3 本目であり、
  新しい実行様式を持ち込まない。
- **導入範囲を 1 箇所に閉じられる。** `HostReferences` は `PrCommitSource` の実装であり、
  読み取り層の `ScanSource`・更新層の `BacklogCli`・監視層の `WatchSession` と同じ境界の
  引き方である（decision-11）。

### 却下した候補と却下理由

| 候補 | 却下理由 |
|---|---|
| `reqwest` に TLS feature（`rustls-tls` / `native-tls`）を足す | `reqwest` 本体は既にビルド木にあるが TLS バックエンドが無いため、rustls・ring・webpki-roots（または OS の TLS 実装）が新規に増える。加えて GitHub トークンの入手経路（環境変数かアプリ設定か）を新設する必要があり、Atlas がトークンを保持する面が生まれる。未認証で使えば 60 req/h の制限を受け、private リポジトリは解決できず、要件を満たせない。 |
| `ureq`（tokio 非依存の同期 HTTP クライアント） | TLS スタックが新規に増える点と、トークン入手経路を新設する必要がある点は `reqwest` と同じ。加えて、既にビルド木にある `reqwest` を使わず別のクライアントを増やすため、HTTP クライアントが 2 本になる重複を招く。 |
| `git fetch` / `git ls-remote` でローカルに解決する（依存ゼロ） | `git ls-remote origin 'refs/pull/*/head'` で得られるのは PR の先頭コミットだけで、doc-6 §6 が求める「Pull Request に属するコミット集合」にならない。集合を得るには `git fetch` が要り、それはローカルリポジトリへオブジェクトを書き込むため、doc-6 §2 の読み取り専用に反する。 |
| `gh` を sidecar として同梱する | decision-7 が `backlog` について整理した論点がそのまま当てはまる。初期用途は開発者＝利用者のローカルアプリであり、同梱はプラットフォーム別バイナリの用意と版追随の継続コストを生む。PATH 前提は後から同梱へ差し替えられるため、初期版で確定を急ぐ必要がない。 |

## Consequences

- 望ましい帰結
  - doc-8 §5 が「参照手段が入った後は、割当表どおり件数（**関連 PR m 件**）へ戻す」と予告
    した状態へ到達する。m は、このタスクのローカルコミットと共有コミットを持つ Pull
    Request の数である。
  - Atlas が GitHub トークンを保持しない。認証情報の保管・失効・漏洩の面を持たずに、
    private リポジトリの PR を解決できる。
  - 新規クレートが増えないため、ビルド時間・監査対象・供給網の面が変わらない。
- 費用・制約
  - `gh` が PATH 上に無い、または未認証の環境では関連解決が参照不能になる。これは doc-6 §6
    が既に定めた縮退であり、コミット検索とローカル履歴（remote 非依存の機能）は縮退しない。
    参照不能は「関連が無い」ではなく「今は確かめられない」であることを画面が述べ、全面
    シングルビューでは解消できる原因かどうかも書き分ける（doc-8 §5）。
  - 呼び出しにタイムアウトを設けていない。`std` だけでは新規依存なしに子プロセスを時間
    付きで待てないためである。代わりに、待つ間はロックを持たない形にした。Tauri コマンドは
    開いているルートの台帳・モデルを守る mutex を本体全体で保持するため、その下で `gh` を
    待つと、遅い 1 回の通信の後ろに再読込・編集・open/close・利用者自身の「再取得」まで
    並んでしまう。`#[tauri::command(async)]` が空けるのは WebView スレッドだけで、backend の
    ロックは解放しない。よって読みを 2 段に割り、モデルから必要な References を取り出す所
    までをロック下で行い、`git`・`gh` の実行はロックを落としてから行う。詳細画面のローダは
    古い応答を破棄し、利用者は「再取得」で取り直せる。
  - 参照失敗の原因は 3 つに型付けして画面まで運ぶ（起動不能・参照不正・照会失敗）。
    doc-8 §5 が「その原因が解消できるかどうか」を求める一方、照会が走って失敗した場合の
    原因（認証・権限・PR の不在・ネットワーク）は終了状態からは分かれないためで、確定
    できない解消経路を画面が約束しないようにする。
  - 同じ Pull Request を指す References が複数あっても、照会と件数は 1 回に畳む。畳む鍵は
    解析済みの座標（ホスト種別・owner・repo・番号）で、同一 URL の重複と `/pull/5` ・
    `/pull/5/files` のような表記違いの双方が同じ PR として扱われる。doc-6 §4 の「複数 PR を
    丸めず全て保持」は References の抽出に掛かる規定であり、Pull Request 区画の表示は
    畳まない。
  - PR ごとに 1 回 `gh` を起動する。1 タスクの Pull Request URL は通常 1〜2 件であり、
    プロセス起動の費用は許容する。件数が増える運用が現れたら見直す。
  - `gh` の版差は本 ADR で固定しない。`gh api` の当該引数は長く安定しており、失敗時は
    stderr の 1 行目を参照不能の理由として画面へ出すため、版差の影響は縮退として現れる。
- 後続への影響
  - GitHub 以外の remote ホスト種別を扱う段になったら、`HostReferences` の分岐に種別を
    足し、その種別の参照手段を本 ADR と同じ導入ゲートで決める。分岐は網羅的な `match` に
    してあり、種別を足すと参照手段の決定を迫られる。
  - GitHub Enterprise は現時点で `RemoteHostKind` に無く、`--hostname github.com` の固定も
    github.com だけを見ている。対応する場合は、ホスト種別の判別（doc-6 §5）と本 ADR の
    両方を改める。
