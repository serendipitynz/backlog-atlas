## Context

読み取り層（doc-4、TASK-28）は Backlog 管理ファイルの frontmatter と `config.yml` を
解析する。decision-2 が読み取りを直接解析と定めた以上、YAML を読む手段が要る。
判断は 2026-07-24 の TASK-28 着手時に、AGENTS「Dependencies」の導入ゲートに従って
着手前にユーザーへ確認したうえで行った。

却下理由の中心になるのが doc-4 §5 の扱いである。§5 の解析不能は原因が二つあり、
必須フィールド（id・title・status）を欠く場合と、frontmatter が YAML として
読めない場合が含まれる。後者を本 ADR では **YAML 由来の解析不能** と呼ぶ
（YAML 由来の解析不能とは、doc-4 §5 の解析不能のうち、frontmatter が YAML として
読めないことを原因とする側を指す）。読み取り層はこれを検出して当該 1 タスクの
縮退に封じ込める義務があるため、YAML として妥当かどうかの判定そのものが、
読み取り層に必要な信号になっている。

**採用時に比較した候補**（採用時に比較した候補とは、その依存を採用した時点で実際に
俎上へ載せ、比較のうえ却下した選択肢を指す）は、`serde_yaml`（0.9.34、upstream
アーカイブ済み）、自前のサブセットパーサ（依存ゼロ）、`yaml-rust2`（serde 非対応の
パーサ）の三つである。

評価軸は次の三つとした。

- YAML 由来の解析不能を、誤読ではなく確実に失敗として検出できるか。
- doc-4 §4 の 3 分類（必須／任意／存在時構造検査）を実装できるか。
- 保守されているか、依存として過不足がないか。

前提として、frontmatter の実データは平坦である（v1.47.1 実測でスカラ・ブロック配列・
フロー配列・真偽値・整数のみ、入れ子なし）。これは自前パーサを一見成立させる条件だが、
管理ファイルは利用者が手編集しうるため、実データの平坦さは将来の入力の平坦さを
保証しない。

## Decision

**`serde_yaml_ng` 0.10**（MIT）を採用する。アーカイブ済み `serde_yaml` の保守
フォークで API は同一である。導入範囲は読み取り層の frontmatter・`config.yml` 解析に
限定する。

なお、フィールド抽出は `#[derive(Deserialize)]` の frontmatter 構造体ではなく、
YAML の `Value` ツリーを歩いて行う。derive では任意フィールド 1 個の型不一致で
デシリアライズ全体が失敗し、読めるはずのタスクが解析不能へ落ちるため、doc-4 §4 の
3 分類を表現できないからである。crate に求めているのは YAML 妥当性の判定と字句解析で
あって、型への自動写像ではない。

### 採用理由

- YAML として読めない入力を、黙って別の意味に読むのではなく失敗として返す。
  YAML 由来の解析不能を doc-4 §5 の独立した事象として扱うには、この失敗が信号として
  必要になる。
- 保守されているフォークであり、API がアーカイブ済み `serde_yaml` と同一なので、
  上流が再び止まった場合に別フォークへ移りやすい。
- `Value` ツリー経由の抽出ができ、doc-4 §4 の 3 分類（必須は欠落で解析不能、任意は
  不在が正常、存在時構造検査は在るときだけ検査）をそのまま実装できる。

### 却下した候補と却下理由

| 候補 | 却下理由 |
|---|---|
| 自前のサブセットパーサ（依存ゼロ） | 依存最小方針には最も適合し、実データが平坦である以上いったんは動く。却下したのは、失敗の仕方が悪い側に倒れるためである。既製パーサが構文エラーとして返す入力を、サブセットパーサは黙って別の値に読む余地がある。誤読は doc-4 §5 の縮退経路に乗らず、間違った値が正常なタスクとして表示される。依存 1 本を避ける利益より、この誤読の害が大きい。手編集された YAML を読む前提（decision-2）では特にそうである。 |
| `serde_yaml` 0.9.34 | 実績は最大で API も同一だが、upstream がアーカイブ済みで今後の修正が入らない。同一 API の保守フォークが在る以上、こちらを選ぶ理由が無い。 |
| `yaml-rust2` | YAML 1.2 準拠のパーサとしては妥当だが、serde 経路を持たないため、YAML イベント列からドメイン型への写像を手で書くことになる。依存の本数は同じで写像コードだけが増える。 |
| `serde_norway` / `serde_yaml_bw` / `serde-saphyr` 等の他フォーク | いずれも `serde_yaml` 系の別フォークで、本用途で必要な機能に差が無い。差が無い以上、フォークを増やして比較する利益が無いため、API 互換と保守状況で `serde_yaml_ng` を選んだ。 |

## Consequences

- 望ましい帰結
  - YAML 由来の解析不能が、誤読ではなく検出可能な失敗として読み取り層へ届き、
    doc-4 §5 の 4 事象の区別が実装できる。
  - 生成元の版に依存しないスキーマ能力検査（doc-4 §4）を、`Value` ツリー上の
    有無検査として書ける。
- 費用・制約
  - 本番依存が 1 本増える（推移的に `unsafe-libyaml`・`ryu` を伴う）。導入範囲を
    読み取り層に限定することで影響を閉じている。
  - `serde_yaml` 系フォークは複数あり、選んだフォークの保守が止まる可能性は残る。
    API 互換のフォークへ移る余地を残すため、YAML 依存の呼び出しは
    `src-tauri/src/read/parse.rs` に閉じてある。
- 後続への影響
  - 更新経路は本決定と無関係である。管理ファイルの更新は Backlog CLI へ委譲し
    （decision-2、doc-5）、Atlas が YAML を書き戻すことはない。本依存は読み取り専用で
    使う。
  - status 正規化（TASK-29）と Type 導出（TASK-8）は、本依存が写した生の値を入力と
    する。値の解釈は本決定の範囲外である。
