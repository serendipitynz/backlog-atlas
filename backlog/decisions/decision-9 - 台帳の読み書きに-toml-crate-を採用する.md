## Context

プロジェクト台帳 `projects.toml`（doc-3）を Rust から読み書きする手段を決める。
判断は 2026-07-23 の TASK-26 で行われ、記録は Implementation Notes にあった。
本 ADR はその判断を決定記録として独立させ、候補と却下理由を明示するものである。

ここには判断が二つあり、決めた時点も決めた文書も別である。混同すると却下理由が
どちらに掛かるか分からなくなるため、本 ADR は次のように扱う。

- **台帳ファイル記法の判断** … 台帳ファイルの記法を TOML とし、JSON を却下した
  doc-3 §2.2 の既存判断。理由は、手編集しやすいこと、Rust（serde）で素直に読み書き
  できること、配列テーブルで台帳エントリの並びを表せることである。本 ADR はこれを
  **前提として動かさない**。
- **台帳読み書き crate の判断** … その記法を型付きで読み書きするために採る crate を
  決める判断。本 ADR が記録するのはこちらである。

TASK-26 の採用時に俎上へ載ったのは `toml` crate だけであり、crate 単位の比較記録は
残っていない。したがって本 ADR の候補比較は **ADR 執筆時に比較した候補**（ADR 執筆時に
比較した候補とは、採用時の検討には無く、本 ADR を書く時点で初めて比較して却下した
選択肢を指す）である。過去に比較したかのようには書かない。

評価軸は次の三つとした。

- serde と組み合わせて台帳の型（`Ledger` / `ProjectEntry`）へ直接 (de)serialize
  できるか。doc-3 §2.2 の記法選定理由がこれを前提にしている。
- doc-3 §3.3 の `status_aliases` サブテーブルと、`[[project]]` 配列テーブルの
  並び順を扱えるか。
- 依存として過不足がないか（AGENTS「Dependencies」の依存最小方針）。

## Decision

台帳ファイルの (de)serialize に **`toml` 0.8**（MIT OR Apache-2.0）を採用する。
導入範囲は `projects.toml` の読み書きに限定し、他の用途へは広げない。

### 採用理由

- `serde` の derive とそのまま噛み合い、`Ledger` / `ProjectEntry` の型定義だけで
  読み書きが済む。doc-3 §2.2 が TOML を選んだ理由（Rust で素直に読み書きできる）を
  そのまま実現する経路である。
- 配列テーブル `[[project]]` の並び順が Vec の順序として保たれ、doc-3 §2.2 の
  「`projects` の順が既定の表示順」をデータ構造の側で満たす。
- サブテーブル（`status_aliases`）を `BTreeMap` として素直に扱える。
- 台帳は Atlas 自身の設定ファイルであり、対象プロジェクトの管理ファイルではない。
  Backlog CLI への委譲対象（decision-2）ではないため、Atlas が直接書いてよい唯一の
  ファイルであり、書き込み経路を持つ crate が必要になる。

### 却下した候補と却下理由

| 候補 | 却下理由 |
|---|---|
| `toml_edit` | 既存の書式とコメントを保ったまま部分更新できる。台帳は doc-3 §2.2 が手編集しやすさを選定理由に挙げているため利点はあるが、`toml` 0.8 は内部でこれを使っており、serde 経由の型付き読み書きという本用途では上位 API で足りる。直接依存すると台帳の全項目を文書ツリー経由で扱う実装になり、型定義だけで済む現状より記述が増える。将来、利用者のコメントを保存する要件が出たら再検討する。 |
| `basic-toml` | 依存はより小さいが、機能を deserialize 中心に絞った実装であり、台帳の保存（serialize）と、doc-3 §3.3 のサブテーブルを含む往復に必要なものが揃わない。台帳は読むだけでなく register / remove / update で書き戻すため、これだけでは足りない。 |
| `serde_json`（記法ごと JSON へ） | doc-3 §2.2 が既に JSON を却下している（手編集容易性で TOML を採る）。ここで crate の都合から記法を JSON へ戻すのは、設計文書の判断を実装の都合で覆すことになる。台帳ファイル記法の判断は本 ADR の前提であり、動かさない。 |
| 自前の TOML パーサ | 台帳は利用者が手編集しうるファイルであり、記法の網羅と往復の正しさを自前で担保する費用が、依存 1 本の費用を明らかに上回る。 |

## Consequences

- 望ましい帰結
  - 台帳の読み書きが型定義だけで済み、`ledger.rs` に記法の詳細が漏れない。
  - `[[project]]` の並び順が表示順としてそのまま使え、並び替え（doc-3 §4.3）が
    Vec の操作で表現できる。
- 費用・制約
  - 書き戻しの際、利用者が手で入れたコメントと書式は保存されない。台帳を手編集する
    運用では、Atlas 側の保存でコメントが失われる。これを問題とする要件が出たら
    `toml_edit` への切り替えを検討する。
  - 本番依存が 1 本増える。導入範囲を台帳ファイルに限定することで影響を閉じている。
- 後続への影響
  - 台帳の互換性（`schema_version` の未知上位版を read_only へ縮退させる扱い、
    doc-3 §2.2）は crate ではなく `ledger.rs` 側の責務であり、本決定では変わらない。
  - Backlog 管理ファイル側の frontmatter 解析は記法が YAML であり、別の依存判断に
    なる（decision-10）。
