# 同一 Backlog ルート更新時の競合検出と再読み込み 設計

TASK-14 の設計。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は decision-2（読み取りは Backlog 管理ファイルの直接解析、更新は Backlog CLI へ委譲）・doc-4（読み取り層・ドメインモデル・再構築単位）・doc-5（更新アダプター・再読込契機）。

**実測基準版**: 本書が「実測」と述べる記述は Backlog CLI v1.50.1 で確かめたものである（decision-7 の最低バージョン要件、decision-27）。個々の記述は版を名乗らない — 名乗るのは、2 つ以上の版の違いそのものを述べる版差記録だけである。最低バージョン要件が上がったら、本行の版と本書の実測記述を併せて測り直す。

## 1. 用語

- **外部変更** … 当該 Atlas の更新アダプター操作の外で、別ウィンドウ・別プロセス・他の backlog 操作が Backlog ルートの管理ファイルを書き換える事象。
- **ファイル監視** … Backlog ルートのファイル変化を OS の変更通知で継続監視する手段。
- **読取版指標** … 読み取り層が最後に読んだ時点のファイルの版（更新時刻・サイズ・内容ハッシュ等）を記録した値。
- **バージョン不整合** … 読取版指標と現ファイルの版が一致しない状態。**旧称は「版ずれ」で、decision-22 が改称した**（指す状態は変えていない）。画面では専用のチップを持たず、そのタスクの不整合（decision-22）の理由行の 1 種として出る。
- **更新前競合** … 更新アダプター実行直前に、対象の読取版指標が現ファイルと一致しない（読取後に外部変更があった）事象。
- **期待版付き更新** … 更新要求に「Atlas が読んだ版」を添え、実ファイルがその版のときだけ適用し、違えば拒否する更新方式（CAS 相当）。照合と更新を不可分化しうる手段。
- **共有ロック** … Atlas と Backlog CLI が共有し、照合から書込み完了までを他プロセスの書込みから守る排他機構。
- **照合後競合窓** … 実行前照合の完了から、Backlog CLI が対象ファイルの書込みを完了するまでの時間帯。この間に入った外部更新は実行前照合では検出できない（4 章）。
- **情報喪失条件** … 照合後競合窓に外部更新が入り、CLI の read-modify-write による書戻しでその外部更新が上書き・消失する条件（4 章に列挙）。
- **書き換え対象集合** … 1 回の更新操作が書き換えるファイルの全体。`task edit` なら当該タスクの 1 ファイル、参照追随書き換えを伴うマイルストーン操作ならマイルストーンのファイルと参照するタスクファイル群を併せた集合になる。
- **参照追随書き換え** … マイルストーン操作が、対象マイルストーンのファイルだけでなく、それを参照するタスクファイル群も併せて書き換える事象（4.2 章）。
- **照合不能** … 書き換え対象集合の照合方法を本設計が定義しておらず、更新前競合検出を適用できない更新操作の状態（4.2 章）。
- **参照タスク集合** … 読み取り時点のドメインモデルで保存区分がアクティブなタスクのうち、frontmatter `milestone` の値が対象マイルストーンの id または title と、前後空白・大文字小文字を無視して一致するものの全体（4.2 章）。
- **走査範囲の同一性** … アクティブなタスクのディレクトリに現在ある各ファイルが、当該モデルを作った読み取りが読んだファイルであり、かつその版が読取版指標と一致している状態（4.2 章）。
- **未読タスクファイル** … アクティブなタスクのディレクトリに在るのに、当該モデルを作った読み取りが読んでおらず読取版指標を持たないファイル（4.2 章）。走査範囲の同一性が破れる 2 通りのうちの一方で、もう一方は既存ファイルのバージョン不整合である。
- **全件一致** … 書き換え対象集合の全要素の版が記録済み読取版指標と一致している状態を、更新実行の条件として求めること（4.2 章）。

## 2. 背景と課題

読み取りはファイル解析、更新は Backlog CLI 経由で経路が分かれる（decision-2）。同じ Backlog ルートを、別ウィンドウの Atlas・別プロセス・素の `backlog` コマンドが更新しうる。この結果、Atlas のドメインモデルは「最後に読んだ時点のファイル内容」の写しであり、その後の外部変更でファイルとずれる。ずれたまま更新アダプターを走らせると、利用者が画面で見ていた内容と実ファイルが食い違った上での更新になる。本設計は、(a) 外部変更をいつ検出するか、(b) 更新の前後で整合をどう確認するか、(c) 検出した競合をどう提示するかを定める。

## 3. 外部変更の検出契機

二つの契機を併用する。

- **ファイル監視（継続検出）**: 各 Backlog ルートの管理ファイル群（tasks / archive / completed / drafts / milestones / docs / decisions と config.yml）をファイル監視で購読し、作成・更新・削除・リネームの通知を受ける。通知を受けたら、そのルートを読み取り層の再構築単位（doc-4）で読み直す。
  - **再構築単位はルートである**（decision-42）。**通知が変化したファイルを挙げられたか、挙げられずルート全体を指すかは、読み直す範囲を変えない** — 2 つの違いは監視が何を言えたかであって、何を読み直すかではない。**初版は「変化したファイル（不能ならルート）」と書いてファイル単位を既定に置いていた**が、実装は初めからルート単位の 1 経路しか持たず、TASK-94 の規模計測がルート全体の読み直しで足りることを実測した。ファイル単位へ戻す条件は decision-42 の再開条件が数値で持つ。
  - 通知は連続・重複しやすいため、短い時間窓で束ねて（デバウンス）から読み直し、1 操作の複数ファイル書き換えを 1 回の再構築にまとめる。
  - 監視は読み取り専用の観測であり、ファイルを書き換えない。
- **更新後の再読込（能動検出）**: 更新アダプターの CLI 成功後は、ファイル監視の通知を待たず、再読込契機（doc-5）で対象を即読み直す。監視の取りこぼしや遅延に依存せず、自分の更新結果を確実に反映するためである。

両契機は同じ読み直し経路に載る（doc-5 の 6 章）。CLI 由来の変化も外部由来の変化も、読み取り層の同一の再構築として扱う。

### 3.1 継続検出の可否（アプリ設定）

継続検出を使うか否かは、アプリ設定（decision-13）で選べる。

- **継続検出を切った場合の見え方は、監視が動かなかった場合と同じ「継続検出停止」とする**。利用者が自分で切ったのか監視が失敗したのかで表示を変えない。どちらであっても「外部変更が画面へ届かない」という、カードの鮮度についての事実は同一だからである。理由の違いは帯の文面で述べ、状態の名前と印は分けない。
- 継続検出を切っても、更新後の再読込（能動検出）と手動の再読込は働く。自分の更新結果が反映されなくなることはない。
- 継続検出を切っている間の外部エディタ経路の扱いは doc-8 §7。

### 3.2 起動時の読み取りは選択にしない

**起動時に全ルートを読むことは必須であり、アプリ設定の項目にしない。** 画面設計案 01 の設定モーダルは「起動時に全ルートを読み直す」を選択肢として置いているが、Atlas が採る構成ではこれを切った状態に指示対象が無い。

- 再起動をまたいで残る記録は台帳ファイルとアプリ設定ファイルの 2 つだけで（doc-3 §2.1、decision-13）、ドメインモデルと読取版指標はプロセス内にしか存在しない。
- したがって起動直後の Atlas は、全ルートを読むまでカードを 1 枚も描けず、最初の更新前競合検出（4 章）に使う基準も持たない。「読み直さない」を選べる形にすると、表示も照合も成立しない状態を利用者が選べてしまう。
- 起動時の読み取りを任意にできるのは、ドメインモデルを永続化するキャッシュを持ち、その無効化・版指標・縮退を定めた場合に限る。本設計はそれを持たない。持つと決めるなら、キャッシュの契約を本書へ足したうえで設定項目を戻す。

## 4. 読取版指標と更新前後の整合確認

外部変更の有無を判定するため、読み取り層はファイルを読むたびに読取版指標を記録する。判定は「読取版指標 ≠ 現ファイルの版」で行う。版指標は更新時刻・サイズを一次判定に、必要時は内容ハッシュで確定する（時刻粒度の粗さやmtime巻き戻しに備える）。

更新アダプター実行の前後で次を確認する。

1. **実行前（更新前競合の検出）**: 更新操作の書き換え対象集合について、記録済み読取版指標と現ファイルの版を照合する。一致すれば、画面が見ている内容と実ファイルが同じとみなし、更新へ進む。不一致なら更新前競合とし、CLI を起動せずに競合を利用者へ提示する（5 章）。書き換え対象集合が 1 ファイルに収まらない操作（参照追随書き換え）は 4.2 章で別に扱う。
   - 照合は「利用者が編集入力を確定した時点で見ていた版」を基準にする。編集ダイアログを開いてから確定するまでの間の外部変更も、この照合で捕まえる。
2. **実行**: 競合が無ければ更新アダプターを実行する（doc-5）。作業ディレクトリ固定・引数配列渡し・CLI 失敗時の扱いは doc-5 に従う。**直接書き込み操作**（doc-5 §1、decision-21。現在の実例はマイルストーン説明の更新 1 件）もこの位置で実行する — 実行するのが CLI プロセスか Atlas 自身の書き込みかによらず、1 の照合を通ってからでなければ実行しない。上の 1 が「CLI を起動せずに」と述べているのは、当時の実行が CLI しか無かったためであり、規則は「照合が通らなければ実行しない」である。
3. **実行後（再読込と再取得）**: CLI 成功後、再読込契機で対象を読み直し、ドメインモデルと読取版指標を更新する。これにより、自分の更新に続く他者の外部変更があっても、次の操作の実行前照合が新しい版を基準にできる。

Atlas は CLI をまたぐロック機構を持たない。正本と更新権は Backlog CLI 側にあり、Atlas は「読んだ版と実ファイルの一致を更新直前に確かめ、ずれていれば止める」楽観的検出に徹する。これは decision-2 の読み書き経路分離と整合する。

### 4.1 CLI の同時更新支援と best-effort の明示

実行前照合（1）と CLI 実行（2）は別プロセスの別操作であり、Atlas 単独では不可分にできない。不可分化には、Backlog CLI 側の**期待版付き更新**か、Atlas と CLI が共有できる**共有ロック**が要る。

- **CLI 支援の可否（確認結果）**: 動作確認版の backlog CLI の `task edit` には、期待版付き更新（`--if-match`／版指定）も共有ロックも、`--force` の類も無い（`task edit --help` で確認）。更新はサブコマンドが対象ファイルを自ら読み直して書き戻す read-modify-write であり、Atlas が読んだ版を条件に付けて適用可否を委ねる手段は無い。したがって「実行前照合 → CLI 更新」を CLI 経由で不可分化できない。
- **best-effort と明記**: 以上より、Atlas の更新前競合検出は不可分性の**保証ではなく best-effort**である。実行前照合の時点までに入った外部変更は捕まえるが、照合の完了後に入る外部変更は捕まえられない。この限界を設計上の保証水準として明記する。
- **照合後競合窓と情報喪失条件**: 照合の完了から CLI の書込み完了までが**照合後競合窓**であり、次が揃うと情報喪失が起こる。
  1. Atlas が実行前照合で一致を確認し、CLI 更新へ進む。
  2. その照合の完了後～当該 CLI 更新の書込み完了までに、**同一タスクファイル**へ外部更新が入る。
  3. CLI の更新がそのファイルを read-modify-write で書き戻し、窓内の外部更新分を上書きする。
  → 窓内に入った外部更新の内容が失われる。喪失は同一タスクファイルへの窓内外部更新に限られ、別ファイルへの外部更新には及ばない。窓は通常ごく短いが、ゼロにはできない（ロック／期待版が無いため）。**直接書き込み操作（doc-5 §1、decision-21）でも窓は閉じない。** 別プロセスの起動を挟まないぶん短くはなるが、照合と `rename` の間に入った外部変更は同じく捕まえられず、上書きされる。窓が短くなることを保証水準として掲げない — 掲げられるのは best-effort であることのままである。
- **喪失後の観測可能性**: CLI 成功後の再読込（3）は、書き戻された最新版を読み直して以後の照合基準にする。ただし上書きで消えた外部更新は既にファイルから消えており、再読込では復元できない。再読込は「その後の版を正す」ことはできるが、「窓内で消えた内容を取り戻す」ことはできない。
- **将来 CLI が支援した場合**: 期待版付き更新を持つ CLI 版が動作確認範囲に入れば、実行前照合をその期待版指定へ移し、照合後競合窓を CLI 側で閉じる（7 章）。本設計は best-effort を現時点の保証水準として固定するにとどめる。

### 4.2 参照追随書き換えの照合

書き換え対象集合が 1 ファイルに収まらない操作がある。**参照追随書き換え**とは、マイルストーン操作が、対象マイルストーンのファイルだけでなく、それを参照するタスクファイル群も併せて書き換える事象を指す。この場合、書き換え対象集合はマイルストーンのファイル 1 件では終わらず、参照するタスク数に応じて増える。集合の大きさは操作の引数からは決まらず、読み取り時点のドメインモデルに依存する。本節は、この集合をどう決めるか（4.2.2）と、どの条件で実行を許すか（4.2.3）を定める。

#### 4.2.1 CLI が実際に書き換えるファイル（実測）

規則の土台を CLI のヘルプ文面ではなく実測に置く。2026-07-31、使い捨ての Backlog ルート（マイルストーン 1 件を、id で参照するアクティブタスク・title で参照するアクティブタスク・draft・completed・archive のタスクが参照する構成）で各操作を実行し、mtime・サイズ・内容ハッシュで変化したファイルを確認した。

| 操作 | 書き換わったファイル |
|---|---|
| `milestone rename <from> <to>` | マイルストーンのファイル（内容とファイル名の双方）。加えて `tasks/` のタスクのうち、frontmatter `milestone` の値が id と異なる参照を持つもの |
| `milestone rename <from> <to> --no-update-tasks` | マイルストーンのファイルのみ |
| `milestone remove <name> --task-handling clear` | マイルストーンのファイル（`archive/milestones/` へ移動）と、`tasks/` の参照タスク（`milestone` 値を除去） |
| `milestone remove <name> --task-handling keep` | マイルストーンのファイルのみ（移動） |
| `milestone remove <name> --task-handling reassign --reassign-to <milestone>` | マイルストーンのファイル（移動）と、`tasks/` の参照タスク（`milestone` 値を付け替え） |
| `milestone archive <name>` | マイルストーンのファイルのみ（移動） |

設計に効く事実が 3 つ出る。

- **参照の照合は id・title のどちらも、前後空白と大文字小文字を無視して行われる**。`  phase FOUR  ` を持つタスクが title `Phase Four` の改称で書き換わり、`"  M-0  "` を持つタスクも id `m-0` の改称で書き換わった（後者は本設計の初版が id を完全一致で照合していたため、PR #31 のレビュー指摘を受けて追試した）。内部の空白の差異（`Tar get`）では一致しない。読み取り層の参照解決（doc-4 §3.2）は id の完全一致だけなので、両者の指す範囲は一致しない。
- **書き換えはアクティブなタスクに限られる**。`drafts/`・`completed/`・`archive/tasks/` のタスクは、同じ値を持っていてもどの操作でも書き換わらない。
- **rename はマイルストーンの id を変えない**。タスクが id を値に持つ限り書き換えるものが無く、CLI は「更新した」と報告してもそのファイルは変わらない。実際に書き換わるのは、値が id と異なる参照を持つタスクだけである。

#### 4.2.2 書き換え対象集合の決定規則

書き換え対象集合は、読み取り時点のドメインモデルと操作の引数から次のように決める。

- **マイルストーンのファイル**（読み取り層が保持するそのファイルのパス）は、6 操作すべてで集合に入る。
- **参照タスク集合**とは、読み取り時点のドメインモデルで保存区分がアクティブなタスクのうち、frontmatter `milestone` の値が対象マイルストーンの id または title と、前後空白・大文字小文字を無視して一致するものの全体を指す。これを集合へ加えるのは、参照追随書き換えを伴う 3 操作（`rename`（`--no-update-tasks` なし）・`remove --task-handling clear`・`remove --task-handling reassign`）に限る。
- 残る 3 操作（`rename --no-update-tasks`・`remove --task-handling keep`・`archive`）の集合はマイルストーンのファイル 1 件で終わり、4 章の 1 対 1 照合がそのまま使える。
- **照合は CLI と同じ緩さで行う**。読み取り層の参照解決（id の完全一致）に合わせると、title を値に持つタスクも、id を前後空白付き・大文字で書いたタスクも集合から漏れ、CLI はそれらを書き換える（4.2.1）。集合は CLI が書き換えうる範囲を覆う必要があり、読み取り層の解決範囲と一致させる必要はない。
- **CLI が実際には書き換えないファイルも集合に含める**。値が既に id と一致するタスクは書き換わらない（4.2.1）が、書き換えを省くこの条件は CLI の内部の挙動であって契約ではない。集合をそこまで狭めると、挙動の変わった版で未照合の書き換えが起きる。集合は CLI が書き換えうるファイルの上界として決める。

#### 4.2.3 照合の合否規則

**全件一致**とは、書き換え対象集合の全要素の版が記録済み読取版指標と一致している状態を、更新実行の条件として求めることを指す。参照追随書き換えの合否は次で判定する。

1. 集合の各要素について、4 章の照合（サイズと、必要時の内容ハッシュ）を行う。**1 件でも不一致なら CLI を起動せず、更新前競合として拒否する**（全件一致）。バージョン不整合のタスクだけを除いて実行する選択肢は取らない。CLI には対象を絞る引数が無く、Atlas が集合を分割して発行することもできないため、「一部を除いた実行」に対応する CLI 呼び出しが存在しないからである。
2. 参照追随書き換えを伴う 3 操作では、さらに**走査範囲の同一性**を求める。アクティブなタスクのディレクトリを走査し、(i) **未読タスクファイル**が 1 件も無いこと、(ii) そこにある各ファイルの版が読取版指標と一致することを確かめる。どちらが破れても、集合そのものが読取時点と違いうるため、更新前競合として拒否する。
   - この条件を置く理由は、参照タスク集合がモデルの**内容**に依存することである。集合の要素だけを照合しても、集合の外にあったタスクが集合に入る変化は捕まらない。読み取り後に作られたタスクが対象マイルストーンを参照する場合（未読タスクファイル）と、読み取り時点では参照していなかった既存タスクが外部編集で参照するようになった場合（既存ファイルのバージョン不整合）の 2 通りがあり、いずれも CLI は書き換えるのに Atlas の集合には入らない。利用者は「どのタスクが書き換わるか」を見て実行を決めており、実際に書き換わる集合がそれと違えば、決めた内容と起きることが食い違う。
   - 走査範囲全体を照合するため、対象マイルストーンと無関係なタスクの新規作成・編集でも拒否になる（偽の競合）。参照の有無は当のファイルの現在の内容が決めるので、「関係あるものだけを照合する」には結局その内容を読む必要があり、読めば版が一致するかどうかは分かってしまう。これは 4 章が既に採っている倒し方（確かめられないなら実行せず再読込を促す）と同じで、利用者は再読込 1 回で先へ進める。
   - 1 対 1 照合の操作にこの条件が要らないのは、そちらの対象が引数だけで決まり、モデルの内容に依存しないためである。
3. 拒否したときは、不一致だったファイルと未読タスクファイルを**すべて**挙げる（提示は 5 章）。1 件目で打ち切ると、利用者は再読込のたびに次の 1 件を知ることになり、何を読み直せば済むのかが最後まで分からない。

この規則をもってしても、4.1 章の照合後競合窓は閉じない。集合の各要素についても、走査範囲の同一性についても、照合の完了後に入る外部変更は捕まえられない。保証水準は 4.1 章のまま best-effort である。

#### 4.2.4 照合不能の位置づけ

**照合不能**とは、書き換え対象集合の照合方法を本設計が定義しておらず、更新前競合検出を適用できない更新操作の状態を指す。4.2.2・4.2.3 により、**現行の更新操作に照合不能なものは無い**。この語は、照合方法を本設計が持たない操作が将来現れたときのために残る契約である。

照合不能な更新操作は、**照合を省いて実行せず、CLI を起動せず拒否する**。理由は 4.1 章の保証水準と一貫させるためである。照合を省いて実行すれば、読取後の外部変更を検出する機会が一度も無いまま CLI の read-modify-write が走り、防げる競合（5 章）に数えていた範囲の上書き喪失を、best-effort の限界の外側で起こしうる。拒否は情報を失わない側の選択であり、利用者は対象を読み直してから操作を選び直せる。

なお、新規作成（`task create`・`doc create`・`milestone add`）は照合不能ではない。Atlas がまだ読んでいないファイルを作る操作であり、照合すべき読取版指標が存在しないため、照合を経ずに実行してよい。照合不能は「照合すべき対象があるのに方法が無い」状態を指し、「照合すべき対象が無い」状態とは区別する。

## 5. 競合の利用者提示

- **更新前競合の提示**: 更新を自動では強行しない。対象タスクが読取後に外部で変わったことを示し、少なくとも次を提示する。
  - 破棄せず、外部変更後の現内容を読み直して画面へ反映する（不整合表示ではなく通常の再読込）。
  - 利用者の選択肢として、(i) 再読込した最新内容を見てから編集をやり直す、(ii) 自分の入力内容を保持したまま最新に対して再適用を試みる、を提示する。どちらも「最新の版に対する新しい更新操作」に帰着させ、古い版に対する上書きは行わない。
  - 参照追随書き換え（4.2）では対象が複数ファイルになるため、版がずれたファイルと未読タスクファイルをすべて挙げる。1 件だけを挙げると、再読込のたびに次の 1 件が現れる提示になる。
- **継続検出時の提示**: 編集中でない通常閲覧中に外部変更を検出したら、スイムレーン・詳細（doc-7・doc-8）の該当箇所を再読込で静かに更新する。利用者の編集入力を巻き込む破壊はしない。編集中のタスクに外部変更が来た場合は、確定時の更新前競合検出で捕まえる（4 章）ため、編集の途中で入力を奪わない。
- **提示の一貫性**: 競合・再読込の提示は、doc-4 が定める読み取り由来の記録（判別できなかった項目・参照欠損）とは区別して**書く**。競合は「正しく読めるが版がずれた」事象であり、解析不能とは違うことが起きているためである。**ただし画面の印は分けない**（decision-22、2026-08-06）— タスク 1 件について利用者が判断するのは「この表示をそのまま信じてよいか」の 1 点で、そこでは両者が同じことを述べる。両者は不整合として 1 つの ⚠️ に束ね、区別は不整合区画の理由行が担う。本項が求める区別は、**理由行の書き分け**として残る。
- **照合不能の提示**: 照合不能（4.2.4）による拒否は、更新前競合の提示とは別に扱う。現行の操作には該当が無くなったが、規則を持たない操作が現れたときの提示としてこの区別を残す。更新前競合は「版がずれていることを検出した」事象であるが、照合不能は「版がずれているかを確かめる方法が本設計に無い」状態であり、版がずれているとは限らない。当該操作が現時点では提供されないことと、その理由がバージョン不整合の検出ではなく照合手段の不在であることを示し、利用者が「競合が起きた」と誤解しないようにする。照合を省いた実行を代替経路として案内しない（4.2 の拒否の理由がそのまま失われるため）。
- **情報喪失条件と提示の関係（best-effort の限界）**: 提示は 2 段に分かれる（4.1）。
  - **防げる競合（実行前照合で捕捉）**: 照合の時点までに入った外部変更は更新前競合として捕まえ、CLI を起動せずに提示する（上記）。この範囲では上書き喪失は起こさない。競合提示はこの範囲を主対象とする。
  - **防げない喪失（照合後競合窓）**: 照合の完了後に入る外部変更は実行前照合では捕まえられず、情報喪失条件（4.1）が揃えば窓内の外部更新が上書きで失われる。best-effort の限界としてこれを設計に残す。CLI 成功後の再読込で版が想定外に進んでいたことを事後に検出できる範囲では、事後の競合として提示するが、上書きで消えた内容は提示できても復元できない。提示は「防げる競合の未然提示」と「防げない窓の事後通知」を、利用者が保証水準を誤解しないよう区別して出す。

## 6. スイムレーン・詳細との関係

- スイムレーン（doc-7）: 外部変更の再読込でカードの内容・配置を更新する。カード位置は doc-7 の安定並びに従い、更新のたびに飛ばないようにする。
- タスク詳細（doc-8）: 表示中タスクに外部変更が来たら再読込で内容を更新し、編集確定時は更新前競合検出を通す（doc-8 の編集は doc-5 経由）。

## 7. 後続への影響

- 本設計はファイル監視・楽観的競合検出の枠組みを与える。監視の実装手段（Rust のファイル監視 crate 等）は実装時に、決め打ちの新規本番依存を入れる前に選定理由を確認する（AGENTS）。
- 不在・読取不能・該当なしの表示区別は TASK-13。競合（バージョン不整合）はそれらと別事象として扱う。**同じタスクの読み取り由来の記録とは、decision-22 が 1 つの印へ束ねた**（TASK-77）。
- 参照追随書き換えを伴うマイルストーン操作の照合規則は 4.2 で定めた（TASK-45）。決定規則は参照タスク集合、合否規則は全件一致と走査範囲の同一性である。操作写像（doc-5）は変更しておらず、拡張は本設計の実行前照合に閉じた。読み取り層はマイルストーンのファイルのパスを保持する必要がある（1 対 1 照合の 3 操作がそれを対象にするため）。
- 4.2.1 の実測は v1.47.1 で行い、2026-08-01 に v1.48.0 で、2026-08-22 に v1.50.1 で測り直した（TASK-58・TASK-153）。決定規則が依存する 3 点——参照の照合の緩さ（id・title とも前後空白・大文字小文字を無視）・書き換えがアクティブなタスクに限られること・rename が id を変えないこと——はいずれも変わっていない。**v1.50.1 での測り直しは、id で・title で・前後空白と大文字小文字を違えた title で参照する 3 件のアクティブタスクと、draft・completed・archive に置いた 3 件を持つルートで行った** — `rename` が書き換えたのはアクティブの 2 件（title で参照していたもの）だけで、id で参照していたアクティブ 1 件は既に id なので書き換わらず、draft・completed・archive の 3 件は元の値のまま残った。初版はこのうち 1 点目を id について取り違えていた。CLI 版が上がったら、同じ 3 点をまた測り直す。
- 本設計の保証水準は現行 CLI（期待版付き更新・共有ロック無し）での best-effort である（4.1）。将来版が期待版付き更新を提供したら、実行前照合をその期待版指定へ移して照合後競合窓を閉じ、保証水準を引き上げる余地がある。CLI 版が上がった際に操作写像（doc-5）とあわせて再検査する。
- **実 OS 通知が現に配送されるかは、本設計の外にある環境の性質である。** 監視の規則（管理ファイルの判別・デバウンス・ルート全体の読み直しへの倒し方）は環境を要さないテストが持ち、**配送そのものは明示実行の 1 本が測る（decision-43）。** **その 1 本が緑であることは「届いた」を述べ、ルート全体の読み直しへ倒れたことは述べない** — 2 つを 1 つの緑にまとめると、緑がどちらを述べたのか読めなくなる。
