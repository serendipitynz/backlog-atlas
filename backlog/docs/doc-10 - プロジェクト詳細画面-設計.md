# プロジェクト詳細画面 設計

画面設計案の反映として書いた設計（実装は TASK-55）。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は doc-3（台帳・台帳エントリ・status 別名表）・doc-5（Backlog 更新アダプターの操作写像）・doc-9（更新前競合検出・照合不能）・decision-13（アプリ設定は台帳と別ファイル）。画面設計案（doc-1 追補で定義。07）を反映する。引用する事実は doc-12 §8 に転記してある。

## 1. 用語

- **プロジェクト詳細画面** … 1 プロジェクトについて、台帳エントリの編集・登録解除・文書の作成と更新・マイルストーン作成・詳細な新規タスク作成を扱う画面を指す。
- **区画切替** … プロジェクト詳細画面の左側に置く 4 項目（概要・文書・マイルストーン・新規タスク）の選択。画面遷移ではなく、同一画面内の表示切替である。
- **区画ナビ** … 区画切替を収める画面左端の幅 12rem の列を指す（画面設計案 07、doc-12 §8）。区画切替が選択という操作であるのに対し、区画ナビはそれを置く場所で、4 区画すべてが同じ 1 本を共有する。幅の値は content box を名指す（TASK-115 の規約。padding・枠は外側に付く）。
- **一覧列** … 区画の中で、選ぶ対象のカードを縦に並べ、選択を保持する幅 16rem の列を指す。文書区画では文書一覧（§5）、マイルストーン区画ではマイルストーン一覧（§6）がこれにあたる。区画ナビと同じく幅の値は content box を名指す。2 区画が同じ形の列を持つのは偶然ではない — どちらも「対象を選び、選んだ対象に対して操作する」区画で、右の列がその選択で差し替わる（§5・§6）。
- **一覧見出し行** … 一覧列の先頭に置き、並んでいるカードの件数の見出しと、その一覧へ 1 件足す**作成の入口**とを 1 行に並べる領域を指す（TASK-117）。一覧のスクローラの外にあり、一覧をどこまでスクロールしても読める。件数は §5・§6 のとおり**並んでいるカードの数**であって、写せなかったファイルを含めない。
- **作成の入口** … 一覧見出し行に置き、押下でその一覧に対応する**作成モーダル**を上げる操作を指す。それ自身は何も発行しない。**契約の語はこちらで、画面に出る文言は区画ごとに違う**（文書は「新規文書」、マイルストーンは「新規マイルストーン」）— 文言を契約の語にすると、同じ形の操作を 2 区画にわたって指せない。
- **作成モーダル** … 作成フォームだけを載せた被せ層（doc-7 §2.1）を指し、閉じるは doc-11 §7 に従う。**一覧列を持つ 2 区画とも同じ型を使う**（TASK-117。2026-08-05 の目視フィードバック由来）— どちらも「対象を選び、選んだ対象に対して操作する」区画（前項）で、そこへ対象を足す入口が 2 通りあると、利用者は区画ごとに足し方を覚え直すことになる。**「同じ型」には欄の積み方が入る — 2026-08-11 に明記した**（TASK-141。2026-08-07 の目視フィードバック由来）: **欄は 1 欄ずつ縦に積む。**本項は明記まで、入口・層の種別・発行しても層を閉じないこと・下部操作行を持たないことを覆っていて欄の積み方を覆っておらず、文書側が title・type・path を横 1 行に、マイルストーン側が名称・説明を縦に並べていた。**覆っていなかったのは本項の欠落であって実装の逸脱ではない**が、本項が「同じ型」を求めた理由（区画ごとに足し方を覚え直させない）は入口と層だけでは満たされない — 同じ型の層が区画によって違う姿で開くなら、覚え直しはそこで起きる。**欄の順序は本項が覆わない**（何を受け取るかを定めるのは §5・§6 で、順序もそちらが決める）— 積み方と順序は同時に動かないので、1 語で束ねない。§6 が 3 カラム化で、decision-24 が写せなかったファイルの一覧で、それぞれ同じ判断をしている。**発行に成功しても層は閉じず、入力欄だけが空になる** — 作成は 1 件で終わるとは限らず（登録直後のプロジェクトへ文書をまとめて足す、マイルストーンを先に何本か切る）、閉じる形にすると入口 → 層 → 閉じるを件数ぶん繰り返すことになる。加えて閉じる形は `×` と「作成」を**下書きの行方の違う 2 つの出口**にし、doc-11 §7 が下部操作行を要求する条件に当たる。出口を 1 つに保てば、`×` を押したときに入力がどうなるかは破棄前確認が述べる（プロジェクト登録モーダルと同じ形。doc-11 §7）。**これは画面設計案 07 からの逸脱に数えない** — 07 の転記（doc-12 §8.3・§8.4）は作成が受け取る項目を挙げているだけで、それをどこに出すかを書いていない。書かれていないことから外れることはできないので、作成モーダルは逸脱の数を動かさない。**その数は 2026-08-08 に §5 の側で 1 件増え**（提供しない操作区画の撤去。TASK-123）、**2026-08-11 に §4 の側で 2 件増えた**（status 別名表の行の控え。TASK-139）ので、現在は §4 が 2 件・§5 が 3 件・§6 が 3 件（画面全体で 8 件）である — **本項が述べているのは「作成モーダルはここに数えない」であって、総数そのものではない。**
- **写せなかったファイルの一覧** … 一覧列の末尾に置き、写せなかったファイル（doc-4 §1）1 件を表示パスと失敗理由の 1 行として並べる領域を指す（decision-24）。**カードではない** — 選べず、右の列へ読み込まれない。id を持たないファイルは開く対象にも更新の宛先にもならないためで、カードと同じ見た目にすると押しても何も起きない領域が一覧に混ざる。**この領域は 0 件のとき出さない** — 見出しだけが残ると、読み手は写せなかったファイルがあると読んで中身を探すことになる。**2026-08-08 にこの理由を本項へ移した**（TASK-123）: それまでは「提供しない操作区画と同じ扱い」として §9 が持つその区画の理由を引いていたが、区画そのものが撤去され、規則を必要とする領域がここだけになった。

## 2. 位置づけ

本画面は、現行の台帳管理画面（TASK-39）とプロジェクト管理画面（TASK-40）を、**1 プロジェクト単位**へ組み替えたものである。両画面は「全プロジェクトの台帳」と「1 プロジェクトの文書・マイルストーン・新規タスク」という異なる粒度を並べており、利用者は同じプロジェクトを扱うのに 2 つの画面を行き来していた。本画面は粒度を 1 プロジェクトへ揃え、そのプロジェクトに対してできることを 1 箇所に集める。

- **入口**: スイムレーン（doc-7）のレーンヘッダ行にあるプロジェクト名、および行末の `›`。読取不能行（doc-7 §6）からも開ける（台帳エントリは読めるため、ルートの修正はここで行う）。
- **出口**: ヘッダの「← スイムレーン」と「このプロジェクトのレーンへ」。**後者は、そのプロジェクトの行が行非表示（doc-7 §5.1）のときは着地を行わず、スイムレーンへ戻るだけである**（2026-08-09 に明記。TASK-131）。**行を表示へ戻しはしない** — 表示・非表示を切り替える控えは doc-7 §2.1 のメニューのプロジェクト一覧だけが持つと定めた以上、この出口をその 2 つ目の書き手にしない。詳細画面はレーンヘッダ行からしか開けないので、この状態になるのは利用者がこの画面に居ながらメニューでその行を非表示にしたときだけであり、戻すのは数秒前の操作を黙って取り消すことになる。**控えを無効化もしない** — この出口の主たる仕事は詳細画面を降りることで、それは行が非表示でも果たされる。doc-7 §2.3 の一時的な強調が備えているのは、着地が何も動かさず復帰が「何も起きなかった」ように見える場合であり、こちらは画面がまるごと入れ替わるのでその場合に当たらない。果たされないのは着地だけである。
- **画面が書くもの**: 概要区画は台帳ファイルだけを書く（doc-3 §2.1）。文書・マイルストーン・新規タスクの各区画は Backlog 更新アダプター（doc-5）を通じて対象プロジェクトの管理ファイルを書く。Atlas 自身は管理対象 Markdown を書かない（doc-2）。
- **全プロジェクトに効く設定**（表示テーマ・カード情報量ほか）は本画面に置かない。アプリ設定（decision-13）として固定ヘッダの設定から開く（doc-7 §2.1）。

## 3. 画面の構成

| 区画 | 内容 | 書き込み先 |
|---|---|---|
| ヘッダ | プロジェクト名・slug・タスク／文書／マイルストーンの件数・スイムレーンへの往復 | 書かない |
| 台帳読取専用帯 | 台帳ファイルが読み取り専用へ縮退している旨と理由（doc-3 §2.2） | 書かない |
| CLI 縮退帯 | 対応 CLI を検出できないため作成・更新を発行できない旨（doc-5 §5） | 書かない |
| 概要 | 台帳エントリ（project_root・backlog_root・Git remote 有無属性）と remote 現在値、status 別名表、登録解除 | 台帳ファイル |
| 文書 | 文書一覧・作成・更新 | 管理ファイル（`doc create` / `doc update`） |
| マイルストーン | 一覧・選んだマイルストーンの操作・作成 | 管理ファイル（`milestone add` / `rename` / `remove` / `archive`） |
| 新規タスク | 詳細な新規タスク作成 | 管理ファイル（`task create`） |

2 本の帯は互いに独立である。台帳読取専用は Atlas が書く先の問題、CLI 縮退は Backlog CLI が使えない問題で、片方だけが立つことがある。台帳操作は CLI を使わないため、CLI 縮退でも概要区画は動く。逆に台帳が読み取り専用でも、文書・マイルストーン・新規タスクは発行できる。帯はこの独立を利用者に伝わる形で書き分ける。

## 4. 概要区画（台帳エントリ）

### 4.1 編集できる属性とできない属性

doc-3 §3 の属性のうち、本区画が編集できるのは `project_root`・`backlog_root`・`status_aliases` の 3 つである。**Git remote 有無属性はここに入らない**（2026-08-08 に TASK-124 で外した）。利用者が値を入力する属性ではなく、次項の再検出が判定して書き換えるものだからである。

- **slug は編集手段を提供しない**。slug は横断タスクID の左辺として全タスクの参照に使われ、変更は同一性を切る（doc-3 §3.1）。値の表示に添えて、変更するには登録を解除して登録し直すこと、そのとき履歴表示の同一性が切れることを述べる。押せない入力欄を置かない。
- **Git remote は現在値を出し、再検出は独立した操作にする**（TASK-124）。**remote 現在値**とは、概要区画がプロジェクトルートの Git から読み取った remote の URL と、その remote 名を指す。名を併記するのは、読むのは `origin`、無ければ設定されている先頭の 1 件と決めているためで、remote を複数持つリポジトリで URL だけを出すとそれが唯一の remote であるかのように読めるからである。**台帳へは保存しない読み取り値**であり、台帳が持つ Git remote 有無属性（doc-3 §3.2）とは別物である。読めなかった事象は decision-6 の書き分けに従い、**Git remote 不在**（リポジトリはあるが remote が構成されていない）・**Git 対象不在**（プロジェクトルートが Git リポジトリでない）・**読み取り失敗**を 1 つの空表示に丸めない。**対象不在に入れてよいのは Git 自身が「リポジトリではない」と答えた場合だけ**である — 所有者検査による拒否・権限や設定の異常・そもそも存在しないパスは、いずれも終了コードが同じでも「リポジトリではない」とは述べていないので読み取り失敗に入る。対象不在と告げると、利用者は remote ではなくプロジェクトルートの指定を直しに行くことになる。台帳の記録と現在値が食い違うときは、台帳が記録している側の値を状態文で述べる（doc-11 §8）。ただし読み取り失敗からは食い違いを言わない — 失敗は remote の有無について何も述べていないため、不在として扱えば観測していない事実を報告することになる。
- **再検出は押した時点で発行する**（TASK-124）。「再検出する」は保存とは別の控えで、押すと台帳エントリの Git remote 有無属性を書き換える。保存に載せないのは、保存が送るのが利用者の入力した値であるのに対し、再検出が書くのは Atlas がプロジェクトルートを見て決めた値だからで、利用者が保存まで持ち越す下書きが存在しない。したがってこの操作は次項の送信属性一覧にも現れない。台帳が読み取り専用のとき、および台帳への書き込みが実行中のときは実行できず、理由を添える（doc-11 §5）。
- **プロジェクトルートを変えたときは Backlog ルートも併せて送る**。既定は `<新ルート>/backlog` だが、送るのは欄に入っている値である。どちらを送るかを利用者が読み取れるよう、ルートを変えた時点でその旨を欄の直下に出す。移動が成立すると、そのプロジェクトについて開いている編集セッション（doc-8 §1）は閉じる。**「開いている編集セッション」は本項が数えず、doc-8 §1 の語が指すもの全部を指す** — 2026-08-07 まで実例は文書区画の 1 つだけだったが、§6 が編集セッションを持った時点で 2 つになり、実装は文書側しか閉じていなかった（PR #74 の 1R [P1]）。**ここに実例を書き並べないのは意図的で**、書き並べれば §6 が持った時点でこの項が偽になる（doc-11 §7 が被せ層の列挙で踏んだのと同じ形）。閉じるとき、その画面が旧ルートの読み取りに解決していた選択も一緒に落とす。
- **送る属性を明示する**: 変更した属性だけを送る。何を送るかを保存操作の直前に列挙し、変更が無いときは「変更なし」として保存を無効化する（無効化の表し方は doc-11 §5）。
- **本区画は発行の控えを 2 つ持つ**（台帳の保存と、次項の登録解除）。したがって発行の行は固定せず、どちらも自分の入力の直後に置く（doc-11 §11。下端の 1 行がどちらのものか決まらないため）。

### 4.2 status 別名表

status 別名表（doc-3 §3.3、decision-4）は「原文の status → 正準ステータス列」の表として編集する。1 行 = 原文の status 入力 + 正準 4 列からの選択。

各行には、その別名が実際に効くかどうかを添える。別名表は、対象プロジェクトが宣言している status に対してのみ効く（doc-3 §3.3）。宣言された集合にその status が無ければ、別名を書いてもそのタスクは未分類のままである。ただし `config.yml` が `statuses` を 1 つも宣言していないルートは別で、矛盾する宣言が無いため別名は効く（decision-4 が実測した未初期化ルート）。行ごとに次の 4 態を区別して示す。

- **宣言あり** … `config.yml` の `statuses` にある status。別名が効く。
- **draft 専用** … `config.yml` が宣言していないが、既知の draft 状態として扱う値（doc-4 §3.4）。別名が効く。
- **宣言集合なし** … `config.yml` が `statuses` を 1 つも宣言していないため、その status が宣言済みかを判定できない状態。矛盾する宣言が無いので別名は効く。
- **宣言なし → 効果なし** … 宣言された集合があり、そこに無い status。別名を書いてもタスクは未分類区画に残る。不整合の族の色で示し、書けてしまうが効かないことを見える状態にする。

**不整合の族の色を与えるのは 4 態目だけ**である。宣言集合なしでは別名が効くため、効かない別名と同じ印を付けると、直しようのないものを直せと言っていることになる。この 4 態は列対応規則の実装（`interpret::status` の `StatusDeclaration`）と 1 対 1 に対応する。

入力の検査は保存の前に行い、重複（大文字小文字・前後空白を同一と見なす）と、対応先が正準ステータス列でない行を拒否する。不正な別名を台帳から削除しない（doc-3 §3.3、TASK-42）。

**行の控えは画面設計案 07 から 2 点で意図的に外れる — 2026-08-11 に記録した**（TASK-139）。原文は行ごとの控えを「行を外す」「＋ 別名を追加」という**可視の文言**で持つ（doc-12 §8.2）。**2 点をここに併記するのは、原文の 2 つの控えのどちらがどう変わっているかを 1 か所で読めるようにするため**で、どちらも 2026-08-11 までどの doc も逸脱として書いていなかった。**行削除のほうは TASK-80 が 2026-08-09 に「文字グリフの `×` を図形へ揃える」と判定しているが、その判定は原文が文言だったことと突き合わされていない**（doc-11 §7 末項の預けは `×` の字形についてのものだった）。

- **行削除は文言を持たず、doc-11 §2.4 のアイコンのみのボタン（図形は lucide の `x`）にする — 本節での 1 件目（画面全体では 7 件目）。** 行は 原文 status の入力欄・正準列の選択・削除・効果表示が横 1 行に並び、正準列の選択は選択肢の語だけで 8 文字を取る。文言 4 文字ぶんの幅は、この行では真っ先に入力欄が失う幅である（doc-7 §2.3 のレーンヘッダ行が文言を落としたのと同じ理由）。**名前は `aria-label` がその行の 原文 status を含めて持つ** — 図形にすると可視の名前が消えるうえ、行が増えると同じ名前の控えが並ぶためである。**入力が空の行では行番号で呼ぶ**（まだ何も名乗っていない行を指す語が他に無い）。
- **「＋ 別名を追加」の `＋` は置かない — 本節での 2 件目（画面全体では 8 件目）。** この控えは管理ファイルへ何も書かず、編集中の表に空の行を 1 つ足すだけである。doc-10 §1 の 作成の入口 が `＋` の図形を持つのは発行の入口だからで（doc-11 §2.4 の 可視の文言を持つ控えの中のアイコン）、同じ印をここへ置くと、押すと何かが作られる控えに見える。**原文がこの 2 つを同じ `＋` で描いているのは、原文が発行するかどうかで控えを描き分けていないためである。**

### 4.3 登録解除

登録解除は台帳エントリを 1 件削除し、スイムレーンからレーンを 1 本外す。プロジェクト側のファイル（`backlog/` 以下のタスク・文書）は削除しない。

- 危険区画として他の操作と区画を分け、削除しないもの（プロジェクトのファイル）を明記する。
- 確認は slug の入力一致とする。一致するまで実行を無効化し、無効の理由を添える（doc-11 §5）。
- 台帳が読み取り専用のときは実行できない。理由は帯と操作の双方に出す。

## 5. 文書区画

- **配置は 3 カラム**（画面設計案 07、doc-12 §8.3）: 区画ナビ（12rem、§1）・文書一覧（16rem）・文書ペイン。文書一覧とは、頭に「文書 N 件」の見出しを持ち、文書ごとのカードを縦に並べる 16rem の列 — すなわち本区画の一覧列（§1）を指す。カードとは、文書一覧に 1 文書ぶんとして並ぶ押せる領域を指し、ID・type・title・タグ・未保存の印を持つ — 領域全体が選択の操作で、別の編集ボタンを持たず、選択中のカードは強調して示す（どの文書を開いているかは一覧から読めること。2026-08-05 の目視指摘）。**文書ペイン**とは、文書一覧の右で残り幅を取る列を指し、文書を選んでいない間は次項の 1 行だけを、文書を選んでいる間は閲覧を、編集セッションが開いている間はその更新フォームだけを出す。**2026-08-07 に作成フォームがこの列から出た**（TASK-117。§1 の作成モーダルへ移った）ので、3 状態の 1 つ目にもう作成フォームは無い。「開いている編集の操作を作成フォームと混ぜない」（2026-08-05 の目視指摘）は、混ぜる相手が列から消えたことで満たされる — 退けた配置ではなく、その配置がもう作れないという状態になった。幅の値はいずれも content box を名指す（§1）。**2026-08-07 に編集ペインから改称した**（TASK-116）: 次項で選択が開くのは閲覧になり、この列が持つ 3 状態のうち編集は 1 つになったので、§6 が置いた「列の名はその列が開くもので決める」規則の下では編集ペインと呼べない。
- **選択は閲覧を開き、編集セッションを開かない — 2026-08-07 の改訂**（TASK-116。2026-08-05 の目視フィードバック由来）: 本節は 2026-08-07 まで「カードを押すことが選択で、選択が更新フォームを開く」と定めており、文書を 1 枚読むだけで編集セッション（doc-8 §1）が開いていた。**閲覧**とは、選んだ文書 1 件を編集セッションを開かずに読んでいる状態を指す。閲覧は入力欄を持たないので未保存入力を持ち得ず、閲覧だけをしている間は破棄前確認も起きない。**閲覧ヘッダ**とは、閲覧の先頭に置く領域を指し、title と「編集」を 1 行に並べ、その下に ID・type・tags・表示パスと、不整合のときだけ理由行（後述）を持つ（**2026-08-07 に「選択を解除」がこの行から抜けた**。TASK-121。次項の次）。ID を添えるのは、title が見出しに出た結果カードの ID と対応づける値が閲覧側に無くなるためで、カードが持つ 4 値（ID・type・title・タグ）はここに全部揃う。本文は閲覧ヘッダの下に、**doc-8 §9 の 整形表示 として出す**（**2026-08-11 に そのまま表示 から替えた**。TASK-142・decision-25）。**決め直さずに引く** — doc-8 §9 は自分が本画面に閉じていないと述べており、引く側が確かめるのは対象が同じかどうかだけである。ここは 管理ファイルの本文 1 つを読むだけの表示 なので、対象は同じである。**本文リンク と 既定ブラウザ起動 も同節のものを引く。**本節は替える前、この扱いを「タスク詳細が Description に対して取っているのと同じ扱いで、Markdown を整形する手段はこの版のどこにも無い」と書いて **doc-8 へ帰属させていたが、doc-8 にその記述は 1 行も無かった**（実際に述べていたのはコード註だけだった。2026-08-11 に判明）。**帰属先は doc-8 §9 として実在した。****本文には doc-8 §2.1 の行長上限 48rem を掛ける** — 文書ペインは残り幅を取る列なので、窓を広げるほど 1 行が長くなる。あの 48rem は「残り幅を取る列に置いた本文ブロック」そのものに対して測った値（TASK-113）であり、ここで新しい数を決める理由が無い。値は `placement.ts` の `PROSE_MAX_WIDTH_REM` を借り、2 つ目の 48 を置かない。**編集への切替**とは、閲覧ヘッダの「編集」の押下で、閲覧している文書について編集セッションが開く事象を指す。切替の後の未保存管理・保存・破棄前確認は従来のままで、変わったのは編集セッションが開く契機だけである。「編集を閉じる」が戻る先は閲覧であって、作成フォームではない。

- **選択を解除する操作は置かない — 2026-08-07 に撤去した**（TASK-121。同日の目視フィードバック由来。§6 と同じ形で、両区画から同時に抜いた）。本節は 2026-08-07 の午前まで、閲覧ヘッダに「選択を解除」を置き、押すと選択が無くなって文書ペインが非選択時の姿へ戻る、と定めていた。**置いた理由は 2 度書かれ、2 度とも当たらなくなった。**TASK-116 が置いたときの理由は、置かないと作成フォームに打った未保存入力がカードを選んだ時点で画面から消え、それでも画面を離れるときの破棄前確認（doc-8 §6.3）には数えられる、というものだった（同日のレビュー [P2]。§6 が TASK-64 の [P2] として名指しした失敗と同型）。**その失敗は TASK-117 が消した** — 作成フォームが作成モーダルへ移り、その入力は層と一緒に破棄されるので、画面外に残る入力そのものが無くなった。TASK-117 が書き直した 2 つ目の理由（どの対象も選んでいない状態は、一覧列を持つ区画がいつでも戻れる状態でなければならない）を、目視で不十分と判断したのが本改訂である。**残す理由を書き直せないなら撤去する、という本節自身の判断順序を、書き直した理由の側に適用した。**
- **撤去で失うのは「利用者の操作で非選択時へ戻ること」だけである**。非選択時の姿そのものは残る（前項）。閲覧が出しているのはカードが持つ 4 値と本文であって、非選択時にしか読めない値は 1 つも無いので、戻れないことで読めなくなるものは無い。**失うものの側から確かめる**のは TASK-116 が [P2] で踏んだ手順で、そのとき見落としたのは「戻れない」ではなく「入力を失う」の方だった。ここで失う入力は無い — 閲覧は入力を持たず、編集セッションの入力は選んでいる文書に結び付いて画面に出ており、作成モーダルの入力は層が自分で破棄する。
- **一覧の先頭を自動選択しない**。撤去しても非選択時は **本節では 3 経路**で到達する: 初回描画、再読み込みで選択対象が消えたとき、**プロジェクトルートの移動が成立したとき**（§4.1。移動は無条件に選択を落とすので、移動先に同じ id があるときも含む — **「再読み込みで消えたとき」の特殊例ではない**）。**§6 はこれに削除・アーカイブの成功が加わって 4 経路である。**（**3 つ目は 2026-08-07 に足した**。PR #74 の 2R [P3]。§4.1 は本 PR より前から文書の選択を落としており、**本節の初版はそれを数え落としていた** — 同じ PR の中で §6 の閉じる契機について「自分の外で定められた契機も数える」と書きながら、その隣で同じ数え落としをしていたことになる。）**経路が 1 つ増えても自動選択を退ける理由は変わらない** — 経路が減ることは無いので、自動選択を入れても非選択時の姿を描かずに済むわけではなく、状態は 1 つも減らない。加えて自動選択は、利用者がしていない選択を画面が主張することであり、選択対象が読み取りから消えたときに隣のカードへ飛ぶことになる — そこは「閲覧に出すものが無くなったので選択を落とす」を明示の理由として選択を落とすと決めた場所である（PR #65 の 1R [P2]）。
- **パスは一覧に出さず、表示パスとして文書ペインに出す — 画面設計案 07 からの意図的な逸脱の 2 件目**: 07 はカードにパスを描く（doc-12 §8.3）が、一覧は選ぶための最小情報に絞り、どのファイルかは選んだ側の列で述べる（2026-08-05 の目視指摘）。表示パスとは、読み取り層の `source_path` をプロジェクトルートからの相対へ直した表示専用の文字列を指す（ルートの下に無いパスはそのまま出す）。**閲覧ヘッダに出し、更新フォームでは path 欄の直上に繰り返す** — あちらは移動要求の欄であり、空欄＝移動しないという意味は現在の所在と並べて初めて読めるためである。更新フォームの path 欄が移動要求であり現在値を入れないことは変わらない。**2 か所とも現在の読み取りから導く**（導出は 1 か所で、2 か所がそれを引く）。編集セッションの baseline から引くと、隣のカードの ⚠️ が現在の読み取りから出ているのと食い違い、同じ 1 件について 2 つの読み取りが描くことになる（decision-22「導出は 1 回」。PR #71 の 1R [P2] が同じ形で出た）。
- **文書一覧と文書ペインは独立にスクロールする — 画面設計案 07 からの意図的な逸脱**: 07 は区画ナビの外側を単一スクローラにしており、列ごとの overflow を持たない（doc-12 §8）。しかし文書を選び直しても一覧の縦位置が保たれる（gmail 的な操作。TASK-63 の要求）には、一覧が自分のスクロールを持ち、文書ペインの内容の入れ替えがその位置に影響しないことが要る。ここは 07 に従わない。**文書ペインの中身が差し替わったときは、文書ペインだけを先頭へ戻す**。差し替わる事象は 4 つで、選択が成立して閲覧が開いたとき・編集への切替で更新フォームが開いたとき・編集セッションが閉じて閲覧へ戻るとき（「編集を閉じる」／更新の成功／破棄して続行）・**選択が落ちて非選択時の姿へ戻るとき**である。**4 つ目は 2026-08-07 に「選択を解除して」から書き換えた**（TASK-121）: 解除の操作が抜けた後も、再読み込みで選択対象が消えれば同じ差し替えが起きる。事象が入れ替わっただけで数は 4 のままである。**作成モーダルの開閉はこの 4 つに入らない** — 層はペインの上に乗るだけで、ペインが出しているものは変わらないためである（TASK-117）。**文書ペインが別のものを出すたびに戻す**のであって、列挙は事象の数え上げにすぎない — 事象を足したらここも足す。ペインの古いスクロール位置が残ると、新しく開いた側が表示範囲の上に隠れ、操作が効かなかったように見える。一覧の位置には触れない。
- **文書区画の破棄前確認は本節自身の契約である**: 未保存入力を持ったまま別の文書を選ぶ・編集を閉じる の 2 経路で確認し、問いは「文書の編集に未保存入力があります。（選んだ文書を開くと／編集を閉じると）破棄されます。」、答えは進む側「破棄して続行」・戻る側「入力に戻る」。doc-8 §6.3 の文言契約は借りない — あちらが定めるのはタスク詳細の編集セッションの 5 経路とモーダル（doc-11 §7 の被せ層）で、この確認はどちらにも属さない。問いは 2 列の外・上に出す — どちらの列がどこまでスクロールしていても見える位置に無いと、問いが立ったことに気づけない。**この 2 経路が確認を出すのは編集セッションが開いていて未保存入力があるときだけ**で、閲覧しかしていない状態から別のカードを選んでも確認は立たない（閲覧は未保存入力を持ち得ない）。経路の数も文言も TASK-116 は動かしていない。**TASK-117 も動かしていない** — 作成モーダルが持つ未保存入力の破棄前確認は doc-11 §7 の経路で、問いも答えもあちらのもの（doc-8 §6.3 の問い文＋「破棄して閉じる」「編集に戻る」）を使い、**本節の 2 という数はそこを数えていない**。同じ喪失を 2 通りに述べないための帰結で、本節が自分の文言を持つのはこの 2 経路についてだけである。**TASK-121 も動かしていない** — 撤去した選択の解除は閲覧からしか押せず、閲覧は未保存入力を持ち得ないので、この 2 経路のどちらでもなかった。**同じ撤去が §6 では経路を 1 つ落とす**（あちらは選択が入力欄を開いていたため）が、§6 は同じ改訂で「編集を閉じる」を得るので数は 2 のままである。**2 区画の 2 という数が同じ 2 経路を指すようになったのは本改訂からで**、それまでは片方が解除を数えていた。
- **一覧**: カード（ID・type・title・タグ・未保存の印）を並べ、カードを選ぶと文書ペインへ読み込んで閲覧を開く。パスは並べない（前項の逸脱のとおり、表示パスとして文書ペインに出す）。
- **選択中の強調と編集中チップは別々に立つ**（TASK-116）。強調は選択が指している 1 枚に付き、閲覧でも編集でも同じように付く。**編集中チップが付くのは編集セッションが開いているカードだけ**である — 選択と編集が別々になったので、強調は「いま読んでいる」を、チップは「いま編集している」を述べる。未保存の印は従来どおり編集セッションの未保存入力を述べる。
- **不整合な文書はカードに不整合印を 1 つ持つ**（decision-22 の ⚠️ をそのまま使う。decision-24 が対象を管理ファイル 1 件へ広げた）。**理由はアクセシブル名と `title` が全文で持ち、カードには語を出さない。**カードの ID・type・title・タグは判別できた値をそのまま出す — 写せなかったのは任意項目だけなので、残りは正常な文書と同じに読める（doc-4 §5）。
- **理由行は閲覧ヘッダに並べる**（decision-22 の理由行を借りる。decision-24 を TASK-116 が原地改訂した）。選んだ文書が不整合のときだけ出し、専用の区画は作らない。**decision-24 は「編集ペインの見出しの下」と定めていた** — 当時は選択が更新フォームを開いたので、それが選択で開く場所だった。選択が開く場所が閲覧になった以上、置き場も閲覧ヘッダへ移る。移さないと、不整合な文書を選んでも理由行が「編集」の向こうに隠れ、**doc-11 §2.4 の「ホバーだけが理由への唯一の経路になってはならない」に触れる**（PR #71 の 1R [P2] で 1 度直したのと同じ形である）。**更新フォームには繰り返さない** — 保証すべきなのは「理由を読むための場所が別にある」ことであり、選択が開く場所がその場所である以上、閲覧ヘッダ 1 つで足りる。**置くこと自体は doc-11 §2.4 の要求である** — 印グリフは「理由を読むための場所が別にある」ことを設計側が保証する条件で置いてよいものであり、タスクにおけるその場所が不整合区画（doc-8 §3）で、ここでは閲覧ヘッダがそれに当たる。

  - **path 欄は現在値を入れない**。読み取り層が持つのは走査で得た `source_path` であり、`-p` に渡す docs 相対パスとは別の値である。空欄＝移動しない、値を入れる＝移動要求、として扱う。
  - **タグ全消しを提供する**（TASK-109 の決定、2026-08-06）。**タグ全消し**とは、tags 欄からタグを 1 件も残さずに文書更新を発行し、その文書の frontmatter から tags を無くすことを指す（本節の初版が「tags を空にする操作」と呼び、提供しないとしていたもの）。写像へは**空集合の tags**として渡す。空集合の tags とは、更新操作の tags が要素 0 個であることを指し、タグ全消しの要求を表す — **未タッチの tags**（欄に触っていないので tags を送らない）とは別の値である。この 2 つを混ぜると、タグに触っていない更新が他人の付けたタグを消す。本節の更新が定める「触って値が変わった項目だけを送る」が、そのままこの区別である。
    提供する理由は 2 つある。①**`--tags ""` はタグを実際に消す**（v1.48.0 で終了コード 0、frontmatter から `tags:` キーごと消える。TASK-58 実測、TASK-109 で再実測）ので、提供しない理由に CLI の制約を挙げられない。本節の初版が挙げていた「効果が未確認で、同型の `--ref ""`・`--depends-on ""` は終了コード 0 のまま何も消さない」は、このフラグには当てはまらなかった。②2 件目までは外せて最後の 1 件だけを拒む形は、規則ではなく段差であり、利用者に述べられる理由を持たない。加えて**文書には外部エディタ経路が無い**（doc-8 §7 が定めるのはタスク詳細のもの）ので、提供しなければタグ全消しは Atlas の中に経路を持たず、管理ファイルを直接編集させることになる。タスクの参照・依存の全消しを外部エディタ経路へ送れるのとは事情が違う。
    **タグ全消しに告知は置かない**。「保存するとタグをすべて外します」の類を欄の隣に出す案は退けた — tags 欄は現在のタグを並べており、それが空になっているのは利用者が 1 件ずつ外した結果そのものなので、告知は読めば分かる状態の言い換えにしかならない（TASK-79 が落とすと定める型）。**path 欄と同列に扱わない**: あちらは常に空で現在値を持たないため空欄の意味が読めないが、tags 欄は現在値を出している。どの CLI フラグを発行するかも述べない — 利用者が確かめるのはタグが消えたことであって、`--tags ""` が走ったことではない。
    なおタグ値にカンマを含められないことは変わらない（CLI が 1 個のカンマ区切り値として受け取るため）。
- **削除は提供せず、そのことを画面に書かない — 画面設計案 07 からの意図的な逸脱の 3 件目**（画面全体では 6 件目。**2026-08-08 の改訂**。TASK-123）。v1.48.0 の `doc` に delete/remove 相当のサブコマンドが無く、Atlas がファイルを直接消すことは decision-2 の境界の外にある。本節は改訂まで、これを提供しない操作区画（当時の §1）へ名称・写像先・理由の 3 点で並べており、**07 も §8.5 としてその区画を持っている**（doc-12）ので、やめることは 07 から外れることである。外れる理由は、**backlog.md が提供しない操作を Atlas が提供しないことが本製品の性格から自明**であり、掲示が守っている実質がこの 1 件だけで、しかも文書ペインの非選択時にしか出ず**文書を選んでいる間は読めない**位置にあったことである（2026-08-08 にユーザーが確定。§9）。**通し数は末尾に足し、既存 5 件の番号を動かさない** — §6 が通し数を添えると決めた理由が「数え直しを避けるため」なので、章の順に挿し込むと避けたはずの数え直しがそこで起きる。

`task create` を 1 回発行する。本区画が渡すのは title（必須・位置引数）・description・status・priority・milestone・labels・受入条件である。

## 8. 縮退時の表示

- **台帳読取専用**（doc-3 §2.2）: 概要区画の入力と登録解除を無効化し、理由を帯と各操作に出す。文書・マイルストーン・新規タスクは影響を受けない。
- **CLI 縮退**（doc-5 §5）: 文書・マイルストーン・新規タスクの発行を無効化し、理由を帯と各操作に出す。概要区画は影響を受けない。
- **ルート読取不能**（doc-4）: 文書・マイルストーン・新規タスクの一覧は出せない。概要区画は台帳エントリから描けるため出し、ルートの修正手段として機能させる。
- 無効化はすべて理由を伴う（doc-11 §5）。理由の無い無効化を置かない。
