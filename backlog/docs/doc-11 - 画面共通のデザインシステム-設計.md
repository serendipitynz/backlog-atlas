# 画面共通のデザインシステム 設計

画面設計案の反映として書いた設計（実装は TASK-48）。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は decision-6（不在・欠損の区別と族の分離）・decision-8（素の Svelte・スタイルはコンポーネントスコープド）・decision-12（表示テーマと印チップ配色規則）。画面設計案（doc-1 追補で定義。04・05・06）を反映する。引用する事実は doc-12 §5・§6・§7 に転記してある。

**本書の px による実測値は、断りのない限り地の 1rem が webview の既定（16px）だった時点のものである。** 2026-08-14 に TASK-164 が地を 110% へ上げたので、**rem で述べた寸法の px は当時の 1.1 倍になる** — 実測値そのものは動かず、その値が指していた画面がもう無い、という形で古くなる。**新しい地で測り直した値には、その旨をその場に書く**（§2.2 の 控えの群、§13 の 3 面がこれにあたる）。**測り直していない値を 1.1 倍して書き替えない** — 掛け算で出た数は測った数ではなく、折り返しの起きる寸法では現に一致しない。

本書は、複数の画面（doc-7 スイムレーン・doc-8 タスク詳細・doc-10 プロジェクト詳細）が共有する見せ方の規則を 1 箇所に置く。各画面の文書は「どこに何を出すか」を定め、本書は「それをどう描くか」を定める。

## 1. 用語

- **デザイントークン** … 複数の画面が同じ値を参照するために名前を与えた寸法・色・角丸・余白を指す。色は表示テーマ（decision-12）が持ち、それ以外は本書が持つ。
- **印** … decision-6 の 3 族（不整合・照合不能／継続検出停止・読取不能）と通知（`--info`）を、対象の脇に示す表示要素。描き方は 2 通りあり、**印チップ**は短い語を持ち**印チップ配色規則**（decision-12）で描き、**印グリフ**は語を持たず族の色を図形自身の色として持つ（decision-22）。**族は 4 つだった** — decision-22 が縮退と版ずれを不整合へ束ねた（§3・§10）。
- **印チップ** … 語を持つ印。文字＝族の色、背景＝族の色 12% 混色、枠＝族の色 45% 混色（decision-12）。
- **印グリフ** … 語を持たず、族の色を図形自身の描画色として持つ印。背景も枠も持たない（decision-22）。現在の唯一の実例は不整合印 ⚠️ で、描き方は §2.4、色の条件は decision-22 の印グリフの収録条件（族の色 対 それが載る面で 3:1 以上）による。**印チップ配色規則を適用しない** — 12% 混色の背景が存在しないので、あの規則の測る対象がここには無い。
- **優先度の縁** … タスクカードの左辺 3px に置き、そのタスクの priority を色で述べる縁を指す（decision-23）。**印ではない** — 対象の状態が正常かどうかを述べておらず、族の色ではなく優先度色を引く。描き方と、問題の縁と形を共有することの扱いは §2.3。
- **優先度色** … priority 3 段のそれぞれを述べる表示要素が引く 3 つの色値を指す（decision-23）。族ではないので、印がこれを借りることはない。**引く表示要素は 4 つ**（優先度の縁 §2.3・priority チップ §3・畳んだ列のレーンセルに並ぶ四角 §3・タスク詳細の priority の値 doc-8 §2.2）で、**満たすべき比は色値ではなく描き方に付く** — 札の文字なら自分の 12% 混色背景に対して 4.5:1、素の文字なら面に対して 4.5:1、図形なら面に対して 3:1（decision-23 の優先度色の収録条件）。
- **上部帯** … フィルタ帯の下に重要度の固定順で積む、横 1 行の告知区画を指す。
- **無効化提示** … 操作を提供できないとき、その操作を消さずに、押せない見た目と理由の 2 つを同時に与える示し方を指す。
- **アイコン** … lucide（ISC）の図形をそのまま写した装飾用 SVG 1 個を指す。文字グリフ（☰・⚙・▼）ではない。描き方は §2.4。
- **アイコンのみのボタン** … 可視の文言を持たず、用途を `aria-label` と `title` だけが述べるボタンを指す。
- **操作に属さないアイコン** … 押せる控えの内側に無く、置かれた帯・区画が何を扱う場所かを図形だけで示すアイコンを指す。アイコンのみのボタンとの別は、押せるかどうかである。
- **フォーム部品** … 利用者が値を入力または選択する 1 行の部品（`input`・`select`）と、それらと同じ行に並ぶ押しボタンを指す（TASK-141）。**`textarea` は入らない** — 高さを `rows` が決めるので、§2.2 の段階から 1 値を選べない。**`input[type="checkbox"]`・`input[type="radio"]` も入らない** — platform が描く正方形の印であって値の入る欄ではなく、文字の入る欄の高さを与えると正方形でなくなる。高さは §2.2 が定める。

## 2. デザイントークン

### 2.1 色

表示テーマ（decision-12）が `--bg`・`--panel`・`--inset`・`--fg`・`--muted`・`--faint`・`--line`・`--line-strong`・`--mark-*`・`--info`・`--sel` を持つ。コンポーネントは変数名と `color-mix` だけを参照し、色値を書かない。

| 変数 | 用途 |
|---|---|
| `--bg` / `--panel` / `--inset` | 地 / カード・パネル面 / くぼみ面（レーンヘッダ行・引用・入力の下地） |
| `--fg` / `--muted` / `--faint` | 本文・本文と同じ強さで描く非文字要素（ACCEPTANCE CRITERIA の達成割合のバーの塗り。doc-8 §3） / 副次（属性名・件数） / 弱（注記・空表示） |
| `--line` / `--line-strong` | 罫線（`--fg` 14% 相当） / 強い罫線・入力枠（30% 相当） |
| `--mark-*` 3 族 | decision-6・decision-22 の族。一箇所定義、コンポーネントは族名だけを選ぶ |
| `--info` | 通知・確認・リンク風操作。族ではない（青い確認は不整合ではない） |
| `--sel` | 選択のアウトライン |
| `--priority-high` / `--priority-medium` / `--priority-low` | 優先度色（decision-23）。priority を述べる 4 つの表示要素が引く（優先度の縁 §2.3・priority チップ §3・畳んだ列の四角 §3・タスク詳細の priority の値 doc-8 §2.2）。**族ではない**ので印はこれを借りない |

### 2.2 寸法

| 対象 | 値 |
|---|---|
| 文字寸法段階 | .62 / .68 / .74 / .80 / .86 / .92 / .98rem |
| 地の 1rem | webview の既定の 110% |
| 余白段階 | .16 / .25 / .3 / .45 / .6 / .75 / 1rem |
| 角丸 | チップ 3px / カード・ボタン 4px / パネル 6px / ラベルピル 999px |
| フォーム部品の高さ | 1.2 / 1.4 / 1.75rem |
| コミット SHA・パス | `ui-monospace` |

**文字寸法段階** とは、字の大きさとして取りうる値の梯子を指す（2026-08-14 に新設。TASK-164）。**余白段階・角丸と同じ形で、どの面がどの段を取るかは本表が列挙しない** — 選ぶのは各画面である。次の 段の役割表 が述べるのは、本書と各画面の設計文書が名指ししている役割の分だけであり、**そこに無い箱も段の 1 つを取る**。

| 役割 | 段 | 段以外に定めるもの |
|---|---|---|
| 画面見出し | .98rem | 650 |
| タスク title（詳細） | .98rem | 650 / line-height 1.35 |
| モーダルとパネルの見出し | .98rem | 650 |
| 整形表示の中の見出し | .92rem（h1・h2）／ .86rem（h3 以下） | 650（§14.1） |
| カード title | .86rem | 400 / line-height 1.35 |
| 整形表示の本文・リスト | .80rem | — |
| 本文・リスト | .74rem | — |
| 副次（ID・件数・注記） | .68rem ／ 最小のものは .62rem | `font-variant-numeric: tabular-nums` |
| 区画見出し | .68rem | 650 / letter-spacing .05em / `--muted` |

**本文の行は 2 本ある**（2026-08-14 に 2 本目が入った。TASK-164 の目視反映）。**整形表示の本文は画面の本文より 1 段大きい** — 2026-08-14 の並置目視でユーザーが「マークダウンのレンダリング部分はまだ小さい」と述べ、対象を整形表示に限って挙げたためである。**画面の本文・リストは動かしていない** — 同じ目視で「前より大きくなって見やすくなった」「カンバンのカードは現在のバージョンがよい」と述べており、動かす理由がその報告のどこにも無い。**2 本になった代償は、どちらの段を取るかを画面が選べてしまうことである**: 整形表示の本文の段を取るのは `Body.svelte` だけで、他の画面は 本文・リスト の段を取る。

**7 段目 `.98rem` は、整形表示の本文を 1 段上げるために入った。** 上げると、その上に載る見出し 2 段も 1 段ずつ上がって パネルの見出し に届く。**届かせる代わりに天井を 1 段上げた** — 段の幅を崩さずに済む唯一の形である。**上限として測ったのは パネルの見出し だけである**（§14.1 が 区画見出し も挙げているが、**整形表示の見出しは TASK-164 の前から 区画見出し より大きかった** — 詳細と数は §14.1。あちらを分けているのは大きさではなく罫線と字間と `--muted` である。§14.1 の当該項をその形へ書き改めた）。

**段の幅は一定の 0.06rem である。** 一定にしたのは、狭い段が段として働かないためである — 置き換えた 18 値には `.74/.75`（0.01 差）や `.92/.95`（0.03 差）の組があり、**隣り合う 2 つを別の大きさとして読める画面は無かった。**「ある幅以上」という下限だけでは、一部だけ詰まった梯子が通る。

**段階を持つ前は、字の大きさを決めている箇所が 18 ファイルに 186 件あり、値は 18 通りで、共有の変数を引くものは 1 件も無かった**（2026-08-14 に数え上げ。TASK-164）。**本表は当時も字の大きさを 7 行持っていて、その 7 行を実装は読んでいなかった** — `App.svelte` の `h1` は本表が `.92rem / 650` と書いている隣で `1rem` を書き、太さは UA の 700 のままだった。**「実装が既にやっている」は「契約がある」ではない**の実例なので記録しておく。いまはその一致を `src/lib/text-scale.test.ts` が押さえ、**画面が長さを直に書いた時点で落ちる。**

**段の役割表は画面設計案 06 のタイポ 3 行から意図的に外れている**（doc-12 §7.1。2026-08-14。TASK-164）。原文は役割ごとに `.92 / .95 / .78 / .72–.74 / .6–.68 / .68rem` を刷っているが、**この 6 値を含む一定幅の梯子は無い** — `.92` と `.95` は 0.03 差、`.74` と `.78` は 0.04 差で、原文自身が段として読めない組を 2 つ持っている。**外れたのは 3 行である**: タスク title を `.95` から `.98` へ（画面見出し・モーダルの見出しと同じ段。太さと置き場で分かれる）、カード title を `.78` から `.86` へ、**本文・リスト を 1 行から 2 行へ分けて 整形表示 だけ `.80rem` へ**（同日の並置目視でユーザーが対象を名指しした）。**残る 3 行は原文の値か、原文が書いた範囲の中にある。** **原文が書いていないことから外れることはできない、という判断はここに掛からない** — 06 はこの寸法を書いており、外れる側が理由を持てばよい。

**地の 1rem は `px` ではなく `%` で述べる。** 利用者が OS 側で字を大きくしている場合、`px` はそれを Atlas が上書きすることになる。110% を選んだのはユーザーの 2026-08-14 の判断で、**「全体的にテキストサイズが小さい」（2026-08-13 の目視）に答えるのはこの 1 行だけである** — 段階の rem 値は本表が前から持っていた数のままで、地が 1.1 倍になることで全部が一緒に伸びる。**これは本タスクの変更の全部ではない** — 同じ 2026-08-14 の並置目視が 整形表示 を名指しし、そちらは段と余白で答えている（段の役割表 と §14）。**地はそのために動かしていない**: 同じ目視が「カンバンのカードは現在のバージョンがよい」と述べており、地を動かせばカードも動く。**段だけを上げる案は実測して退けた**（同日。WebKit）: 余白が付いてこないので ×1.18 でカードの 印 と priority チップが別行へ落ちた。**地を上げると rem で書かれた寸法がすべて動く** — 余白段階・角丸・フォーム部品の高さ・行長上限 48rem（doc-8 §2.1）・§13 の上限がこれに当たり、§13 はその帰結を自分の節で述べている。

**角丸の「チップ 3px」は §3 のチップの 4 系統すべてに掛かる**（priority を含む）。**掛かる先をその 4 つに限る行ではない** — §3 の 中立の情報 の札と、整形表示 の中のコードと引用（§14.2）も、系統ではないまま同じ値を取る。999px を取るのは通常ラベルだけで、それは画面設計案 04 の契約 #4「Type とラベルを混ぜない」が通常ラベルに与えた形である（doc-12 §5）。priority が 999px だった実装は本表からの逸脱で、decision-23 が実装を本表へ合わせた — **本表の値は動いていない**。

件数・ID・日付には `tabular-nums` を与える。桁が揃わないと、行をまたいで数を比べる読み方（doc-7 の縦読み）が成立しないためである。

**フォーム部品（§1）の高さは段階から 1 値を選び、`box-sizing: border-box` と `height` で述べる — 2026-08-11 に新設**（TASK-141）。述べなければ高さを決めるのは webview の既定であり、**同じ 1 つの宣言に対して 2 つのエンジンが別の値を返す**。実測（2026-08-11、WebKit・Chromium）では、`input[type="text"]` と `select` に同じ `padding` を書いた画面で computed padding が WebKit `0px` / Chromium `4px` になり、**`select` では著者の padding 自体が WebKit で効かない**。Atlas は 3 OS で別々の webview の上に載る（decision-11）ので、揃うかどうかを既定に委ねられない。**`box-sizing: border-box` を伴うのは、このリポジトリに全体リセットが無いためである**（TASK-115）— 無いと枠 1px×2 が述べた高さの外へ足される。その宣言は `app.scss` が 1 か所で持ち、呼び出し側が落とせる形にしない（§5 の無効化提示と同じ理由）。

**1 値を共有する範囲は入力面（§11）である。** 同じ入力面に載るフォーム部品は、段階から選んだ同じ 1 値を高さに取る。**入力面を持たない行**（フィルタ帯）では、その行に並ぶフォーム部品が同じ 1 値を取る。**範囲を行だけにすると、欄を 1 つずつ縦に積んだフォームが規則の外へ出る** — 文書作成モーダル（doc-10 §1）は 3 欄を縦に積んだ後も入力欄 27.73px・`select` 18px（WebKit の変更前実測）のままで、行の中では 1 部品ずつなので「同じ行は揃っている」を満たしながら不揃いが残る。**どの面がどの値を取るかは本表が列挙しない** — 余白段階・角丸と同じく、選ぶのは各画面である。

**控えの群も同じ段階から 1 値を取る。** **控えの群**とは、入力欄も選択欄も持たず、**1 つの対象について働く押しボタンを 2 つ以上横に並べた領域**を指す — レーンヘッダ行の控え（doc-7 §2.3）と、タスク詳細の見出しの 1 行目が右端に置く 前後移動 と 配置切替＋閉じる（doc-8 §2.2）がこれにあたる。**そこに並ぶのはフォーム部品ではない**（§1 の定義は `input`・`select` と**それらと同じ行に並ぶ**押しボタンを指すので、両方が無いところでは誰も当たらない）が、**並んだ控えの高さを揃える理由は同じ**であり、段階を 2 本持つ理由が無い。**この 1 値は群のものであって、同じ画面の入力面の値と一致しなくてよい** — スイムレーンはレーンヘッダ行の群が 1.2rem・フィルタ帯が 1.4rem である。

**対象は行ではなく群である。** 1 行の中に、群と、群に属さない控えが同居するためで、タスク詳細の見出しの 1 行目がその実例である — **doc-8 §2.2 は、この行の左端に 横断タスクID・ID コピー・印 を、右端に 前後移動・位置・配置切替・閉じる を置くと定めて 2 つを分けており**、コピーは「ID から離れた位置に置かない」ことと「何をコピーするかを述べているのは隣の ID である」ことを理由に **ID の寸法から大きさを取る**（実測 23.75px、群の 24.63px に対して。両エンジンとも。**地 110% で測り直した値である** — 16px の地では 21.59px と 22.39px だった）。**行を対象にすると、この 1 件が規則違反になるか、doc-8 §2.2 の置き方を壊すかのどちらかになる。** したがって、**値の隣に付いてその値から大きさを取る控えは、控えの群に入らない。**

**押しボタンが 1 つしか無い領域も入らない** — 揃える相手がいないためである。**§11 の発行の行もここに含めない**: あの行が並べるのは発行と取りやめで、高さは §11 と各画面が決める。

**`select` は枠と面を持たないとこの高さを取れない。** WebKit は、native menulist のまま描いている `select` には著者の `height` も `padding` も効かせない（2026-08-11 に実測。枠を持たない 3 つだけが同じ宣言に対して WebKit 18px・Chromium 28px を返し、枠を持つ 4 画面では両エンジンとも効いた）。**したがって `select` を置く画面は、同じ入力面の入力欄と同じ枠と面をそれに与える。**`background` を `transparent` にすると menulist の描画が残るので、面は色を持つ値にする — そのとき `select` を入力欄と見分ける矢印も native の描画に付いてくる。

**画面設計案 06 のトークン一覧（doc-12 §7.1）にこの寸法は無い。** 06 が書いていないことから外れることはできない（doc-10 §1 が作成モーダルについて下したのと同じ判断）ので、**意図的な逸脱には数えない。** 原文に無いものを新しく置いた例は §2.4 のフィルタ帯の funnel（TASK-112）に続いて 2 件目である。

### 2.3 状態の描き分け

| 状態 | 描き方 |
|---|---|
| hover | 枠線を `--line` → `--line-strong` |
| 選択 | `outline: 2px solid var(--sel)` ＋ offset 1px |
| 無効 | 破線枠 ＋ opacity .45 ＋ 理由（5 章）。マウスカーソルは地の矢印のまま（5 章） |
| 問題の縁 | 上部帯左 4px・レーンヘッダ行左 3px（読取不能の行）・タスク詳細の不整合区画の左 3px |
| 優先度の縁 | タスクカード左 3px。priority 3 段のときだけ 優先度色（§2.1）を置く（decision-23） |

**カード左 3px の族色は decision-22 で外れた**（TASK-77）。不整合であることをカードで述べるのは印グリフだけで、同じ 1 つのことを図形と縁の 2 つで述べない。区画の左 3px が残るのは、そこでは図形ではなく面そのものが「何の区画か」を述べているためである。**問題の縁の列挙にレーンヘッダ行が無かったのを decision-23 のときに足した** — `Swimlane.svelte` は読取不能の行に前からこの縁を描いており（族の色を面全体へ敷くと、その上に載る印チップの 12% 混色背景が検算した色と変わるため）、落ちていたのは列挙のほうである。

**空いたカードの縁は decision-23 が priority へ渡した。優先度の縁**とは、タスクカードの左辺 3px に置き、そのタスクの priority を色で述べる縁を指す。**問題の縁とは別の行として数える** — 述べているのは問題ではなく優先順位で、族の色ではなく優先度色（族ではない）を引く。**同じ装置を同じ色相で使う衝突は残っている**（赤の左端はカードでは high、レーンヘッダ行では読取不能）ので、**区別は色相ではなく、その縁を何が持っているかで行う**。カード（1 件のタスク）・レーンヘッダ行（1 プロジェクト行）・上部帯（画面全体）は大きさも位置も別の表示要素で、問題の縁を持つ 2 つは語を伴う。**priority 未設定・priority 未知 には縁を出さない**（縁が無いことが「3 段のどれでもない」を述べる）。縁は語を持たない非文字要素なので、満たすべき比は decision-23 の**優先度色の収録条件**のうち面に対する 3:1 である（**「優先度の縁の収録条件」という縁だけの契約は無い** — 条件は色値ではなく描き方に付き、優先度色を引く 4 つの表示要素で 3 通りに分かれる）。

- **置き場は `src/lib/icons/`** で、図形データ（`lucide.ts`）と描画（`Icon.svelte`）を分ける。**lucide のパッケージを本番依存に入れない** — 要るのは 10 個前後で、AGENTS.md の最小依存の方針に合う。出典（**パッケージ名**・版・ISC・写した元ファイル）は図形データの冒頭に書く。**パッケージ名まで書く** — lucide は同じ図形を複数のパッケージで配っており、実際に座標を読んだ 1 つを名指ししない限り、後から元と突き合わせる先が定まらない（`lucide` と書いてあったものが実は `lucide-react` だった、が TASK-112 で見つかった）。ISC の告知をリリース物へ載せるかどうかは TASK-97 が扱う。
- **図形は写すだけで、描き直さない**。手書きのパスや、`rect` をパスへ潰したものは lucide に似た図形であって lucide の図形ではなく、後からどちらなのかを区別できない。使う SVG 要素の種類は閉じた列挙で持ち、要素が足りない図形を入れるときは列挙を増やす。**列挙を増やしたときに描画が抜けることは、型で止める** — 種別から描画要素への写像を網羅的な `switch` 1 つに置き、テンプレートはその返り値を描く。テンプレート側の条件分岐では止まらない（列挙が 1 種類のうちは分岐漏れが型エラーにならず、空の `<svg>` が描かれてビルドは成功する）。
- **同じ図形を別の操作へ与えない**（本項は TASK-139 で新設）。**chevron と arrow は 2 つの族をなし**、**chevron は折畳み、arrow は移動**を指す。行折畳み（`chevron-up`／`chevron-down`。doc-7 §2.3）・列折畳み（`chevron-left`／`chevron-right`。doc-7 §2.2）・区画見出しの開閉印（`chevron-down`／`chevron-right`。doc-8 §3）が前者で、前後移動（`arrow-up`／`arrow-down`。doc-8 §2.2）・行の並べ替え（同じ 2 つ。doc-7 §2.3）・行末の入口（`arrow-right`。doc-7 §2.3）が後者である。**分ける軸は、その図形が指すのが同じ面の開閉なのか、別の対象への移動なのかである。**`lucide.ts` は TASK-67 以来この規則どおりに書かれていたが、規則としてはどこにも無く、`arrow-up` の註が 1 度だけ理由を述べていただけだった。**族を持つのはこの 7 つだけで、残りの図形には族が無い** — `x`・`plus`・`check`・`funnel`・`menu`・`maximize`・`clipboard`・`clipboard-check`・`panel-right`・`panel-top-dashed`・`triangle-alert`・`square-check`・`square`・`circle-question-mark`・`undo`・`refresh-ccw` は、向きの組で意味を分ける図形ではないので族に入らない。**族が無いことは共有してよいことではない** — **本項が数えているのは操作であって図形の族ではなく**、族はそのうち向きで対になるものを名前で束ねただけである（`x` が閉じる・解除・削除の 4 か所に出るのは、どれも「その 1 件を取り除く」で指すものが同じだからで、族の話ではない）。**及ぶのは操作を指す図形だけである** — **操作に属さないアイコン**（下記）は押せる控えの中に無く、指す操作を持たないので、同じ図形が操作の側と重なっても本項には触れない（status 別名表 と 保存で送る属性 の **値の対応を示す `arrow-right`** は、行末の入口 と同じ図形だがどちらの画面にも一緒には出ず、押せるかどうかで先に見分けが付く）。**その描き方を定めるのはその型のほうである。** 逆に、**族に入る図形を操作に与えるときは、必ず族の側で判定する**（`arrow-right` を別の操作へ与えるなら、行末の入口 と指すものが同じかを問う）。
  - **行末の入口に `chevron-right` を共用しない**（TASK-139 で確定）。列折畳みと区画見出しが既に取っており、スイムレーン画面では列ヘッダと行末が同時に出るので、1 つの図形が「列を開く」と「別画面を開く」の 2 つを指すことになる。原文（doc-7 §2.3 の図）が刷る `›` は山括弧そのものだが、**本節が写すのは記号の字形ではなく、その記号が指していた操作である** — 字形で選ぶなら、同じ字形の 2 つの操作は必ず同じ図形になる。
  - **行の並べ替えは前後移動と同じ 2 つを取る**（TASK-139 で確定）。どちらも「上下へ 1 つ動かす」ことそのもので、原文も 2 つとも `↑↓` と刷っている（doc-7 §2.3 の図・doc-12 §3）。**本項が禁じているのは指すものが違う操作の共有であって、同じことを指す操作の共有ではない。** 脇パネル配置では両方が同時に画面へ出るが、動かす対象（行の表示順／詳細パネルが指すタスク）はそれぞれの `aria-label` と `title` が述べる。
  - **`refresh-ccw` を 既定に戻す へ与えてよい**（2026-08-15 に TASK-175 が判定）。本項に触れるかを問うた相手は 再読込 だが、**あれはまだ図形を 1 つも持っていない** — レーンヘッダ行の 再読込 も 上部帯 ④ の 該当行を再読込（doc-7 §5.3・doc-9 §3）も可視の文言だけの控えなので、同じ図形を 2 つの操作が持つ状態がそもそも無い。**判定が閉じるのは 再読込 の側の将来の選択肢のほうである。** あの控えに図形を与える回は、`refresh-ccw` そのものに加えて**向きだけが違う `refresh-cw` も取れない** — 2 つが揃った時点でそれは向きで対になる図形、すなわち族であり、族に入る図形を操作に与えるときは族の側で判定するのが上項の要求だからである。**2 つは指すものが違う**: 既定に戻す が戻すのは絞り込みで、戻す先は画面を開いたときの状態であって（doc-7 §5.2）、読み直すファイルは 1 つも無い。**スイムレーン画面ではフィルタ帯とレーンヘッダ行が同時に出る**ので、共用すれば 行末の入口に `chevron-right` を共用しない と同じ形の衝突になる。
- **寸法は 1em**。`viewBox` 24・線幅 2 という lucide の値をそのまま使い、大きさはアイコンを置く箱（ボタンでも、操作に属さないアイコンならそれを含む帯・区画でも）の `font-size` が決める。単独のボタンでは 1rem（16px）を既定とする。アイコン専用の寸法指定を足さないのは、隣の文字と食い違う 2 つめのつまみを作らないためである。
- **色は `currentColor` だけ**。表示テーマ（decision-12）へ追加する変数は無い。
- **アイコンは常に装飾** として `aria-hidden` を付け、アクセシブル名に寄与させない。図形は語を持たないので、`<svg>` を読ませると名前の無いボタンになる。
- **アイコンのみのボタン** とは、可視の文言を持たず、用途を `aria-label` と `title` だけが述べるボタンを指す。`aria-label` を必ず置き、そこには操作の名前だけを入れる（キーを含めると読み上げが「設定 ⌘,」になる）。ショートカットの併記は doc-7 §2.1 の規則に従い、`title`・`aria-keyshortcuts` と割り当て一覧のモーダルが担う。
- **アイコンのみのボタンが持続する状態の印を持つとき**、印を可視の文言にしない。文言を足したボタンは可視の文言を持つことになり、上項の定義からアイコンのみのボタンでなくなる。印は図形の外側の線・塗りで示し、**同じことを `aria-label` にも語で足す** — 線も塗りも図形と同じく読み上げに何も残さないので、目で見た利用者にしか届かない状態になる。上項の「`aria-label` には操作の名前だけを入れる」が退けているのはショートカットキーの併記であり、そのボタンが担う状態は名前の一部として入れてよい。押されているかどうかは `aria-pressed` が担うので、ここで言う状態はそれ以外のもの（3 配置切替の既定印。doc-8 §2.2）を指す。**持続する** とは、利用者が操作しない限りその状態が続くことを指す。
- **押した結果を一定時間だけ述べる表示には、上項を適用しない**（本項は TASK-72 で新設）。図形の差し替え・色の付与でそれを示してよく、**語は隣接する live region（`role="status"`）が担い、`aria-label` は操作の名前のまま変えない**。理由は 2 つある。ボタンのアクセシブル名は、そのボタンを名前で探し直す利用者にとっての識別子であり、押した後しばらく別の名前になる控えは、その間だけ見失われる。もう 1 つは、上項が `aria-label` へ語を足させる理由が「目で見た利用者にしか届かない状態になる」ことであって、隣に語があるならその理由自体が成り立たないことである。**規則を伸ばすのではなく適用条件で分ける**のは、この違いによる。live region は**内容が空のときも DOM に置いたまま**にする — 語が現れるのと同時に挿入された領域は、確実には読み上げられない。**この語は見える必要がない**。図形の差し替えが目に対して結果を述べているので、同じことを述べる可視の文は、操作のたびに読み飛ばす対象が 1 つ増えるだけである。可視にしない場合は**視覚的にのみ隠す**（`display: none` や要素の取り外しはアクセシビリティツリーからも外し、ツリーに無い live region は埋まっても読み上げられない — 常時 DOM に置く理由がそこで消える）。ただし**結果が図形の述べていないことを含むなら、その部分は可視で残す**（コピー失敗時に選択してコピーするための ID 文字列など。図形はそれを述べていない）。
- **可視の文言を持つ控えの中のアイコン**（本項は TASK-73 で新設）とは、押せる控えの内側にあり、**その控えが可視の文言も持つ**ときのアイコンを指す（タスク詳細の区画見出しの開閉印。doc-8 §3）。上の 2 つのどちらでもない — アイコンのみのボタンは可視の文言を持たないことを定義にしており、操作に属さないアイコンは押せる控えの中に無いことを定義にしているためである。置き場・寸法・色・`aria-hidden` は上の各項と同じで、加わるのは次の 2 つ。
  - **`aria-label` を与えない**。控えの名前は可視の文言が既に持っており、`aria-label` はそれに優先する（TASK-72 で確かめた）ので、足すと目に見える名前と読み上げられる名前が食い違う。
  - **上項を適用しないのは次の 2 つの場合だけである**（本項は TASK-139 で足した）。上項が禁じているのは、**完結した可視の名前と食い違う `aria-label` を足すこと**であり、可視の名前が完結していないなら食い違う相手がいない。**判定は「可視の文言があるか」ではなく「その文言でこの控えを指せるか・この控えについて画面が述べるべきことを述べているか」である。** 指せて述べているなら足さない（区画見出しの開閉印・メニューの表示切替行・文書とマイルストーンの 作成の入口 はどれも当たる）。**この項は `＋新規` の `＋` を図形にしたときに要ったもので、文字グリフの間は本節の型がそもそも当たっていなかった。**
    - **同じ文言の控えが同じ画面に何度も並び、どれなのかを文言が述べないとき。** レーンセルの `＋新規`（doc-7 §4.1）は 1 行あたり列の数だけ並び、どの控えなのかを決めているのは文言ではなくセルの位置である。`aria-label` を落とすと、同じ名前の控えが 1 行に 4 つ読み上げられる。
    - **§5 の保留理由を控え自身が名前で運んでいるとき。** 同じ `＋新規` は CLI 縮退時に理由を `aria-label` に入れる。**理由が画面全体に効くものだから**である（CLI 縮退・発行中。§5 はそれを上部帯 ② へ出すと定めており〔doc-7 §5.3〕、§8 は同じ文を控えごとに繰り返すことを退ける）ので、**この控えの隣にはその理由を持つ要素が無く、`aria-describedby` の指す先が作れない。** 上項を字義どおり適用すると、押せない理由を控え自身が何も述べない状態になる。**この控えが `disabled` ではなく `aria-disabled` なのは別の理由による** — フォーカスを保たせるためで、`aria-describedby` が使えないのは要素が無いからであってフォーカスの問題ではない（`Swimlane.svelte` の並べ替えは、行の上に理由の 1 行を置けるので `aria-describedby` を使っている）。
  - **図形が述べる状態を `aria-label` へ語で足さない**。「アイコンのみのボタンが持続する状態の印を持つとき、同じことを `aria-label` にも語で足す」を適用しないのは、その項が語を足させる理由（線も塗りも読み上げに何も残さないので目で見た利用者にしか届かない）が、ここでは成り立たないからである。区画見出しの開閉印なら、`<summary>` がその `<details>` の開閉をアクセシビリティツリーへ出しており、図形は同じことを目に対して繰り返している。**控えの仕組みがその状態を既に述べているかどうかが、適用の分かれ目**である。
- **印グリフ**（本項は TASK-77 で新設。decision-22）とは、押せる控えの内側に無く、**対象に付いてその状態を述べる**アイコンを指す（不整合印 ⚠️）。操作に属さないアイコンとの別は、指示対象が「置かれた帯・区画」ではなく「隣にある 1 つの対象」であることと、**族の色を持つ**ことである。置き場・寸法・`viewBox`・線幅は上の各項と同じで、加わるのは次の 3 つ。
  - **色は族の色**。図形自身は `currentColor` のままで、族の色は図形を包む要素が `color` として与える（`--mark-*` を参照する。decision-12 の色値一式は増えない）。満たすべき比は decision-22 の印グリフの収録条件（族の色 対 それが載る面で 3:1 以上）で、**印チップ配色規則の 4.5:1 ではない** — あれは 12% 混色背景との比であり、印グリフにその背景は無い。
  - **図形は `aria-hidden` のまま、包む要素が名前を持つ**。`role="img"` と `aria-label` をその要素へ置き、族名と理由を語で入れる。図形を読ませないのは上の各項と同じ理由（図形は語を持たない）で、包む側に名前を置くのは、押せないので `aria-label` を受け取れる控えがそこに無いためである。
  - **語を可視にしない**。印グリフを置く場所は、その語を出さないと決めた場所である（decision-22 のカード）。理由の全文は `title` と `aria-label` が持ち、**それを読むための場所が別にある**ことを設計側が保証する（タスクではタスク詳細の不整合区画、文書では閲覧ヘッダの理由行、マイルストーンでは操作ペインの理由行。doc-10 §5・§6。**場所そのものではなく「選択が開く場所」が規則である** — TASK-116 で文書の選択が開く先が更新フォームから閲覧へ移ったとき、理由行もそちらへ移った）。ホバーだけが理由への唯一の経路になってはならないのは §5 と同じである。**印グリフを足す場所は、この保証ができる場所に限る**（decision-24 が文書・マイルストーンへ広げたときに、置き場を先に決めたのはこの条件のためである）。
- **族を持たない状態の印**（本項は TASK-139 で新設）とは、押せる控えの内側に無く、対象に付いてその状態を述べ、**族の色を持たない**アイコンを指す（ACCEPTANCE CRITERIA の各項に付く完了印。doc-8 §3）。印グリフと分かれるのは次の 2 点だけで、置き場・寸法・`viewBox`・線幅・`aria-hidden` は上の各項と同じである。**編集セッション中の同じ印は押せる控えの中に入るので、そちらはアイコンのみのボタンである** — 同じ図形が、閲覧では状態を述べ、編集ではそれを切り替える控えになる。
  - **族の色を与えない**（図形は `currentColor` のまま）。完了かどうかは decision-6 の族のどれでもなく、族の色を借りると正常な項目が不整合・読取不能と同じ色で描かれる。印グリフの収録条件（decision-22）も、族の色を前提にしているのでここには掛からない。
  - **包む要素が `role="img"` と `aria-label` を持つ**のは印グリフと同じだが、入るのは族名と理由ではなく状態の語 1 つである（`完了`／`未完了`）。理由への到達経路を別に保証する条件（印グリフの 3 つ目）は当たらない — 述べているのは真偽 1 つで、そこに読むべき理由が無いためである。**`role="img"` を落とさない** — 図形が `aria-hidden` なので、包む要素は中身の無い `<span>` になり、`role` の無いその要素に置いた `aria-label` は読み上げに現れない（文字グリフだったころは中身そのものが名前だったので、この差は替えたときに初めて出る）。
- 無効化提示（5 章）はアイコンのみのボタンでも同じで、理由をホバーだけに置かない。
- **操作に属さないアイコン** とは、押せる控えの内側に無く、置かれた帯・区画が何を扱う場所かを図形だけで示すアイコンを指す（フィルタ帯の先頭の funnel。doc-7 §5.2）。置き場・色・`aria-hidden` は上の各項と同じで、寸法もアイコンを置く箱の `font-size` に従う（フィルタ帯なら帯の .72rem。既定の 1rem はボタンに与えたものなので、ここには効かない）。押せる控えの中に無いことから、次の 3 つが加わる。
  - **図形が示すことは、同じ帯・区画の中の語も述べていなければならない**。アイコンは常に装飾なので、読み上げには図形が何も残さない。図形だけが述べている状態にすると、その帯が何をする場所かは、目で見た利用者にしか届かない。フィルタ帯では「＋ 絞り込み」と絞り込みトークンの 属性名 が可視でそれを述べ、テキスト欄と 2 つの解除の控えの `aria-label` が語として述べており、funnel はそれを図形で繰り返している。**可視の例に 既定に戻す を挙げていたのは 2026-08-15 までである** — あの控えはアイコンのみのボタンになり、語は `aria-label` と `title` が持つ（TASK-175。doc-7 §5.2）。**並び順 は可視の例にならない** — doc-7 §5.2 が「並び順はフィルタではない」と定めており、あの語が述べるのは帯が絞り込む場所であることではない。
  - **隣の控えの `<label>` の中に入れない**。図形の指示対象は帯全体で、1 つの入力欄より広い。ラベルに入れると、より狭い対象の名前として読まれ、図形と指示対象が食い違う。
  - 押せないので `aria-label`・`title`・フォーカスのいずれも与えない。与えると、押しても何も起きない要素が操作として読み上げられる。
- **図形へ替えない文字がある**（本項は TASK-139 で新設）。本節が替えるのは**記号** — 単独で立って対象・操作に代わる 1 文字 — であって、画面に出る非英数字すべてではない。**「文字グリフだから替える」で通すと、契約が別のところで 1 文字と定めたものまで替わる。** 次の 4 つは替えない。
  - **正常な不在の `—`**（§6）。§6 が「`--faint` の `—` 1 文字だけで示す／警告記号・アイコン・枠を付けない」と定めており、図形にすると §6 に反する。**原文も同じことを述べている**（画面設計案 06 の契約 #2「空セルの `—` には色も記号も与えず、読取不能とは決して同じ見た目にしない」。doc-12 §7.2）ので、ここは逸脱でも追随でもなく、替えないこと自体が両方に従っている。
  - **約物**（`読み込み中…`・`選択…` の `…`、括弧、中黒）。文の一部であって対象に代わっていない。**§12 の 語尾の `…` もここに入る** — あれは押下が実行前確認を通ることを控えの語で予告する規則であり、図形にすると控えの語の一部だけが図形になる。
  - **語の中の記号**とは、可視の文言と同じ文字列の中にあり、単独では控えの名前にならない記号を指す（パンくずの `← スイムレーン`〔原文。doc-12 §8〕、フィルタ帯の `＋ 絞り込み`〔原文。doc-12 §4.3〕、GIT 履歴の `全面表示で開く →`）。記号だけを図形へ抜き出すと語が変わる。**1 つ目については、その語が変わることを承知のうえで図形へ替えた**（2026-08-15。decision-31。TASK-176）。プロジェクト詳細画面の 戻る は `arrow-left` のアイコンのみのボタンになり、可視の語を持たない — 行き先の語は `aria-label` が持つ。**本項は替えないと定めており、これはそこからの意図的な逸脱である。** 替えた理由は、固定ヘッダの廃止で ☰ がこの画面のヘッダ行へ降り、行の左右が語で埋まると 1 行に収まらなくなったことである。**原文（doc-12 §8）はそのままにする** — doc-12 §1 が原文の値のまま写すと定めており、本項が引く鎖はそこで切れる。**逸脱はこの 1 件に限り、他の 2 例には及ばない。** **3 つ目だけは原文の語ではない** — 原文が同じ位置に刷るのは件数を含む「残り 1 件と関連 PR は全面表示で →」で（doc-12 §3）、実装のラベルはそれを取れない（この控えは展開する残りが無いときにも出る）ので TASK-79 が自前の語を置き、**画面設計案 02 へ帰属させないと決めた**（TASK-80 が「原文は『全面表示で開く →』」を誤りとして記録している）。**それでも語の中の記号である理由は原文の側ではなく本節の側にある** — `→` が可視の文言と同じ文字列の中にあり、単独では控えの名前にならない、という定義に当たるからである。**レーンセルの `＋新規` はこれに当たらない** — `＋` が語の外に独立して立っており（原文も列の下の「＋」を記号として刷っている。doc-12 §8.6）、同じ 作成の入口 が doc-10 §1 では既に図形だったので、同じ入口が画面によって 2 通りの姿になっていた。
  - **キーの名前**（`⌘`）。和音を刷るのは doc-7 §2.1 の要求で、`⌘` はそのキーそのものの名前である。

## 3. チップの 4 系統

同じ「小さな四角い札」に見えるものが 4 系統あり、混ぜると別の意味が同じ見た目になる。形・塗り・太さで分ける。**印だけは札ではない形も持つ**（印グリフ。decision-22）ので、1 つ目は 2 つに分けて書く。

- **印チップ**（照合不能・継続検出停止・読取不能・通知、および不整合のうち欠けた値の位置に置くもの）: 文字＝族の色、背景＝族の色 12% 混色、枠＝族の色 45% 混色、角丸 3px、`cursor: help` と説明（decision-12 の印チップ配色規則）。**この `cursor: help` は §5 が無効化提示から撤去した後も残る**（TASK-138。理由は §5）。族の判別は色相の距離とチップ文言の二重化で行う。
- **印グリフ**（不整合印 ⚠️。decision-22）: 語を持たず、族の色を図形自身の色として持ち、背景も枠も持たない。**印チップと同じく `cursor: help` と説明を伴う**（TASK-138 が §5 の撤去の対象から外した。理由は §5）。**この 4 系統の 1 つ目の別形であって 5 系統目ではない** — 系統を分ける軸は「対象に付いてその状態を述べる札かどうか」で、印グリフはその軸では印と同じものである。分かれるのは描き方だけなので、収録条件も別に置かれる（decision-22 の印グリフの収録条件）。
- **Type**（`kind:*` 由来の分類、decision-5）: `--fg` 13% 混色の塗り ＋ 太字 ＋ 角丸 3px。未知 Type は実線輪郭のみ、Type 未設定は破線輪郭で色を与えない（decision-6 の中立表示）。
- **通常ラベル**（自由タグ）: 輪郭のみのピル（角丸 999px）＋ 細字 ＋ `--muted`。Type と同一の一覧に混ぜない（doc-7 §3・doc-8 §4）。
- **priority**: 文字＝優先度色（§2.1）、背景＝優先度色 12% 混色、枠＝優先度色 45% 混色、角丸 3px（§2.2）。**印チップ配色規則と同じ描き方だが、引く色は族ではなく優先度色である**（decision-23）。**族の色を借りていない**ので decision-12 が禁じた族の汚染は起きない — あの項が挙げた理由は「high の赤と medium の黄土が読取不能・不整合の族の色と同色である」ことで、優先度色は独立した 3 値であり、族の色そのものでないことは `src/lib/theme.test.ts` が押さえる。**無彩 3 段（旧: high＝`--fg` 塗り、medium＝`--line-strong` の輪郭、low＝`--line` の輪郭）はやめた** — 同じ priority を優先度の縁（§2.3）が色で・チップが濃淡で述べる状態は、利用者に 2 つの符号を覚えさせる。priority 未設定 と priority 未知（3 段のどれにも一致しない値）は色を持たず、輪郭のみ・`--muted` の中立の姿のままで、frontmatter の語をそのまま出す。

保存区分印と、未分類区画に出す原文 status と、決定事項の status は、族でも Type でもない中立の情報である。輪郭のみ・`--muted` で示し（角丸は §2.2 の チップ の 3px）、族の色を与えない。述べているのは「どこに置かれているか」「元の語は何か」であって、対象に問題があることではない。

**決定事項の status がこの括りへ入ったのは 2026-08-18 である**（TASK-166。それまでは素のテキストだった）。**入れた判断は「色を与えない」であって、5 系統目を作る判断ではない** — 本節が既に持っているこの括りへ 3 つ目として入る。ユーザーは 2026-08-13 の目視で「強いて言えば `accepted` が backlog browser の方が目立っている」と述べており、**上流の browser は 4 語を色で描く**（実測: `proposed` 黄・`accepted` 緑・`rejected` 赤・`superseded` 灰。一致しない値はすべて灰で、鍵は小文字化して引く）。**それでも色を与えないのは、この値には台帳の側が宣言する集合が無いためである** — タスクの status は `config.yml` が宣言し（decision-4）、priority は Backlog CLI 自身が 3 段を列挙するのに対し、`decision create` は `-s` に渡された文字列を検証せずそのまま書く（実測。`-s` が無いときに書くのは `proposed`）。**上流の 4 語は上流 UI の申し合わせであって、Atlas がそれを色で述べれば Atlas の契約になる。** 札の縁を与えるところまでが、Atlas がこの値について言えることである。**色値を 1 つも足していない**ので、この形に 収録条件 は無い — 引くのは既にある `--line-strong` と `--muted` だけである。**出す場所は doc-10 §10 が決めている 2 か所**（決定事項一覧のカードと閲覧ヘッダ）で、**どちらも同じ姿を取る** — 同じ値が同じ画面で 2 通りに描かれない。

**札にするのは、その対象自身の状態を述べる語である。** 出どころは問わない — frontmatter が持つ語（未分類区画に出す原文 status、決定事項の status）でも、置かれた場所から導いた語（保存区分印。frontmatter の status とは独立した軸である）でもよい。**同じプロジェクト詳細の 一覧列 に並ぶ 文書の `type` とマイルストーンの件数は素のテキストのまま残る** — 件数は Atlas がそのマイルストーンに紐づくタスクを数えた値であって、そのマイルストーン自身の状態ではなく、`type` は状態ではなく分類（タスク側で Type として扱う対象であり、そちらは decision-5・decision-20 の系統）である。**その結果、3 つの一覧列で card-head の体裁が揃わなくなる**（決定事項の列だけが札を持つ）。**承知のうえで採っているので、揃っていないことを欠陥として起票しない。**

**畳んだ列のレーンセルに並ぶ四角（doc-7 §2.2）もこの 4 系統に入らない。** 小さな四角に見えるが、対象に付いてその状態を述べる札ではなく、そのセルのカード 1 枚を 1 つずつ置き換えた図形である。**族の色は与えない** — 借りると不整合・読取不能の札と同じ見た目になる（decision-6）。文字を持たず、読み上げにも出さない。**優先度色は与える**（decision-23。**本節は長く「色を与えない」と書いていたが、その理由は族の色についてのものだった**）。畳んだ列でも priority の分布が読めるようにするためで、3 段のどれでもないタスクの四角は中立の `--line-strong` のまま残る。非文字要素なので満たすべき比は面に対する 3:1（優先度色の収録条件の 3 番目）。

**色だけで述べない**（WCAG 1.4.1）。四角は 段 ごとにまとめ、high → medium → low → 段なし の順に並べ、**段ごとに高さを変える**（段なしは幅も狭くする — そこだけは low と色相でしか違わなくなるため）。分布は色である前に形である。**読み上げには、四角ではなくセルの件数が内訳を語で持つ** — `aria-hidden` の図形を N 個読ませるのは雑音であり、色が足した情報を総数だけでは代われないためである（doc-7 §2.2）。

**絞り込みトークン（doc-7 §5.2）はこの 4 系統に入らない。** 見た目は札に近いが、内側に自分を解除する控え（§2.4 のアイコンのみのボタン。図形は lucide の `x`。**2026-08-11 まで文字グリフの `×` だった** — TASK-139）を持つ操作要素であり、対象に付いてその状態を述べるチップではない。角丸は §2.2 の**ボタンの 4px** を取る（チップの 3px ではない）。1 系統として数えないのは、4 系統が「対象に付く札を混ぜない」ための区別であり、押せるものをそこへ足すと区別の軸が 2 つになるためである。

## 4. 上部帯

上部帯は**下表の種**で、**出現順ではなく重要度の固定順**に積む。同時に立ちうる最大は表の行数と同じで、表に挙げた種以外に上部帯を作らない。各帯は 1 行に収め、左端 4px にその帯の族の色を置く。

**閉じた集合は表そのものが持ち、本文はその数を書かない**（2026-08-09 に改めた。TASK-131）。数を書くと、行を落とすたびに表と本文の 2 か所を揃えることになり、同じ表から別々に 1 行を落とす作業が並んだとき（TASK-131 の ⑥ と、⑤ を落とすことがありえた TASK-134）に、先に走ったほうが後のほうの前提を書き換える。数が要るのは本節末の最悪ケースだけで、あれは高さの上限を述べる主張なので、その時点の行数をそこに書く。**TASK-134 は結果として ⑤ を落とさなかった**（2026-08-10。成功を落としても ⑤ には失敗・差し控え・画面が述べない帰結が残った。下記）が、それが分かったのは着手して ⑤ が現に運んでいるものを数えた後である。**この規則の値打ちは、落ちる行が事前に分からないところにある。**

| 順 | 帯 | 何を伝えるか | 左端 4px | 閉じられるか |
|---|---|---|---|---|
| ① | 確認（未保存入力の破棄前確認など） | 利用者の回答待ち | `--info` | 閉じられない（回答で消える） |
| ② | CLI 縮退（doc-5 §5） | 作成・更新をどこからも発行できない | `--mark-inconsistent`（借用。下記） | 閉じられない（CLI を検出できると消える） |
| ③ | 台帳読取専用（doc-3 §2.2） | 台帳の更新・登録解除・並べ替えができない | `--mark-unreadable` | 閉じられない |
| ④ | 継続検出停止（doc-9 §3） | 表示が実ファイルより古いかもしれない | `--mark-undetectable` | 閉じられない（再読込で消える） |
| ⑤ | 通知 | 1 件の失敗・差し控えと、画面が述べない帰結（下記） | `--info` | × で閉じる |

順は「回答待ち → 発行できない → 表示が古いかもしれない → 1 件についての報せ」で並べる。②③ が④より上なのは、操作が通らないことは表示の鮮度より先に知る必要があるためで、②が③より上なのは、CLI 縮退が止める操作の範囲（タスク・文書・マイルストーンの全更新）のほうが台帳読取専用（台帳のみ）より広いためである。②③ を 1 本にまとめないのは、原因が別で片方だけ立つことがあり、族の色もそれぞれ異なるからである。

**② は不整合の族の色を借りる**（decision-22）。CLI 縮退はアプリ全体の発行可否であって管理ファイル 1 件の不整合ではなく、改称もしていないが、独自の族は立てない — 族は色を選ぶ単位であって事象の分類ではなく、この 2 つが同じ 1 つの対象に同時に付くことはないからである。

順を出現順にしない理由は、帯が積まれるほど上の行が下へ押し出され、回答待ちの ① が通知 ⑤ の下に埋もれうるためである。①〜④ を閉じられなくするのは、無視できる形にすると「発行できない状態や古い表示のまま操作を続ける」経路ができるからである。

**⑥ 行非表示 は 2026-08-09 に表から降りた**（TASK-131）。利用者が自分で作った状態を告知する帯であり、切り替えも一覧も共通入口のメニューへ寄せたので（doc-7 §2.1）、帯が受け持つものが残らなかった。非表示が何件あるかは doc-7 §2.1 の総件数のプロジェクト数の比が述べている。**画面設計案 03 の追加帯 4 種は 4 番目にこれを数えており**（doc-12 §4.2）、撤去はそこからの意図的な逸脱である。

**⑤ が運ぶものを 2026-08-10 に絞った**（TASK-134）。**発行が通った事実そのものは ⑤ に載せない。** 発行の結果を述べる本則の置き場は**控えの隣の結果文**である — 控えの隣の結果文とは、発行した控えと同じ層・同じ区画の中に置く、その発行の結果を述べる文を指す（設定モーダルの下部操作行に出る「保存できませんでした: …」、プロジェクト詳細の各区画が控えの隣に出す発行結果）。**⑤ はその置き場が無いときの届け先である** — 押下そのものが無い起動時の失敗（設定の読取・変更通知の購読・外部エディタの確認）、控えの隣に結果を置く場所を持たない操作（レーンヘッダの並べ替え）、押した層が結果より先に閉じるもの。

**⑤ に成功が載るのは、押下の結果として画面に現れた姿が押下の名前と食い違い、その理由が画面のどこにも無いときに限る**（状態遷移が id と保存区分を変えるため詳細パネルを閉じたこと〔doc-5 §3.3〕、作成したカードが絞り込みに落ちて出ていないこと〔doc-7 §5.2〕）。**成功したこと自体を伝えるためだけの帯は立てない** — 画面は既にその姿になっており、帯はそれを繰り返すだけである。

**この規則で設定の保存の成功が帯を持たなくなった**（TASK-134。レーンセルの作成の成功も、カードが絞り込みに落ちない限り同じく持たない）。設定モーダルは書込みが通ったときだけ閉じ、失敗のときは層を保ったまま控えの隣の結果文を出す（§7 の下部操作行）ので、**層が下りたこと自体が保存の通った報せ**である。既定の保存区分・既定の詳細配置・外部エディタ指定が後の起動・後の押下でしか効かないことは、帯を立てる理由にならない — それらは画面を変えないので、説明を要する食い違いがそもそも起きていない。

**TASK-74 の目視が残した「保存後の ⑤ の変化が分かりづらい」は、これで対象ごと無くなった**（TASK-134）。⑤ だけを他の種と違う目立ち方にする案は採らない — 目立ち方は本節が全種に共通で決めており、1 種だけを強めると描き分けが崩れる（TASK-74 の判断をそのまま引く）。**気づくのが遅れて害になるのは、その帯が唯一の報せである場合に限る**: 残る ⑤ はどれも読まれた時点で内容が要るもので、見逃した瞬間に無価値になる成功の報せとは性質が違う。

**⑤ の左端 4px は `--info` のままである。** 失敗の族の色を取ると、②③ の「画面全体で発行できない状態」と ⑤ の「1 件の発行が通らなかったこと」が同色になる。⑤ が述べるのは 1 件についてであって画面全体の状態ではない。成功と失敗が同色になることは承知のうえで採り、分けるのは色ではなく隣の語である（doc-8 §2.2 のコピー成功の表示が先に同じ判断をしている）。

②③④ は個々の操作の無効化理由（5 章）と内容が重複するが、それでよい。ホバーしないと理由に到達できない状態を作らないためである。

**1 行に収まらない内容は折り返さず、要約へ縮約して全体を別の場所から読ませる**。折り返しを許すと、狭いウィンドウ・長い理由文・文字サイズ拡大で上部の占有が伸び、「フィルタ帯 1 行 ＋ 上表の帯」で頭打ちという性質が崩れる。縮約の形は帯ごとに定める（例: 継続検出停止の帯は理由と「表示が実ファイルより古い可能性があります」に縮約し、行ごとの説明はその行の印が持つ）。ただし帯が持つ操作（確認への回答・再読込）は縮約しても帯に残し、操作へ到達するために別の場所を開かせない。

フィルタ帯 1 行 ＋ 上部帯 5 本（上表の全種）が同時に立つのが最悪ケースで、画面上部の占有はここで頭打ちになる。

## 5. 無効化提示

提供できない操作は、消さずに無効化し、理由を必ず添える。

- 見た目は破線枠 ＋ opacity .45 の 2 点とする。押せる操作（実線枠）と見分けられる形にする。**マウスカーソルは地の矢印のままにする — 2026-08-11 に `cursor: help` を撤去した**（TASK-138）。理由と、撤去が宣言を落とすことではない理由は、本節末の 契約 #9 からの逸脱 の項にある。
- **理由をホバーに依存させない**。`disabled` を付けたネイティブの操作はフォーカスを受け取らず、`title` はキーボード・タッチ・スクリーンリーダーのいずれからも安定して到達できない。理由は次のどちらかで到達可能にする。
  - 操作の近くに**常時表示する補助文**として置く。この場合は `disabled` のままでよい。
  - 操作を `aria-disabled` とフォーカス可能なまま（押しても発行しない）にし、`aria-describedby` で理由の要素へ結ぶ。
  `title` はこれらの補助にとどめ、唯一の格納先にしない。
- 画面全体に効く理由（CLI 縮退・台帳読取専用）は上部帯にも出す。個々の操作の理由と重複してよい。
- 理由の無い無効化を置かない。「なぜ押せないか」が分からない操作は、故障と区別できない。
- **理由に要るのは、押せないのが Atlas の側の事情だと読めることまでで、どの機構が手段を欠くかは要らない — 2026-08-17 に明示した**（TASK-192。オーナーの画面目視から）。「References は Atlas からは最後の 1 件を削除できません」は本節の理由であり、そこに添えていた「CLI に空集合化の手段がないため」は落としてよい。**この例文はもう画面に無い** — 2026-08-22 に空集合化が CLI から行えるようになり、無効化ごと消えた（TASK-153、doc-5 §3.5）。**規則は動かない** ので、例として引き続き引く。**根拠を読んでも利用者の取れる行動は変わらず**、`Atlas からは` の側が「外からなら行える」ことまで述べている。**落としてよいのは、残る句が不可の及ぶ範囲を述べているときだけである** — 「削除できません」だけにすると前項の「故障と区別できない」に戻る。§8 の 発行手段の記述 が「『CLI に手段が無い』を落とすと不可の理由がそのまま消える」と述べているのは、範囲を述べる句を他に持たない文についてである。
- **保留判定と保留理由を別の欄に持つ — 2026-08-08 に新設**（TASK-127）。**保留判定**とは、その控えを無効化するかどうかの真偽そのものを指し、**保留理由**とは、その無効化の理由として画面へ出す文を指す。実装はこの 2 つを 1 つの値の別々の欄として持ち、**理由文が非 null であることを保留判定そのものにしない**。前項は「理由の無い無効化」を禁じており、それを守るには判定と理由が 1 つの値であればよいのだが、**兼ねさせると逆向きに壊れる** — 理由文を落とした時点で無効化も一緒に落ちる。`ProjectDetail.svelte` の概要区画の保存が現にそうなり、§8 の一掃が理由文 2 件を落としたときに、変更が無いときも入力に問題があるときも保存が押せる状態になった（doc-10 §4.1 に反する）。判別子と理由を別の欄に持てば、どちらの向きにも壊れない — `IssuePlan`（doc-5 §5）と `RedetectControl`（doc-10 §4.1）が先にこの形を取っている。**画面に出る文を落とす作業は、その文が保留判定を兼ねていないかを先に見る**（§8 の一掃がこの検査を持たなかった）。**2026-08-19 に 18 か所を本項の形へ揃え、以後は 1 つの型で書く**（TASK-128、`src/lib/availability.ts`）。**18 は、TASK-127 が数えた 8 の残り 7 に 11 を足したものである** — そのうち 3 つは本項が書かれた後に書かれた控えで、**規則を書いただけでは新しい控えが同じ形で書かれるのを止められないことがここで実測になった。** **`{ 可否, 理由 }` の 2 欄でも、可否を理由の非 null から導けば同じように壊れる** — 可否はその原因から組む。**走査は `src/lib/availability.test.ts` が持つが、押さえるのは字面（`…Blocked` のような理由名の値を `null` と比べて無効化している控え、および理由の非 null から導いた `enabled`）だけで、本項そのものではない。** **18 件目（`ProjectRegister.svelte`）を見つけたのは走査ではなくレビュワーの通読である** — あれは判定と理由を同じ述語から別々に導いており、`null` と比べる箇所がどこにも無いので、TASK-128 の数え直しも新しい走査も構造的に届かない。**したがって「揃え終えた」とは書かない** — 数えた範囲で揃えた、が正確なところである。
- **提供しない操作**（Atlas がこの版で出さないと決めたもの）は、無効化されたボタンとして並べない。無効化は「今は条件が揃っていない」を意味し、提供しない操作はそれとは別だからである。**その先で不在を掲示することも、2026-08-08 にやめた**（TASK-123）: 本項は改訂まで、提供しない操作を名称・写像先・理由の 3 点で並べる区画（当時の doc-10 §6）へ置くよう求めていた。**Atlas は backlog.md の CLI が提供する範囲で操作を出す製品なので、その外にあるものが画面に出ないことは製品の性格から自明**であり、区画が守っていた実質は撤去の時点で文書の削除 1 件だけだった（doc-10 §9）。**本項が今も禁じているのは、押せない控えを画面に置くことである** — 出さないと決めた操作については控えを置かず、したがって添える理由も無い。
- **破壊的操作の確認は §12 の実行前確認が定める**（2026-08-11 に移した。TASK-137）。本項は改訂まで「破壊的操作の確定は二度押しとし、一度目でラベルを確認文へ差し替える」と定めていた。撤去した理由と替わりに置いた規則は §12 にある。**本節に残るのは無効化提示だけである** — 実行前確認は押せる控えの話であって、押せない控えの話ではない。
- **画面設計案 06 の契約 #9 からは 2 点で意図的に外れる — 2026-08-11 に記録した**（TASK-138）。原文は無効を **破線枠 ＋ opacity .45 ＋ `cursor:help` ＋ `title` で理由** の 4 点で定めており（doc-12 §7.1・§7.2）、実装が採るのは前の 2 点だけである。**2 点をここに併記するのは、4 点のうちどれが生きているかを 1 か所で読めるようにするため**で、`title` 必須 のほうは 2026-08-11 までどの doc も逸脱として書いていなかった — 本節は次項の規則とその理由を前から持っていたが、それが原文の 4 点目を採らないことだ、とは述べていなかった。**規則の側は書けていて、それが逸脱であるという帰属だけが無かった**状態である。
  - **`cursor: help` を与えない。** このカーソルが述べるのは「ここにホバーで読める説明がある」ことであって、押せないことではない。押せないことは破線枠と opacity が形と濃度で既に述べており、3 点目が足していたのは説明の予告だけである。**その予告が全画面へ一律に掛かるので、説明を持たない控えにも同じカーソルが出て、出ないツールチップを約束していた**（2026-08-09 のユーザーフィードバック「押せないボタンに対してカーソル変更はしなくてよいかも」）。実測では、無効化提示が掛かりうる記述 50 件のうち **11 件が `title` 属性を持たず、さらに 2 件が保留理由ではなく動作の名を出す** — 合わせて 13 件では、カーソルが予告した説明がそこに無い。**説明の有無で出し分ける案は採らない** — §3 の印がその形を取っているが、あちらはカーソルが説明への唯一の予告であるのに対し、こちらは理由の到達経路を次項が 2 形で保証しているので、予告そのものが要らない。出し分ければ、同じ「押せない」が控えによって 2 通りに見える。**`not-allowed` も置かない** — component ごとに `default` と `not-allowed` へ散っていたものを 1 か所へ寄せたのが `cursor: help` だったので、別の特別なカーソルを置けば同じ散逸を別の値で作り直すことになる。**ただし撤去は宣言を落とすことではない。** 押せる控えを描いているのは 14 の Svelte ファイルに散った 30 本の `cursor: pointer` で、`cursor: help` はそれを上書きしていた。宣言を落とすと手の形が通り、**押せない控えが「押せる」と約束するカーソルを出す** — 指摘の裏返しになる（2026-08-11 に WebKit・Chromium で実測。落とした状態では 3 画面とも `pointer` を返した）。したがって無効化提示は**地の矢印を明示する**（`cursor: default`）。**押せる控えの `pointer` には触れない**（実測 56 件、両エンジンとも変化なし）。
  - **`title` を必須にしない。** 理由は次項が述べているとおりで、`disabled` を付けた操作はフォーカスを受け取らず、`title` はキーボード・タッチ・スクリーンリーダーのいずれからも安定して到達できない。原文の 4 点目をそのまま採ると、理由の唯一の格納先が `title` になる。**必須なのは理由が到達可能であることであって、その手段が `title` であることではない。**
- **§3 の 印チップ・印グリフ の `cursor: help` は落とさない**（2026-08-11。TASK-138）。**約束している相手が違う** — 無効化提示のカーソルは `title` の有無を見ずに全画面へ掛かっていたが、印チップのカーソルは説明の存在に鍵が掛かっており、印グリフは説明を無条件に伴う。「カーソルが変わるのにツールチップが出ない」という指摘の前提が、印では成り立たない。**そもそも印は押せない控えではない**ので、本節が及ぶ対象でもない。

## 6. 空・不在の描き方

- **正常な不在**（空セル・コミット該当なし）は、`--faint` の `—` 1 文字だけで示す。族の色を与えず、警告記号・アイコン・枠を付けない。「該当タスクが無い」ことを読み取れる必要があるため、何も描かないのではなく中立の目印を 1 つ置く。decision-6 が禁じているのは、正常な不在にエラー色・警告記号を与えることと、読取不能と同じ見た目にすることであって、中立の目印そのものではない。この形は現行の実装（`LaneCell.svelte`）と一致する。
- **読取不能**は族の色（`--mark-unreadable`）と理由と復帰操作を伴う。正常な不在と決して同じ見た目にしない。
- **Type 未設定**は破線輪郭で色を与えない。未知 Type（実線輪郭）とも区別する。

## 7. モーダルの閉じる

本節の**モーダル**は doc-7 §2.1 の被せ層のうち、開いている間フォーカスを内側に留め、Escape で閉じ、閉じたら開く前の操作へフォーカスを戻す層を指す。**§2.1 が「同時に 1 枚」を数えるときの被せ層はこれより広く、メニューと値一覧ポップオーバーを含む**（2026-08-19 に書き分けた。TASK-120）。**本節の契約はその 2 つに掛からない** — 掛かるのは、いま挙げた 3 つの形を満たす層だけである。それらの閉じる契機は §2.1 のメニューの項と §5.2 が別に定める。**2026-08-07 に、開く先の列挙から層の形の定義へ改めた**（TASK-117）。本節は 2026-08-07 まで「プロジェクト登録・設定・キーボード操作の一覧が開く先」と数え上げており、その 3 つはどれも固定ヘッダの入口だった。TASK-117 が足した文書・マイルストーンの**作成モーダル**（doc-10 §1）を上げるのは 1 プロジェクトに閉じた操作で、doc-7 §2.1 は自分の末尾でそれを共通入口から締め出している。**列挙のままだと、締め出された側が上げた層に本節の契約が付くかどうかが、どちらの節からも読めない** — doc-7 §2.1 はその操作を数える立場になく、本節は §2.1 の数え上げを引いていたからである。層の形で定義すれば、誰が上げたかは契約に関わらない。本節が述べるのは層の出口であって、入口ではない。doc-8 §2.1 の**中央モーダル詳細配置は含まない** — あちらはタスク詳細の 3 配置の 1 つで、閉じるは見出し 1 行目の操作群が持つ（doc-8 §2.2）。

- **モーダルは右上に `×` を 1 つ持ち、それがモーダル自身の閉じる操作である**（TASK-76 で導入。原文は画面設計案 01 の設定モーダル。doc-12 §2.2）。描くのは層そのものであって中身ではない。中身ごとに置くと、同じ 1 つの操作が中身の数だけ別の位置・別の見た目になる — TASK-76 の前は 3 つの中身が見出しの脇にそれぞれ文言ボタンを置いており、設定モーダルだけは TASK-74 でそれを失っていた。
- **`×` は §2.4 のアイコンのみのボタン**として描く（図形は lucide の `x`）。`aria-label` は「閉じる」だけとし、何を閉じるかを加えない — それは `role="dialog"` の `aria-label` が既に述べており、2 つを繋ぐと「プロジェクトを登録を閉じる」になる。**§2.4 に型は増えない。**
- **`×` はモーダルの中で最初の操作**に置く。層の出口が開いた直後から 1 打鍵の距離にあり、フォーカスを与える操作が対象をスクロール領域へ引き入れるので、長い中身のモーダルが自分の見出しより下へスクロールした状態で開くこともない。
- **`×` が述べるのは「この層を閉じる」だけ**である。**下書きを持つモーダルは、それに加えて下部操作行を持ち**、そこの押下が下書きをどう扱って出るのかを可視の文言で述べる（設定モーダルの「変更せずに閉じる」「保存する」。TASK-74）。**役割の別は、下書きの行方を語で述べるかどうかにある** — 破棄するかどうかではない。`×` も「変更せずに閉じる」も下書きを書かずに出るので、そこでは分かれない。原文の設定モーダルで `×` と下部の「閉じる」が同じ操作なのは（doc-12 §2.2）、原文に保存が無く、述べ分ける下書きが存在しないためである。
- **下部操作行の押下が発行するとき、その発行の結果は同じ層の中で述べ、失敗ではこの層を閉じない**（TASK-74 が設定モーダルで取った形を、2026-08-10 に本節の契約として書いた。TASK-134）。閉じてしまうと下書きが層と一緒に消え、何も書かれていないことを利用者は次の起動で知ることになる。**述べる場所は押した控えの隣である**（§4 の 控えの隣の結果文）— 層が残るのだから、⑤ 通知へ回す理由が無い。⑤ が届け先になるのは、押した層が結果より先に閉じるときだけである。
- **出口はすべて 1 つの閉じる要求へ集まる**。`×`・Escape（doc-7 §2.1）・下部操作行の「変更せずに閉じる」は、モーダルを配線している側（シェル）の 1 つの経路へ届く。TASK-86 の破棄前確認は、その 1 経路の前に置く。
- **いま閉じられない事情はシェルが持ち、`×` へ渡す**。発行中の書込みがあるなど、閉じる要求を受け付けられない事情があるとき、`×` は 5 章の無効化提示に従う（`aria-disabled` のままフォーカスを受け、`aria-describedby` で理由へ結ぶ）。事情を持つのがシェルなのは、Escape と下部操作行の押下も同じ 1 つの事情に従わなければならないからで、`×` だけが自分で判断すると 3 つの出口が別々の事実を見る。**理由を可視で出すかどうかは中身が決める** — 下部操作行が同じ理由を刷っているなら、`×` の側は目に見えない置き方（アクセシビリティツリーには残す）でよい。同じ 1 つの事情を 1 つの箱の中で 2 度述べないためである。
- **本節はモーダル以外の閉じる・解除を覆わない。** 上部帯の通知・絞り込みトークンの解除・status 別名表の行削除も同じ lucide の `x` を描くが（**2026-08-11 に TASK-139 が 3 か所とも文字グリフから替えた。それを定めるのは §2.4 であって本節ではない**）、本節が定めているのは**層の出口としての `×`** — 右上に 1 つだけ置くこと、`aria-label` を「閉じる」だけにすること、シェルが持ついま閉じられない事情に従うこと、破棄前確認を通ること — であり、3 か所のどれもその条件を持たない（上部帯の通知は帯 1 本を降ろし、トークンの解除は条件 1 件を外し、別名表の行削除は編集中の表から行を 1 つ外す。どれも層ではない）。**図形が同じであることは、契約が同じであることではない。**
- **破棄前確認を通すのは、下書きの行方を語で述べていない出口だけである**（TASK-86）。`×` が述べるのは「この層を閉じる」だけで、Escape は語を 1 つも持たない。下書きがあるなら、その行方を述べるものが問いのほかに無いので、この 2 つは問いを通る。下部操作行の「変更せずに閉じる」は既に述べているので通さない — 控えの文言と問いが同じことを述べ、**押した利用者はもう答えている**からである。**これは出口ごとに別の事実を見ることではない**: 3 つとも 1 つの閉じる要求へ集まり、いま閉じられない事情も 1 つのまま従う。分かれるのは本節が既に立てている軸 — その出口が下書きの行方を語で述べているかどうか — の側だけで、**規則は 1 本のままである**。
- **モーダルの出口が上げた破棄前確認は、モーダルの中に出す**（TASK-86）。破棄前確認そのものは doc-8 §6.3 が定め、その置き場は上部帯の ①（doc-7 §5.3）だが、本節のモーダルはその上部帯を覆う（doc-7 §2.1 のフォーカス内留めのため意図的）。覆っている層の出口が上げた問いを ① に置くと、問いの対象であるモーダルが消えるまで読めず答えられない。**これは §4 の表に 1 種を足すものではない** — §4 が数えているのは画面が積む告知で、こちらは同じ ① の告知を、それを上げた層の中に描いたものである。**問いの文は doc-8 §6.3 のものをそのまま使う**。モーダルの経路は §6.3 が数える 5 経路の外にあり、失われる未保存入力も編集セッションのものではないが、同じ喪失を 2 通りに述べないためである。**進む側の答えだけは「破棄して閉じる」とする** — §6.3 が「破棄して続ける」と広く言うのは、5 経路の行き先が同じでない（別タスクを開く・前後移動・詳細配置の切替は何も閉じない）からで、モーダルの 2 経路はどちらもこの層を閉じることに限られる。**指示対象より広い語を選ばない。** 戻る側は「編集に戻る」のままである。**問いを描く場所は、いま最前面にある層で決まる** — したがって、別の経路が上げた確認が立っているところへモーダルを開いたときは、その確認は失効する。モーダルが自分のものとして描くと、進む側の答えが背後で別の経路を実行し、変わってしまった画面の上にモーダルだけが残る。同じ理由で、**確認に答えないままモーダルが閉じたときも、確認は層と一緒に消える**（残すと、もうどこにも無い入力について問い、既に起きた継続を差し出す帯が背後に立つ）。**失効で破棄されるものは無い** — 要求が取り下げられるだけである。
- **答えを待っている状態と、いま閉じられない事情は別である**（TASK-86）。前者は閉じる要求が出ていて答えを待つ状態で、`×` は押せるままにする（もう一度押しても同じ問いをもう一度出すだけである）。後者は要求そのものを出さない状態で、`×` は §5 の無効化提示に従う。混ぜると、答えの控えが同じ箱の中にあるのに「答えていないから押せない」を理由に無効化することになる。**順序は後者が先で、発行中は破棄前確認より前に断る** — 発行した書込みが解決していない間に「破棄して閉じる」を差し出すと、いま台帳やファイルへ入ろうとしている入力について破棄を選ばせることになる。
- **Escape は、問いが立っている間はその問いに答える**（「編集に戻る」。TASK-86）。押下は最も内側の開いている層に費やされる（doc-7 §2.1 の Escape。絞り込みの値一覧も同じ）ので、問いが立っている間の最も内側はモーダルではなく問いである。閉じる要求を出し直す形にすると、Escape は画面上何も変えない打鍵になる。
- **下部操作行を持つのは、下書きを書いて出る出口を併せ持つモーダルだけである**（TASK-86 で条件を明示）。未保存入力を持つだけでは要らない — プロジェクト登録モーダルは 3 欄の入力を保持するが、「登録」は台帳へ書いても層を出ないので、出方が 1 通りしかなく述べ分ける相手がいない。そこで `×` を押したときに入力がどうなるかは、下部操作行ではなく破棄前確認が述べる。原文が「登録」と対で持つ「取消」（doc-12 §2.3）は**足さない**（2026-08-09 に TASK-80 が判定。画面設計案 01 からの意図的な逸脱として記録する）。判定の根拠は本項が既に持っている — 「取消」が述べられるのは「入力を捨ててこの層を出る」ことだが、それは `×` の「この層を閉じる」と破棄前確認の組が既に述べており、控えを足しても述べ分ける相手が増えない。**原文の「登録」が層を出るのかどうかは doc-12 §2.3 に転記が無く、このリポジトリからは確かめられない** — したがって足さない理由を原文の側の事情に置かない。理由は Atlas の側にあり、本節の条件がそれである。**作成モーダル（doc-10 §1）が 2 例目**で、理由も同じ — 「文書を作成」「マイルストーンを作成」は管理ファイルへ書いても層を出ず、入力欄を空にして次の 1 件を受ける。**この条件は「書くかどうか」ではなく「書いて出るかどうか」である** — 2 例とも書いており、それでも下部操作行を持たない。

## 8. 画面に置く文

本節は、画面に出る散文について落とすものと残すものを分ける（TASK-79 で新設）。**対象は利用者が読む文だけ**であり、コードコメントは含まない（そちらは TASK-107）。**分ける軸は量ではなく、その文が何について書かれているかである** — 同じ長さの 2 文でも、押した結果を述べるものは残り、既に画面に出ている値を言い直したものは落ちる。「冗長かどうか」で判断すると、長い結果の予告が落ちて短い言い換えが残る。

- **状態文** … 画面のその場所に何が出ているか・何が無いかを述べる文を指す（「文書はありません。」「文書が選択されていません」「説明はありません。」）。**本節の対象ではない** — 落とす 4 種にも残す 3 種にも入らず、置き方は §6 と各画面の設計文書が定める（doc-10 §5・§6）。状態文とその他を分けるのは、**その文が画面に出ていないことを述べているかどうか**である。仕組み・理由・経緯へ踏み出した時点で、以下のどれかに当たる。**別の場所で何ができるかへ踏み出した時点では、下の 代替経路の案内 に当たる。**（**2 つ目の例は 2026-08-08 に「文書を選ぶと内容を表示します。」から直した** — TASK-79 の目視が実装の側だけを書き換え、本節と doc-10 §5・§6 が旧文言のまま残っていた。TASK-123 で 3 か所とも揃えた。）

**落とす 4 種。**

- **状態の言い換え** … 画面に既に出ている値・印・欄の中身や、**操作の名がすでに述べていること**を、散文で言い直しただけの文。**判定は「その欄が現在値を出しているか」で行う** — 出しているなら、その状態自身が語っているので告知は要らない。doc-10 §5 が文書の tags 欄について先に決めた形で、本節はそれを画面全体へ広げる。現在値を持たない欄（常に空で、空欄の意味が読めないもの）はこれに当たらない。
- **設計文書参照** … 文の中に置いた `doc-N §X`・`decision-N`。**1 つも残さない。** 利用者はその文書を読めない。参照が括弧の中で事実と同居しているときは、**事実だけを残して参照を落とす** — 括弧ごと消すと、押せない理由や結果の予告まで一緒に消える。
- **設計文の写し** … 設計文書の本文の一文を、指示対象を利用者の側へ置き換えずに画面へ刷ったもの。**ラベルは操作の名で書く。** 画面設計案の同じ位置に語があるならそれを取る（doc-12）。この型は書いた側には自然に見える — その節を書いた直後は、節の一文が最も正確な説明に読めるためである。**動作確認済み版の版数もこの型である — 2026-08-12 に足した**（TASK-154、decision-27）。「v1.48.0 の CLI に空集合化の手段がないため」の版数が指しているのは doc がその事実を測った版であって、利用者の状況ではない。**落とすのは版数だけで、「CLI に手段が無い」は残るので不可の理由は失われない。** **版数を持てるのは、利用者の CLI の版と動作確認済み版の差そのものを述べる文だけである**（現在は上部帯の CLI 縮退の unsupported の 1 文だけ。§4）。差を述べない文が版数を名乗れない理由は 2 つあり、①利用者がその瞬間に訊いていないことに答える（2026-08-11 の目視が状態遷移の確認質問について先に下した判断。doc-8 §6.5 がその測定を持つ）、②その文は CLI の確認が済む前にも画面へ出るので、名乗れる版が実行時に無い。測定は doc-5 §3.1・doc-9 §4.2.1 が持つ。
- **発行手段の記述** … Atlas が発行する操作について、そのサブコマンド名・フラグ名・引数を書いたもの。利用者が確かめるのは結果であって、どのコマンドが走ったかではない（doc-10 §5 が `--tags ""` について先に決めた形）。**1 つも残さない — 2026-08-08 に除外が無くなった**（TASK-123）。本種は改訂まで doc-10 §6 の写像先と §7 のフラグ掲示を除外し、あの 2 つが名指すのは Atlas が提供しないものの同一性であって Atlas の行うことの手順ではない、という区別で支えていた。**§6 の区画は撤去され、§7 は理由もフラグも落として代替経路の案内だけの注記になった**ので、除外する相手が画面に無い。§7 のフラグ掲示が果たしていた「『CLI に無いから』という偽の説明を禁じる」役目は、**理由文そのものが落ちたことで満たされる** — 偽の理由を書く場所が画面に残っていない。**「CLI に手段が無い」はサブコマンド名でもフラグ名でもないので、本種に当たらない**（落とすと不可の理由がそのまま消える）。**この括弧が述べているのは、不可の及ぶ範囲を述べる句を他に持たない文についてである — 2026-08-17 に限定した**（TASK-192）。「Atlas からは最後の 1 件を削除できません」のように文の側が範囲を述べているなら、添えた「CLI に空集合化の手段がないため」を落としても理由は残る。**落としてよいかどうかを決めるのは §5 であって本種ではない。** **2026-08-12 まで本種はここに版数を並べていた**（TASK-154 で分けた。decision-27）— 版数と「CLI に手段が無い」を 1 つの句で扱っていたため、版数を落とすと理由も消えるかのように読めた。実際には版数だけを落としても理由は残るので、**版数は 設計文の写し として落とす**。

**残す 3 種。**

- **結果の予告** … 押下の前にしか読めない、その押下が **元に戻せない形で** 何を変えるかを述べる文（登録解除が台帳エントリを 1 件消してスイムレーンから行を外すこと、保存が **欄の見せていない範囲まで** 書き換えること）。残す。**軸は取り返しがつくかどうかである** — 可逆な操作が何をするかの一行ヒントはこれに当たらない。**全置換であること自体は本種の根拠にならない — 2026-08-17 に例を狭めた**（TASK-192。オーナーの画面目視から）。本項は改訂まで 2 例目を「保存が既存を含む全置換になること」と書いており、非空全置換で送る欄すべてがそれを名乗れた。**判定は、欄が並べているものと、保存が書き換える範囲が同じかどうかで行う。**
  - **同じなら落とす**: assignee・References・依存 の 3 欄は、送る集合の要素を 1 行 1 件で並べ、そこで足し引きさせている。触っていない要素は同じ値のまま戻るので、**保存で失われるものが画面の外に無い** — 「既存を含む全集合で置き換えます」が述べているのは発行の仕組みであって、利用者が失うものではない。2026-08-17 にこの 3 欄の注記を落とした。
  - **違うなら残す**: AC の 全体差し替え は、読み取り時点の全項目を index で消してから作り直す（doc-5 §3.1 の複合操作）。欄が並べているのは作り直した後の姿で、消される旧項目の側ではない — 欄から 1 件外すと画面から消え、それでも保存はその項目を消す。文書本文の更新は `doc update --content` に部分更新が無いため（doc-5 §3.1）、欄が預かるのは足す分ではなく本文の全体であり、欄はその全体を一度に見せていない。**この 2 件は残す。**
- **不可の理由** … **押せない**理由。**本節はこれを減らせない** — §5 が押せる控えを無効化したときの掲示を要求している。本節が及ぶのは、その理由文の中の設計文書参照と発行手段の記述だけである。**1 つの文が落とす種と不可の理由の両方に当たるときは、書き直しが優先し、撤去はしない** — 落とす 4 種は書き方についての規則であって、理由を掲示しなくてよくする規則ではない。**画面が操作も欄も見せていないものについて、なぜ無いかを述べない** — 画面がその不在を提示していない以上、読み手はその問いを持っていない（TASK-79 の Description が挙げた「絞り込みは既定のままです。戻す条件も解除する条件もありません。」がこの型）。**2026-08-08 に、この本則の例外が無くなった**（TASK-123）: 本項は改訂まで doc-10 §6 の提供しない操作区画と §7 の欄を出さない項目を「不在そのものを一覧として提示する区画で、そこでは読み手が現に問いを持っている」として除外していたが、**前者は撤去され、後者は理由を落として代替経路の案内だけの注記になった**。**本則は例外なしで立つ。** また、**提供しない操作についての掲示要求は §5 から消えた**ので、本項が「減らせない」と述べる相手は押せる控えの側だけである。**画面設計案が置いている項目を Atlas が持たないことも、それだけでは理由を掲示する根拠にならない**（2026-08-08 の目視で、設定画面の起動時読み取りの注記がこの理由で撤去された）。
- **代替経路の案内**（本種は 2026-08-08 に新設。TASK-123） … 画面がその場所で提供していないことについて、**それをどこですればよいか**を述べる文（作成フォームに欄の無い 5 項目をタスク詳細の編集で足せること〔doc-10 §7〕、slug を変えるには登録を解除して登録し直すこと〔doc-10 §4.1〕）。残す。**落とす 4 種のどれでもない** — その場所に値が無いので言い直す相手がおらず、設計文書参照でも設計文の写しでも発行手段の記述でもない。**状態文でもない** — 状態文が述べるのはその場所に何が出ているか・何が無いかであって、別の場所で何ができるかではない。**なぜそこに無いかは述べない** — それは不可の理由の側で、画面が不在を提示していないなら前項の本則が禁じている。したがって**この 2 種は同じ文に同居しない**: 押せる控えがあるなら不可の理由に従い、控えごと無いなら本種だけを置く。**本種を足したのは、TASK-79 が全画面を数えたときに種別を与えないまま残した文が既に 2 例あった**（assignee の解除 と、上の 2 例目の slug）ためで、本節はそこを覆っていなかった。**その項目についてだけ言える先を落とす選択肢は無い** — 読み手がその画面から取れる行動を述べるのはこの文だけであり、落とすと「ここには無い」で終わる。**2026-08-17 の絞りはこれと矛盾しない**（TASK-192）: 落ちた 2 つは、先が画面のどの欄からも同じであるか、同じ区画に控えとして見えているかのどちらかで、**文を落としても読み手の行動が「ここには無い」で終わらない**。**述べるのは、その項目についてだけ言える先に限る — 2026-08-17 に絞った**（TASK-192。オーナーの画面目視から）。**2 例が残るのは、行き先がその項目ごとに違うからである**: 作成フォームに欄の無い 5 項目はタスク詳細の編集へ、slug は登録の解除と再登録へ向かい、その項目について読まなければどちらとも分からない。落ちるのは次の 2 つで、**どちらも先が画面から無くなったのではなく、各欄でそれを名指しする文が無くなっただけである。**

**置き方。**

- **無効化の理由が、その操作と同じ区画の表示そのものであるときは、文を別に置かない。**§5 が求めるのは理由に到達できることであって、同じことを 2 度述べることではない — 欄が「（必須）」と述べていて空ならその空欄が理由であり、フィルタ帯の 既定に戻す なら帯が現に出している条件が理由である。実装では可視の文を落とす 保留理由 を列挙して持つ（`manage.ts` の `omitsSentence`）— 規則ではなく列挙にするのは、どの licence に拠るかが理由ごと・区画ごとの事実であり、**項目を足すときにその区画を開いて確かめさせる**ためである。**可視の文を省いてよいのは次の 2 つだけで、どちらにも当たらない理由は描く。** ①**区画がその理由を可視で述べている**（「（必須）」の印が付いた欄が空、など）— そのとき控えは §5 の 1 つ目の形（常時表示する補助文）を既に満たしているので `disabled` のままでよい。②**理由が「まだ入力していない・まだ変えていない」だけを述べており、次に何をすればよいかがフォーム自身から明らかである** — このときは §5 の 2 つ目の形（`aria-disabled` ＋ フォーカス可能 ＋ `aria-describedby` で、常時 DOM にある要素へ結ぶ）にして、理由をアクセシビリティツリーへ残す。**原因が画面の外にある理由は、どちらにも当たらないので必ず可視にする**（CLI 縮退・台帳読取専用・発行中・競合）— 利用者が取るべき行動がフォームから読めないためである。**①と②では控えの属性が違う**ので、隠す前にどちらの licence に拠るかを決める（TASK-79 の 4R [P1]: ②に当たる理由を①のつもりで `disabled` のまま落とし、理由が `title` だけになった）。**1 つの控えが、licence に当たる理由と当たらない理由を併せ持つときは、§5 の 2 つ目の形へ揃え、licence は文を可視にするかどうかだけを決める — 2026-08-08 に新設**（TASK-127）。概要区画の保存がその例で、4 つの保留理由のうち 台帳読取専用 と 発行中 は原因が画面の外にあるので可視の文を持ち、入力に問題があるとき と 変更が無いとき は①に当たる。①の「`disabled` のままでよい」を理由ごとに適用すると、**同じ 1 つのボタンが、なぜ押せないかによってフォーカスを受けたり受けなかったりする**。①が与えているのは可視の文を省いてよいという licence であり、省くのはその文だけでよい — 理由の要素は `aria-describedby` の指す先として DOM に残す。
- **結果の予告と不可の理由は、操作の近くに常時表示する**（§5 の 1 つ目の形）。`title` へ移して可視から消さない。**この 2 種以外の一行ヒント**（可逆な操作がどこへ届くかを `title` で述べるもの。メニュー行など）**は本節の対象ではない** — 落とす 4 種に当たらない限り、置き方は各画面が決める。この 2 種は、**不可の理由**が §5 のホバー依存の禁止に当たり、**結果の予告**は押す前に読めないと役に立たないので、どちらもホバーの向こうへ置けない。`title` は §5 のとおり補助にとどめる。**画面のノイズは移設ではなく削除で減らす** — 移設先の候補は、落とす 4 種を落とした後には残らない（TASK-79 で全画面を数えて確かめた）。
- **代替経路の案内の置き場は各画面が決める**（2026-08-08。TASK-123）。**結ぶ相手の控えが画面に無いので「操作の近く」が定まらない** — 上の 2 種は押せる控えに付くから置き場が控えから決まるのに対し、この種が述べているのは**そこに控えも欄も無いこと**である。したがって**前項の「移設ではなく削除で減らす」もこの種には当たらない**: あれは落とす 4 種を落とせば移設先の候補が残らないという数え上げの結果であって、落ちない文の置き場についての規則ではない。**求めたときに読ませる形にしてよく、そのときは押して開く導線を置き、キーボードとスクリーンリーダーから到達できるようにする**（doc-10 §7 の 注記の入口 と 注記モーダル がその 1 例目で、区画見出しの横のアイコンのみのボタンから被せ層を上げる）。**常時表示にするかどうかは、その文が画面の主要な操作面をどれだけ占めるかで決まる** — doc-10 §7 の 5 項目は常設で 361px あり、区画がスクローラに収まらない原因そのものになっていた（実測。doc-10 §7）。

**足すときの検査。**

- **画面へ新しい文を足すときは、落とす 4 種のどれかでないかを先に見る。** 特に設計文書の節を書いた直後の実装では、設計文の写しと発行手段の記述が入りやすい。
- **priority チップの語は状態文であって状態の言い換えではない**（decision-23）。色は 3 段のどれかを述べるが、語はその段の名前そのものであり、言い直している相手がいない。**同じ判定を他の印・チップにも当てる** — 語が値そのものなら状態文である。

## 11. 発行の控えの置き方

本節は、フォームに入れた値を書き込みとして送る控えを、画面をまたいで 1 つの規則から置くために新設した（2026-08-09 のユーザーフィードバック。TASK-135）。**節番号は既存を動かさず末尾へ足した** — 番号はコード註と decision から参照されており、§10 が最後に来なくなる読みにくさより、番号が 1 つずれる害のほうが大きい。

- **発行の控え** … 入力欄の集まりに入れた値を、押下 1 回で管理ファイルまたは台帳への書き込みとして送る押しボタンを指す。**入力を持たない発行はこれに当たらない**（状態遷移〔doc-8 §6.5〕・Git remote の再検出〔doc-10 §4.1〕・外部エディタ起動〔doc-8 §7〕・再読込）— 送る値が無く、フォームではなく対象の隣に付く操作なので、置き場はその対象を定める節が決める。
- **取りやめの控え** … 同じ入力欄の集まりに付き、押すと発行せずにその入力を終える押しボタンを指す（「キャンセル」「編集を止める」「変更せずに閉じる」）。
- **発行の行** … 発行の控えと、あればその取りやめの控えを並べる横 1 行の領域を指す。**§7 の下部操作行とは別のものである**（下記）。
- **入力面** … その入力欄の集まりを載せていて、内容が入り切らないとき自分がスクロールする箱を指す。どの要素がそれかは画面ごとに違うので、本節は要素の名で規則を書かない。

**規則は次の 1 本である。**

> **発行の控えは、その入力欄の並びの直後に置いた発行の行に置き、行の中では左端から並べる。ただしその控えが入力面のスクロールで画面外へ運ばれうるときは、発行の行を入力面の下端へ固定し、行の中で中央に置く。1 つの入力面が発行の控えを 2 つ以上持つときは固定しない** — 下端の 1 行がどちらのものか決まらないためである。

**固定する理由は 2 つあり、本体は 2 つ目である。** 押せる状態が保たれること、そして**押した結果を述べる文が押した瞬間に見えていること**（§4 の 控えの隣の結果文）。後者は実測から来ている — 設定モーダルは失敗文をパネル上端に置いていて、スクロールしたフォームでは押した瞬間にそれが画面外にあった（TASK-74）。**固定しない側で同じことが起きないのは、行が入力の直後にあるためである**: 利用者は自分が入れた値を見ながら押すので、そのとき行は画面の中にある。**したがって固定するときは、押す前に読めなければならないもの — §5 の無効化の理由と、doc-7 §2.1 の発行のキーの併記 — を同じ固定の中に入れる。** 控えだけを固定すると、固定した理由の半分が満たされない。**§4 の控えの隣の結果文も、押した後に入力面が残るならそこへ入れる**（設定モーダルの「保存できませんでした: …」がこれである）。**入力面が発行の成功で閉じるときは入れられない** — 行ごと消えるので、結果を述べる文は自分が生き残る場所に置くことになり、その置き場はその画面の設計文書が定める（タスク詳細では編集卓。doc-8 §3）。**この非対称は 2026-08-10 に実装して分かった**: 固定するかどうかは面がスクロールするかで決まるのに、結果文を置けるかどうかは面が発行で閉じるかで決まり、2 つの条件は同じ面について別々に立つ。

**並び順は 取りやめ → 発行 とする。** 行の中で中央へ寄せる以上、面ごとに順が違うと同じ押下が画面によって左右どちらにも来る。設定モーダルが既にこの順で（TASK-74）、肯定の操作を末尾に置く形は macOS の慣習とも一致する。**原文は順を定めていない** — doc-12 §2.2 の設定モーダルは控えを 1 つしか持たず、§2.3 の登録モーダルの「登録」「取消」は転記が位置を持たない。

**§7 の下部操作行と同じ 1 行になることがあるが、条件は別である。** 下部操作行が立つ条件は**出口の数**（下書きを書いて出る出口を併せ持つモーダルだけ。§7）で、発行の行が立つ条件は**発行があること**である。現在この 2 つが重なるのは設定モーダルだけで、そこでは「保存する」が発行の控えかつ書いて出る出口、「変更せずに閉じる」が取りやめの控えかつ書かずに出る出口である。**作成モーダル・登録モーダルが固定された発行の行を持つことは、それらが下部操作行を持つことを意味しない**（doc-10 §1・§7 の条件は動いていない）— あちらが並べるのは出口で、こちらが並べるのは発行である。

**固定しない箇所は次の 2 つの条件で決まる。本節はどの面が該当するかを列挙しない** — 1 つの面が発行の控えをいくつ持つかは各画面の設計文書（doc-8・doc-10）が決めるので、列挙はそれが動いた時点で偽になる。

- **その面が発行の控えを 2 つ以上持つとき。** 下端の 1 行を 1 つの発行が占められない。
- **その面がスクロールしないとき。** 控えが運ばれえないので固定するものが無く、行は既に面の下端にある。

**画面設計案からは 2 か所で意図的に外れる。**

- 01 の設定モーダルは控えを**下部左端**に置いている（doc-12 §2.2）。中央にするのは本節の規則によるもので、原文の位置は採らない。**原文にそもそも保存が無い**（値の変更が即時に効く前提）ので、原文の左端は 1 つしかない出口の位置であり、2 つを並べたときの順や寄せを述べていない。
- 02 のタスク詳細は編集の入口を**属性表の下の固定行**に置き、「編集」ボタンと保存キーの注記を並べている（doc-12 §3）。Atlas は編集入口を見出しの 2 行目に置いたまま（doc-8 §3。この位置そのものも原文からの逸脱で、理由はあちらにある）、**編集セッション中の 保存・キャンセル だけを本節の固定行へ出す**。

本節は、押下がその控えの名乗る動作に届く前に立てる問いを、画面をまたいで 1 つの規則から置くために新設した（2026-08-09 のユーザーフィードバック。TASK-137）。**節番号は既存を動かさず末尾へ足した** — §11 が同じ理由で末尾へ足しており（TASK-135）、番号はコード註と decision から参照されている。

- **実行前確認** … 押下が、その控えの名乗る動作（CLI 更新の発行、または外部エディタの起動）に届く前に立ち、その動作を行うかどうかだけを問う問いを指す。答えるまで動作は始まらず、戻る側の答えでは何も起きない。
- **破棄前確認（doc-8 §6.3）とは問う相手が違う。** あちらが問うのは未保存入力の行方で、進む側の答えでは入力が失われて経路が進む。こちらが問うのは動作を行うかどうかで、進む側の答えで初めて動作が始まる。同じ被せ層の使い方をしても 1 語にまとめない。
- **`発行` では対象を覆えないので、この名にした。** 通る控えのうち外部エディタ起動の 2 件が始めるのは CLI 更新ではなく起動であり、doc-5 の 発行 はそれを含まない。

**2026-08-11 に二度押し確定を撤去した。** §5 は改訂まで「破壊的操作の確定は二度押しとし、一度目でラベルを確認文へ差し替える」と定めており、実装はタスク詳細の状態遷移 5 件と外部エディタ起動 2 件でその形を取っていた。**画面設計案 06 が同じ形を定めているので（doc-12 §7.2）、撤去はそこからの意図的な逸脱である。** 逸脱の理由は 2 つあり、どちらも「問いと答えを同じ座標に置く」ことから出ている。

- **同じ座標の 2 打で確定に届く。** 1 打目と 2 打目が同じ控えなので、連打がそのまま発行になる（ユーザーが 2026-08-09 に「ボタン連打でほぼ確認なく実行できてしまうので危険」と述べた）。文言を強めても消えない性質である。
- **問いが控えのラベルの中にしか無いので、対象が替わったことを問いが知らない。** 実装の待機状態はタスクのファイルを鍵に持たず（`TaskDetail.svelte` の `confirming`。同じ画面の起動通知と外部エディタ側の待機状態は鍵を持っていた）、詳細パネルは別のカードを選んでも作り直されないので、1 打してから別のタスクを選ぶと、そのタスクの同じ控えが 1 打で発行していた（2026-08-11 に実測）。

**規則は次の 3 本である。**

> **① 実行前確認は被せ層（doc-7 §2.1）を 1 枚上げて問う。層はシェルが持つ。**
> **② 通る控えは、その語の末尾に `…` を付ける。条件付きで問う控えでは、問いが立つときだけ付ける。**
> **③ 問いは、それを立てた対象が替わったら失効する。**

**①について。** 層を上げるのは、答えの控えが押した控えとは別の座標に来ることが、連打で素通りできないことの根拠そのものだからである。**上部帯 ①（§4）に載せる案は採らなかった** — 帯は 1 行に収める規則を持ち（§4）、押した控えから視線も遠い。**区画の中に確認の行を描く案（§7 が破棄前確認で取っている形）も採らなかった** — 層が上がらないので、押した控えと答えの控えが同じスクロール領域の中に並ぶ。**層を持つのはシェルである** — 被せ層を同時に 1 枚しか立てないことを保つのはシェルなので、区画が自分で上げるとその数え上げから外れる（§7 が破棄前確認について同じ理由でシェルに持たせている）。**中央モーダル詳細配置（doc-8 §2.1）は被せ層ではない**ので、詳細がその配置のときも立つ層は 1 枚である。**この層は下書きを 1 つも持たないので §7 の下部操作行を持たない** — 並ぶのは出口ではなく 2 つの答えである。**答えは 進む → 戻る の順に並べ、進む側は動作を名乗る**（`アーカイブする`・`draft へ差し戻す`）。順を既存の破棄前確認 2 か所（帯・§7 の層の中の行）と揃えるのは、同じ形の問いが場所によって左右入れ替わらないようにするためで、**§11 の 取りやめ → 発行 とは並べているものが違う**（あちらは入力の発行と取りやめ、こちらは問いの 2 答である）。進む側に `実行する` のような広い語を選ばないのは、§7 が「破棄して閉じる」で取った判断と同じである。**戻る側は `やめる` の 1 語とする。** **層の出口（`×`・Escape）は戻る側と同じに扱う** — 答えないまま閉じた問いは動作を始めない。

**②について。** `…` が述べるのは「押しても動作に届かない」ことである。**doc-7 §2.1 がメニュー行から落とした `…`（TASK-130）とは別物で**、あちらは入口の名前が「一覧へ導く行」を名乗るための記号だった。**押すと層が上がる控え一般に `…` を付ける規則ではない** — そう書くと、ユーザーが落とした記号が規則として戻る。**条件付きで問う控えでは、問いが立つときだけ付ける**（外部エディタ起動の 2 控えは未保存入力があるときだけ問うので、`…` もそのときだけ付く）。付けたまま問わない控えがあると、記号が予告する相手を失う。

**③について。** 問いは、それを立てた控えが載っている対象についてのものである。詳細パネルが別のタスクを指したら、その問いは答えられる相手を持たないので失効する。**§7 が破棄前確認について同じことを既に書いている**（問いを描く場所は最前面の層で決まり、答えないまま層が閉じたときも問いは消える）。**失効で失われるものは無い** — 動作は始まっていないので、取り下げられるのは要求だけである。

**「破壊的操作」という語で範囲を書かない。** §5 はその語を定義しておらず、doc-8 §6.5 は「逆操作の無い」と限定していたが、**その限定では状態遷移の 5 件を分けられない** — 押す前の状態へ戻せるものが 1 件も無い（`--help` で測った内訳は doc-8 §6.5）。外部エディタ起動のほうはそもそも破壊しない（問うているのは二重取り込み。doc-8 §6.4）。**通る控えを名指しで持つのは各画面の設計文書である**（現在はタスク詳細の状態遷移 5 件〔doc-8 §6.5〕と外部エディタ起動 2 件〔doc-8 §7〕）。本節はその一覧も件数も持たない — 持つと、控えが 1 つ増えるたびに 2 か所を揃えることになる。

**同じ形に見えて本節を通らないものが 3 つある。** どれも 2 打目が別の要素なので、連打が動作に届かない。

- **起動の差し控え**（doc-8 §7）… 押下が継続検出の停止を見つけて起動せず、注意を出した状態。1 打目は問いを立てておらず、押下が事実を見つけて報せている。
- **slug 入力一致**（doc-10 §4.3）… 登録解除が求める確認で、本節より強い条件である。
- **副パネル ＋ 発行の控え**（doc-10 §6）… マイルストーンの改称・削除・アーカイブが、押下で副パネルを開き、必須入力を受けてから別の控えで発行する形。

## 13. 固定行の高さの上限

本節は、面の上端・下端に貼り付く行が面の高さを取り過ぎるのを止めるために新設した（2026-08-11。TASK-145）。**節番号は既存を動かさず末尾へ足した** — §11・§12 と同じ理由で、番号はコード註と decision から参照されている。

- **固定行** … 自分がスクロールする面の中に立ち、面の上端または下端に貼り付いて位置を保つ行を指す。**§11 の 発行の行 と、各画面が固定する見出しの両方がこれにあたる** — 覆う側としては 1 つの型であり、置き場を定める節が別なので、上限は本書が 1 か所で持つ。
- **覆われない帯** … 面のうち、固定行のどれにも覆われていない縦の範囲を指す。値は「面の clientHeight − 上端に貼り付いた固定行の高さ − 下端に貼り付いた固定行の高さ」である。
- **到達不能** … 面をどのスクロール位置へ送っても、その控えの中心の最前面が控え自身にならない状態を指す。

**規則は次の 1 本である。**

> **覆われない帯は、その面に立つ控えの高さ（§2.2 のフォーム部品の高さの段階の最大値、1.75rem）を下回らない。**

**下回ると控えが到達不能になる。** 固定行は自分の場所を流れの中に確保するので、帯が正である限り、面のどこかに控えの中心が帯へ入るスクロール位置が必ず 1 つある — 逆に帯が 0 以下になると、その位置がどこにも無い。帯が正でも控えの高さに満たなければ、控えは最良の位置でも上下どちらかが固定行の下に残る。**この規則が守るのは読みやすさではなく、控えに手が届くことである。**

**満たし方は 1 つで、固定行に置くのは、面が狭くなっても高さの増えないものに限る。** 帯が足りないときに固定行の中を切り詰めたり、その面をスクロールしない形へ替えたりしない — 前者は固定行の中に 2 つ目のスクロールを作り、後者は面が持てる内容の量を寸法で決めることになる。**高さの増えるものは固定行の外へ出す。** タスク詳細の主要属性の属性表がその実例で、6 つの値は面が狭くなるほど折り返して 55.78 → 162.58px（WebKit・閲覧）まで育っていた（doc-8 §3）。

**外へ出せないものは、固定行の中で長さを止める。**§11 が固定行の中に置くことを求めているもの（無効化の理由〔§5〕・発行のキーの併記）と、各画面が固定行に置くと定めた値（タスク詳細の title。doc-8 §3）がこれにあたる。**止め方は 2 通りあり、どちらを取るかは §5 が決める。**

- **落としても役目が残る値は、行数で止め、全体を `title` が持つ。** タスク詳細の title（2 行）がこれである。落ちるのは描かれる字だけで、どのタスクを読んでいるかは頭の 2 行が述べる。
- **押す前に読めなければならない文は、文の側に上限を持たせる。**§5 の無効化の理由がこれで、**描画で切ってはならない** — §5 が求めているのはホバーせずに読めることであり、行数で止めると半分が `title` へ移る。**上限は「利用者が打った値を丸ごと引用しない」ことで作る**（実装は `manage.ts` の `commaReason` が頭 20 字＋省略記号で引用する。引用の役目はどの値かを言うことなので、頭で足りる）。

**どちらの経路でも、値そのものに上限が無いことを、面の幅が上限になっていることで代替しない。** 2026-08-11 の実測では、上限を持たない title は 480 字で 640×480 の窓の帯を −126.0px にし、パネルの控え 12 件すべてを到達不能にした。**同じ窓で、上限を持たないラベルを引用した理由文は固定行を 367px の面の中で 350.25px まで押し広げ、帯を 16.75px にした**（600 字。規則の 28px を割る）。**止めた後はどちらも入力の長さで動かない** — title は 2,000 字で、理由文は 600 字で確かめた（両エンジン）。

**現に確かめた値は次のとおり**（2026-08-11 実測。WebKit・Chromium、窓 1280×800 と 560×300）。

**この規則が掛かる範囲は「利用者が作れるあらゆる窓」であり、その範囲は窓の最小寸法が閉じる。**`tauri.conf.json` は既定 1200×800 に加えて **最小 640×480** を持つ（2026-08-11 に導入。TASK-145）。**最小寸法が無いと規則は成り立たない** — 上限を持つ固定行だけにしても、**面の高さが足りなければ帯は控えの高さに届かない**（実測では窓の高さ 320px 以下で割れ、幅 1280px でも高さ 200px なら帯 18.63px になる）。**規則を割る条件は高さだけで決まり、高さ 360px 以上ならどの幅でも成り立つ**ので、640×480 はその境目に余裕を取った値である（640×480 の帯は閲覧 263.8px・編集 243.8px で、規則の 8.7 倍）。**最小寸法は「狭い窓を対象外にする」ものではない** — 対象外にできる窓は無く、最小寸法は規則が成り立つ範囲を作るためにある。

## 14. 整形表示の中の見え方

本節は、doc-8 §9 の **整形表示** の中身をどう描くかを定めるために新設した（2026-08-11。TASK-142・decision-25）。**節番号は既存を動かさず末尾へ足した** — §11〜§13 と同じ理由で、番号はコード註と decision から参照されている。

**何を 整形表示 にするかは doc-8 §9 が持ち、本節は見え方だけを持つ。** 寸法は §2.2 から取り、本節で新しい数を決めない — §2.2 へ足したのは 整形表示の中の見出し と 整形表示の本文・リスト の 2 行である（TASK-141 がフォーム部品の高さで足したのと同じ形）。**本節の中の余白も §2.2 の 余白段階 から取る** — 2026-08-14 まで `.body-block` の padding が `0.35rem` を持っており、これは段階に無い値だった（同日の目視で余白を広げる際に段階の値へ直した）。

**本節が定めるのは 1 か所である。** タスク詳細・文書・マイルストーン・決定事項 の 4 か所が同じ見え方を取るのは、4 つを揃えた結果ではなく、**4 つとも `Body.svelte` 1 つを描いているからである。** したがって押さえるのは一致そのものではなく、**本文を描く経路が 1 本しか無いこと**である（`src/lib/text-scale.test.ts`。一致を測る形にすると、5 か所目が自前の本文を描いたときに何も起きない）。

### 14.1 見出し

- **見出しの段は、大きさ・太さ・上の余白の 3 つが揃って述べる。** 大きさは 2 段だけで（§2.2 の 段の役割表 — h1・h2 が .92rem、h3 以下が .86rem）、どちらも 650 を取る。**整形表示の本文（.80rem）より大きい。** **6 段を大きさで作らないのは変わらない** — 作れば、本文の中の階層のために文字寸法段階そのものが増える。
- **本文の中の見出しの上限は、それが載っているパネルの見出し（.98rem）である。** 上回ると、パネルが何を表示しているかより本文の中の段が強く読める。**区画見出しは上限ではない** — あちらは本文の**外**の階層（doc-8 §3 の罫線付き見出し）だが、**分けているのは大きさではなく罫線と字間と `--muted` である。** **この項は長く 区画見出し も上限として挙げていたが、実装は一度もそれを満たしていなかった。**

  数を 2 つの時点で書き分ける。**TASK-164 の前**（地が 16px）: 整形表示の h1・h2 は `.78rem`＝12.48px、タスク詳細の 区画見出し は `.68rem`＝10.88px で、**すでに上回っていた**（この 2 つはコミット済みの rem 値からの算出であって、実測ではない）。**現在**（地 110%。2026-08-14 の実測）: 16.19px 対 11.97px。**プロジェクト詳細のペインの見出しは書き分けが要る** — TASK-164 の前はどちらも `.78rem` で**等しく**、上回るようになったのは本タスクが 整形表示 を上げてからである（現在 16.19px 対 14.08px）。 **したがって「一度も満たしていない」が言えるのは §14.1 が名指ししている 区画見出し についてであり、ペインの見出しについてではない。** **満たしていない上限を書き続けるほうが、後から読む人を誤らせる。** **上限が効いていることは `src/lib/text-scale.test.ts` が押さえる** — 整形表示の本文より大きく、2 段が互いに別で、上段がパネルの見出しの段に届かない、の 3 つを見る。
- **初版は段を大きさで作らず、太さと余白だけで作っていた。** 2026-08-11 の目視でユーザーはそれを許容し（「見出しは正直あまり区別つかないが大きな問題もなさそう」）、**2026-08-14 に本人が広げることを選んだ**（TASK-164）。**実測は 1.054 倍から 1.162 倍へ**（h1・h2 と本文の比。2026-08-11 は本文 11.84px に対し h1・h2 12.48px・h3 以下 11.84px、2026-08-14 は 13.02px に対し 15.14px・14.08px。両エンジンとも、**4 か所すべてで同値**）。**同日の並置目視を受けて本文と見出しをさらに 1 段ずつ上げ、本文 14.08px・h3 以下 15.14px・h1・h2 16.19px になった**（比は 1.149 倍。段が一定幅なので比はほぼ保たれる）。**h3 以下が本文と同じ大きさだったことが、段の別を読み取れなかった主因である** — あの状態の h3 は、太さと余白しか本文と違わなかった。

### 14.2 GFM 表・コード

- **doc-8 §2.1 の行長上限 48rem は 整形表示 にも掛かる。** その内側に収まらない要素は、**その要素自身の中で横スクロールする** — GFM 表は表が、コードフェンスはそのブロックが持つ。**パネルごと横スクロールさせない**（させると本文の他の行まで一緒に動く）。**§13 が固定行について採った「外へ出せないものは中で止める」と同型**で、あちらは高さ、こちらは幅である。
- **コードフェンスとインラインコードの字は `ui-monospace`**（§2.2 の コミット SHA・パス と同じ）。**コードフェンスの中身は折り返さない** — 行として意味を持つためで、そのかわりブロックの中で横スクロールする。
- **コードと引用の地は本文ブロックと同じままにし、区別は罫線（`--line`）が述べる。** 本文ブロック自身が既にくぼみ面（`--inset`）であり — 画面設計案 02 が「Description と実装計画の本文はくぼみ面に入る」と描いている（doc-12 §3）— **その中でもう一段くぼませる面を §2.1 が持たない。** 地を `--panel` へ起こす道もあるが、それは本文の中のコードを面より手前に見せることになり、くぼみ面の中の引用と逆向きの階層になる。角丸は §2.2 のチップと同じ 3px。

### 14.3 リンク

- **押せる 本文リンク だけが色と下線を持ち、色は `--info` である**（§2.1 の「通知・確認・リンク風操作」）。
- **押せないものはリンクとして描かず、本文と同じ見た目で出す**（doc-8 §9.3）。**押せる／押せないを色だけで分けているのではない** — 押せないものはリンクの見た目を持たないので、区別は見た目の有無そのものである。したがって §5 の無効化提示（破線枠・opacity・カーソル）はここに現れない。
- **フォーカスの輪は画面が書く。** 本文リンク は `href` を持たない（doc-8 §9.3）ので、engine はこれをリンクとして扱わず、リンクに与える見え方も与えない。**選択のアウトライン（§2.1 の `--sel`）をキーボードで到達したときに出す** — 出さないと、タブで来た読み手にどこにいるかを述べるものが画面に無くなる。

### 14.4 タスクリスト

- **チェックの印は §2.4 の 族を持たない状態の印 とし、`square-check`／`square` を描く。** **native の `<input type="checkbox">` を置かない** — ACCEPTANCE CRITERIA の項目が同じ「押せないチェックの印」を既にその形で描いているので（doc-8 §3）、同じものを同じ画面が 2 通りに描く理由が無い。**印の図形の出どころは 1 つに保つ**（`lucide.ts` の図形をそのまま使い、整形表示 のために別に書き起こさない）。
- **印が置き換えるのは、印を持つ項目の marker だけである。** **一覧の側に規則を掛けない** — 1 つの一覧は `- [x] 済み` と `- ふつうの項目` を同時に持てるので、一覧に marker の抑止を掛けると**ふつうの項目からも中黒が消える**（2026-08-11 の実装で現にそうなっていた）。**項目はブロックのままにする** — 項目自身を横並びの箱にすると、入れ子の一覧が項目の文の**隣**に出て、下に入らない。
- **これは控えではなく値の表示なので、§5 の無効化提示は当たらない。** §5 が扱うのは提供しない操作であり、ここには操作が無い — 読んでいる本文の中の値である。

### 14.5 作図結果

- **幅は本文ブロックに収める。** 収まらない場合は 作図結果 自身の中で横スクロールする（§14.2 の表と同じ扱い）。
- **配色は表示テーマの明暗にだけ従う。** decision-12 が持つのは色値集合と収録テーマ名で、**作図結果 の中の色は作図の実装が持つ**（明・暗の 2 通り）。**収録テーマ 10 組それぞれに図の配色を作らない** — 作れば decision-12 の色値集合を図の内部へ写すことになり、色値を持つ場所が 2 つになる（§2.1 の「ここだけが色値を持つ」に反する）。
- **描けなかったときは 作図フェンス をコードフェンスとして出す**（doc-8 §9.2 の「整形が失敗したら そのまま表示 へ落とす」の作図版）。**空にしない** — 本文にあったものが画面から消える。
- **描けなかったときに、画面のどこにも残骸を残さない。** 作図の実装は、解釈できない図に対して**自分の容器を作って誤り図を描く**ことがある（実装の既定）。それを抑止しない限り、失敗のたびに 本文ブロック の外へ要素が積もる — 再描画とテーマ切替のたびに 1 つずつである。**抑止して、残るものを 作図フェンス だけにする。**

**作図結果 は `style-src` に `'unsafe-inline'` を要求する（2026-08-11 の実測）。**
mermaid は描いた SVG の中へ `<style>` を入れるので、`style-src 'self'` だけでは**図は描かれるが色を失う**
— 出荷物の形（外部 CSS 1 本）を CSP ヘッダ付きで配って測ったところ、`style-src 'self'` では
`fill` が `rgb(236, 236, 255)` から `rgb(0, 0, 0)` へ落ち、違反の報告が WebKit 111 件・Chromium 192 件
出た。`'unsafe-inline'` を足すと 0 件で色も戻る。**整形表示 の中でこれを要求しているのは 作図結果 だけで
ある** — 同じ CSP で**作図フェンスを持たない本文は違反 0 件**であり（両エンジン）、外部 CSS も画面の
インライン style 属性（doc-8 §2.1 の 48rem を運ぶ `--prose-max-width`）もそのまま効いていた
（**属性が CSP の対象外なのではない** — Svelte が CSSOM 経由で入れているためで、
`setAttribute("style", …)` のほうは両エンジンとも止まる。2026-08-13 の実測、decision-28）。
**ただし「整形表示 の中で」を外すと成り立たない** — 編集部品 の Ace も同じ source を要求する
（同日の実測。`importCssString` が `<style>` を作り、止めると `.ace_editor` が `relative` から `static` へ
落ちる）。**したがって 作図結果 の色を捨てても `'unsafe-inline'` は消せない。** 採った値と、緩めるときに
どの行を書き換えるかは decision-28 が持つ。
測ったのは 2 度で、1 度目は 作図結果 だけ、2 度目は 6 画面ぶんである（どちらも出荷形で、違反の数を数えた）。

### 14.6 画面設計案との関係

**画面設計案 02 は本文の中の記法の見え方を描いていない。** doc-12 §3 が転記しているのは「Description と実装計画の本文はくぼみ面に入る」までで、その面の中に見出しや表が現れた姿は原文に無い。**原文が書いていないことから外れることはできない**（doc-10 §1 が作成モーダルについて下したのと同じ判断）ので、**本節を意図的な逸脱に数えない。3 件目である** — §2.4 のフィルタ帯の funnel（TASK-112）・§2.2 のフォーム部品の高さ（TASK-141）に続く。

### 14.7 本文画像 と 添付画像

**本節は 2026-08-17 に新設した**（TASK-186）。何を描くかは doc-8 §9.5 が持ち、本節は見え方だけを持つ — §14 の他の項と同じ分担である。**番号は既存を動かさず末尾へ足した。**

- **描かれなかった 本文画像 は、その位置に §2.4 の 族を持たない状態の印 を出す。** 図形は `image-off`、色は `--muted`。**alt があればその文字を印の隣に置き、無ければ印だけになる** — 本リポジトリの画像記法は 2 件とも alt が空で、印が出なければ画面に何も残らない。**これは値の表示であって控えではない**ので、§5 の 無効化提示 は当たらない（差し控えている操作が無い。§14.4 の タスクリスト の印 と同じ位置づけである）。
- **遠隔の 本文画像 は §14.3 の 押せる 本文リンク として描く**（doc-8 §9.5）。図形は `image`、色と下線は §14.3 のもの — **押せるので、押せるものの見た目を取る。** **alt が無いときは URL を可視の語にする** — 押せる控えに読む字が無いのを避けるためで、`title` にも同じ URL が入る（§14.3 と同じ扱い）。
- **描かれた 添付画像 は本文ブロックに収める。** 幅は上限いっぱいまで、高さは画面の 60% を上限とする。**高さに上限を置くのは §14.2・§14.5 が幅にだけ置いているのと違う点で、理由は対象が違うことにある** — 表とコードと図は横にはみ出すが、画面いっぱいを写した画像は縦に伸び、本文の続きをパネルの外へ押し出す。**角丸と罫線は §2.2 の値**（3px、`--line`）で、画像の縁と本文ブロックの地を分ける。
- **明暗で描き分けない。** §14.5 の 作図結果 は Atlas 側が配色を持つので明暗に従うが、**添付画像 の色は利用者のファイルのものである。**

**この 3 つは新しい寸法段階を作らない。** 高さの 60% だけが §2.2 の表に無い値で、**あれは段階ではなく画面に対する比である** — §13 の固定行が高さについて「外へ出せないものは中で止める」と決めたのと同じ形で、値の出どころが画面そのものだからこの節が持つ。
