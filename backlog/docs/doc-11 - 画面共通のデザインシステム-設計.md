# 画面共通のデザインシステム 設計

画面設計案の反映として書いた設計（実装は TASK-48）。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は decision-6（不在・欠損の区別と族の分離）・decision-8（素の Svelte・スタイルはコンポーネントスコープド）・decision-12（表示テーマと印チップ配色規則）。画面設計案（doc-1 追補で定義。04・05・06）を反映する。引用する事実は doc-12 §5・§6・§7 に転記してある。

本書は、複数の画面（doc-7 スイムレーン・doc-8 タスク詳細・doc-10 プロジェクト詳細）が共有する見せ方の規則を 1 箇所に置く。各画面の文書は「どこに何を出すか」を定め、本書は「それをどう描くか」を定める。

## 1. 用語

- **デザイントークン** … 複数の画面が同じ値を参照するために名前を与えた寸法・色・角丸・余白を指す。色は表示テーマ（decision-12）が持ち、それ以外は本書が持つ。
- **印** … decision-6 の 4 族（縮退・版ずれ・照合不能／継続検出停止・読取不能）と通知（`--info`）を、対象の脇に短い語で示す表示要素。**印チップ配色規則**（decision-12）で描く。
- **上部帯** … フィルタ帯の下に重要度の固定順で積む、横 1 行の告知区画を指す。
- **無効化提示** … 操作を提供できないとき、その操作を消さずに、押せない見た目と理由の 2 つを同時に与える示し方を指す。
- **アイコン** … lucide（ISC）の図形をそのまま写した装飾用 SVG 1 個を指す。文字グリフ（☰・⚙・▼）ではない。描き方は §2.4。
- **アイコンのみのボタン** … 可視の文言を持たず、用途を `aria-label` と `title` だけが述べるボタンを指す。
- **操作に属さないアイコン** … 押せる控えの内側に無く、置かれた帯・区画が何を扱う場所かを図形だけで示すアイコンを指す。アイコンのみのボタンとの別は、押せるかどうかである。

## 2. デザイントークン

### 2.1 色

表示テーマ（decision-12）が `--bg`・`--panel`・`--inset`・`--fg`・`--muted`・`--faint`・`--line`・`--line-strong`・`--mark-*`・`--info`・`--sel` を持つ。コンポーネントは変数名と `color-mix` だけを参照し、色値を書かない。

| 変数 | 用途 |
|---|---|
| `--bg` / `--panel` / `--inset` | 地 / カード・パネル面 / くぼみ面（レーンヘッダ行・引用・入力の下地） |
| `--fg` / `--muted` / `--faint` | 本文 / 副次（属性名・件数） / 弱（注記・空表示） |
| `--line` / `--line-strong` | 罫線（`--fg` 14% 相当） / 強い罫線・入力枠（30% 相当） |
| `--mark-*` 4 族 | decision-6 の族。一箇所定義、コンポーネントは族名だけを選ぶ |
| `--info` | 通知・確認・リンク風操作。族ではない（青い確認は版ずれではない） |
| `--sel` | 選択のアウトライン |

### 2.2 寸法

| 対象 | 値 |
|---|---|
| 画面見出し | .92rem / 650 |
| タスク title（詳細） | .95rem / 650 / line-height 1.35 |
| カード title | .78rem / 400 / line-height 1.35 |
| 本文・リスト | .72–.74rem |
| 副次（ID・件数・注記） | .6–.68rem ＋ `font-variant-numeric: tabular-nums` |
| 区画見出し | .68rem / 650 / letter-spacing .05em / `--muted` |
| コミット SHA・パス | `ui-monospace` |
| 余白段階 | .16 / .25 / .3 / .45 / .6 / .75 / 1rem |
| 角丸 | チップ 3px / カード・ボタン 4px / パネル 6px / ラベルピル 999px |

件数・ID・日付には `tabular-nums` を与える。桁が揃わないと、行をまたいで数を比べる読み方（doc-7 の縦読み）が成立しないためである。

### 2.3 状態の描き分け

| 状態 | 描き方 |
|---|---|
| hover | 枠線を `--line` → `--line-strong` |
| 選択 | `outline: 2px solid var(--sel)` ＋ offset 1px |
| 無効 | 破線枠 ＋ opacity .45 ＋ `cursor: help` ＋ 理由（5 章） |
| 問題の縁 | カード左 3px（縮退／版ずれ。両方あれば版ずれを優先）・上部帯左 4px |

### 2.4 アイコン

画面設計案や各画面の設計文書が入口や折畳みに置いた記号（01 の入口の ☰・⚙〔doc-12 §2.4〕、折畳みは画面設計案 06 の ▾▸ ＋ 可視の文言「畳む」〔doc-12 §7.2〕と doc-7 §2.3 の図の ▼▲、画面設計案 02 の区画見出しの ▼▶〔doc-12 §3〕、01 の設定モーダルの右上の ×〔doc-12 §2.2〕）は文字グリフであり、それを図形へ替えるのが TASK-67・69・71・72・73・76・77 である。**TASK-73 が替えるのは `<details>` の UA 既定マーカー**で、これは文書が刷った記号ではなくブラウザが描くものだが、字面と大きさが WebKit と Chromium で変わる点は文字グリフと同じであり、Atlas は 3 OS で別々の webview の上に載る（decision-11）。**この節は折畳みの記号を長く「∧∨」と書いていたが、転記のどこにもその記号は無い** — TASK-69 の title の記号をそのまま写したものだった（TASK-69 で判明）。**画面設計案 01 が折畳みに何を刷っていたかは doc-12 に転記が無く、このリポジトリからは確かめられない**ので、ここでは 01 に帰属させない。図形が元の記号の向きを保つかどうかは画面ごとの判断で、折畳みについては doc-7 §2.2・§2.3 が定める。TASK-112 のフィルタ帯の funnel だけは置き換えではなく、画面設計案に無いものを新しく置く（doc-12 §4.3）。

- **置き場は `src/lib/icons/`** で、図形データ（`lucide.ts`）と描画（`Icon.svelte`）を分ける。**lucide のパッケージを本番依存に入れない** — 要るのは 10 個前後で、AGENTS.md の最小依存の方針に合う。出典（**パッケージ名**・版・ISC・写した元ファイル）は図形データの冒頭に書く。**パッケージ名まで書く** — lucide は同じ図形を複数のパッケージで配っており、実際に座標を読んだ 1 つを名指ししない限り、後から元と突き合わせる先が定まらない（`lucide` と書いてあったものが実は `lucide-react` だった、が TASK-112 で見つかった）。ISC の告知をリリース物へ載せるかどうかは TASK-97 が扱う。
- **図形は写すだけで、描き直さない**。手書きのパスや、`rect` をパスへ潰したものは lucide に似た図形であって lucide の図形ではなく、後からどちらなのかを区別できない。使う SVG 要素の種類は閉じた列挙で持ち、要素が足りない図形を入れるときは列挙を増やす。**列挙を増やしたときに描画が抜けることは、型で止める** — 種別から描画要素への写像を網羅的な `switch` 1 つに置き、テンプレートはその返り値を描く。テンプレート側の条件分岐では止まらない（列挙が 1 種類のうちは分岐漏れが型エラーにならず、空の `<svg>` が描かれてビルドは成功する）。
- **寸法は 1em**。`viewBox` 24・線幅 2 という lucide の値をそのまま使い、大きさはアイコンを置く箱（ボタンでも、操作に属さないアイコンならそれを含む帯・区画でも）の `font-size` が決める。単独のボタンでは 1rem（16px）を既定とする。アイコン専用の寸法指定を足さないのは、隣の文字と食い違う 2 つめのつまみを作らないためである。
- **色は `currentColor` だけ**。表示テーマ（decision-12）へ追加する変数は無い。
- **アイコンは常に装飾** として `aria-hidden` を付け、アクセシブル名に寄与させない。図形は語を持たないので、`<svg>` を読ませると名前の無いボタンになる。
- **アイコンのみのボタン** とは、可視の文言を持たず、用途を `aria-label` と `title` だけが述べるボタンを指す。`aria-label` を必ず置き、そこには操作の名前だけを入れる（キーを含めると読み上げが「設定 ⌘,」になる）。ショートカットの併記は doc-7 §2.1 の規則に従い、`title`・`aria-keyshortcuts` と割り当て一覧のモーダルが担う。
- **アイコンのみのボタンが持続する状態の印を持つとき**、印を可視の文言にしない。文言を足したボタンは可視の文言を持つことになり、上項の定義からアイコンのみのボタンでなくなる。印は図形の外側の線・塗りで示し、**同じことを `aria-label` にも語で足す** — 線も塗りも図形と同じく読み上げに何も残さないので、目で見た利用者にしか届かない状態になる。上項の「`aria-label` には操作の名前だけを入れる」が退けているのはショートカットキーの併記であり、そのボタンが担う状態は名前の一部として入れてよい。押されているかどうかは `aria-pressed` が担うので、ここで言う状態はそれ以外のもの（3 配置切替の既定印。doc-8 §2.2）を指す。**持続する** とは、利用者が操作しない限りその状態が続くことを指す。
- **押した結果を一定時間だけ述べる表示には、上項を適用しない**（本項は TASK-72 で新設）。図形の差し替え・色の付与でそれを示してよく、**語は隣接する live region（`role="status"`）が担い、`aria-label` は操作の名前のまま変えない**。理由は 2 つある。ボタンのアクセシブル名は、そのボタンを名前で探し直す利用者にとっての識別子であり、押した後しばらく別の名前になる控えは、その間だけ見失われる。もう 1 つは、上項が `aria-label` へ語を足させる理由が「目で見た利用者にしか届かない状態になる」ことであって、隣に語があるならその理由自体が成り立たないことである。**規則を伸ばすのではなく適用条件で分ける**のは、この違いによる。live region は**内容が空のときも DOM に置いたまま**にする — 語が現れるのと同時に挿入された領域は、確実には読み上げられない。**この語は見える必要がない**。図形の差し替えが目に対して結果を述べているので、同じことを述べる可視の文は、操作のたびに読み飛ばす対象が 1 つ増えるだけである。可視にしない場合は**視覚的にのみ隠す**（`display: none` や要素の取り外しはアクセシビリティツリーからも外し、ツリーに無い live region は埋まっても読み上げられない — 常時 DOM に置く理由がそこで消える）。ただし**結果が図形の述べていないことを含むなら、その部分は可視で残す**（コピー失敗時に選択してコピーするための ID 文字列など。図形はそれを述べていない）。
- **可視の文言を持つ控えの中のアイコン**（本項は TASK-73 で新設）とは、押せる控えの内側にあり、**その控えが可視の文言も持つ**ときのアイコンを指す（タスク詳細の区画見出しの開閉印。doc-8 §3）。上の 2 つのどちらでもない — アイコンのみのボタンは可視の文言を持たないことを定義にしており、操作に属さないアイコンは押せる控えの中に無いことを定義にしているためである。置き場・寸法・色・`aria-hidden` は上の各項と同じで、加わるのは次の 2 つ。
  - **`aria-label` を与えない**。控えの名前は可視の文言が既に持っており、`aria-label` はそれに優先する（TASK-72 で確かめた）ので、足すと目に見える名前と読み上げられる名前が食い違う。
  - **図形が述べる状態を `aria-label` へ語で足さない**。「アイコンのみのボタンが持続する状態の印を持つとき、同じことを `aria-label` にも語で足す」を適用しないのは、その項が語を足させる理由（線も塗りも読み上げに何も残さないので目で見た利用者にしか届かない）が、ここでは成り立たないからである。区画見出しの開閉印なら、`<summary>` がその `<details>` の開閉をアクセシビリティツリーへ出しており、図形は同じことを目に対して繰り返している。**控えの仕組みがその状態を既に述べているかどうかが、適用の分かれ目**である。
- 無効化提示（5 章）はアイコンのみのボタンでも同じで、理由をホバーだけに置かない。
- **操作に属さないアイコン** とは、押せる控えの内側に無く、置かれた帯・区画が何を扱う場所かを図形だけで示すアイコンを指す（フィルタ帯の先頭の funnel。doc-7 §5.2）。置き場・色・`aria-hidden` は上の各項と同じで、寸法もアイコンを置く箱の `font-size` に従う（フィルタ帯なら帯の .72rem。既定の 1rem はボタンに与えたものなので、ここには効かない）。押せる控えの中に無いことから、次の 3 つが加わる。
  - **図形が示すことは、同じ帯・区画の中の語も述べていなければならない**。アイコンは常に装飾なので、読み上げには図形が何も残さない。図形だけが述べている状態にすると、その帯が何をする場所かは、目で見た利用者にしか届かない。フィルタ帯では「＋ 絞り込み」「全解除」とテキスト欄の `aria-label` がそれを述べており、funnel はそれを図形で繰り返している。
  - **隣の控えの `<label>` の中に入れない**。図形の指示対象は帯全体で、1 つの入力欄より広い。ラベルに入れると、より狭い対象の名前として読まれ、図形と指示対象が食い違う。
  - 押せないので `aria-label`・`title`・フォーカスのいずれも与えない。与えると、押しても何も起きない要素が操作として読み上げられる。

## 3. チップの 4 系統

同じ「小さな四角い札」に見えるものが 4 系統あり、混ぜると別の意味が同じ見た目になる。形・塗り・太さで分ける。

- **印**（縮退・版ずれ・継続検出停止・読取不能・通知）: 文字＝族の色、背景＝族の色 12% 混色、枠＝族の色 45% 混色、角丸 3px、`cursor: help` と説明（decision-12 の印チップ配色規則）。族の判別は色相の距離とチップ文言の二重化で行う。
- **Type**（`kind:*` 由来の分類、decision-5）: `--fg` 13% 混色の塗り ＋ 太字 ＋ 角丸 3px。未知 Type は実線輪郭のみ、Type 未設定は破線輪郭で色を与えない（decision-6 の中立表示）。
- **通常ラベル**（自由タグ）: 輪郭のみのピル（角丸 999px）＋ 細字 ＋ `--muted`。Type と同一の一覧に混ぜない（doc-7 §3・doc-8 §4）。
- **priority**: 族の色を借りず、`--fg`／`--bg` の濃淡 3 段で示す（high＝`--fg` 塗りに `--bg` 文字、medium＝`--line-strong` の輪郭、low＝`--line` の輪郭に `--muted` 文字）。理由は decision-12（現行の high・medium が読取不能・縮退の族の色と同色で族を汚染する）。

保存区分印と、未分類区画に出す原文 status は、族でも Type でもない中立の情報である。輪郭のみ・`--muted` で示し、族の色を与えない。

**畳んだ列のレーンセルに並ぶ四角（doc-7 §2.2）もこの 4 系統に入らない。** 小さな四角に見えるが、対象に付いてその状態を述べる札ではなく、そのセルにカードが何枚あるかだけを示す図形である。**色を与えない**のがこの区別の担保で、族の色を借りると縮退・読取不能の札と同じ見た目になる（decision-6）。文字を持たず、読み上げにも出さない（同じセルの件数がその役を負う）。

**絞り込みトークン（doc-7 §5.2）はこの 4 系統に入らない。** 見た目は札に近いが、内側に自分を解除する `×` を持つ操作要素であり、対象に付いてその状態を述べるチップではない。角丸は §2.2 の**ボタンの 4px** を取る（チップの 3px ではない）。1 系統として数えないのは、4 系統が「対象に付く札を混ぜない」ための区別であり、押せるものをそこへ足すと区別の軸が 2 つになるためである。

## 4. 上部帯

上部帯は 6 種で、**出現順ではなく重要度の固定順**に積む。同時に立ちうる最大は 6 本で、この 6 種以外に上部帯を作らない。各帯は 1 行に収め、左端 4px にその帯の族の色を置く。

| 順 | 帯 | 何を伝えるか | 左端 4px | 閉じられるか |
|---|---|---|---|---|
| ① | 確認（未保存入力の破棄前確認など） | 利用者の回答待ち | `--info` | 閉じられない（回答で消える） |
| ② | CLI 縮退（doc-5 §5） | 作成・更新をどこからも発行できない | `--mark-degraded` | 閉じられない（CLI を検出できると消える） |
| ③ | 台帳読取専用（doc-3 §2.2） | 台帳の更新・登録解除・並べ替えができない | `--mark-unreadable` | 閉じられない |
| ④ | 継続検出停止（doc-9 §3） | 表示が実ファイルより古いかもしれない | `--mark-undetectable` | 閉じられない（再読込で消える） |
| ⑤ | 通知 | 済んだ操作の結果 | `--info` | × で閉じる |
| ⑥ | 行非表示（doc-7 §5.1） | 利用者が自分で外した行と、戻す入口 | 色を与えない（`--line-strong`） | 閉じられない（戻すと消える） |

順は「回答待ち → 発行できない → 表示が古いかもしれない → 済んだことの報告 → 自分で隠したもの」で並べる。②③ が④より上なのは、操作が通らないことは表示の鮮度より先に知る必要があるためで、②が③より上なのは、CLI 縮退が止める操作の範囲（タスク・文書・マイルストーンの全更新）のほうが台帳読取専用（台帳のみ）より広いためである。②③ を 1 本にまとめないのは、原因が別で片方だけ立つことがあり、族の色もそれぞれ異なるからである。

順を出現順にしない理由は、帯が積まれるほど上の行が下へ押し出され、回答待ちの ① が通知 ⑤ の下に埋もれうるためである。①〜④ を閉じられなくするのは、無視できる形にすると「発行できない状態や古い表示のまま操作を続ける」経路ができるからである。⑥ に色を与えないのは、利用者が自分で隠した状態であって異常ではないためである（decision-6 の中立表示）。

②③④ は個々の操作の無効化理由（5 章）と内容が重複するが、それでよい。ホバーしないと理由に到達できない状態を作らないためである。

**1 行に収まらない内容は折り返さず、要約へ縮約して全体を別の場所から読ませる**。折り返しを許すと、狭いウィンドウ・長いプロジェクト名・文字サイズ拡大で上部の占有が伸び、「フィルタ帯 1 行 ＋ 上部帯 6 本」で頭打ちという性質が崩れる。縮約の形は帯ごとに定める（例: 行非表示の帯は「非表示のレーン n 件」に縮約し、個々のレーンはメニューの一覧から戻す）。ただし帯が持つ操作（確認への回答・再読込・戻す）は縮約しても帯に残し、操作へ到達するために別の場所を開かせない。

フィルタ帯 1 行 ＋ 上部帯 6 本が同時に立つのが最悪ケースで、画面上部の占有はここで頭打ちになる。

## 5. 無効化提示

提供できない操作は、消さずに無効化し、理由を必ず添える。

- 見た目は破線枠 ＋ opacity .45 ＋ `cursor: help`。押せる操作（実線枠）と見分けられる形にする。
- **理由をホバーに依存させない**。`disabled` を付けたネイティブの操作はフォーカスを受け取らず、`title` はキーボード・タッチ・スクリーンリーダーのいずれからも安定して到達できない。理由は次のどちらかで到達可能にする。
  - 操作の近くに**常時表示する補助文**として置く。この場合は `disabled` のままでよい。
  - 操作を `aria-disabled` とフォーカス可能なまま（押しても発行しない）にし、`aria-describedby` で理由の要素へ結ぶ。
  `title` はこれらの補助にとどめ、唯一の格納先にしない。
- 画面全体に効く理由（CLI 縮退・台帳読取専用）は上部帯にも出す。個々の操作の理由と重複してよい。
- 理由の無い無効化を置かない。「なぜ押せないか」が分からない操作は、故障と区別できない。
- **提供しない操作**（Atlas がこの版で出さないと決めたもの）は、無効化されたボタンとして並べず、名称・写像先・理由の 3 点を並べる区画に置く（doc-10 §6 の提供しない操作区画）。無効化は「今は条件が揃っていない」を意味し、提供しない操作はそれとは別だからである。
- 破壊的操作の確定は二度押しとし、一度目でラベルを確認文へ差し替える。

## 6. 空・不在の描き方

- **正常な不在**（空セル・コミット該当なし）は、`--faint` の `—` 1 文字だけで示す。族の色を与えず、警告記号・アイコン・枠を付けない。「該当タスクが無い」ことを読み取れる必要があるため、何も描かないのではなく中立の目印を 1 つ置く。decision-6 が禁じているのは、正常な不在にエラー色・警告記号を与えることと、読取不能と同じ見た目にすることであって、中立の目印そのものではない。この形は現行の実装（`LaneCell.svelte`）と一致する。
- **読取不能**は族の色（`--mark-unreadable`）と理由と復帰操作を伴う。正常な不在と決して同じ見た目にしない。
- **Type 未設定**は破線輪郭で色を与えない。未知 Type（実線輪郭）とも区別する。

## 7. モーダルの閉じる

本節の**モーダル**は doc-7 §2.1 の被せ層（プロジェクト登録・設定・キーボード操作の一覧が開く先）を指す。doc-8 §2.1 の**中央モーダル詳細配置は含まない** — あちらはタスク詳細の 3 配置の 1 つで、閉じるは見出し 1 行目の操作群が持つ（doc-8 §2.2）。

- **モーダルは右上に `×` を 1 つ持ち、それがモーダル自身の閉じる操作である**（TASK-76 で導入。原文は画面設計案 01 の設定モーダル。doc-12 §2.2）。描くのは層そのものであって中身ではない。中身ごとに置くと、同じ 1 つの操作が中身の数だけ別の位置・別の見た目になる — TASK-76 の前は 3 つの中身が見出しの脇にそれぞれ文言ボタンを置いており、設定モーダルだけは TASK-74 でそれを失っていた。
- **`×` は §2.4 のアイコンのみのボタン**として描く（図形は lucide の `x`）。`aria-label` は「閉じる」だけとし、何を閉じるかを加えない — それは `role="dialog"` の `aria-label` が既に述べており、2 つを繋ぐと「プロジェクトを登録を閉じる」になる。**§2.4 に型は増えない。**
- **`×` はモーダルの中で最初の操作**に置く。層の出口が開いた直後から 1 打鍵の距離にあり、フォーカスを与える操作が対象をスクロール領域へ引き入れるので、長い中身のモーダルが自分の見出しより下へスクロールした状態で開くこともない。
- **`×` が述べるのは「この層を閉じる」だけ**である。**下書きを持つモーダルは、それに加えて下部操作行を持ち**、そこの押下が下書きをどう扱って出るのかを可視の文言で述べる（設定モーダルの「変更せずに閉じる」「保存する」。TASK-74）。**役割の別は、下書きの行方を語で述べるかどうかにある** — 破棄するかどうかではない。`×` も「変更せずに閉じる」も下書きを書かずに出るので、そこでは分かれない。原文の設定モーダルで `×` と下部の「閉じる」が同じ操作なのは（doc-12 §2.2）、原文に保存が無く、述べ分ける下書きが存在しないためである。
- **出口はすべて 1 つの閉じる要求へ集まる**。`×`・Escape（doc-7 §2.1）・下部操作行の「変更せずに閉じる」は、モーダルを配線している側（シェル）の 1 つの経路へ届く。TASK-86 の破棄前確認は、その 1 経路の前に置く。
- **いま閉じられない事情はシェルが持ち、`×` へ渡す**。発行中の書込みがあるなど、閉じる要求を受け付けられない事情があるとき、`×` は 5 章の無効化提示に従う（`aria-disabled` のままフォーカスを受け、`aria-describedby` で理由へ結ぶ）。事情を持つのがシェルなのは、Escape と下部操作行の押下も同じ 1 つの事情に従わなければならないからで、`×` だけが自分で判断すると 3 つの出口が別々の事実を見る。**理由を可視で出すかどうかは中身が決める** — 下部操作行が同じ理由を刷っているなら、`×` の側は目に見えない置き方（アクセシビリティツリーには残す）でよい。同じ 1 つの事情を 1 つの箱の中で 2 度述べないためである。
- **本節はモーダル以外の `×` を覆わない。** 上部帯の通知・絞り込みトークンの解除・status 別名表の行削除は文字グリフの `×` のままで、本節より古い（TASK-80 が実装と画面設計案の差分としてまとめて扱う）。
- **モーダルの出口が上げた破棄前確認は、モーダルの中に出す**（TASK-86）。破棄前確認そのものは doc-8 §6.3 が定め、その置き場は上部帯の ①（doc-7 §5.3）だが、本節のモーダルはその上部帯を覆う（doc-7 §2.1 のフォーカス内留めのため意図的）。覆っている層の出口が上げた問いを ① に置くと、問いの対象であるモーダルが消えるまで読めず答えられない。**これは 7 種目の上部帯ではない** — doc-11 §4 の 6 種は画面が積む告知で、こちらは同じ ① の告知を、それを上げた層の中に描いたものである。**文言と 2 つの答えは doc-8 §6.3 のものをそのまま使う**。モーダルの経路は §6.3 が数える 5 経路の外にあり、失われる未保存入力も編集セッションのものではないが、同じ喪失を 2 通りに述べないためである。
- **答えを待っている状態と、いま閉じられない事情は別である**（TASK-86）。前者は閉じる要求が出ていて答えを待つ状態で、`×` は押せるままにする（もう一度押しても同じ問いをもう一度出すだけである）。後者は要求そのものを出さない状態で、`×` は §5 の無効化提示に従う。混ぜると、答えの控えが同じ箱の中にあるのに「答えていないから押せない」を理由に無効化することになる。**順序は後者が先で、発行中は破棄前確認より前に断る** — 発行した書込みが解決していない間に「破棄して続ける」を差し出すと、いま台帳やファイルへ入ろうとしている入力について破棄を選ばせることになる。
- **Escape は、問いが立っている間はその問いに答える**（「編集に戻る」。TASK-86）。押下は最も内側の開いている層に費やされる（doc-7 §2.1 の Escape。絞り込みの値一覧も同じ）ので、問いが立っている間の最も内側はモーダルではなく問いである。閉じる要求を出し直す形にすると、Escape は画面上何も変えない打鍵になる。
- **下部操作行を持つのは、下書きを書いて出る出口を併せ持つモーダルだけである**（TASK-86 で条件を明示）。未保存入力を持つだけでは要らない — プロジェクト登録モーダルは 3 欄の入力を保持するが、「登録」は台帳へ書いても層を出ないので、出方が 1 通りしかなく述べ分ける相手がいない。そこで `×` を押したときに入力がどうなるかは、下部操作行ではなく破棄前確認が述べる。原文が「登録」と対で持つ「取消」（doc-12 §2.3）を足すかどうかは TASK-80 のままである。

## 8. SCSS への写し方

- 表示テーマの `[data-theme="…"]` ブロック群は `src/app.scss` に置く。ここだけが色値を持つ（decision-12）。
- 各コンポーネントのスタイルは Svelte の `<style lang="scss">` に置き、`var(--…)` と `color-mix` だけを参照する（decision-8）。ユーティリティクラスは導入しない。
- 本書の寸法・角丸・余白は、複数コンポーネントが参照するものだけを `app.scss` の変数として置き、1 コンポーネントでしか使わない値はそのコンポーネントに置く。
