# 画面共通のデザインシステム 設計

画面設計案の反映として書いた設計（実装は TASK-48）。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は decision-6（不在・欠損の区別と族の分離）・decision-8（素の Svelte・スタイルはコンポーネントスコープド）・decision-12（表示テーマと印チップ配色規則）。画面設計案（doc-1 追補で定義。04・05・06）を反映する。引用する事実は doc-12 §5・§6・§7 に転記してある。

本書は、複数の画面（doc-7 スイムレーン・doc-8 タスク詳細・doc-10 プロジェクト詳細）が共有する見せ方の規則を 1 箇所に置く。各画面の文書は「どこに何を出すか」を定め、本書は「それをどう描くか」を定める。

## 1. 用語

- **デザイントークン** … 複数の画面が同じ値を参照するために名前を与えた寸法・色・角丸・余白を指す。色は表示テーマ（decision-12）が持ち、それ以外は本書が持つ。
- **印** … decision-6 の 3 族（不整合・照合不能／継続検出停止・読取不能）と通知（`--info`）を、対象の脇に示す表示要素。描き方は 2 通りあり、**印チップ**は短い語を持ち**印チップ配色規則**（decision-12）で描き、**印グリフ**は語を持たず族の色を図形自身の色として持つ（decision-22）。**族は 4 つだった** — decision-22 が縮退と版ずれを不整合へ束ねた（§3・§10）。
- **印チップ** … 語を持つ印。文字＝族の色、背景＝族の色 12% 混色、枠＝族の色 45% 混色（decision-12）。
- **印グリフ** … 語を持たず、族の色を図形自身の描画色として持つ印。背景も枠も持たない（decision-22）。現在の唯一の実例は不整合印 ⚠️ で、描き方は §2.4、色の条件は decision-22 の印グリフの収録条件（族の色 対 それが載る面で 3:1 以上）による。**印チップ配色規則を適用しない** — 12% 混色の背景が存在しないので、あの規則の測る対象がここには無い。
- **優先度の縁** … タスクカードの左辺 3px に置き、そのタスクの priority を色で述べる縁を指す（decision-23）。**印ではない** — 対象の状態が正常かどうかを述べておらず、族の色ではなく優先度色を引く。描き方と、問題の縁と形を共有することの扱いは §2.3。
- **優先度色** … priority 3 段のそれぞれを述べる表示要素が引く 3 つの色値を指す（decision-23）。族ではないので、印がこれを借りることはない。**引く表示要素は 4 つ**（優先度の縁 §2.3・priority チップ §3・畳んだ列のレーンセルに並ぶ四角 §3・タスク詳細の priority の値 doc-8 §2.2）で、**満たすべき比は色値ではなく描き方に付く** — 札の文字なら自分の 12% 混色背景に対して 4.5:1、素の文字なら面に対して 4.5:1、図形なら面に対して 3:1（decision-23 の優先度色の収録条件）。
- **上部帯** … フィルタ帯の下に重要度の固定順で積む、横 1 行の告知区画を指す。
- **無効化提示** … 操作を提供できないとき、その操作を消さずに、押せない見た目と理由の 2 つを同時に与える示し方を指す。
- **アイコン** … lucide（ISC）の図形をそのまま写した装飾用 SVG 1 個を指す。文字グリフ（☰・⚙・▼）ではない。描き方は §2.4。
- **アイコンのみのボタン** … 可視の文言を持たず、用途を `aria-label` と `title` だけが述べるボタンを指す。
- **操作に属さないアイコン** … 押せる控えの内側に無く、置かれた帯・区画が何を扱う場所かを図形だけで示すアイコンを指す。アイコンのみのボタンとの別は、押せるかどうかである。

## 2. デザイントークン

### 2.1 色

表示テーマ（decision-12）が `--bg`・`--panel`・`--inset`・`--fg`・`--muted`・`--faint`・`--line`・`--line-strong`・`--mark-*`・`--info`・`--sel` を持つ。コンポーネントは変数名と `color-mix` だけを参照し、色値を書かない。

| 変数 | 用途 |
|---|---|
| `--bg` / `--panel` / `--inset` | 地 / カード・パネル面 / くぼみ面（レーンヘッダ行・引用・入力の下地） |
| `--fg` / `--muted` / `--faint` | 本文 / 副次（属性名・件数） / 弱（注記・空表示） |
| `--line` / `--line-strong` | 罫線（`--fg` 14% 相当） / 強い罫線・入力枠（30% 相当） |
| `--mark-*` 3 族 | decision-6・decision-22 の族。一箇所定義、コンポーネントは族名だけを選ぶ |
| `--info` | 通知・確認・リンク風操作。族ではない（青い確認は不整合ではない） |
| `--sel` | 選択のアウトライン |
| `--priority-high` / `--priority-medium` / `--priority-low` | 優先度色（decision-23）。priority を述べる 4 つの表示要素が引く（優先度の縁 §2.3・priority チップ §3・畳んだ列の四角 §3・タスク詳細の priority の値 doc-8 §2.2）。**族ではない**ので印はこれを借りない |

### 2.2 寸法

| 対象 | 値 |
|---|---|
| 画面見出し | .92rem / 650 |
| タスク title（詳細） | .95rem / 650 / line-height 1.35 |
| カード title | .78rem / 400 / line-height 1.35 |
| 本文・リスト | .72–.74rem |
| 副次（ID・件数・注記） | .6–.68rem ＋ `font-variant-numeric: tabular-nums` |
| 区画見出し | .68rem / 650 / letter-spacing .05em / `--muted` |
| コミット SHA・パス | `ui-monospace` |
| 余白段階 | .16 / .25 / .3 / .45 / .6 / .75 / 1rem |
| 角丸 | チップ 3px / カード・ボタン 4px / パネル 6px / ラベルピル 999px |

**角丸の「チップ 3px」は §3 のチップの 4 系統すべてに掛かる**（priority を含む）。999px を取るのは通常ラベルだけで、それは画面設計案 04 の契約 #4「Type とラベルを混ぜない」が通常ラベルに与えた形である（doc-12 §5）。priority が 999px だった実装は本表からの逸脱で、decision-23 が実装を本表へ合わせた — **本表の値は動いていない**。

件数・ID・日付には `tabular-nums` を与える。桁が揃わないと、行をまたいで数を比べる読み方（doc-7 の縦読み）が成立しないためである。

### 2.3 状態の描き分け

| 状態 | 描き方 |
|---|---|
| hover | 枠線を `--line` → `--line-strong` |
| 選択 | `outline: 2px solid var(--sel)` ＋ offset 1px |
| 無効 | 破線枠 ＋ opacity .45 ＋ `cursor: help` ＋ 理由（5 章） |
| 問題の縁 | 上部帯左 4px・レーンヘッダ行左 3px（読取不能の行）・タスク詳細の不整合区画の左 3px |
| 優先度の縁 | タスクカード左 3px。priority 3 段のときだけ 優先度色（§2.1）を置く（decision-23） |

**カード左 3px の族色は decision-22 で外れた**（TASK-77）。不整合であることをカードで述べるのは印グリフだけで、同じ 1 つのことを図形と縁の 2 つで述べない。区画の左 3px が残るのは、そこでは図形ではなく面そのものが「何の区画か」を述べているためである。**問題の縁の列挙にレーンヘッダ行が無かったのを decision-23 のときに足した** — `Swimlane.svelte` は読取不能の行に前からこの縁を描いており（族の色を面全体へ敷くと、その上に載る印チップの 12% 混色背景が検算した色と変わるため）、落ちていたのは列挙のほうである。

**空いたカードの縁は decision-23 が priority へ渡した。優先度の縁**とは、タスクカードの左辺 3px に置き、そのタスクの priority を色で述べる縁を指す。**問題の縁とは別の行として数える** — 述べているのは問題ではなく優先順位で、族の色ではなく優先度色（族ではない）を引く。**同じ装置を同じ色相で使う衝突は残っている**（赤の左端はカードでは high、レーンヘッダ行では読取不能）ので、**区別は色相ではなく、その縁を何が持っているかで行う**。カード（1 件のタスク）・レーンヘッダ行（1 プロジェクト行）・上部帯（画面全体）は大きさも位置も別の表示要素で、問題の縁を持つ 2 つは語を伴う。**priority 未設定・priority 未知 には縁を出さない**（縁が無いことが「3 段のどれでもない」を述べる）。縁は語を持たない非文字要素なので、満たすべき比は decision-23 の**優先度色の収録条件**のうち面に対する 3:1 である（**「優先度の縁の収録条件」という縁だけの契約は無い** — 条件は色値ではなく描き方に付き、優先度色を引く 4 つの表示要素で 3 通りに分かれる）。

### 2.4 アイコン

画面設計案や各画面の設計文書が入口や折畳みに置いた記号（01 の入口の ☰・⚙〔doc-12 §2.4〕、折畳みは画面設計案 06 の ▾▸ ＋ 可視の文言「畳む」〔doc-12 §7.2〕と doc-7 §2.3 の図の ▼▲、画面設計案 02 の区画見出しの ▼▶〔doc-12 §3〕、01 の設定モーダルの右上の ×〔doc-12 §2.2〕）は文字グリフであり、それを図形へ替えるのが TASK-67・69・71・72・73・76・77 である。**TASK-73 が替えるのは `<details>` の UA 既定マーカー**で、これは文書が刷った記号ではなくブラウザが描くものだが、字面と大きさが WebKit と Chromium で変わる点は文字グリフと同じであり、Atlas は 3 OS で別々の webview の上に載る（decision-11）。**この節は折畳みの記号を長く「∧∨」と書いていたが、転記のどこにもその記号は無い** — TASK-69 の title の記号をそのまま写したものだった（TASK-69 で判明）。**画面設計案 01 が折畳みに何を刷っていたかは doc-12 に転記が無く、このリポジトリからは確かめられない**ので、ここでは 01 に帰属させない。図形が元の記号の向きを保つかどうかは画面ごとの判断で、折畳みについては doc-7 §2.2・§2.3 が定める。TASK-112 のフィルタ帯の funnel だけは置き換えではなく、画面設計案に無いものを新しく置く（doc-12 §4.3）。

- **置き場は `src/lib/icons/`** で、図形データ（`lucide.ts`）と描画（`Icon.svelte`）を分ける。**lucide のパッケージを本番依存に入れない** — 要るのは 10 個前後で、AGENTS.md の最小依存の方針に合う。出典（**パッケージ名**・版・ISC・写した元ファイル）は図形データの冒頭に書く。**パッケージ名まで書く** — lucide は同じ図形を複数のパッケージで配っており、実際に座標を読んだ 1 つを名指ししない限り、後から元と突き合わせる先が定まらない（`lucide` と書いてあったものが実は `lucide-react` だった、が TASK-112 で見つかった）。ISC の告知をリリース物へ載せるかどうかは TASK-97 が扱う。
- **図形は写すだけで、描き直さない**。手書きのパスや、`rect` をパスへ潰したものは lucide に似た図形であって lucide の図形ではなく、後からどちらなのかを区別できない。使う SVG 要素の種類は閉じた列挙で持ち、要素が足りない図形を入れるときは列挙を増やす。**列挙を増やしたときに描画が抜けることは、型で止める** — 種別から描画要素への写像を網羅的な `switch` 1 つに置き、テンプレートはその返り値を描く。テンプレート側の条件分岐では止まらない（列挙が 1 種類のうちは分岐漏れが型エラーにならず、空の `<svg>` が描かれてビルドは成功する）。
- **寸法は 1em**。`viewBox` 24・線幅 2 という lucide の値をそのまま使い、大きさはアイコンを置く箱（ボタンでも、操作に属さないアイコンならそれを含む帯・区画でも）の `font-size` が決める。単独のボタンでは 1rem（16px）を既定とする。アイコン専用の寸法指定を足さないのは、隣の文字と食い違う 2 つめのつまみを作らないためである。
- **色は `currentColor` だけ**。表示テーマ（decision-12）へ追加する変数は無い。
- **アイコンは常に装飾** として `aria-hidden` を付け、アクセシブル名に寄与させない。図形は語を持たないので、`<svg>` を読ませると名前の無いボタンになる。
- **アイコンのみのボタン** とは、可視の文言を持たず、用途を `aria-label` と `title` だけが述べるボタンを指す。`aria-label` を必ず置き、そこには操作の名前だけを入れる（キーを含めると読み上げが「設定 ⌘,」になる）。ショートカットの併記は doc-7 §2.1 の規則に従い、`title`・`aria-keyshortcuts` と割り当て一覧のモーダルが担う。
- **アイコンのみのボタンが持続する状態の印を持つとき**、印を可視の文言にしない。文言を足したボタンは可視の文言を持つことになり、上項の定義からアイコンのみのボタンでなくなる。印は図形の外側の線・塗りで示し、**同じことを `aria-label` にも語で足す** — 線も塗りも図形と同じく読み上げに何も残さないので、目で見た利用者にしか届かない状態になる。上項の「`aria-label` には操作の名前だけを入れる」が退けているのはショートカットキーの併記であり、そのボタンが担う状態は名前の一部として入れてよい。押されているかどうかは `aria-pressed` が担うので、ここで言う状態はそれ以外のもの（3 配置切替の既定印。doc-8 §2.2）を指す。**持続する** とは、利用者が操作しない限りその状態が続くことを指す。
- **押した結果を一定時間だけ述べる表示には、上項を適用しない**（本項は TASK-72 で新設）。図形の差し替え・色の付与でそれを示してよく、**語は隣接する live region（`role="status"`）が担い、`aria-label` は操作の名前のまま変えない**。理由は 2 つある。ボタンのアクセシブル名は、そのボタンを名前で探し直す利用者にとっての識別子であり、押した後しばらく別の名前になる控えは、その間だけ見失われる。もう 1 つは、上項が `aria-label` へ語を足させる理由が「目で見た利用者にしか届かない状態になる」ことであって、隣に語があるならその理由自体が成り立たないことである。**規則を伸ばすのではなく適用条件で分ける**のは、この違いによる。live region は**内容が空のときも DOM に置いたまま**にする — 語が現れるのと同時に挿入された領域は、確実には読み上げられない。**この語は見える必要がない**。図形の差し替えが目に対して結果を述べているので、同じことを述べる可視の文は、操作のたびに読み飛ばす対象が 1 つ増えるだけである。可視にしない場合は**視覚的にのみ隠す**（`display: none` や要素の取り外しはアクセシビリティツリーからも外し、ツリーに無い live region は埋まっても読み上げられない — 常時 DOM に置く理由がそこで消える）。ただし**結果が図形の述べていないことを含むなら、その部分は可視で残す**（コピー失敗時に選択してコピーするための ID 文字列など。図形はそれを述べていない）。
- **可視の文言を持つ控えの中のアイコン**（本項は TASK-73 で新設）とは、押せる控えの内側にあり、**その控えが可視の文言も持つ**ときのアイコンを指す（タスク詳細の区画見出しの開閉印。doc-8 §3）。上の 2 つのどちらでもない — アイコンのみのボタンは可視の文言を持たないことを定義にしており、操作に属さないアイコンは押せる控えの中に無いことを定義にしているためである。置き場・寸法・色・`aria-hidden` は上の各項と同じで、加わるのは次の 2 つ。
  - **`aria-label` を与えない**。控えの名前は可視の文言が既に持っており、`aria-label` はそれに優先する（TASK-72 で確かめた）ので、足すと目に見える名前と読み上げられる名前が食い違う。
  - **図形が述べる状態を `aria-label` へ語で足さない**。「アイコンのみのボタンが持続する状態の印を持つとき、同じことを `aria-label` にも語で足す」を適用しないのは、その項が語を足させる理由（線も塗りも読み上げに何も残さないので目で見た利用者にしか届かない）が、ここでは成り立たないからである。区画見出しの開閉印なら、`<summary>` がその `<details>` の開閉をアクセシビリティツリーへ出しており、図形は同じことを目に対して繰り返している。**控えの仕組みがその状態を既に述べているかどうかが、適用の分かれ目**である。
- **印グリフ**（本項は TASK-77 で新設。decision-22）とは、押せる控えの内側に無く、**対象に付いてその状態を述べる**アイコンを指す（不整合印 ⚠️）。操作に属さないアイコンとの別は、指示対象が「置かれた帯・区画」ではなく「隣にある 1 つの対象」であることと、**族の色を持つ**ことである。置き場・寸法・`viewBox`・線幅は上の各項と同じで、加わるのは次の 3 つ。
  - **色は族の色**。図形自身は `currentColor` のままで、族の色は図形を包む要素が `color` として与える（`--mark-*` を参照する。decision-12 の色値一式は増えない）。満たすべき比は decision-22 の印グリフの収録条件（族の色 対 それが載る面で 3:1 以上）で、**印チップ配色規則の 4.5:1 ではない** — あれは 12% 混色背景との比であり、印グリフにその背景は無い。
  - **図形は `aria-hidden` のまま、包む要素が名前を持つ**。`role="img"` と `aria-label` をその要素へ置き、族名と理由を語で入れる。図形を読ませないのは上の各項と同じ理由（図形は語を持たない）で、包む側に名前を置くのは、押せないので `aria-label` を受け取れる控えがそこに無いためである。
  - **語を可視にしない**。印グリフを置く場所は、その語を出さないと決めた場所である（decision-22 のカード）。理由の全文は `title` と `aria-label` が持ち、**それを読むための場所が別にある**ことを設計側が保証する（タスクではタスク詳細の不整合区画、文書では閲覧ヘッダの理由行、マイルストーンでは操作ペインの理由行。doc-10 §5・§6。**場所そのものではなく「選択が開く場所」が規則である** — TASK-116 で文書の選択が開く先が更新フォームから閲覧へ移ったとき、理由行もそちらへ移った）。ホバーだけが理由への唯一の経路になってはならないのは §5 と同じである。**印グリフを足す場所は、この保証ができる場所に限る**（decision-24 が文書・マイルストーンへ広げたときに、置き場を先に決めたのはこの条件のためである）。
- 無効化提示（5 章）はアイコンのみのボタンでも同じで、理由をホバーだけに置かない。
- **操作に属さないアイコン** とは、押せる控えの内側に無く、置かれた帯・区画が何を扱う場所かを図形だけで示すアイコンを指す（フィルタ帯の先頭の funnel。doc-7 §5.2）。置き場・色・`aria-hidden` は上の各項と同じで、寸法もアイコンを置く箱の `font-size` に従う（フィルタ帯なら帯の .72rem。既定の 1rem はボタンに与えたものなので、ここには効かない）。押せる控えの中に無いことから、次の 3 つが加わる。
  - **図形が示すことは、同じ帯・区画の中の語も述べていなければならない**。アイコンは常に装飾なので、読み上げには図形が何も残さない。図形だけが述べている状態にすると、その帯が何をする場所かは、目で見た利用者にしか届かない。フィルタ帯では「＋ 絞り込み」「既定に戻す」とテキスト欄の `aria-label` がそれを述べており、funnel はそれを図形で繰り返している。
  - **隣の控えの `<label>` の中に入れない**。図形の指示対象は帯全体で、1 つの入力欄より広い。ラベルに入れると、より狭い対象の名前として読まれ、図形と指示対象が食い違う。
  - 押せないので `aria-label`・`title`・フォーカスのいずれも与えない。与えると、押しても何も起きない要素が操作として読み上げられる。

## 3. チップの 4 系統

同じ「小さな四角い札」に見えるものが 4 系統あり、混ぜると別の意味が同じ見た目になる。形・塗り・太さで分ける。**印だけは札ではない形も持つ**（印グリフ。decision-22）ので、1 つ目は 2 つに分けて書く。

- **印チップ**（照合不能・継続検出停止・読取不能・通知、および不整合のうち欠けた値の位置に置くもの）: 文字＝族の色、背景＝族の色 12% 混色、枠＝族の色 45% 混色、角丸 3px、`cursor: help` と説明（decision-12 の印チップ配色規則）。族の判別は色相の距離とチップ文言の二重化で行う。
- **印グリフ**（不整合印 ⚠️。decision-22）: 語を持たず、族の色を図形自身の色として持ち、背景も枠も持たない。**この 4 系統の 1 つ目の別形であって 5 系統目ではない** — 系統を分ける軸は「対象に付いてその状態を述べる札かどうか」で、印グリフはその軸では印と同じものである。分かれるのは描き方だけなので、収録条件も別に置かれる（decision-22 の印グリフの収録条件）。
- **Type**（`kind:*` 由来の分類、decision-5）: `--fg` 13% 混色の塗り ＋ 太字 ＋ 角丸 3px。未知 Type は実線輪郭のみ、Type 未設定は破線輪郭で色を与えない（decision-6 の中立表示）。
- **通常ラベル**（自由タグ）: 輪郭のみのピル（角丸 999px）＋ 細字 ＋ `--muted`。Type と同一の一覧に混ぜない（doc-7 §3・doc-8 §4）。
- **priority**: 文字＝優先度色（§2.1）、背景＝優先度色 12% 混色、枠＝優先度色 45% 混色、角丸 3px（§2.2）。**印チップ配色規則と同じ描き方だが、引く色は族ではなく優先度色である**（decision-23）。**族の色を借りていない**ので decision-12 が禁じた族の汚染は起きない — あの項が挙げた理由は「high の赤と medium の黄土が読取不能・不整合の族の色と同色である」ことで、優先度色は独立した 3 値であり、族の色そのものでないことは `src/lib/theme.test.ts` が押さえる。**無彩 3 段（旧: high＝`--fg` 塗り、medium＝`--line-strong` の輪郭、low＝`--line` の輪郭）はやめた** — 同じ priority を優先度の縁（§2.3）が色で・チップが濃淡で述べる状態は、利用者に 2 つの符号を覚えさせる。priority 未設定 と priority 未知（3 段のどれにも一致しない値）は色を持たず、輪郭のみ・`--muted` の中立の姿のままで、frontmatter の語をそのまま出す。

保存区分印と、未分類区画に出す原文 status は、族でも Type でもない中立の情報である。輪郭のみ・`--muted` で示し、族の色を与えない。

**畳んだ列のレーンセルに並ぶ四角（doc-7 §2.2）もこの 4 系統に入らない。** 小さな四角に見えるが、対象に付いてその状態を述べる札ではなく、そのセルのカード 1 枚を 1 つずつ置き換えた図形である。**族の色は与えない** — 借りると不整合・読取不能の札と同じ見た目になる（decision-6）。文字を持たず、読み上げにも出さない。**優先度色は与える**（decision-23。**本節は長く「色を与えない」と書いていたが、その理由は族の色についてのものだった**）。畳んだ列でも priority の分布が読めるようにするためで、3 段のどれでもないタスクの四角は中立の `--line-strong` のまま残る。非文字要素なので満たすべき比は面に対する 3:1（優先度色の収録条件の 3 番目）。

**色だけで述べない**（WCAG 1.4.1）。四角は 段 ごとにまとめ、high → medium → low → 段なし の順に並べ、**段ごとに高さを変える**（段なしは幅も狭くする — そこだけは low と色相でしか違わなくなるため）。分布は色である前に形である。**読み上げには、四角ではなくセルの件数が内訳を語で持つ** — `aria-hidden` の図形を N 個読ませるのは雑音であり、色が足した情報を総数だけでは代われないためである（doc-7 §2.2）。

**絞り込みトークン（doc-7 §5.2）はこの 4 系統に入らない。** 見た目は札に近いが、内側に自分を解除する `×` を持つ操作要素であり、対象に付いてその状態を述べるチップではない。角丸は §2.2 の**ボタンの 4px** を取る（チップの 3px ではない）。1 系統として数えないのは、4 系統が「対象に付く札を混ぜない」ための区別であり、押せるものをそこへ足すと区別の軸が 2 つになるためである。

## 4. 上部帯

上部帯は 6 種で、**出現順ではなく重要度の固定順**に積む。同時に立ちうる最大は 6 本で、この 6 種以外に上部帯を作らない。各帯は 1 行に収め、左端 4px にその帯の族の色を置く。

| 順 | 帯 | 何を伝えるか | 左端 4px | 閉じられるか |
|---|---|---|---|---|
| ① | 確認（未保存入力の破棄前確認など） | 利用者の回答待ち | `--info` | 閉じられない（回答で消える） |
| ② | CLI 縮退（doc-5 §5） | 作成・更新をどこからも発行できない | `--mark-inconsistent`（借用。下記） | 閉じられない（CLI を検出できると消える） |
| ③ | 台帳読取専用（doc-3 §2.2） | 台帳の更新・登録解除・並べ替えができない | `--mark-unreadable` | 閉じられない |
| ④ | 継続検出停止（doc-9 §3） | 表示が実ファイルより古いかもしれない | `--mark-undetectable` | 閉じられない（再読込で消える） |
| ⑤ | 通知 | 済んだ操作の結果 | `--info` | × で閉じる |
| ⑥ | 行非表示（doc-7 §5.1） | 利用者が自分で外した行と、戻す入口 | 色を与えない（`--line-strong`） | 閉じられない（戻すと消える） |

順は「回答待ち → 発行できない → 表示が古いかもしれない → 済んだことの報告 → 自分で隠したもの」で並べる。②③ が④より上なのは、操作が通らないことは表示の鮮度より先に知る必要があるためで、②が③より上なのは、CLI 縮退が止める操作の範囲（タスク・文書・マイルストーンの全更新）のほうが台帳読取専用（台帳のみ）より広いためである。②③ を 1 本にまとめないのは、原因が別で片方だけ立つことがあり、族の色もそれぞれ異なるからである。

**② は不整合の族の色を借りる**（decision-22）。CLI 縮退はアプリ全体の発行可否であって管理ファイル 1 件の不整合ではなく、改称もしていないが、独自の族は立てない — 族は色を選ぶ単位であって事象の分類ではなく、この 2 つが同じ 1 つの対象に同時に付くことはないからである。

順を出現順にしない理由は、帯が積まれるほど上の行が下へ押し出され、回答待ちの ① が通知 ⑤ の下に埋もれうるためである。①〜④ を閉じられなくするのは、無視できる形にすると「発行できない状態や古い表示のまま操作を続ける」経路ができるからである。⑥ に色を与えないのは、利用者が自分で隠した状態であって異常ではないためである（decision-6 の中立表示）。

②③④ は個々の操作の無効化理由（5 章）と内容が重複するが、それでよい。ホバーしないと理由に到達できない状態を作らないためである。

**1 行に収まらない内容は折り返さず、要約へ縮約して全体を別の場所から読ませる**。折り返しを許すと、狭いウィンドウ・長いプロジェクト名・文字サイズ拡大で上部の占有が伸び、「フィルタ帯 1 行 ＋ 上部帯 6 本」で頭打ちという性質が崩れる。縮約の形は帯ごとに定める（例: 行非表示の帯は「非表示のレーン n 件」に縮約し、個々のレーンはメニューの一覧から戻す）。ただし帯が持つ操作（確認への回答・再読込・戻す）は縮約しても帯に残し、操作へ到達するために別の場所を開かせない。

フィルタ帯 1 行 ＋ 上部帯 6 本が同時に立つのが最悪ケースで、画面上部の占有はここで頭打ちになる。

## 5. 無効化提示

提供できない操作は、消さずに無効化し、理由を必ず添える。

- 見た目は破線枠 ＋ opacity .45 ＋ `cursor: help`。押せる操作（実線枠）と見分けられる形にする。
- **理由をホバーに依存させない**。`disabled` を付けたネイティブの操作はフォーカスを受け取らず、`title` はキーボード・タッチ・スクリーンリーダーのいずれからも安定して到達できない。理由は次のどちらかで到達可能にする。
  - 操作の近くに**常時表示する補助文**として置く。この場合は `disabled` のままでよい。
  - 操作を `aria-disabled` とフォーカス可能なまま（押しても発行しない）にし、`aria-describedby` で理由の要素へ結ぶ。
  `title` はこれらの補助にとどめ、唯一の格納先にしない。
- 画面全体に効く理由（CLI 縮退・台帳読取専用）は上部帯にも出す。個々の操作の理由と重複してよい。
- 理由の無い無効化を置かない。「なぜ押せないか」が分からない操作は、故障と区別できない。
- **提供しない操作**（Atlas がこの版で出さないと決めたもの）は、無効化されたボタンとして並べず、名称・写像先・理由の 3 点を並べる区画に置く（doc-10 §6 の提供しない操作区画）。無効化は「今は条件が揃っていない」を意味し、提供しない操作はそれとは別だからである。
- 破壊的操作の確定は二度押しとし、一度目でラベルを確認文へ差し替える。

## 6. 空・不在の描き方

- **正常な不在**（空セル・コミット該当なし）は、`--faint` の `—` 1 文字だけで示す。族の色を与えず、警告記号・アイコン・枠を付けない。「該当タスクが無い」ことを読み取れる必要があるため、何も描かないのではなく中立の目印を 1 つ置く。decision-6 が禁じているのは、正常な不在にエラー色・警告記号を与えることと、読取不能と同じ見た目にすることであって、中立の目印そのものではない。この形は現行の実装（`LaneCell.svelte`）と一致する。
- **読取不能**は族の色（`--mark-unreadable`）と理由と復帰操作を伴う。正常な不在と決して同じ見た目にしない。
- **Type 未設定**は破線輪郭で色を与えない。未知 Type（実線輪郭）とも区別する。

## 7. モーダルの閉じる

本節の**モーダル**は doc-7 §2.1 の被せ層 — 開いている間フォーカスを内側に留め、Escape で閉じ、閉じたら開く前の操作へフォーカスを戻す層 — を指す。**2026-08-07 に、開く先の列挙から層の形の定義へ改めた**（TASK-117）。本節は 2026-08-07 まで「プロジェクト登録・設定・キーボード操作の一覧が開く先」と数え上げており、その 3 つはどれも固定ヘッダの入口だった。TASK-117 が足した文書・マイルストーンの**作成モーダル**（doc-10 §1）を上げるのは 1 プロジェクトに閉じた操作で、doc-7 §2.1 は自分の末尾でそれを固定ヘッダから締め出している。**列挙のままだと、締め出された側が上げた層に本節の契約が付くかどうかが、どちらの節からも読めない** — doc-7 §2.1 はその操作を数える立場になく、本節は §2.1 の数え上げを引いていたからである。層の形で定義すれば、誰が上げたかは契約に関わらない。本節が述べるのは層の出口であって、入口ではない。doc-8 §2.1 の**中央モーダル詳細配置は含まない** — あちらはタスク詳細の 3 配置の 1 つで、閉じるは見出し 1 行目の操作群が持つ（doc-8 §2.2）。

- **モーダルは右上に `×` を 1 つ持ち、それがモーダル自身の閉じる操作である**（TASK-76 で導入。原文は画面設計案 01 の設定モーダル。doc-12 §2.2）。描くのは層そのものであって中身ではない。中身ごとに置くと、同じ 1 つの操作が中身の数だけ別の位置・別の見た目になる — TASK-76 の前は 3 つの中身が見出しの脇にそれぞれ文言ボタンを置いており、設定モーダルだけは TASK-74 でそれを失っていた。
- **`×` は §2.4 のアイコンのみのボタン**として描く（図形は lucide の `x`）。`aria-label` は「閉じる」だけとし、何を閉じるかを加えない — それは `role="dialog"` の `aria-label` が既に述べており、2 つを繋ぐと「プロジェクトを登録を閉じる」になる。**§2.4 に型は増えない。**
- **`×` はモーダルの中で最初の操作**に置く。層の出口が開いた直後から 1 打鍵の距離にあり、フォーカスを与える操作が対象をスクロール領域へ引き入れるので、長い中身のモーダルが自分の見出しより下へスクロールした状態で開くこともない。
- **`×` が述べるのは「この層を閉じる」だけ**である。**下書きを持つモーダルは、それに加えて下部操作行を持ち**、そこの押下が下書きをどう扱って出るのかを可視の文言で述べる（設定モーダルの「変更せずに閉じる」「保存する」。TASK-74）。**役割の別は、下書きの行方を語で述べるかどうかにある** — 破棄するかどうかではない。`×` も「変更せずに閉じる」も下書きを書かずに出るので、そこでは分かれない。原文の設定モーダルで `×` と下部の「閉じる」が同じ操作なのは（doc-12 §2.2）、原文に保存が無く、述べ分ける下書きが存在しないためである。
- **出口はすべて 1 つの閉じる要求へ集まる**。`×`・Escape（doc-7 §2.1）・下部操作行の「変更せずに閉じる」は、モーダルを配線している側（シェル）の 1 つの経路へ届く。TASK-86 の破棄前確認は、その 1 経路の前に置く。
- **いま閉じられない事情はシェルが持ち、`×` へ渡す**。発行中の書込みがあるなど、閉じる要求を受け付けられない事情があるとき、`×` は 5 章の無効化提示に従う（`aria-disabled` のままフォーカスを受け、`aria-describedby` で理由へ結ぶ）。事情を持つのがシェルなのは、Escape と下部操作行の押下も同じ 1 つの事情に従わなければならないからで、`×` だけが自分で判断すると 3 つの出口が別々の事実を見る。**理由を可視で出すかどうかは中身が決める** — 下部操作行が同じ理由を刷っているなら、`×` の側は目に見えない置き方（アクセシビリティツリーには残す）でよい。同じ 1 つの事情を 1 つの箱の中で 2 度述べないためである。
- **本節はモーダル以外の `×` を覆わない。** 上部帯の通知・絞り込みトークンの解除・status 別名表の行削除は文字グリフの `×` のままで、本節より古い（TASK-80 が実装と画面設計案の差分としてまとめて扱う）。
- **破棄前確認を通すのは、下書きの行方を語で述べていない出口だけである**（TASK-86）。`×` が述べるのは「この層を閉じる」だけで、Escape は語を 1 つも持たない。下書きがあるなら、その行方を述べるものが問いのほかに無いので、この 2 つは問いを通る。下部操作行の「変更せずに閉じる」は既に述べているので通さない — 控えの文言と問いが同じことを述べ、**押した利用者はもう答えている**からである。**これは出口ごとに別の事実を見ることではない**: 3 つとも 1 つの閉じる要求へ集まり、いま閉じられない事情も 1 つのまま従う。分かれるのは本節が既に立てている軸 — その出口が下書きの行方を語で述べているかどうか — の側だけで、**規則は 1 本のままである**。
- **モーダルの出口が上げた破棄前確認は、モーダルの中に出す**（TASK-86）。破棄前確認そのものは doc-8 §6.3 が定め、その置き場は上部帯の ①（doc-7 §5.3）だが、本節のモーダルはその上部帯を覆う（doc-7 §2.1 のフォーカス内留めのため意図的）。覆っている層の出口が上げた問いを ① に置くと、問いの対象であるモーダルが消えるまで読めず答えられない。**これは 7 種目の上部帯ではない** — doc-11 §4 の 6 種は画面が積む告知で、こちらは同じ ① の告知を、それを上げた層の中に描いたものである。**問いの文は doc-8 §6.3 のものをそのまま使う**。モーダルの経路は §6.3 が数える 5 経路の外にあり、失われる未保存入力も編集セッションのものではないが、同じ喪失を 2 通りに述べないためである。**進む側の答えだけは「破棄して閉じる」とする** — §6.3 が「破棄して続ける」と広く言うのは、5 経路の行き先が同じでない（別タスクを開く・前後移動・詳細配置の切替は何も閉じない）からで、モーダルの 2 経路はどちらもこの層を閉じることに限られる。**指示対象より広い語を選ばない。**戻る側は「編集に戻る」のままである。**問いを描く場所は、いま最前面にある層で決まる** — したがって、別の経路が上げた確認が立っているところへモーダルを開いたときは、その確認は失効する。モーダルが自分のものとして描くと、進む側の答えが背後で別の経路を実行し、変わってしまった画面の上にモーダルだけが残る。同じ理由で、**確認に答えないままモーダルが閉じたときも、確認は層と一緒に消える**（残すと、もうどこにも無い入力について問い、既に起きた継続を差し出す帯が背後に立つ）。**失効で破棄されるものは無い** — 要求が取り下げられるだけである。
- **答えを待っている状態と、いま閉じられない事情は別である**（TASK-86）。前者は閉じる要求が出ていて答えを待つ状態で、`×` は押せるままにする（もう一度押しても同じ問いをもう一度出すだけである）。後者は要求そのものを出さない状態で、`×` は §5 の無効化提示に従う。混ぜると、答えの控えが同じ箱の中にあるのに「答えていないから押せない」を理由に無効化することになる。**順序は後者が先で、発行中は破棄前確認より前に断る** — 発行した書込みが解決していない間に「破棄して閉じる」を差し出すと、いま台帳やファイルへ入ろうとしている入力について破棄を選ばせることになる。
- **Escape は、問いが立っている間はその問いに答える**（「編集に戻る」。TASK-86）。押下は最も内側の開いている層に費やされる（doc-7 §2.1 の Escape。絞り込みの値一覧も同じ）ので、問いが立っている間の最も内側はモーダルではなく問いである。閉じる要求を出し直す形にすると、Escape は画面上何も変えない打鍵になる。
- **下部操作行を持つのは、下書きを書いて出る出口を併せ持つモーダルだけである**（TASK-86 で条件を明示）。未保存入力を持つだけでは要らない — プロジェクト登録モーダルは 3 欄の入力を保持するが、「登録」は台帳へ書いても層を出ないので、出方が 1 通りしかなく述べ分ける相手がいない。そこで `×` を押したときに入力がどうなるかは、下部操作行ではなく破棄前確認が述べる。原文が「登録」と対で持つ「取消」（doc-12 §2.3）を足すかどうかは TASK-80 のままである。**作成モーダル（doc-10 §1）が 2 例目**で、理由も同じ — 「文書を作成」「マイルストーンを作成」は管理ファイルへ書いても層を出ず、入力欄を空にして次の 1 件を受ける。**この条件は「書くかどうか」ではなく「書いて出るかどうか」である** — 2 例とも書いており、それでも下部操作行を持たない。

## 8. 画面に置く文

本節は、画面に出る散文について落とすものと残すものを分ける（TASK-79 で新設）。**対象は利用者が読む文だけ**であり、コードコメントは含まない（そちらは TASK-107）。**分ける軸は量ではなく、その文が何について書かれているかである** — 同じ長さの 2 文でも、押した結果を述べるものは残り、既に画面に出ている値を言い直したものは落ちる。「冗長かどうか」で判断すると、長い結果の予告が落ちて短い言い換えが残る。

- **状態文** … 画面のその場所に何が出ているか・何が無いかを述べる文を指す（「文書はありません。」「文書を選ぶと内容を表示します。」「説明はありません。」）。**本節の対象ではない** — 落とす 4 種にも残す 2 種にも入らず、置き方は §6 と各画面の設計文書が定める（doc-10 §5・§6）。状態文とその他を分けるのは、**その文が画面に出ていないことを述べているかどうか**である。仕組み・理由・経緯へ踏み出した時点で、以下のどれかに当たる。

**落とす 4 種。**

- **状態の言い換え** … 画面に既に出ている値・印・欄の中身や、**操作の名がすでに述べていること**を、散文で言い直しただけの文。**判定は「その欄が現在値を出しているか」で行う** — 出しているなら、その状態自身が語っているので告知は要らない。doc-10 §5 が文書の tags 欄について先に決めた形で、本節はそれを画面全体へ広げる。現在値を持たない欄（常に空で、空欄の意味が読めないもの）はこれに当たらない。
- **設計文書参照** … 文の中に置いた `doc-N §X`・`decision-N`。**1 つも残さない。**利用者はその文書を読めない。参照が括弧の中で事実と同居しているときは、**事実だけを残して参照を落とす** — 括弧ごと消すと、押せない理由や結果の予告まで一緒に消える。
- **設計文の写し** … 設計文書の本文の一文を、指示対象を利用者の側へ置き換えずに画面へ刷ったもの。**ラベルは操作の名で書く。**画面設計案の同じ位置に語があるならそれを取る（doc-12）。この型は書いた側には自然に見える — その節を書いた直後は、節の一文が最も正確な説明に読めるためである。
- **発行手段の記述** … Atlas が発行する操作について、そのサブコマンド名・フラグ名・引数を書いたもの。利用者が確かめるのは結果であって、どのコマンドが走ったかではない（doc-10 §5 が `--tags ""` について先に決めた形）。**doc-10 §6 の写像先と doc-10 §7 のフラグ掲示は当たらない** — あの 2 つが名指すのは **Atlas が提供しないもの**（§6 は出さない操作、§7 は欄を置いていない項目）の同一性であって、Atlas が行うことの手順ではない。§7 は「CLI に無いから」という偽の説明を禁じるためにフラグを掲示させており、落とすとその禁止が成り立たなくなる。**当たるかどうかは「Atlas が発行するか」ではなく、その名前が「Atlas の行うことの手順」を述べているか「Atlas が提供しないものの同一性」を指しているかで決まる** — §7 のフラグは Atlas が発行する `task create` のオプションでありながら、指しているのは後者である。**版数や「CLI に手段が無い」はサブコマンド名でもフラグ名でもないので、本種に当たらない**（落とすと不可の理由がそのまま消える）。

**残す 2 種。**

- **結果の予告** … 押下の前にしか読めない、その押下が **元に戻せない形で** 何を変えるかを述べる文（登録解除が台帳エントリを 1 件消してスイムレーンから行を外すこと、保存が既存を含む全置換になること）。残す。**軸は取り返しがつくかどうかである** — 可逆な操作が何をするかの一行ヒントはこれに当たらない。
- **不可の理由** … 押せない・提供しない理由。**本節はこれを減らせない** — §5 と doc-10 §6 が既に掲示を要求している。本節が及ぶのは、その理由文の中の設計文書参照と発行手段の記述だけである。**1 つの文が落とす種と不可の理由の両方に当たるときは、書き直しが優先し、撤去はしない** — 落とす 4 種は書き方についての規則であって、理由を掲示しなくてよくする規則ではない。**画面が操作も欄も見せていないものについて、なぜ無いかを述べない** — 画面がその不在を提示していない以上、読み手はその問いを持っていない（本タスクの Description が挙げた「絞り込みは既定のままです。戻す条件も解除する条件もありません。」がこの型）。**doc-10 §6 の提供しない操作区画と §7 の欄を出さない項目は当たらない** — あれは不在そのものを一覧として提示する区画で、そこでは読み手が現に問いを持っている。**画面設計案が置いている項目を Atlas が持たないことも、それだけでは理由を掲示する根拠にならない**（2026-08-08 の目視で、設定画面の起動時読み取りの注記がこの理由で撤去された）。

**置き方。**

- **無効化の理由が、その操作と同じ区画の表示そのものであるときは、文を別に置かない。**§5 が求めるのは理由に到達できることであって、同じことを 2 度述べることではない — 欄が「（必須）」と述べていて空ならその空欄が理由であり、フィルタ帯の 既定に戻す なら帯が現に出している条件が理由である。実装では可視の文を落とす 保留理由 を列挙して持つ（`manage.ts` の `omitsSentence`）— 規則ではなく列挙にするのは、どの licence に拠るかが理由ごと・区画ごとの事実であり、**項目を足すときにその区画を開いて確かめさせる**ためである。**可視の文を省いてよいのは次の 2 つだけで、どちらにも当たらない理由は描く。**①**区画がその理由を可視で述べている**（「（必須）」の印が付いた欄が空、など）— そのとき控えは §5 の 1 つ目の形（常時表示する補助文）を既に満たしているので `disabled` のままでよい。②**理由が「まだ入力していない・まだ変えていない」だけを述べており、次に何をすればよいかがフォーム自身から明らかである** — このときは §5 の 2 つ目の形（`aria-disabled` ＋ フォーカス可能 ＋ `aria-describedby` で、常時 DOM にある要素へ結ぶ）にして、理由をアクセシビリティツリーへ残す。**原因が画面の外にある理由は、どちらにも当たらないので必ず可視にする**（CLI 縮退・台帳読取専用・発行中・競合）— 利用者が取るべき行動がフォームから読めないためである。**①と②では控えの属性が違う**ので、隠す前にどちらの licence に拠るかを決める（TASK-79 の 4R [P1]: ②に当たる理由を①のつもりで `disabled` のまま落とし、理由が `title` だけになった）。
- **残す 2 種は、操作の近くに常時表示する**（§5 の 1 つ目の形）。`title` へ移して可視から消さない。**この 2 種以外の一行ヒント**（可逆な操作がどこへ届くかを `title` で述べるもの。メニュー行など）**は本節の対象ではない** — 落とす 4 種に当たらない限り、置き方は各画面が決める。残る 2 種は、**不可の理由**が §5 のホバー依存の禁止に当たり、**結果の予告**は押す前に読めないと役に立たないので、どちらもホバーの向こうへ置けない。`title` は §5 のとおり補助にとどめる。**画面のノイズは移設ではなく削除で減らす** — 移設先の候補は、落とす 4 種を落とした後には残らない（TASK-79 で全画面を数えて確かめた）。

**足すときの検査。**

- **画面へ新しい文を足すときは、落とす 4 種のどれかでないかを先に見る。**特に設計文書の節を書いた直後の実装では、設計文の写しと発行手段の記述が入りやすい。
- **priority チップの語は状態文であって状態の言い換えではない**（decision-23）。色は 3 段のどれかを述べるが、語はその段の名前そのものであり、言い直している相手がいない。**同じ判定を他の印・チップにも当てる** — 語が値そのものなら状態文である。
