# プロジェクト別スイムレーン画面 設計

TASK-11 の設計。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は doc-3（台帳・横断タスクID）・doc-4（読み取り層・ドメインモデル）・decision-4（status はプロジェクト個別許容、正準ステータス列へ列対応規則で対応、未分類 status は未分類区画）・decision-5（kind 接頭辞除去で Type 導出、複数併記・未設定・未知）・decision-13（アプリ設定）。描き方（色・寸法・チップの形・無効化の見た目）は doc-11 が定め、本書は何をどこに出すかを定める。画面設計案（doc-1 追補で定義。01・03・04）を反映する。引用する事実は doc-12 §2・§4・§5 に転記してある。

**実測基準版**: 本書が「実測」と述べる記述は Backlog CLI v1.50.1 で確かめたものである（decision-7 の最低バージョン要件、decision-27）。個々の記述は版を名乗らない — 名乗るのは、2 つ以上の版の違いそのものを述べる版差記録だけである。最低バージョン要件が上がったら、本行の版と本書の実測記述を併せて測り直す。

## 1. 用語

- **プロジェクト別スイムレーン** … `project` を行、status を列に、複数プロジェクトのタスクを同時表示する画面（doc-1）。
- **プロジェクト行** … スイムレーンで 1 台帳エントリに対応する横 1 行。その行のタスクは全て同一プロジェクト。
- **レーンヘッダ行** … プロジェクト行の上端に置き、行の識別（プロジェクト名・slug・件数）と行単位の操作（行折畳み・並べ替え・プロジェクト詳細画面への入口）を収める横 1 行を指す。
- **レーンセル** … プロジェクト行と正準ステータス列の交点で、該当タスク群を収める区画。
- **タスクカード** … レーンセル内で 1 タスクを表し、横断タスクID・Type・通常ラベル・priority 等を載せる表示単位。
- **カード情報量** … タスクカードに載せる項目の多寡を S・M・L の 3 段で選ぶ設定値を指す（アプリ設定、decision-13）。
- **列折畳み** … 1 つの列を全プロジェクト行で同時に縦帯へ縮め、列名と行ごとの件数だけを残す状態を指す。対象は正準ステータス列 4 つと、出ている間の未分類区画である。
- **行折畳み** … 1 プロジェクト行のレーンセル群を隠し、レーンヘッダ行と列別件数だけを残す状態を指す。
- **行非表示** … 1 プロジェクト行を画面から取り除き、件数も読めなくする状態を指す。行折畳みとは別の操作で、両者は「件数が読めるか」で分かれる。切り替える控えは 2.1 のメニューのプロジェクト一覧だけが持つ。
- **列内新規タスク入力** … レーンセルの末尾に開き、title のみを受け取って status をその列から確定する新規タスク作成の入力欄を指す。
- **列の作成時 status 候補** … ある正準ステータス列へ列対応規則で対応づく、そのプロジェクトの `config.yml` が宣言する原文 status の集合を指す（4.1）。
- **絞り込みトークン** … 選択中の絞り込み条件 1 件を、属性名・値・解除操作の組で示す表示要素を指す。
- **上部帯** … フィルタ帯の下に重要度の固定順で積む、横 1 行の告知区画を指す（順序と描き方は doc-11 §4）。
- **active タスク** … タスク保存区分（doc-4 の 3.4）が active（走査元 tasks/）のタスク。スイムレーンの既定表示対象。draft・completed・archive のタスクは既定では出さない。

## 2. 全体構成（タイトルバー・フィルタ帯・列・レーンヘッダ行・セル）

画面は上から、タイトルバー・フィルタ帯・上部帯（立っているものだけ）・グリッドの順に積む。**画面が持つ行はフィルタ帯からで、タイトルバーは窓の帯である**（§2.1）。グリッドはプロジェクト行を縦に並べ、各行はレーンヘッダ行とレーンセル群からなる。

### 2.1 タイトルバーと共通入口

**タイトルバー**とは、窓の題を出す帯を指す。総件数はここに出し、**全プロジェクトに効く入口**はメニュー 1 つに集約して、そのメニューをその画面の最上段の帯の右端に置く（本画面ではフィルタ帯、プロジェクト詳細画面では doc-10 §3 のヘッダ行）。**画面名は出さない。**

タイトルバーの出し方は OS で分ける（decision-31）。macOS は窓装飾を OS に残したまま帯を透明にし、その帯をアプリが描く（**重ね型**）。Windows・Linux は窓の題そのものを書き替える。**どちらの経路でも窓を操作する控えはアプリが持たない** — 最小化・最大化・閉じるは OS の装飾のままである。

- **Linux では総件数が画面に出ない**（2026-08-15 の実測。decision-31 の Linux の改訂）。題の書き込みは拒否されず、書いた値を読み戻せるのに、装飾に出る題が変わらない — **Atlas から届く層ではない。** アプリが帯を描く案は実装して実機で見たうえで退けた（OS の装飾が既にアプリ名を刷っているので 1 行おきに 2 度出る、かつ内容の高さを 32px 払う）。**失うのは全体の 2 つの比だけで、行ごとの内訳はレーンヘッダ行に残る。**

- **重ね型の帯は、つかんで窓を動かせる。** ダブルクリックで拡大する。帯が押せる控えを 1 つも持たないので、帯の全面をその領域にできる。
- **重ね型では、窓そのものの題はアプリ名のままとする。** 総件数はアプリが描く帯だけが持つ。**したがってこの帯の文は読み上げの対象である** — 窓の題の写しではなく総件数の唯一の在り処なので、装飾として隠すと 2 つの比がどこからも読めなくなる。
- **題の書き込みが拒否されたら言う**（⑤ 通知。doc-11 §4）。黙って落とすと、**Windows では総件数がどこにも出ないまま利用者に理由が残らない** — doc-11 §5 が理由の無い無効化を退けるのと同じ理由である。**書けたかどうかまでは確かめない** — 一度は確かめていたが、そのために測っていた「受け取ったか」は、まさに問題の環境で「受け取っている」と答える（上記）。仮に測れても、述べる先は承知のうえで採った状態であり、起動のたびに帯が立つのは決着済みの判断についての雑音になる。
  - **実測（2026-08-15、オーナーの実機）**: macOS は帯に出る。Windows は題が変わる。**Linux（GNOME・Wayland）は題が変わらない** — `plugin:window|set_title` は拒否されず、直後の `plugin:window|title` は書いた値を返すので、GTK は新しい題を保持している。**装飾だけが古いままである。** どの層が描き替えていないかは測っていない。
- **帯の左は信号機帯のぶんだけ空ける。** **全画面のあいだも空けたままとする**（2026-08-15 に判定。TASK-176）。全画面では信号機が隠れるが、画面上端へポインタを寄せると OS がタイトルバーごと降ろすので、空けた幅は使われる場所を空けている。落とす案も採れたが、全画面へ出入りするたびにアプリ名と総件数が横へ動くうえ、窓が全画面かどうかを画面の側が知る必要が出る（CSS からは読めず、そのための権限は decision-31 が足すと定めた 2 つに入っていない）。**この規則に全画面の分岐は無く、分岐が無いことがこの判定の姿である。**

**この節が「画面の最上段の帯」と言うとき、それはタイトルバーではない。** タイトルバーは窓の帯で、画面が変わっても同じ 1 本が立ち続ける。

- **メニュー** … 全プロジェクトに効く入口・キーボード操作一覧を開く項目・**版の告知 の行**・プロジェクト一覧を収める。**画面の最上段の帯に常設する、その帯自身のものでない操作はこれだけである。** 帯に出している操作はメニューにも同じものを置く（帯の幅が狭いときにも到達できるようにするため）という規則は、帯がこのメニュー以外の共通入口を出さないことで満たす。各入口が何に届くかの 1 行説明は、その入口がボタンだった頃から引き継いでメニュー項目が持つ。**メニューのボタンは、その帯の 1 行の高さ（§5.2）に収まる寸法を取る** — 帯は 1 行のままでなければならないので、控えの側が帯に合わせる。**メニューを開くボタンはアイコンのみとし（doc-11 §2.4）、用途は `aria-label` が述べる**。項目の並びは、外部で開く → 入口 → キーボード操作一覧 → リリースページ → プロジェクト一覧とする（**リリースページ は 2026-08-24 に足した。TASK-157、decision-44 §3。外部で開く は 2026-08-25 に足した。TASK-83、decision-45 §2** — 先頭なのはオーナーが示した図のとおりである）。プロジェクト一覧は台帳エントリの数だけ伸びるので、固定の項目をその後ろに置くと登録・登録解除のたびに位置が変わる。**メニューの幅は、そこに並ぶ行の内容から決める**（2026-08-09 に明記。TASK-130）。固定値を与えると、メニューが収めるものが減ったときに幅だけが残る — 現に、TASK-67 が割り当て一覧の表をモーダルへ出した後も表があった頃の 24rem が残り、幅の 6 割が空いていた。**内容から決まる幅には上限を置き、その値は 24rem と窓幅の 90% の小さいほうとする**（2026-08-09 に明記。TASK-130 の PR #85 1R）。上限が要るのは、表示切替行が名乗る語（プロジェクト名、無ければ slug）が長いとパネルが窓を横切ってグリッドを覆いうるためで、**上限に当たった行はラベルを折り返し、パネルはそれ以上伸びない**。**24rem という値は本タスク以前のパネル幅そのものである** — 上限を新しく選ぶ根拠は本書にも doc-11 §2.2 の寸法表にも無く、いちばん広いときの見え方を従来から変えない値がこれだからである。**上限に当たっている間、幅を決めているのは内容ではなくこの値である。** **パネルは右辺で固定されるので、内容が変わったときに動くのは左辺である** — いちばん長い語を持つプロジェクトの登録を解除すると、次に開いたときラベルの左端がずれる。**この揺れの引き金は 2026-08-09 に変わった**（TASK-131）: 一覧が非表示の行だけを並べていた間は行を隠すたびに動いたが、いまは登録済みプロジェクトを常に並べるので、動くのは台帳が変わったときだけである。項目の縦の位置が開くたびに変わらないことは上で定めたが、**この横の揺れは承知のうえで採る**（行の幅はパネルいっぱいのままで、並びも押せる範囲も変わらない）。
- **群と区切り線**（2026-08-09 に新設。TASK-130） … **群**とは、押した結果の種類でメニューの項目を分けた単位を指す。**新設の時点では 2 つで、いまは 4 つである** — 被せ層を上げる項目（プロジェクトを登録・設定・キーボード操作一覧）、グリッドが描く行を変える項目（すべてのプロジェクトを表示・各プロジェクトの表示切替行）、**Atlas の外へ出て画面を何も変えない項目**（リリースページを開く。2026-08-24 に足した。TASK-157、decision-44 §3）、**選択中の管理ファイル を外部のプログラムへ渡す項目**（外部で開く。2026-08-25 に足した。TASK-83、decision-45 §2）である。**4 つ目を 3 つ目と束ねないのは、対象を持つ点が違うからである** — 3 つ目は押せば必ず同じ先へ行き、4 つ目は 選択中の管理ファイル が無いと押せない（doc-11 §5）。**区切り線**とは、群と群の境目に置く水平の線を指す。**区切り線を出すかどうかは群だけで決め、その境目の行が無効化されているかどうかを読まない。** この規則が要ったのは、doc-11 §5 の破線枠がこの境目に立っていたためである（非表示の行が無いとき「すべてのプロジェクトを表示」がそれを持っていた） — 境目の印をその枠に兼ねさせると、非表示の行の有無で群分けが現れたり消えたりして見える。**枠そのものは 2026-08-09 に落としたが（下記）、規則は残す** — 述べているものが別だからで、無効化を述べる印をこの境目に将来また置いたとしても、群を述べるのは区切り線のほうである。1 本の線に 2 つを述べさせない。**区切り線は目に対してだけ引き、支援技術には出さない**（2026-08-09 に明記。TASK-130 の PR #85 1R）。線は語を持たないので読み上げに何も残さないが、**群の別を述べているのは線ではなく各行の語のほうである** — 被せ層を上げる行は開く先の名前を名乗り、行を変える行は「表示」を名乗るか、対象のプロジェクトを名乗る。doc-11 §2.4 が操作に属さないアイコンへ課している判定（図形が示すことは同じ区画の中の語も述べていなければならない）が、ここでも満たされている。**群そのものを支援技術へ出すかどうかは別の問いで、出すと決めるなら本項を改める** — そのときに決めるのは線の役割ではなく、群を名前のある単位として持つかどうかである。
- **外部で開く**（メニュー内。2026-08-25 に新設。TASK-83、decision-45） … **選択中の管理ファイル** を Atlas の外のプログラムへ 1 件渡す操作の群であり、メニューの先頭に置く。**選択中の管理ファイル** とは、外部で開く の対象になりうる、いま 1 件だけ定まっている管理ファイルを指す — 定まる経路は 4 つで、タスク詳細が開いているタスク（doc-8 §2.1 のどの配置でも同じ）・プロジェクト詳細の 選択中の文書（doc-10 §5）・選択中のマイルストーン（doc-10 §6）・選択中の決定事項（doc-10 §10）である。**画面ではなく対象で定まる** — 本画面だけが出ている状態も、プロジェクト詳細で区画を開いただけの状態も、どちらも **対象未選択** である。**行の集合とプラットフォームごとの起動の形は decision-45 §4 の表が正本で、ここに写しを置かない。** 渡す値・注意・write 契約との関係は doc-8 §7 が持つ。
  - **この群をメニューへ置くのは、本節の粒度の規則からの意図的な逸脱である**（decision-45 §2）。本節は 1 プロジェクトに閉じた操作を共通入口から締め出しており、外部で開く は**管理ファイル 1 件に閉じた操作**なのでそれより狭い。**それでも置くのは、対象が 2 画面の 4 区画にまたがるためである** — 区画ごとに置くと、同じ行の集合・注意・抑止 が 4 つの写しを持つ。**doc-10 §2 が記録した逸脱と同型で、向きが逆である**（あちらは全プロジェクトに効く入口を 1 プロジェクトの画面へ置いた）。**逸脱で足すのは群 1 つだけで、他の 1 プロジェクトに閉じた操作は依然としてここに置かない。**
  - **行はサブメニューに並べ、メニューの中では展開しない。** **サブメニュー**とは、メニューの 1 行に係留され、その行を押している間だけ横に開く層を指す。**展開する案を退けたのは本節自身の規則による** — 本節は項目の縦の位置が開くたびに変わらないことを定めており、展開はその下にある プロジェクト一覧 を行の数だけ押し下げる。**加えてパネルの高さに上限が無い**ので、台帳のエントリが多い環境では展開したパネルが窓の高さを超える。
  - **サブメニューは親と合わせて 被せ層 1 枚と数える**（下の 被せ層 の項）。**出口の梯子は 3 段である**: Escape はサブメニューだけを降ろす、外側の押下は両方を降ろす、親の行の再押下はサブメニューだけを降ろす。**別の被せ層を上げる操作は両方を降ろす**（下の「層を上げる経路は、前の層が残っていればそれを降ろす」がそのまま効く）。
  - **対象未選択 のときは行を消さず、理由付きで保留する**（doc-11 §5）。消す案は採らない — 行の有無が状態を述べる形になり、上の リリースページを開く で退けたのと同じ形である。**保留理由が述べるのは「開く相手が無い」であって「開けない」ではない。** **この理由の可視の文は省く**（doc-11 §8 の licence ②。2026-08-25 にオーナーが実機で判断 — **不活性な行だけで足り、あの文はメニューの中でいちばん長かった**）。**省くのは可視の文だけで、理由は読み上げに残る**（`aria-disabled` ＋ 常に DOM にある要素への `aria-describedby`。§5 の 2 つ目の形）。**選んでいるファイルが読み取り結果から消えたときの理由は省かない** — 原因が画面の外にあるので doc-11 §8 が必ず可視にすると定めている。
  - **サブメニューはメニューの一覧の外に置く。** 一覧は登録済みプロジェクトの数だけ伸びるのでスクロールを持ち（本節の上の項）、**スクロール容器は自分の外へ出た子孫を両軸で切る**。**2026-08-25 の実機でこれが起きた** — サブメニューは描かれているのに見えず、押しても何も起きないように見えた。**矩形は正しい値のまま当たり判定だけが失われる**ので（借り物 playwright の実測、WebKit・Chromium とも）、矩形を測っても捕まらない。**位置の基準はパネルであり、行ではない** — 親の行は一覧の先頭に固定されているので（decision-45 §2）、パネルの上端がその行の位置になる。
  - **この群の行を押すとメニューは閉じる。** 群 で決まる規則のとおりで、理由は リリースページを開く と同じである — 上がる層は無く、押下 1 回で用事が済み、行き先は Atlas の外である。**その帰結として、押下の失敗は ⑤ 通知 である**（doc-11 §4 の 3 つ目の型）。**成功は何も述べない** — 前へ出るのは起動されたプログラムそのものである。
  - **frontmatter の注意 を述べる層は、この群の一部ではない。** 押下が上げる層で、抑止できる（doc-11 §15、decision-45 §6）。**抑止されている間は層が立たず、押下がそのまま起動になる。**
- **プロジェクトを登録**（メニュー内） … 台帳へエントリを 1 件足す（doc-3 §4.1）。台帳ファイルだけを書き、プロジェクトのファイルには触れない。登録するとグリッドの末尾にプロジェクト行が 1 本増える。
- **設定**（メニュー内） … アプリ設定（decision-13）を開く。表示テーマ・カード情報量・既定の保存区分・既定の詳細配置・ファイル監視の可否・外部エディタ指定を扱う。

入口ごとのボタンをメニューの隣に併置しないのは、同じ入口を 2 か所で提示すると帯の横幅がその重複に費やされるためである。ショートカットは各入口へ直接届き、本節が下に置く「ショートカットだけが入口の操作を作らない」はメニュー項目が併置として満たす。モーダルを閉じたときのフォーカスの戻り先も、帯に常時あるメニューのボタンとする（押したメニュー項目は開いた時点で消えているため）。

**総件数**はタイトルバーに、タスク数（表示数 / 全件）とプロジェクト数（表示数 / 全件）の 2 つの比として出す。数え方は 2 つの比で異なり、その違いが両方を出す理由である。**出す先は本画面に限る** — 2 つの比はどちらもグリッドを述べるので、グリッドを持たない画面では数える対象が無い（プロジェクト詳細画面では題はアプリ名だけになる）。

- **タスク数**は、グリッドが描いている行だけを数える。行非表示にしたレーンは表示数からも全件からも外れる。この総計はレーンヘッダ行の行ごとの内訳の総和であり、画面に無い行を含めると 2 つが足し合わない。非表示の行はメニューのプロジェクト一覧が受け持つ。
- **プロジェクト数**は、全件を台帳のエントリ数とする。行非表示は表示数だけを動かし、比が「いくつ仕舞ってあるか」を述べる。両方から外すと 2 つの数が常に一致して比が何も述べなくなる。ルート読取不能の行は、画面に出ている登録済みプロジェクトなので表示数に数え、カードは持たないのでタスク数には寄与しない。

画面設計案 01 のレーン側は `{laneCount} レーン` という単一値で、全件との比を出していない。プロジェクト数を比にするのは 01 からの意図的な変更で、ユーザーが 2026-08-01 にこの差異を認識したうえで指示を優先すると確定した。語を「レーン」ではなく「プロジェクト」とするのは、数える対象が画面の行ではなく台帳のエントリ（doc-1）になったためである。

1 プロジェクトに閉じた操作（台帳エントリの編集・登録解除・文書・マイルストーン・詳細な新規タスク作成）は共通入口のメニューに置かず、プロジェクト詳細画面（doc-10）へ集める。粒度の違う操作を同じ場所に混ぜないためである。**この規則の鏡にあたる「全プロジェクトに効く入口を 1 プロジェクトの画面の帯へ置く」については、doc-10 §2 が意図的な逸脱として記録している** — メニューを置かない案では、プロジェクト詳細画面に居る間、下の「ショートカットだけが入口の操作を作らない」を満たす可視の入口が無くなる。

**キーボードショートカットの契約**（画面全体に効くため本節に置く）:

- 修飾キーは macOS で Command、Windows・Linux で Control に対応させる。同じ操作を両方で別のキーに割り当てない。
- 単独キーを含むショートカット（絞り込みの追加・解除など）は、フォーカスが `input`・`textarea`・`contenteditable`・編集部品（doc-8 §6.1）の内側にある間は発火させない。文字入力が画面操作に取られないようにするためである。
- IME の composition 中（`compositionstart`〜`compositionend`）は、いずれのショートカットも発火させない。doc-8 §6.2 が Enter を保存に割り当てない理由と同じで、変換操作を画面操作に取られないようにする。
- 既定動作の打ち消し（`preventDefault`）は、それが要るキーだけに限り、割り当て一覧に明記する。
- モーダルは開いている間フォーカスを内側に留め、Escape で閉じ、閉じたら開く前の操作へフォーカスを戻す。**押して閉じる操作（右上の ×）の形と、下部操作行を持つモーダルでの両者の役割の別は doc-11 §7 が定める。** 本項が定めるのは Escape とフォーカスの扱いだけで、× はここには無い。
- **前項が定めるのは被せ層という層の振る舞いであって、それを上げる操作の一覧ではない**（2026-08-07 に明記。TASK-117）。メニューの 3 入口（プロジェクトを登録・設定・キーボード操作一覧）が開く先は、この契約に従う層が本節に 3 つあるということであって、被せ層がその 3 つに限られるという意味ではない。**本節の 1 つ上の段落がメニューから締め出した「1 プロジェクトに閉じた操作」も被せ層を上げる** — プロジェクト詳細画面の文書・マイルストーンの作成モーダル（doc-10 §1）がそれで、上げるのが本画面の入口でないだけで、フォーカスの内留め・Escape・フォーカスの戻り先は前項がそのまま効く。**どの画面がどの層を持つかは各画面の設計が持ち、本節はその一覧を持たない** — 持つと、この節が置き場所として退けた操作を、この節自身が列挙することになる。被せ層を形で定義し直したのは doc-11 §7 で、本項はその形がここから来ていることを述べている。**「同時に何枚立てられるか」はこの一覧の話ではない** — あれは層 1 枚の振る舞いの契約なので、前項と同じくここが置き場である（次の 4 項がそれで、§5.2 がそれを引く。TASK-120）。**一覧を降りることと、振る舞いの契約を持つことは別である。**
- **被せ層は同時に 1 枚だけ立てる**（2026-08-19 に本節へ書いた。TASK-120）。**入れ子の層は親と合わせて 1 枚と数える**（2026-08-25 に足した。TASK-83、decision-45 §3）— **親の行に係留され、親と同時に降りる層**がそれで、いまはメニューの サブメニュー 1 つである。**入れ子が数を増やさないのは、本項が守っているものが「Escape と外側の押下が何に効くか利用者が一意に読めること」だからである** — 出口の梯子が定まっていれば、押した 1 回が何を降ろすかは常に 1 つに決まる。**梯子を持たない入れ子はこの言い直しの外にある**ので、2 段目を足す回は一意性を測り直す。**数えるのは画面を覆って立つ層で、層の内側に描かれる問いは数えない** — モーダルの出口が上げた破棄前確認（doc-11 §7）は Escape をその場で費やすが、それを上げた層の中に描かれるので枚数を増やさない。**実行前確認はこちら側ではない** — あれは自分で被せ層を 1 枚上げて問い、層はシェルが持つ（doc-11 §12 ①）ので、下の数の中にある。**数える対象は画面を覆う層すべてで、どの入口が上げたかを問わない** — 共通入口が開くモーダルのほかに、本節のメニューと絞り込みの値一覧ポップオーバー（§5.2）も 1 枚に数え、プロジェクト詳細画面が自分で上げる作成モーダル（doc-10 §1）・列間ドロップの候補選択の問い（§4.2）・実行前確認（doc-11 §12 ①）も同じ 1 枚の中にある。**いま挙げた 5 つは数え上げではない** — ここに名の無い層も、画面を覆って立つならば同じ 1 枚に数える。**前項が一覧を降りたことは本項に掛からない** — 一覧を持たないまま「すべて」と言えるのは、数えているのが層の形だからである。
- **層を上げる経路は、前の層が残っていればそれを降ろす。** **列間ドロップだけは降ろす手当てを持たないが、穴ではない** — メニューも値一覧ポップオーバーも外側の押下で閉じるので（本節のメニューの項・§5.2）、カードを掴んだ押下の時点で既に降りている。**§5.2 の末尾が逆向きの同じ註を持つ** — あちらは届かない経路に対して降ろす側の記録で、こちらは降ろす先が残らない経路の記録である。
- **本項が数える層は、上のモーダルの項が定めた層より広い。** あちらが述べているのはフォーカスを内側に留める層（doc-11 §7 が形で定義したモーダル）で、本項が数えるのは画面を覆って立ち、その場で Escape を費やす層すべてである。**メニューと値一覧ポップオーバーはフォーカスを内側に留めないが、この数の中にある。** **モーダルの項の契約（内留め・戻り先と、doc-11 §7 の右上の `×`・破棄前確認）がその 2 つに掛かるという意味ではない** — メニューの閉じる契機は本節のメニューの項が、ポップオーバーのそれは §5.2 が別に定める。**本節が以下で「被せ層」と言うときは広いほうを指す**（下の 使える場所 の「被せ層の内側」も同じで、`closeOverlay` が答える範囲と一致する）。
- **上の 3 項が支えているのは、Escape が閉じる相手が 1 つに定まることである。** 割り当て一覧の `closeOverlay` は操作を「開いている層を閉じる」としか述べておらず、覆う層が 2 枚立てば、どちらを閉じるのかがその 1 行から読めなくなる。**層の内側の問いはこれを揺らさない** — 問いは自分を上げた層の中にあるので、押鍵が費やされる順序が決まっている（doc-11 §7）。**モーダルのフォーカスの内留めも同じ前提に乗っている** — 内側に留める層が 2 枚あれば留め先が 2 つになる。§5.2 が値一覧ポップオーバーの閉じる契機に数えている「別の被せ層を上げる操作」は、この 3 項の側から出ている。
- 割り当て一覧（キー・操作・使える場所・入力欄内で発火するか・打ち消す既定動作）を 1 箇所に持ち、操作の近くにも併記する。**併記は、その操作から到達できる形であればよく、可視の文である必要はない**（2026-08-10 に明記。TASK-135 の目視）。控えの `title` と `aria-keyshortcuts`、そしてキーボード操作一覧のモーダルが担ってよい — **下のアイコンのみのボタンについて既に定めている形を、可視の文言を持つ控えへも広げたもの**である。**控えの中に刷る形も残る**（列内新規タスク入力の 作成 は和音を控えの内側に持つ）。**落としたのは、控えの外に 1 行の文として置いていた 3 か所**（タスク詳細の 保存・文書の更新・新規タスクの作成）で、ユーザーが「キーボード操作一覧にあるので不要」と判断した。**控えが押せないときは、その `title` は理由を述べる**（和音を名乗ると、発行できない操作を広告することになる。doc-5 §5）。**使える場所**とは、その割り当てが答えられる場所を指す（旧称は「発火する画面」。2026-08-09 に改称。TASK-125）。**画面に限らない** — 被せ層の内側・編集部品の内側・列内新規タスク入力の内側も値に取るので、見出しに「画面」を含めると値の過半が見出しと食い違う。取り得る値の一覧は本節が持たない（持つと、値が 1 つ増えるたびに本節の改訂を要求することになる）。
- **本節が「割り当て一覧」と言うときの相手は、上の 5 欄を持つ記録であって、画面に出す表ではない**（2026-08-09 に書き分けた。TASK-125）。上の 単独キーの抑止 と 既定動作の打ち消しの明記 が相手にしているのも、この記録である。**画面でこの一覧を読む先は、メニューの「キーボード操作一覧」が開くモーダル 1 つとし、そこに出す列はキー・操作・使える場所の 3 列とする。** 入力欄内で発火するか と 打ち消す既定動作 の 2 欄は記録が持ち続け、画面には出さない — 利用者が押す前に要るのは、どのキーが何をどこで行うかだけだからである（2026-08-09 にユーザーが確定）。**単独キーが文字入力中に効かない理由を画面から読む手段が無くなることは、承知のうえで採った。** 5 欄と 5 列が 1 対 1 だった間は「割り当て一覧」1 語で両方を指せていたので、本節は 2026-08-09 まで両者を書き分けておらず、**列の列挙も 4 列しか挙げていなかった**（打ち消す既定動作 が落ちており、同じ節の明記要求と食い違っていた）。
- **アイコンのみのボタン（doc-11 §2.4）では、併記は `title` とこのモーダルが担う** — 文言を持たない操作の隣にキーだけを刷ると、アイコンのみという形が成立しないためである。`aria-label` が担うのは操作の名前で、キーは持たない（名前にキーを含めると読み上げが「設定 ⌘,」になる）。キーは `aria-keyshortcuts` でも渡し、印字とデータの両方から到達できるようにする。ショートカットだけが入口の操作を作らない（ボタンかメニュー項目を必ず併置する）。
- **プロジェクトを登録 のキーは `⌘N`（Windows・Linux では `Ctrl+N`）で、これは画面設計案 01 からの意図的な逸脱である**（2026-08-19 に記録。TASK-143）。原文は同じ入口に `⌘⇧N` を併記している（doc-12 §2.4）。**外れているのはキーの組そのものであって、入口の置き場ではない。** 置き場のほうは 2 度動いており、どちらも別の判断で、どちらも記録がある — 個別のボタンからメニューの行へ畳まれたのが TASK-66（2026-08-02。記録は本節）、固定ヘッダそのものが無くなったのが decision-31（2026-08-15。TASK-176。記録は doc-12 §2.4）である。**その行はどちらの後もいまも `⌘N` を刷っている。** 採る理由は 3 つある。（1）上の 割り当て一覧 の記録を持つのは `shortcuts.ts` で、それが正本である（§5.2 と doc-12 §4.1 は本節をそう引いている）— 原文はこの記録の外にあり、値を決める立場にない。（2）doc-12 は転記であって決定ではなく、原文と食い違う場合は引用している側が優先すると自ら定めている（doc-12 §1）。（3）**原文より後の 2026-08-09 に、ユーザーがメニューの中身を書き直して示した図が `⌘N` を刷っている** — 差は原文の時点のもので、その後に示された形は実装と同じである。**この差が 2026-08-19 まで記録を持たなかった理由は、数え落としである** — TASK-80 の 01 の洗い出しは doc-12 §2.4 について「レーン側の単一値」と「右端の入口 3 つ」の 2 件を数えており、キーの割り当てはそこに入っていなかった。

### 2.2 列（正準ステータス列）

- 画面上部に To Do / In Progress / In Review / Done の 4 列を固定配置する（decision-4）。列はプロジェクト横断で共通・固定で、プロジェクト行が変わっても列位置は動かない。これによりプロジェクトをまたいだ同一 status の縦読み（優先順位判断、doc-1）が成立する。
- **列折畳みは全行同時にのみ行える**。ある行だけで列を畳めると、同じ status が行ごとに違う x 座標に来て、縦読みが崩れるためである。畳んだ列は幅の狭い縦帯になり、**列ヘッダは列名だけを残す**。件数は列の合計をヘッダに出さず、行ごとの内訳としてレーンセルが持つ（下記）。合計をヘッダにも出すと、同じ数を 2 か所が刷ることになり（§5.2 の総計と同じ理由）、狭い帯がその 1 行のために縦へ伸びる。
- **列ヘッダは畳んでも 1 行のまま**。列名は折り返さず、帯の幅に収まらない分は省略記号で切る（全文は `title` から読める）。畳んだときにヘッダが縦へ積むと、列ヘッダ行はどの列も最も高い列に揃うので、1 列を畳んだだけでグリッド全体が押し下がる。
- **列折畳みの控えは図形だけで示し、ヘッダの左端に置く**（doc-11 §2.4 の アイコンのみのボタン）。可視の文言を持たず、名前は `aria-label`、押すと何が起きるかは `title` が述べる。図形は、畳める状態の列に ＜、畳んだ列に ＞ を置く。**この 2 つが指すのは押した結果であって、いまの状態ではない** — 横方向には「開いている／畳んである」を指せる向きが無く、幅の狭い縦帯そのものが既に畳まれていることを述べているためである。行折畳みは逆で、状態を指す（§2.3）。1 画面の中で軸ごとに規則が分かれるので、両方をここと §2.3 に書き分けてある。左端に置くのは、列名の長さが変わっても控えの x が動かないようにするためである（畳んだ帯では列名が省略記号で切れる）。
- **畳んだ列のレーンセルは、タスクカード 1 枚を小さな四角 1 つに置き換えて並べ、その下にそのセルの件数を出す**。四角はそのセルにどれだけあるかを一目で示すためのもので、カード 1 枚 1 枚を指す操作ではない。**族の色は持たない**（doc-11 §3。持つと不整合・読取不能の札と同じ見た目になる）が、**そのカードの priority の優先度色は持つ**（decision-23）— 畳んだ列でも、何件あるかに加えてどういう仕事が溜まっているかが読める。3 段のどれでもないタスクの四角は中立の色のまま残る。**四角は 段 ごとにまとめて high → medium → low → 段なし の順に並べ、段ごとに高さを変える**ので、色を見分けられなくても分布が読める（doc-11 §3）。読み上げには四角を出さず、**件数がその内訳を語で持つ**（例:「In Progress 5 件（high 1・medium 1・low 1・priority 未設定・未知 2）」）。件数を残す理由は変わらない — 畳んだ列に何件あるかを読めなくしないためで、内訳を足したのは、色付きの四角が加えた情報を総数だけでは代われないからである。
- **すべての列を同時に畳むことはできない**。展開中の列が 1 つだけになったら、その列の控えを無効化する（理由は doc-11 §5 の形で、ホバーだけに置かない）。4 列すべてが帯になると、どの列のカードも読めない画面になり、戻す手段が帯の控えだけになる。無効化するのは畳む向きだけで、畳んだ列を戻す控えは常に押せる。
畳んだ列の見え方（`＞` は図形の代用、`■` はカード 1 枚ぶんの四角）:

```
 ＞ To D…  |
 ----------|
 ■■■■■ |
 ■              |
      6         |
```

- **未分類区画**: 列対応規則でどの正準ステータス列にも対応づかなかったタスク（未分類 status、decision-4）は、正準 4 列へ紛れ込ませず、末尾の未分類列へ集める。区画には元の status 文字列をそのまま示す。未分類列は常設ではなく、いずれかの行に未分類 status のタスクがある間だけ現れる。
- **未分類列も列折畳みの対象にする**。正準ステータス列ではないことは、畳めるかどうかとは関係がない — カードを持つ列であり、畳んだときの見え方も正準列と同じである（ヘッダは列名だけ、セルは四角と件数）。**ただし「展開中の最後の 1 列」には数えない**。未分類列は、どの行にも未分類 status のタスクが無くなった時点で自分から消えるので、それを最後の 1 列として扱うと、4 列すべてが帯のまま戻せない画面になりうる。未分類列そのものは、畳んでも正準列を 1 つも奪わないので常に畳める。
- **語と識別子**: 「未分類 status」「未分類区画」「未分類列」は 2026-08-04 に「未対応」系から改称した（TASK-70）。status の値そのものは欠けておらず、正準ステータス列へ対応づけられなかったのは Atlas の側だからである。**コード識別子の `unmapped` は据え置く** — この語は「列へ対応づかない」ことをそのまま述べていて、改称の理由（「未対応」が値の欠落を含意する）が当たらないためである。改称が及ぶのは本書・decision-4・decision-6・doc-3・doc-10・doc-11・doc-12 と画面に出る文字列であり、**完了済みタスクの記録は当時の語のまま残す**（実施時点の記録であって契約ではない）。Git 履歴区画の画面文言「未対応ホスト」は、remote のホスト種別を判別できない状態（doc-8 §5 の「remote 非対応」）を指しており指示対象が別なので、この改称は及ばない。

### 2.3 レーンヘッダ行とセル

- **行（プロジェクト行）**: 台帳エントリ（doc-3）ごとに 1 行を置く。行の並び順は台帳の並び（doc-3 の表示既定順）を既定とし、画面で変更できる（5 章）。
- **レーンヘッダ行**: 各プロジェクト行の上端に横 1 行として置く。左端に固定幅のプロジェクト名カラムを設けない。固定カラム方式は、名前の長さに合わせて幅を取ると 4 列に配れる横幅がその分減り、狭めるとプロジェクト名が読めなくなる、という両立しない要求を抱えるためである。レーンヘッダ行が横幅を丸ごと使えば、名前・slug・件数・行単位の操作を折り返しなしに収められる。
- レーンヘッダ行が収めるもの: 行折畳みの開閉、プロジェクト名（プロジェクト詳細画面への入口）、slug、表示件数／全件数、継続検出停止の印（doc-9 §3）とその行の再読込、並べ替え、プロジェクト詳細画面への入口。**行非表示の控えはここに置かない**（2026-08-09。TASK-131） — 表示・非表示は §2.1 のメニューのプロジェクト一覧 1 か所で扱う。画面設計案 06 は行ヘッダに「畳む」と「隠す」を別の語・別の操作として置いており（doc-12 §7.2）、これはそこからの**意図的な逸脱**である。逸脱の理由は同じ 1 つの状態を 3 か所が扱っていたこと（2026-08-09 にユーザーが要求）で、06 が「畳む」と「隠す」を分けた理由（件数が読めるか）そのものは §5.1 が持ち続けている。**行ヘッダに残るのは「畳む」だけである。**
- **行折畳み**時は、レーンセル群の代わりに列別の件数をレーンヘッダ行へ並べる。畳んでも件数は読めるという性質を、この表示で保つ。
- **行折畳みの控えも図形だけで示す**（§2.2 の列折畳みと同じ アイコンのみのボタン）。ただし**図形が指すのはいまの状態**で、レーンセルが開いている行に ∨、畳んだ行に ∧ を置く。可視の文言が無くなると、その行がどちらの状態にあるかを述べるものは図形だけになるためである（2026-08-03 にユーザーが 2 案から選択）。
- **画面設計案から意図的に外れた点**（TASK-69）: 置き換えた文字グリフは 2 つある。**画面設計案 06 の `▾` / `▸` ＋ 可視の文言「畳む」**（doc-12 §7.2 が転記している）と、**本節の図が刷っていた `▼` / `▲`**（Atlas 自身の姿を描いた図であって転記ではない）。Atlas は文言を落とし、記号を lucide の図形へ替えた。理由は 2 つで、(1) 文字グリフは字面と大きさがフォントによって変わり、画面共通の寸法規則（doc-11 §2.4 の viewBox 24・線幅 2・1em）に乗らない、(2) レーンヘッダ行は折り返さない 1 行で、文言 2 文字ぶんの幅（実測 21px）は真っ先にプロジェクト名が失う幅である。**向きは 06 と同じ流儀を保った** — `▾` は開いている行に置かれており、状態を指している。**画面設計案 01 が折畳みの控えに何を刷っていたかは doc-12 に転記が無く**（§2.5 は「§7 の 06 に部品として整理されている」と送るだけ）、このリポジトリからは確かめられない。AC #3 が言う「画面設計案 01 から意図的に外れた点」は、したがって確かめられる範囲（06 の転記と本節の図）に対する逸脱として記録している。
- **2 層スティッキー**: グリッドを縦にスクロールする間、列ヘッダ行は上端に、いま読んでいる行のレーンヘッダ行はそのすぐ下に残す。列ヘッダ行だけを残すと、どの列かは読めてもどのプロジェクトの行を読んでいるかが分からなくなり、プロジェクト詳細画面からの「このプロジェクトのレーンへ」（doc-10 §2）の着地先も視界外に出るためである。レーンヘッダ行が貼り付く位置は列ヘッダ行の下端で、固定長ではない — 列ヘッダ行は §2.2 のとおりどの状態でも 1 行だが、その 1 行の高さは文字寸法（OS・ブラウザの拡大）で変わり、ヘッダの持ち物を増やせばまた変わるので、その時点の高さを測って接する。
- 着地は行の先頭を列ヘッダ行の下端へ置く。レーンヘッダ行は貼り付いている間、自分の行がどこにあるかを示さない（上端に留まったまま行だけが上へ流れる）ので、行の先頭は別に測る。行の先頭が列ヘッダ行の裏にあるか、下端で切れているときだけ動かす。
- **着地には一時的な強調が伴う**（TASK-62）。一時的な強調とは、着地した行のレーンヘッダ行に付き、ひとりでに消える背景の色づきを指す。対象行が既に視界内にあると着地は何も動かさないので、これが無いと復帰は「何も起きなかった」ように見える — 強調はスクロールの有無によらず、着地のたびに付く。付く先はレーンヘッダ行 1 本である（行の可視の身元はこの行で、行折畳み中はセルが無くこの行だけが行を代表する）。消えた後に何も残らず取り消す操作も持たない点で、doc-11 §2.3 の描き分け（持続する状態）とは別のものであり、選択の `outline` を借りない（借りると持続する選択と見分けが付かない）。
- **セル（レーンセル）**: プロジェクト行 × 正準ステータス列の交点に、当該プロジェクトで当該列へ対応づいたタスクのタスクカードを縦に並べる。タスクが 0 件のセルの示し方は 6 章に定める（該当タスク無しと読取不能の区別も 6 章）。セル末尾には列内新規タスク入力の入口を置く（4 章）。

```
 [タイトルバー] Backlog Atlas — 表示 60 / 183 件 ・ 6 / 8 プロジェクト
 [フィルタ帯] (漏斗) [横断タスクID・title] [保存区分: active+draft ×] [ラベル: parser ×] ＋ 絞り込み                    ☰
         ＜ To Do      ＜ In Progress   ＜ In Review   ＜ Done  | ＜ 未分類
 ∨ Backlog Atlas  atlas  12 / 40 件                         ↑ ↓  ›
                [card][card]   [card]         —         [card]    | [card: status=保留]
                [＋]           [＋]           [＋]      [＋]      |
 ∧ 社内管理 API   kanri  9 / 31 件   To Do 3 ・ In Progress 2 …   ↑ ↓  ›
```

図の `(漏斗)`・`∨`・`∧`・`＜`・`↑`・`↓`・`›`・`[＋]`・`☰` は lucide の図形の代用である（ASCII の図に SVG は置けない）。文字グリフをそこへ替えた理由と描き方は doc-11 §2.4 が持つ。**`↑`・`↓`・`›` は 2026-08-11 まで文字グリフのままだった** — 置き換えの対象に入っておらず（doc-11 §2.4 が挙げていた 5 タスクのどれもこの 3 つを扱わない）、2026-08-09 に TASK-80 が 追随する 側と判定して TASK-139 として起票し、そこで `arrow-up`・`arrow-down`・`arrow-right` へ替えた。§2.4 の規則は記号の出自ではなく画面共通の寸法（viewBox 24・線幅 2・1em）に基づくので、これまで扱ったタスクが無いことは対象外である理由にならない。**行末の入口が列折畳みと同じ `chevron-right` を取らない理由**（同じ画面で 1 つの図形が「列を開く」と「別画面を開く」を指すことになる）**と、行の並べ替えが前後移動と同じ 2 つを取る理由は、doc-11 §2.4 の 同じ図形を別の操作へ与えない が持つ。** フィルタ帯の中身は §5.2 が定める。

## 3. タスクカードとカード情報量

タスクカードは、一覧上で識別・優先順位判断に要る最小限を載せる。ドメインモデル（doc-4）のタスクから写す。載せる項目はカード情報量（アプリ設定）で 3 段に切り替える。

| 項目 | 由来 | S | M（既定） | L |
|---|---|---|---|---|
| 横断タスクID | slug（台帳）＋ TASK-ID（frontmatter id）。`<slug>:<TASK-ID>`（doc-3 の 5.3） | ○ | ○ | ○ |
| priority | frontmatter priority。カード左 3px の優先度の縁と priority チップの両方が優先度色で述べる（decision-23・doc-11 §2.3・§3） | ○ | ○ | ○ |
| 状態の印 | 不整合印（doc-4 の判別できなかった項目・参照欠損と doc-9 のバージョン不整合。decision-22）・保存区分印・未分類区画の原文 status | ○ | ○ | ○ |
| title | frontmatter title | 1 行 | 2 行 | 3 行 |
| Type | kind ラベルと frontmatter `type` の 2 つの Type 導出元から（decision-5・decision-20）。0 個以上を併記し、Type 候補なし（どちらの導出元からも候補を得ない）は「Type 未設定」、未知 Type は中立表示に印 | — | ○ | ○ |
| 通常ラベル | labels の非 kind 要素（doc-4）。Type と混ぜない | — | — | ○ |
| assignee | frontmatter assignee | — | — | ○ |

- **既定は M**。画面設計案は 01（Tweaks の既定値）で L、04（割当表）で M を既定としており一致していない。M を採るのは、L だけに載る可変長の項目（通常ラベル・assignee）がカードの高さを予測できなくし、既定の状態で行数が読めなくなるためである（04 の割当表がそれらを L 限定にしたのと同じ理由）。既定値の正本は本章とする。
- **状態の印はどの段でも落とさない**。落とすと、問題のあるタスクが正常なカードとして見える。カード情報量は密度の調整であって、異常の隠蔽ではない。
- **不整合はカードでは ⚠️ の印 1 つだけで示す**（decision-22）。由来（判別できなかった項目・参照欠損・バージョン不整合）も族名もカードには出さず、理由はタスク詳細の不整合区画（doc-8 §3）が持つ。**カード左 3px の族色は decision-22 で外れた** — 不整合を述べるのは印グリフだけである（doc-11 §2.3）。
- **priority は優先度色で述べる**（decision-23）。カードでは**カード左 3px の優先度の縁**（doc-11 §2.3）と **priority チップ**（doc-11 §3）の 2 つがその色を引き、priority の行は 3 段とも ○ なので、どちらも段では落ちない。**priority 未設定 と priority 未知（`high`・`medium`・`low` のどれにも一致しない値）には色を与えない** — 色が無いことが「3 段のどれでもない」を述べ、値そのものは priority チップが原文のまま出す。優先度色は族ではないので、⚠️ の族の色と取り違えないための区別は doc-11 §2.3 が定める。
- **通常ラベルと assignee を L 限定にする**のは、件数が可変でカードの高さを予測できない項目だからである。S・M で行数を保証するには、可変長の項目を外すほかない。
- **保存区分印**は、既定表示（active のみ）では付けない。フィルタで draft / completed / archive を加えたときだけ、active と区別する印を付ける（5 章）。
- 依存・AC 進捗などの詳細はカードに載せず、タスク詳細画面（doc-8）へ委ねる。カードは一覧の密度を保つ。
- カードを選ぶとタスク詳細画面（doc-8）を開く。開き方（併置サイドバー・中央モーダル・全面シングルビュー）は doc-8 §2 の詳細配置に従う。
- Type チップ・通常ラベルチップ・印・priority チップの描き分けは doc-11 §3、優先度の縁は doc-11 §2.3。

## 4. プロジェクト／status のマッピングと列内新規タスク入力

- **status → 列**: 各タスクの status を、そのプロジェクトの列対応規則（decision-4）で正準ステータス列へ対応づけ、対応先セルへ置く。どの列にも対応づかない status は未分類区画へ置く。config.yml 未定義の想定外 status（doc-4 の想定外スキーマ）は未分類区画に置きつつ不整合印を付ける（decision-4）。
- **タスク → プロジェクト行**: タスクの所属プロジェクトは、読み込んだ Backlog ルートに対応する台帳エントリで決まる（doc-3 の決定規則）。タスクへ `project:` ラベルを付けない。
- **列対応規則の別名**: 別名表（decision-4、台帳エントリの任意属性）が設定されていれば適用する。既定は名称一致（大文字小文字・前後空白を無視）。

### 4.1 列内新規タスク入力

レーンセルの末尾から、そのセルの列で新規タスクを作れる。受け取るのは title だけで、`task create` を 1 回発行する（doc-5 の操作写像）。

**列の作成時 status 候補**とは、ある正準ステータス列へ本章冒頭の列対応規則で対応づく、そのプロジェクトの `config.yml` が宣言する原文 status の集合を指す。列内新規タスク入力が `-s` へ渡す値は、この候補から決める。

- **正準列名をそのまま渡さない**。`-s` は `config.yml` に宣言済みの値だけを受け取り、未宣言の値は終了コード 1 で拒否される（doc-5 §3）。`backlog init --defaults` が宣言するのは `To Do` / `In Progress` / `Done` の 3 つで、`In Review` は宣言されない（実測）。列対応規則は「原文 status → 列」の向きにしか定められておらず、逆向きは対応先が無い場合・複数ある場合・列名と原文が一致しない場合のいずれにもなる。
- **候補が 1 件の列**: その原文 status を渡し、渡す値を入力欄に表示する。
- **候補が 0 件の列**: 入口を置かない。その列に対応する status がこのプロジェクトでは宣言されていないため、作成時の初期値を決められないからである。置かない理由を短く書く。
- **候補が 2 件以上の列**: 入力欄の status を候補からの選択にし、既定を `config.yml` の宣言順で先頭の候補にする。どの値が渡るかは、候補の数によらず常に入力欄で読める状態を保つ。
- **未分類列には入口を置かない**。未分類列は正準ステータス列に対応しない status の集まりであり、候補集合をそもそも定義できないためである。入口を無効化して置くのではなく、置かない（無効化と提供しないの区別は doc-11 §5）。**この 1 件については、置かない理由を画面に出さない**（2026-08-03 にユーザーが 2 案から選択）。理由は 3 つ — 押せない控えを置いていないので doc-11 §5 が理由を要求する対象（無効化）ではない、正準 4 列に入口があって未分類列だけに無いという並びが画面に出ている、そして未分類列は未分類 status を持つプロジェクトでは出続けるので、常設の 1 文は列ヘッダ行の 1 行保持（§2.2）で得た高さをそのまま食う。候補 0 件の列（上記）は引き続き理由を書く — そちらは同じ列がプロジェクトによって入口を持つので、無いことが並びから読み取れない。
- **title は必須**。空のまま発行できない（`task create` の位置引数であり、doc-4 §3.1 の必須項目でもある）。
- priority・milestone・ラベル・受入条件を伴う作成は、プロジェクト詳細画面の新規タスク区画（doc-10 §7）で行う。両者が発行するのは同じ `task create` である。
- CLI 縮退時（doc-5 §5）は、入口を理由付きで無効化する。読み取りは続く。

### 4.2 列間ドロップ

**列間ドロップ**とは、タスクカード 1 枚をつまんで同じプロジェクト行の別の列のレーンセルへ落とし、`task edit -s` 1 回を発行させる操作を指す（decision-34）。発行するのは doc-5 §3 の「タスク status 変更」1 行そのもので、操作写像は増えない。**受け先**とは、列間ドロップを受け取って発行へ進むレーンセルを指す。

**受け先になれるのは、§4.1 の 列の作成時 status 候補 を 1 件以上持つ正準ステータス列のレーンセルだけである。**§4.1 が定めた候補集合を、列間ドロップはそのまま読む — 列対応規則は「原文 status → 列」の向きにしか定められておらず、逆向きを画面側で解き直せば、カードが**置かれる**列とカードを**落とせる**列が食い違いうるためである。**したがって §4.1 の 列の作成時 status 候補 は 2 つの操作が読む値である。** 語は「作成時」のままとする（decision-34。改称は decision-4・本書・wire・読み取り層・画面の 5 か所を一斉に動かし、得るものは語の正確さだけである）。

- **候補が 1 件の受け先**: その原文 status を渡す。選ぶものが無いので問わない。
- **候補が 2 件以上の受け先**: **候補選択の問い**を立て、選ばれた候補を渡す。**候補選択の問い**とは、候補が 2 件以上の受け先への列間ドロップが立て、渡す status を候補から 1 つ選ばせる被せ層を指す。§4.1 が「どの値が渡るかは、候補の数によらず常に入力欄で読める状態を保つ」と要求しているのに対し、列間ドロップには入力欄が無いためである。**doc-11 §12 の実行前確認ではない** — あちらが問うのは動作を行うかどうかで答えは 2 つだが、こちらが問うのは渡る値で答えは候補の数だけある。借りるのは被せ層の作法（同時に 1 枚・出口は取りやめと同じ扱い）であって、§12 の規則ではない。**§12 の `…` は掛からない**（付ける先の控えが無い）。
- **候補 0 件の正準ステータス列**: 受け先にせず、**置かない理由を短く書く**（§4.1 の候補 0 件の列と同じ理由 — 同じ列がプロジェクトによって受け先になったりならなかったりするので、無いことが並びから読み取れない）。`backlog init --defaults` は `In Review` を宣言しないので、これは辺縁ではなく既定の構成で起きる。
- **未分類列は受け先にせず、理由も画面に出さない**。候補集合をそもそも定義できない点は §4.1 の入口と同じで、理由を出さない判断も §4.1 のものを引く（2026-08-03 にユーザーが 2 案から選択。3 理由のうち「押せない控えを置いていないので doc-11 §5 の対象ではない」と「常設の 1 文が §2.2 の 1 行保持で得た高さを食う」の 2 つがそのまま当たる）。**TASK-81 の受入条件は当初これと逆を求めていたが、2026-08-15 に本節の側へ揃えた**（decision-34）。
- **カードが既に居る列は受け先にしない**。渡る status が現在の status と同じになる発行は、更新ではない。
- **行またぎのドロップ**（別のプロジェクト行のレーンセルへ落とす操作）**は成立しない**。タスクの所属プロジェクトは読み込んだ Backlog ルートに対応する台帳エントリで決まり（4 章）、ルート間でタスクを移す写像は doc-5 §3 に無い。**これは「提供しない操作」であって無効化ではない**ので、受け先にしないだけで理由も添えない（doc-11 §5 の区別）。

**CLI 縮退時（doc-5 §5）は、カードをドラッグの起点にしない**（**つまめないカード**）。§4.1 の入口は「理由付きで無効化」だが、ドラッグには無効化する控えが無く、つまめるが落とすと拒む形は操作できるように見せてから拒むことになる。**理由をカードに添えない** — doc-11 §5 が「画面全体に効く理由（CLI 縮退・台帳読取専用）は上部帯にも出す」と定めており、その 1 文が既に画面に出ているためである。**カードは押せば詳細を開くままで、失うのはつまめることだけである。**

**発行中のカードは元の列に留まる。** **発行中のカード**とは、列間ドロップの発行が返るのを待っている間のタスクカードを指す。カードの列は読み取り結果の status の関数であり、位置を別に持つ場所が無い — 楽観的に動かすには読み取り結果と別のカード位置を持つことになり、doc-5 §5（失敗した更新操作は Atlas 側のドメインモデルを変更しない）と doc-5 §6（更新の結果はファイルを読み直して初めてドメインモデルへ入る）の両方に反する。**発行は最長で CLI 終了期限（30 秒。decision-18）掛かるので、発行中であることを画面に出す。**

**更新前競合（doc-9 §4）は既存の経路がそのまま持つ。** 列間ドロップも他の更新操作と同じ入口を通るので、版がずれていれば CLI は起動されず、再読込された status の列へカードが描かれる。**発行が失敗したときも同じで、カードは読み取り結果の位置に居続ける** — カードの位置とディスクの内容が食い違う状態は、位置が読み取り結果の関数である限り作れない。

**OS のドラッグ&ドロップの横取りを外す**（decision-34）。`src-tauri/tauri.conf.json` の窓設定は `"dragDropEnabled": false` を持つ。既定の `true` では Tauri が窓へ handler を登録して OS の既定動作を止め、Windows では画面内のドラッグ&ドロップが成立しない（実測。`tauri-utils` の当該設定の doc がそう述べる）。Atlas は OS のドラッグ&ドロップ事象を消費していないので、外して失う機能は無い。

## 5. フィルタ・並び順・上部帯

### 5.1 行の並びと表示

- **プロジェクト行の並び**: 既定は台帳の並び順。画面で行の表示順を変更でき、変更は台帳の表示順（doc-3 の更新で許す並び順）へ反映してよい。台帳が読み取り専用のとき（doc-3 §2.2）は並べ替えを理由付きで無効化する。
- **行折畳み**: レーンセル群を畳み、レーンヘッダ行と列別件数を残す。件数は読めるままである。
- **行非表示**: 行を画面から取り除く。件数も読めなくなる。**切り替えるのは §2.1 のメニューのプロジェクト一覧だけ**で（2026-08-09 に一元化。TASK-131）、表示中の行には印が付き、押すと非表示になる。行折畳みとは別の操作・別の語として扱う。両者を同じ語で呼ぶと、「畳んだつもりで件数まで失った」「隠したつもりが件数だけ見えている」という取り違えが起きる。
- **行折畳み・列折畳み・行非表示 はいずれもアプリ設定へ保存し、再起動をまたいで効く**（decision-13 の 再起動をまたぐ保持の改訂。2026-08-18 にユーザーが 3 値すべてを保存すると判断した — それまで本項は「いずれも画面の一時状態で、アプリ設定にも台帳にも保存しない」と定めていた）。**保存の契機は押下ごとである** — 既定の並び順（§5.4）・既定の詳細配置（doc-8 §2.2）と同じく、画面が先に変わり、ファイルがそれに続く。**保存が拒まれたら doc-11 §4 の ⑤ 通知 が述べる**（押した操作そのものは効いており、失われるのは次回起動時の再現だけである）。アプリ設定ファイルが未知の上位版で読み取り専用へ縮退している間は（decision-13）どの項目とも同じく書かれない。
- **復元時の正規化**とは、保存された 3 値を画面へ戻す前に、台帳に無い slug を落とし、正準ステータス列 4 つがすべて畳まれている列集合を（未分類列を残して）空として読む処理を指す。**通る時点は 2 つの側で違う。列の側はアプリ設定を最初に読んだ時点で 1 度だけ通り**（それ以降の読み取りは、この画面か設定画面が直前に行った書き込みの答えなので、取り込み直すと、保存の往復の間に行った折畳みを取り消すことになる）、**行の側は台帳の答えを受け取るたびに通る**（起動時と、登録・登録解除・並べ替えのたび）。**行の側を、アプリ設定が届く場所へ置くことはできない** — 起動ではアプリ設定の読み取りが台帳より先で、その時点では slug が 1 つも分かっていない。**行の側が実際に slug を落としたときは、その結果をアプリ設定へ書く** — 落としたまま書かないと、その slug は登録より長く生き残り、同じ slug を登録し直したときにその行が畳まれた状態・非表示の状態で現れる。**落としたときだけ書くので、直すものが無い起動はアプリ設定ファイルを書かない。** **slug を落とすのは**、下の「落とす操作」が登録解除でその行の値を落とすのと同じ帰結を、アプリ設定ファイルを手で書いた場合（doc-3 §2.2）にも保つためである。**4 列すべてを含む列集合を空として読むのは**、§2.2 が「すべての列を同時に畳むことはできない」と定めており、その集合を画面の控えからは作れないためである — 利用者の選択を近似できる規則が無いので、どの列も読める状態へ倒す。未分類列はこの数え上げに入らない（§2.2）。
- **実行内保持**とは、1 回のアプリ実行の中で画面を移って戻っても値が効いたままであることを指す。**上の 3 値はいずれも実行内保持の対象である** — プロジェクト詳細画面（doc-10）へ移って戻っても、全面シングルビュー（doc-8 §2.1）でタスクを開いて閉じても、行の再読込（§2.3・doc-9 §3）を受けても、移る前の値がそのまま効いている。**再読込がその行を読取不能に変えたときだけは、その行の 行折畳み は効いた形で描かれない**（§6。畳む対象のセルが無いため）が、値は保たれ、次に読めた時点で再び効く。**利用者が落とした場合を除けば、3 値は失われない** — 2026-08-18 の改訂まではアプリの終了で失われ、それが上の項の帰結だった（落とす操作は 2 つある — プロジェクトの登録解除（doc-3 §4.2）はその行の 行折畳み・行非表示 を行ごと落とし、すべてのプロジェクトを表示（§2.1）は 行非表示 を空にする。どちらも利用者が求めた結果である）（2026-08-11 に補った。TASK-147。それまで本節は 3 値を一時状態と呼ぶだけで実行の中の寿命を述べておらず、実装は折畳み 2 種を画面の切替で降ろされる部品に持たせていた）。
- **したがって 3 値の置き場は、画面の切替で降ろされる部品の外である。** 画面を移るたびに畳み直させることは、保存の有無とは別の話である — 実行内保持 が求めるのは値を持つ場所であって、値がファイルへ書き出されるかどうかではない。**この項は 2026-08-18 の改訂の後も残る**: 3 値がアプリ設定へ保存されるようになっても、画面の切替で降ろされる部品に値を持たせれば、1 回の実行の中で失われることは変わらない。

### 5.2 フィルタ

フィルタはカードの取捨のみを行い、行・列の骨格（プロジェクト行と正準ステータス列）は保つ。次を単独・組合せで適用する。

- Type（decision-5・decision-20 の Type 値。複数 Type 値のタスクはいずれか一致で残す。未設定・未知も選べる）。
- 通常ラベル。
- priority。
- assignee。
- テキスト（横断タスクID・title 部分一致）。
- 不整合（不整合のタスクだけを抽出し、問題を洗い出す）。**判定は 3 章のカードの ⚠️ と同じ**（decision-22）ので、読み取り由来の理由が無くバージョン不整合だけのタスクもここに残る。⚠️ を出しているカードをこの絞り込みが隠すと、同じ画面が同じタスクについて 2 つのことを言うことになる。
- タスク保存区分（doc-4 の 3.4）。既定は active のみで、既定値はアプリ設定で変えられる（decision-13）。フィルタで draft / completed / archive を明示的に加えられる。加えた区分のタスクは対応する status 列（対応不能なら未分類区画）へ並べ、active と区別する保存区分印（3 章）をカードに付ける。
- 更新期間（updated_date が指定の期間に入るタスクだけを残す）。**上の 7 つと違い、値の集合から選ぶのではなく端を入力する**（規則は下の「更新期間」）。

**選択中の条件は絞り込みトークンとして帯に並べる**。ファセットの値を常時展開しない。値の一覧は「＋ 絞り込み」から開くポップオーバー（検索・スクロール・値ごとの件数・選択数）で選ぶ。**更新期間だけは値の一覧を持たず、同じポップオーバーの末尾で端を入力する**（下の「更新期間」）。

- **理由**: 常時展開はラベルが 20 種・assignee が 6 名まで増えると帯が数行に伸び、その分だけグリッドの高さを奪う。トークンは選択中の条件だけを見せるため、条件を増やしても折り返し 2 行程度で頭打ちになる。
- **解除の順序**: トークンは条件を足した順に並び、末尾から 1 件ずつ解除できる。属性ごとのドロップダウン集合には解除順の概念が無く、「直前の 1 つを戻す」が成立しない。
- **既定に戻す**: 帯は、効いている条件をまとめて降ろす控えを 1 つ持つ。名は「既定に戻す」で、これは画面設計案 03 案A が同じ控えに与えた語である（doc-12 §4.3）。**この操作にキーは割り当てない**（2026-08-09 に TASK-80 が判定。画面設計案 03 からの意図的な逸脱）。原文は `⇧F` を 直前の 1 つを解除、`⌥⇧F` を 全解除 に割り当てている（doc-12 §4.1）が、割り当て一覧の正本は `shortcuts.ts`（§2.1）であり、実装は 直前の 1 つを戻す を `Backspace` に割り当ててこの控えにはキーを持たせていない。両方とも帯の上に控えとして常に見えているので、キーの有無が操作の到達可能性を変えない。押すと Type・通常ラベル・priority・assignee・テキスト・不整合・更新期間の選択を外し、**保存区分だけは既定の保存区分（decision-13）へ戻す**。保存区分は肯定的な選択なので、他のファセットと同じように空にすると、カードが 1 件も残らない。この控えが戻す先は「条件が 1 つも無い状態」ではなく**画面を開いたときの状態**であり、名もそれを述べている。
- **「既定に戻す」が無効になるのは、絞り込みが既定のままで、かつ「直前の 1 つを戻す」が戻すものを持たないときに限る**。値だけを見て「既定のまま」と判定しない — 保存区分の既定をトークンの解除で外し、同じ区分を値一覧で選び直すと、値は既定に戻る一方で、条件を足した順にはその 1 件が残る。値だけで判定すると、無効になった「既定に戻す」の隣で「直前の 1 つを戻す」が押せ、押すとグリッドが空になり、残った順を消す手段がどこにも無くなる。
- **2 つの控えはアイコンのみのボタンである**（2026-08-15。TASK-175）。直前の 1 つを戻す が lucide の `undo`、既定に戻す が `refresh-ccw` を持ち、**「直前の 1 つを戻す」「既定に戻す」の語は可視の文言ではなくなった** — 名は `aria-label`、押せるときの操作の説明と押せないときの理由は `title` が持つ（doc-11 §2.4 の アイコンのみのボタン）。**替えた理由は帯の横幅である** — この 2 語が帯の右側を占めていたのを縮めるためで、操作そのものも、到達経路も、上の各項が定める無効化の条件も変えていない。**判定（`refresh-ccw` を 既定に戻す へ与えてよいか）は doc-11 §2.4 が持つ** — まだ図形を持たない 再読込 が争点だった。**和音の併記が要るのは 直前の 1 つを戻す だけである** — 既定に戻す は上のとおりキーを持たないので、併記する和音が無い。併記の形は §2.1 がアイコンのみのボタンに定めるとおり `title`・`aria-keyshortcuts` とキーボード操作一覧のモーダルが担い、**帯に刷っていた可視の和音は落とした**（文言を持たない操作の隣にキーだけを刷ると、アイコンのみという形が成立しない）。**無効化提示は doc-11 §5 の 2 つ目の形のままである**（`aria-disabled` とフォーカス可能なまま、`aria-describedby` で理由の要素へ結ぶ）— 理由をホバーだけに置かないことは、控えが語を可視で持つかどうかと関係しない。**画面設計案 03 案A は 既定に戻す を語のボタンとして刷っている**ので、これは 03 からの意図的な逸脱である（doc-12 §4.3）。
- **総計の置き場**: 総計はフィルタ帯に置かず、§2.1 の総件数としてタイトルバーだけに出す。レーンヘッダ行の「n / m 件」は行ごとの内訳として残す。画面設計案 03 の判断節は総計をフィルタ帯の右端に常設し行の内訳と両方を出すとしているが、01 は総計を画面名の横に置き帯には解除のキーボード説明を置いており、2 案が食い違う。後発の全景案である 01 を採る。同じ数を 2 か所が刷ると食い違いうるので、刷る場所は 1 つに限る。**置き場が画面名の横からタイトルバーへ移ったのは decision-31 である**（画面名そのものが無くなった）。刷る場所を 1 つに限るという判断はそのまま効いている。
- クエリ言語型の絞り込みは採らない。1 人用のローカルアプリに学習コストが見合わない。
- **未分類区画とフィルタ**: フィルタは未分類区画にも同じく効く。フィルタで未分類区画のカードが全行から無くなれば、§2.2 のとおり列ごと消える。

**値一覧ポップオーバーの閉じる契機は次の 5 つで、これ以外では降りない**。ここでいう閉じる契機とは、ポップオーバーを降ろす利用者の操作を指し、画面遷移のようにポップオーバーに対して行ったのではない消え方は含まない。

- **「閉じる」ボタン**: ポップオーバーの下端に常設する。選択数の隣に置き、選択を終えた位置から動かずに閉じられるようにする。
- **Escape**: §2.1 の割り当て一覧の `closeOverlay`（開いている層を閉じる）。ポップオーバーは被せ層の 1 つなので、この押鍵はここで止め、下の層へ渡さない。
- **ポップオーバーの外側の押下**: 「＋ 絞り込み」の控えとポップオーバーのどちらの箱にも入らない位置で押し始めた操作。**押し始めの位置で判定する**ので、押した後にポップオーバーの上へ動かして離しても閉じる。押し終わりで判定すると、ポップオーバーが覆っていたものの上で押し始めた操作が、まずその下の要素に届いてしまう。
- **「＋ 絞り込み」の再押下**: 開いている間、この控えは開く操作ではなく閉じる操作を持つ。控え自身は上の「外側」に入らない。ここを外側に含めると、押下が閉じた直後に控えの click が開き直し、この控えでは決して閉じられなくなる。
- **別の被せ層を上げる操作**: §2.1 の共通入口（プロジェクト登録・設定・キーボード操作一覧）を開く操作と、メニューを開く操作。**被せ層は同時に 1 枚しか立てない**ので、これらはポップオーバーを降ろしてから上がる。Escape が「開いている層」を 1 つに定められるのはこの前提による。**この 1 枚だけという規則は §2.1 が持つ**（2026-08-19 に書いた。TASK-120）— あちらが持つのは被せ層という層の振る舞いの契約で、同時に何枚立てられるかはその契約に属する。**§2.1 が 2026-08-07 に降りたのは「どの画面がどの層を持つか」の一覧のほうで、振る舞いの契約ではない**（TASK-117）。**ポップオーバーが 1 枚に数えられることは §2.1 の側にも書いてある** — 本項と併せて読める。
  **プロジェクト詳細画面の作成の入口（doc-10 §1）も被せ層を上げる操作である**が、本項の列挙には入らない — 本項が数えているのは**ポップオーバーが上がっている間に届く操作**で、ポップオーバーは本画面のものだから、あちらの入口と同時に画面へ出ることがない（2026-08-07。TASK-117）。**実装はそれでもポップオーバーを降ろす** — 1 枚だけという規則を画面ごとに判断させず 1 か所で守らせているためで、届かない経路に対する備えであって本項の穴ではない。

**閉じる契機に含めないもの**は次のとおり。

- **値の選択は閉じる契機ではない**。値を押すと条件は即時に適用され、ポップオーバーは開いたまま残る。ラベルを 3 つ選ぶのは 1 つの用事であり、選ぶたびに閉じるとその 1 つの用事が 3 往復になる。
- **値一覧を開く押鍵（§2.1 の `addFilter`）は閉じない**。割り当て一覧がその操作を「絞り込みを追加（値一覧を開く）」と書いており、「メニューを開く／閉じる」（`toggleMenu`）と違って開く側だけを持つ。開いている層を閉じるのは `closeOverlay` の役割である。
- **閉じる契機は、選んだ条件の適用とは無関係である**。条件は選んだ時点で適用済みなので、どの契機で閉じても結果は同じであり、閉じ方によって適用される・されないが変わることはない。

**更新期間は 8 つ目のファセットで、値の集合を持たない**（2026-08-10。TASK-133）。上の 7 つはワークスペースが現に持つ値から選ぶが、暦日はどの集合にも属さないので、値一覧ポップオーバーの検索も件数もこの条件について何も言えない。**それでも入口は「＋ 絞り込み」のままにする** — 条件を足す入口が 2 つになると、どちらが何を足す入口なのかを画面が述べる必要が出る。ポップオーバーの末尾に、値の一覧ではなく入力欄を持つ区画を 1 つ置き、上の閉じる契機 5 つをそのまま適用する。**値一覧ポップオーバーは画面設計案 03 案A では検索・スクロール・件数だけを持つ共通部品なので、これは 03 からの意図的な逸脱である**（doc-12 §4.3）。帯の控えを 1 つ増やす逸脱（funnel・直前の 1 つを戻す・並び順の 3 例）とは種類が違い、増えるのは帯の上のものではなくポップオーバーの中身である。

- **端は 2 つで、それぞれが独立した絞り込み条件である。** 始端（その日以降を残す）と終端（その日以前を残す）。**両端指定・始端指定・終端指定の 3 形は「どちらの端が立っているか」** であって、期間という 1 つの条件が取る 3 つの状態ではない。端はそれぞれトークンを持ち、条件を足した順に自分の位置を取り、「直前の 1 つを戻す」は端を 1 つずつ剥がす。端の日付を直したときは条件を足し直したことにならず、足した順の位置は動かない（テキスト欄と同じ扱い）。
- **端は暦日で、両端とも含む。** 終端の日に更新されたタスクは、その日の何時に更新されていても残る。比較するのは暦日どうしなので、日の中の時刻は比較に届かない。
- **基準時間帯は読み手のローカル暦日である。** frontmatter の値は UTC として読み、実行環境のローカル暦日へ直してから端と比べる。**Backlog CLI が UTC で書くことは実測した**（ローカルの時計が 2026-08-10 10:46（UTC+12）を指しているとき、作られたタスクは `created_date: '2026-08-09 22:46'` を持つ）。直さずに比べると、いま更新したタスクが「今日」から時差ぶんだけ外れる。
- **これは §5.4 の「日付を文字列のまま比べる（timezone を発明しない）」と矛盾しない。** あちらが守るのは 2 つの値の相対順序であり、全体が一様にずれても順序は変わらないので、文字列のまま比べてよい。こちらが比べるのは利用者が名指しした**絶対の境界**で、ずれはそのまま取捨に出る。しかも「今日更新したもの」は、問う人がどこにいるかで答えが変わる問いである。ずれを踏むことは、時間帯に依らない画面を作ることではなく、誰もいない時間帯で値を読むことにしかならない。
- **時刻を持たない値は直さない。** `updated_date: '2026-07-22'` の形は既に暦日そのもので、直すには先に時刻を決めることになる。本リポジトリの台帳にも 9 件ある形なので、想定上の話ではない。よってこの形の値はどの時間帯でも同じ日を名乗る。
- **暦日を読めないタスクは、どちらかの端が効いている間は落とす。** updated_date を持たないタスクと、受け付ける 2 形（`YYYY-MM-DD` と `YYYY-MM-DD HH:MM`、秒は任意）のどちらでもない値を持つタスクがこれにあたる。期間の条件が問うのは「期間の中にあるか」で、どちらも中にあると示せない。**§5.4 が並びで同じ欠落を末尾へ送るのとは逆になる** — あちらは全部のカードを並べたうえでどこに置くかを問うので末尾という答えがあるが、こちらは残すか否かを問うので、残す側の答えが無い。
- **相対指定は始端だけを与える。**「いまから X 日 / 週 / 月」を暦日へ直して始端に入れる。日と週は日数で数え（週 = 7 日）、月は暦月で数えて短い月へは詰める（3 月 31 日の 1 か月前は 2 月 28 日）。**解決時点は押した時点**で、直った暦日がそのまま条件になる。条件が絶対の日になるので、画面を開いたままでも境界は動かず、トークンが名乗る日と実際の境界が食い違うことがない。
- **この操作を「ショートカット」と呼ばない。** その語は §2.1 の割り当て一覧が押鍵の和音に対して既に持っており、同じ帯の上で 1 つの語が 2 つを指すことになる。
- **相対指定が受け取るのは 1 〜 9999 の整数で、それ以外のときは控えを理由付きで無効化する**（doc-11 §5）。上限は入力欄が受ける桁数であって暦の限界ではない（9999 は 日 で 27 年、週 で 191 年、月 で 833 年にあたり、どの単位でも実在する日に着く）。**暦日を作れない値からは始端を作らない** — 作れないまま進むと、トークンが読めない日を名乗り、その隣で条件がトークンの述べていない取捨をする。
- **始端が終端より後のとき、カードは 1 枚も残らない。** これに説明の文は置かない — 2 つのトークンがその 2 つの日付を並べて出しているので、空になった理由は帯の上で読める。保存区分が 1 つも選ばれていない場合に文を置くのは、あちらは**トークンが無いこと**が原因であり、画面に手掛かりが残らないためである。
- **端の入力欄は OS の日付書式で表示される。** 条件そのものは暦日（`YYYY-MM-DD`）で、トークンもその形で名乗るが、入力欄はプラットフォームの日付入力なので表示は OS の書式に従う（実測: この環境では両エンジンとも `01/08/2026`）。**同じ日を 2 つの書式が同時に画面へ出ることは承知のうえで採る** — 文字列の入力欄に替えれば書式は揃うが、暦を開いて選ぶ手段と桁ごとのキーボード送りが画面から無くなる。取り出す値はどの書式で表示していても暦日である。
- **更新期間はアプリ設定へ保存しない。** 他の絞り込みと同じく画面の一時状態である（decision-13）。並び順（§5.4）を保存するのは、あれがカードを 1 枚も失わせないためであって、絞り込み帯に置くものだからではない。**2026-08-18 以降、カードを 1 枚も失わせないことは保存する値の唯一の条件ではない** — 行非表示（§5.1）は行そのものを画面から失わせ、それでも保存する（根拠は decision-13 の 再起動をまたぐ保持の改訂）。**更新期間 を保存するかどうかは、その回に見直していない。**

**帯の先頭には、絞り込みの目印として lucide の funnel を 1 つ置く**（doc-11 §2.4 の 操作に属さないアイコン）。押せる操作ではなく、帯全体が何をする場所かを図形で述べる。**画面設計案 03 案A の帯はテキスト入力欄から始まり、アイコンを置いていない**（doc-12 §4.3）ので、これは 03 からの意図的な逸脱である（2026-08-09 に TASK-80 が判定。doc-12 §4.3 が預けていた未判定を閉じる）。置いたままにする根拠は本項と次項が既に持っており、判定が足したのは帰属だけである。

- **テキストの入力欄は可視の属性名を持たない**。名前は `aria-label`、受け取るものは placeholder（横断タスクID・title）が述べる。可視の「テキスト」を撤去したのは、その語が何を絞り込むのかを述べておらず、画面を見た利用者に伝わらなかったためである（TASK-68 の目視で判明し、TASK-112 で直した）。
- **funnel を入力欄のラベルにしない**。漏斗が指すのは絞り込み全般であって「テキスト」ではない。入力欄の位置に置くと「この入力欄＝絞り込み」と読め、隣の「＋ 絞り込み」やトークン群と指示対象が重なる。帯そのものの目印にすれば図形と指示対象が一致する（2026-08-03 にユーザーが 3 案から選択）。
- **帯の高さは 1 行のまま**（画面設計案 03 案A）。先頭に目印を足しても、帯が持つ 1 行の高さ（実装の `--bar-control`）を増やさない。余白を足して増やすと、案A が避けた「帯がグリッドの高さを奪う」に戻る。

**帯は並び順の控えを 1 つ持つ**（並び順そのものは §5.4）。**並び順はフィルタではない** — フィルタはカードの取捨のみを行うと本節の冒頭が定めており、並び順は 1 枚も取捨しない。よってこの控えは絞り込みトークンを持たず、条件を足した順にも入らず、「直前の 1 つを戻す」「既定に戻す」のどちらの対象にもならない（並びを既定へ戻すのは、選択肢から priority 降順 を選ぶことである）。同じ帯に置く理由は、帯がグリッドの見え方を決める場所だからであって、並び順が条件の一種だからではない。**この操作にキーは割り当てない** — 帯に常に見えているので、キーの有無が到達可能性を変えない（既定に戻す と同じ理由）。控えは帯の 1 行の高さ（`--bar-control`）を取る。

- **画面設計案 03 に並び順の控えは無い**（doc-12 §4.3）。03 案A の帯はテキスト入力欄・＋ 絞り込み・トークン・既定に戻す だけを持つ。TASK-112 が置いた funnel、Atlas が足した 直前の 1 つを戻す に続く **3 例目の追加**で、これは 03 からの意図的な逸脱である（2026-08-10。TASK-132。根拠は 2026-08-09 のユーザーの要求そのもの）。

**帯の右端は共通入口のメニュー（☰）である**（2026-08-15。decision-31。TASK-176）。本画面ではフィルタ帯が最上段の帯なので、§2.1 のメニューはここに立つ。**この控えはフィルタの控えではない** — カードを 1 枚も取捨せず、絞り込みトークンを持たず、「直前の 1 つを戻す」「既定に戻す」のどちらの対象にもならない。並び順の控えと同じ理由でここに在り（帯が画面の最上段だから）、置き場は並び順よりさらに右、帯の右端とする。**寸法は帯の 1 行の高さ（`--bar-control`）を取り、帯の高さは変えない** — 上の「帯の高さは 1 行のまま」がこの控えにも同じく効く。**画面設計案 03 に ☰ は無い**ので、これは funnel・直前の 1 つを戻す・並び順 に続く **4 例目の追加**であり、03 からの意図的な逸脱である。

### 5.3 上部帯

フィルタ帯の下に、立っている告知だけを横 1 行ずつ積む。**下表の種を、出現順ではなく重要度の固定順**に置く。同時に立ちうる最大は表の行数と同じで、表に挙げた種以外に上部帯を作らない（順序・左端の色・縮約の規則は doc-11 §4）。

| 順 | 帯 | 内容 |
|---|---|---|
| ① | 確認 | 未保存入力の破棄前確認（doc-8 §6.3）など、利用者の回答を待つもの |
| ② | CLI 縮退 | 対応 CLI を検出できず、作成・更新を発行できない旨（doc-5 §5） |
| ③ | 台帳読取専用 | 台帳の更新・登録解除・並べ替えができない旨（doc-3 §2.2） |
| ④ | 継続検出停止 | 変更監視が動いていない行がある旨と、該当行の再読込への案内（doc-9 §3） |
| ⑤ | 通知 | 操作の結果の報告。閉じられる |

②③④ の内容は個々の操作の無効化理由（doc-11 §5）と重複するが、ホバーしないと理由に到達できない状態を作らないために、画面上部にも出す。

### 5.4 セル内タスクの並び

**並び順は絞り込み帯から選ぶ**（控えの置き場は §5.2）。選べるのは 5 属性 × 2 方向の 10 通りで、**既定は priority 降順**である。並び順が決めるのはレーンセルと未分類区画の中のカードの順序だけで、行・列の骨格にも値の解釈（doc-4）にも触れない。

| 並び順 | 最初に見るもの |
|---|---|
| priority 昇順・降順（降順が既定） | priority の段（high > medium > low > 段なし） |
| task id 昇順・降順 | frontmatter の id。**横断タスクID ではない** — セル内のカードは同一プロジェクト行のものなので、slug は全件同じで順序に効かない |
| updated 昇順・降順 | updated_date |
| created 昇順・降順 | created_date |
| milestone 昇順・降順 | タスクの frontmatter の milestone。doc-10 のマイルストーン区画が扱う対象そのものではない |

**控えが並べる順は、属性が上の表の順、方向はどの属性も 昇順 → 降順 とする**（2026-08-10 にユーザーが判断）。属性の順は原文の列挙のままだが、**方向は原文と違う** — 原文は priority だけを 降順・昇順 の順で挙げており、5 属性のうち 1 つだけが逆に読めることが最初に目に付く。**既定（priority 降順）が先頭に来ないことは承知のうえで採る** — 控えは選択中の値を出すのであって先頭の項目を出すのではなく、既定であることは並びの位置とは別の事実である。

**同順のときの比較規則は、10 通りとも同じ 1 つである。** 選んだ並び順で差が付かなかったカードは、**既定の 3 段**（priority 降順 → ordinal（frontmatter）昇順 → updated_date の新しい順）を順に見て決め、それでも差が付かなければ**読み取り順**（読み取り層のパス順）に従う。選んだ並び順が priority・updated_date を既に見ているときも、同順であればその段は必ず差 0 を返すので二重には効かない。**この規則の下で priority 降順 は 2026-08-10 の改訂前の並びと同一**であり、並び順を選ばない利用者の画面はカード 1 枚ぶんも動かない。

**安定した並びであること**は改訂前から変わらない。10 通りとも決定的で、同じ入力からは同じ並びを返し、更新のたびにカード位置が飛ばない。読み取り順を最後の段に置いているのはそのためで、それ以前の段がすべて同順のカードでも位置は決まる。**「安定」は「並びが 1 本しか無い」ことではない。**

**値を持たないタスクの置き場**は 2 通りに分かれ、分かれる理由は属性の側にある。

- **priority の 段なし**（未設定・未知）は**方向に従う**。降順では末尾に、昇順では先頭に来る。priority は 3 段（decision-23）に段なしを加えた 4 段の順序を既に持っており、段なしはその最下段だからである。decision-23 が段なしに色を与えないのは順序とは別の話で、順序の側では段として実在する。
- **task id・updated・created・milestone を持たないタスクは、方向に依らず常に末尾**。欠落は値ではないので、値の列に混ぜない。方向に従わせると、日付を持たないタスクが昇順で先頭を占め、最初に読まれる位置を欠落が取ることになる。同順の 2 段目の ordinal も同じ扱いで、置かれていないタスクを 0 と見なせば、置かれたタスクより上へ飛ぶ。

**日付は文字列のまま比べる（timezone を発明しない）。** Backlog が書く `YYYY-MM-DD[ HH:MM]` は文字列の順が暦の順と一致し、値そのものは時間帯を持たない — 比べるために時間帯を 1 つ選べば、**選んだ側の都合で並びが変わる。** 本節が要るのは 2 つの値の相対順序だけで、全体が一様にずれても順序は変わらないので、選ばずに済む（§5.2 の 更新期間 が絶対の境界を比べるので分かれる。そちらの理由はあちらが持つ）。**2026-08-14 に本節自身の文として書き直した**（TASK-165）— それまでこの規則は、次の項が locale を読まない理由を述べるときの引き合いとしてしか本節に無く、**その項を doc-4 §7 へ移した時点で、本節を引いている 2 か所（§5.2 の 更新期間 の項・`src/lib/period.ts`）の引用先が消えていた。**

**id をどう比べるかは doc-4 §7 の id の比較規則が決め、本節はそれを引く**（`TASK-2` が `TASK-10` より前に来るのはその規則による）。**2026-08-14 に本節から §7 へ移した**（TASK-165）— 非タスク管理ファイルの 3 つの一覧が同じ比較を要ることになり、**規則を書く場所を 1 か所にする**ためである。移したのは 2 つの id のどちらが先かを決める段だけで、**本節が決めるのは、どの属性をその段に渡すかと、値を持たないカードをどこへ置くかである。**

**選んだ並び順はアプリ設定へ既定として保存する**（decision-13 の項目。書き戻しは doc-8 §2.2 の 既定の詳細配置 と同じ形で、選んだ時点でそれが既定になる）。並び順はカードを 1 枚も画面から失わせないため、次回起動時に前回の選択が効いていても「登録したはずのものが消えた」とは読めない。**行折畳み・列折畳み・行非表示（§5.1）も 2026-08-18 からアプリ設定へ保存する** — 本節が「一時状態としているのとは別で」と書いていた区別は無くなった。**その判定が保存の唯一の条件でもなくなっている**: 行非表示 は行そのものを画面から失わせ、それでも保存する根拠は decision-13 の 再起動をまたぐ保持の改訂 が持つ。

## 6. 読取不能・不在時の表示

- **ルート読取不能**: 台帳エントリの Backlog ルートが読めない（doc-4 のルート読取不能）場合、そのプロジェクト行を消さず、行全体を読取不能として示す（セルにタスクを出さず理由を示す）。他プロジェクト行の表示には影響させない。読取不能行は行折畳み・列折畳みの対象にならない（畳む対象のセルが無いため）が、プロジェクト詳細画面への入口は保ち、§2.1 のプロジェクト一覧にも他の行と同じく並ぶ（名前を持たないので slug で名乗る）。台帳エントリ自体は読めており、ルートの修正はそこで行うためである。
- **空セルと不在**: タスクが 0 件のセルは、中立の目印 1 つ（`--faint` の `—`）だけで示す。族の色・警告記号は与えない（doc-11 §6）。「該当タスクが無い」ことと「ルートが読めない」ことは区別する（前者は空セル、後者は行単位の読取不能表示）。decision-6 が求めるのは、この 2 つが決して同じ見た目にならないことである。
- **不整合のタスク**: 不整合（doc-4 の不整合表示）のタスクは破棄せず、判別できた status で対応列（不能なら未分類区画）に置き、カードに不整合印を付ける。
