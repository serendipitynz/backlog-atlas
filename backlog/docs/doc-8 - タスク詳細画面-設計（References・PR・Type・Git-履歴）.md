# タスク詳細画面 設計（References・PR・Type・Git 履歴）

TASK-12 の設計。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は doc-4（読み取り層・ドメインモデル・References 保持）・doc-5（Backlog 更新アダプター）・doc-6（Git・PR 履歴参照）・decision-5（Type 導出）・decision-13（アプリ設定）。描き方は doc-11 が定める。画面設計案（doc-1 追補で定義。02）を反映する。引用する事実は doc-12 §3 に転記してある。

## 1. 用語

- **タスク詳細画面** … 1 タスクの全項目（Description・AC・Type・通常ラベル・References・Pull Request URL・Git 履歴）を 1 画面で見せ、編集操作の起点とする面。
- **詳細配置** … タスク詳細画面をスイムレーンに対してどこへ置くかの選択（併置サイドバー／中央モーダル／全面シングルビュー）を指す。
- **Git 履歴欄** … doc-6 のコミット一覧・Pull Request URL・コミット・PR 関連解決結果を、タスク詳細でまとめて見せる欄。
- **編集セッション** … 編集を開始してから保存またはキャンセルで終わるまでの、Backlog 更新アダプター（doc-5）へ未発行の**未保存入力**を画面に保持する状態（6 章）。**発行先を「CLI へ」と書いていたのを 2026-08-07 に改めた**（TASK-121）: 次項の未保存入力は初版から更新アダプターを発行先に書いており、同じ 1 つの状態を隣り合う 2 項が別の発行先で定義していた。doc-5 §1 の直接書き込み操作（decision-21 の、マイルストーン説明の本文範囲を Atlas 自身が書くもの）は CLI 呼び出しではないので、字面の広い次項に揃えないと、その入力を保持する状態が編集セッションに当たるかが読めない。**タスク詳細の編集セッションはすべて CLI 発行なので、本書の中で指す範囲は変わらない** — 変わるのは doc-10 §6 のように更新アダプターの両方の発行形式を使う画面が、この語を引けるようになることである。
- **未保存入力** … 編集セッション中に利用者が入力したが、まだ Backlog 更新アダプター（doc-5）へ発行していない編集内容。
- **明示保存** … 利用者の明示操作（保存ボタン／保存ショートカット）でのみ CLI 更新を発行し、入力を随時自動保存しない保存方式。
- **編集部品** … 複数行入力・マウス選択/置換・全選択を担う UI テキスト編集部品。Ace を第一候補、素の `textarea` を基本形かつフォールバックとする（6.1）。
- **外部エディタ経路** … タスクの管理ファイルを利用者の外部エディタで開き、GUI 内編集の外で編集させる経路（7 章）。

## 2. 位置づけと詳細配置

タスク詳細画面は、スイムレーン（doc-7）のタスクカードから開く単一タスクの面である。読み取りはドメインモデル（doc-4）から写し、Git・PR 参照は doc-6 の出力を用いる。編集は Backlog 更新アダプター（doc-5）経由で行い、管理ファイルを直接書き換えない。横断画面ではない（単一プロジェクト文脈）ため、タスク ID は `TASK-ID` のみ表示してよいが、見出しには横断タスクID を併記し、どのプロジェクトのタスクかを明示する（doc-3 の 5.3）。

### 2.1 3 つの詳細配置

同じタスク詳細画面を、3 通りの置き方から選べる。読む内容が同じでも、必要な広さは作業によって違う（カードを次々に見比べる／1 タスクの本文をじっくり編集する／Git 履歴を全件たどる）ためである。

- **併置サイドバー**（幅 30rem 固定・スイムレーンの右）… カードを選び替えながら読む。グリッドが幅を譲る。
- **中央モーダル**（2 列）… スイムレーンを背景に置いたまま、主列（Description・AC・実装計画）と脇列（Type・ラベル・依存・References・PR）を並べる。1280×800 でも 2 列を保つ（脇列 18rem は確保できる）。狭いからといって縦積みへ落とさない。
- **全面シングルビュー**（2 列）… スイムレーンを退け、**全区画を開いた状態で出す**。Git 履歴の全件と関連解決の状態を読むのはここである。**開いた状態で出すのであって常設にするのではない**（2026-08-05 に改訂。TASK-114）— 折畳みの区画もここでは既定で開くが、利用者はそれを畳める。以前の本書は「全区画を常設で出す」と書いており、画面設計案 02 の全面の図が **5 つの開閉印**を描いている（doc-12 §3）のと正面から衝突していた。**下の割当表ではこれが 4 行になる** — 状態遷移・外部エディタが画面上は 2 区画で、割当表では 1 行だからである。全面が全部を一度に見せる場所であることは、常設にしなくても既定開閉（§3）で足りる。**列構成は中央モーダルと同じ**で、主列・脇列の 2 列に同じ区画を割り当て、脇列は同じく 18rem を取る（画面設計案 02 の全面の図。doc-12 §3。TASK-113）。全面が広いのは主列であって、脇列が持つ短い値の並びは窓が広くなっても長くならないためである。**列を持たないのは併置サイドバーだけ**になる。

**本文の 1 行の長さに上限を持つ**（本書で導入。TASK-113）。**上限は 48rem**（1280×800 で 768px）で、**タスク詳細の中で**掛ける先は **Description・Acceptance Criteria・実装計画・実装ノートの 4 区画の本文ブロックだけ**とする。

**「4 区画だけ」はタスク詳細の中での限定であって、この上限が本画面に閉じているという意味ではない**（2026-08-07 に明記。TASK-116）。値と根拠は本項が持ち、**残り幅を取る列に置いた本文ブロック**という同じ状況にある他画面は、決め直さずに本項を引く — 最初の例が doc-10 §5 の閲覧の本文である。決め直さないのは、48rem が「1 行が長いほど次の行の先頭を見失う」という読みの性質から来た値で、どの画面かに依らないためである。**引く側が確かめるのは状況が同じかどうかだけ**で、下の 3 項（値の由来・配置ごとの効き方・4 区画に限る理由）はいずれも本画面の実測と本画面の事情なので、そのまま持ち出さない。

- **値の由来**は中央モーダルの主列である。「窓幅から脇列 18rem を引いた残り」という既存の契約（上項）が 1280×800 で主列に与える幅は **49.25rem＝788px** の 1 つで、幾何計算と実レイアウトが一致する（2026-08-05 に一致させた。TASK-115）。48rem はその主列に収まる 1rem 単位の幅であり、**既存の契約が主列に与えている幅の内側**である。新しい数字を持ち込まないためにこう取った。以前の本書はここに **47.75rem（幾何計算）と 49.25rem（実レイアウト）** の 2 値を併記し「48rem はその間に取った値」と書いていたが、誤っていたのは 47.75rem の側である — 本リポジトリには box-sizing の全体リセットが無く `width` は content box なので、パネルの左右パディングは幅の外へ足されるのに、幾何計算がそれを引いていた。**関数の側を実レイアウトへ寄せて解消した**。実レイアウトの側を関数へ寄せる（モーダルに `box-sizing: border-box` を与える）道もあったが、中央モーダルが 26px 狭まって上限 48rem が主列に届かなくなり、しかも枠 1px×2 を rem で表せないため一致が 2px 残る。
- **効き方は配置で違う**（TASK-113 の実測、WebKit・Chromium とも一致）。全面シングルビューでは主列 956px に対して本文が 768px へ収まり、**最長行は 1237.0px から 746.6px へ落ちる**。中央モーダルでは 788px を 768px へ削るだけで、20px しか動かない。**併置サイドバーでは上限が掛かっても効かない** — 本文ブロックの幅が 480px で上限の 6 割に留まるためである。
- **掛ける先を 4 区画に限る**のは、Git 履歴欄の一覧とパネル自体は幅が要るからである。全面は Git 履歴の全件を読む場所（上項）であり、パネルごと絞ると一覧まで狭くなる。実測でも Git 履歴欄は全面で 956px を保っている。
- 上限が無いと、全面の 1 行は窓幅いっぱいへ伸びる。**上限を入れる前の 1 列実装では 1280×800 で 1 行が 1241.6px を走り、併置サイドバーの 2.67 倍**だった（TASK-113 の実測）。1 行が長いほど次の行の先頭を見失う。契約を**幅**で述べて文字数で述べないのは、同じ幅でも日本語と英字で 1 行に載る文字数が 2 倍近く変わるためで、文字数で書くと日本語のタスクと英語のタスクで別の契約になる。

### 2.2 切替と既定

- **切替の置き場所**: 3 配置の切替は、見出しの「閉じる ×」と同じ操作群に置く。開き方を変える操作と閉じる操作は、どちらも「この面をどうするか」であり、本文中の操作と混ぜない。
- **既定の永続**: 選んだ配置はアプリ設定（decision-13）に保存し、再起動後も保つ。セッション内だけで忘れる方式は採らない。既定の配置がどれかは切替の見た目で示す。
- **切替はアイコンのみのボタン**（doc-11 §2.4）とし、3 配置に `panel-right`（併置サイドバー）・`panel-top-dashed`（中央モーダル）・`maximize`（全面シングルビュー）を割り当てる。
- **既定印**（本書で導入）とは、3 つの切替ボタンのうち、アプリ設定に既定として保存されている配置のボタンだけが持つ目印を指す。いま画面に出ている配置を示す `aria-pressed` とは別で、次回起動時にどれで開くかを述べる。既定印は**そのボタンに引く下線**とし（画面設計案 02 の下線印。doc-12 §3）、ボタンの中へ文言を足さない — アイコンのみのボタンは可視の文言を持たないからである。下線は目にしか届かないので、そのボタンの `aria-label`・`title` には配置名に「（既定）」を併記する（doc-11 §2.4）。**既定と、いま出ている配置が一致するときは下の補助文が沈黙する**ので、そのときは併記だけが既定を述べる唯一の場所になる。
- **配置の切替も未保存入力の確認を通す**: 未保存入力がある状態で配置を切り替えるときは、閉じる・別タスクを開くときと同じ破棄前確認（6.3）を通す。同じ確認をどの経路にも適用する。
- **前後移動**: 同一レーンセル内の前後のタスクへ移る操作を、3 配置とも見出しに置く。**位置（「n / m 件」。例「2 / 3 件」）を添える** — 群の名前は添えない（理由は下項）。未保存入力があれば同じ破棄前確認を通す。
- **前後移動は未分類区画（doc-7 §2.2）にも及ぶ**。カードが並ぶ 1 かたまりであり、そこを移るのはレーンセルを移るのと同じ操作だからである。ただし**未分類区画はレーンセルではない**（doc-7 §1 がレーンセルをプロジェクト行 × 正準ステータス列の交点に限る）ので、群を語で呼ぶときは「未分類区画」と呼び、「セル」と呼んではならない。
- **群の名前を画面に刷る箇所は 2 つ**（前後移動の控え 2 つ。例「未分類区画内のひとつ前のタスクへ」）で、1 か所で決めた語を両方とも取る — 片方が「セル」、片方が「未分類区画」と刷ると、同じ 1 つの群を同じ行の中で 2 つの語で呼ぶことになる。**位置表示はこの 2 つに含まれない**（TASK-72 で 3 つから 2 つへ減らした）。見出しの 1 行目は固定表示であり 1 行に収める必要があるところ、群の名前がその行の 97px を占めていたためである（併置サイドバー 30rem・長い横断タスクID で実測）。**減らしたのは刷る箇所の数であって規則ではない** — 名前を出す控えは今も同じ 1 か所から語を取るので、未分類区画をセルと呼ぶ画面は生じない。画面設計案 02 の位置表示も「セル内 3 / 7」で群の名前を持たない（doc-12 §3）。
- **タスクがいまグリッドに出ていないときは群が定まらない**ので、位置は「スイムレーン上の位置不明」とし、出ていない理由は控えが述べる（doc-11 §5）。
- **横断タスクID のコピー**: 見出しに ID をコピーする操作を置く。Atlas には URL が無く、これがタスクを他所（コミットメッセージ・チャット）で指し示す唯一の手段だからである。全面シングルビューでは常設する。控えは**横断タスクID の右横に置くアイコンのみのボタン**（doc-11 §2.4）で、図形は `clipboard`。ID から離れた位置に置かない — 何をコピーするかを述べているのは隣の ID そのものだからである。**原文は「ID をコピー」の文言ボタンである**（doc-12 §3）ので、アイコンのみにしているのは画面設計案 02 からの意図的な逸脱にあたる（2026-08-09 に TASK-80 が記録）。逸脱の根拠は本項が既に引いている doc-11 §2.4 で、判定が足したのは「これは原文との差である」という帰属だけである。
- **コピー成功の表示**: コピーが済んだら、図形を `clipboard-check` へ替え、**成功色**を一定時間与えてからフェードさせ、元へ戻す。**成功色は `--info` とし、decision-12 の色値一式へ新しい変数を足さない**（本書で決定。TASK-72）。理由は 3 つある。(1) `--info` は doc-11 §2.1 が通知・確認の色と定めており、コピーの成功は確認そのものである。(2) 成功は図形（`clipboard-check`）が述べていて色はその繰り返しなので、色相を 1 つ増やしても新しい判別は生まれない。(3) decision-12 が収録条件の検算という費用を表示テーマの追加・変更ごとに課しており、変数を増やすとその費用も増える。**実測**（`app.scss` から計算）では収録 10 テーマとも `--info` 対 `--panel` が 5.67:1 以上・対 `--bg` が 5.86:1 以上で、非文字要素の下限 3:1 を満たす。**この画面では通知の枠（クリップボードへ書けなかったときの案内）も `--info` を使う**ので、成功と失敗が同色になる — 両者が同時に出ることはないが、色だけでは分かれないことを承知のうえで採る。成功・失敗を語で述べるのは隣の文であり、そちらが両者を分ける。

## 3. 表示項目と配置ごとの割当

ドメインモデル（doc-4）と doc-6 の出力から、次を表示する。割当表の 1 セルは次の 3 値のいずれかを取る。

- **常設** … 開いたまま置く状態で、利用者がそれを閉じる手段を持たない。
- **折畳み・既定開** … 利用者が開閉でき、開いた状態で始まる。
- **折畳み・既定閉** … 利用者が開閉でき、閉じた状態で始まる。見出しと件数だけが見える。

**「閉じられるかどうか」と「最初に開いているかどうか」は別のことである**（2026-08-05 に分けた。TASK-114）。以前の本書は「折畳み」の定義に「既定で閉じた状態」を束ねており、同じ区画を配置によって開いて始めることができなかった。画面設計案 02 は 3 図とも同じ 4 行（実装計画・実装ノート・References・状態遷移/外部エディタ）を折畳みとして描き、その開閉印の向きだけを配置ごとに変えている（doc-12 §3。**図の初期値が既定の状態である**ことは 2026-08-05 にユーザーが確定した）ので、束ねたままでは原文を写せない。「常設」の定義は 2026-08-04 の TASK-73 のまま動かさない。

**折畳みかどうかは 3 配置とも同じで、配置で変わるのは既定開閉だけである**。次項の区画見出しの体裁が述べるのは前者だけなので、体裁は区画に固定される。

## 4. Type・PR URL の分離表示

AC の要請（Type と Pull Request URL を通常ラベル・References から分離）を、次の 3 区画の分離で満たす。

- **Type ↔ 通常ラベル**: labels は読み取り層で kind ラベルと通常ラベルへ分離済み（doc-4・decision-5）。詳細画面は Type 区画に Type 値（複数併記・未設定・未知）を、通常ラベル区画に非 kind ラベルを、別区画として出す。同一の labels 一覧へ混在させない。チップの形の違い（塗り／輪郭ピル）は doc-11 §3。**原文は通常ラベルに罫線付きの区画見出しを与えず、TYPE 区画の中の小見出しとして描いている**（doc-12 §3。3 図とも）ので、別区画にしているのは画面設計案 02 からの意図的な逸脱である（2026-08-09 に TASK-80 が判定）。根拠は本章が冒頭で述べている AC の要請そのもので、小見出しは区画ではないため、原文の形では「Type と Pull Request URL を通常ラベル・References から分離する」が区画の単位で成立しない。
- **Type 値の由来は画面に出さない**: Type 値は kind ラベルと frontmatter `type` の 2 つの Type 導出元から集まる（decision-20）が、Type 区画はどちらの導出元から来た値かを区別せず、1 つの並びとして出す。両方が値を持つ Type の二重指定は、decision-5 の複数 kind と同じ見た目になる。大文字小文字を無視して同じ値になる Type 候補（同値の重複）は導出元を問わず 1 つに畳み、綴りは先に来たものを残す。
- **Type 編集の非提供**（decision-20）: Type 区画に出ている値は、どちらの Type 導出元のものも、この画面からも 6 章の編集操作からも変更できない。理由は導出元ごとに別で、kind ラベル由来の値は読み取り層が保持するのが接頭辞を外した値であり元のラベル文字列と一致する保証が無いため、frontmatter `type` 由来の値は doc-5 の操作写像に `--type` が無いためである（6 章の編集草案が持つラベルは通常ラベルだけで、画面はこの 2 つの理由を Type 区画に述べる）。したがって Type の二重指定を解消したい利用者は Backlog CLI か管理ファイルの手編集による。編集経路を持つかどうかは m-3 の判断。
- **Pull Request URL ↔ References**: References の URL のうち PR URL 抽出規則（doc-6）で Pull Request と判定した URL を Pull Request 区画へ、残りを References 区画へ分ける。1 タスクに複数 PR があれば全て並べる（doc-6）。
- 分離は表示上の区画分けであり、正本の labels・references を書き換えない。抽出・分離は読み取り済みデータへの後処理である。

## 5. Git 履歴欄

Git 履歴欄は doc-6 の出力をまとめて見せる。

- **コミット一覧**: doc-6 のコミット検索結果（識別子・要約・日時・作者、新しい順）。0 件のときは「対応コミット無し」を示す（remote 不在・ルート不在との区別は TASK-13）。
- **Pull Request との関連**: `git_remote_present` が真かつ remote ホスト種別を判別できた場合、doc-6 のコミット・PR 関連解決結果を用い、各コミットに関連 Pull Request を紐づけて示す。remote 非対応・参照不能時は、コミット一覧と Pull Request 区画（4 章）を各々独立に出し、関連が解決できないことを「対象不在」と区別して示す（doc-6・具体は TASK-13）。
- **配置ごとの粒度**（3 章の割当表）: 配置ごとに、コミット一覧と関連 PR を次の粒度で出す。
  - **併置サイドバー**: コミット件数を 1 行、関連 PR を 1 行、そして全面表示への導線。
  - **中央モーダル**: 直近 2 件と残り件数、関連 PR を 1 行、そして全面表示への導線。
  - **全面シングルビュー**: 全件と、関連解決の状態を原因ごとに書き分けたもの（解決済み／remote 不在／種別判別不能／突き合わせ不能、および Pull Request ごとの 参照不能・対象外）と、その原因が解消できるかどうか。
- **参照不能の原因は 4 つに分けて出す**（decision-14・decision-19）: 起動不能（参照手段を起動できない）は導入で解消でき、参照不正（References の URL から座標を得られない）は URL の修正で解消でき、照会失敗（照会が走って成功しなかった）は認証・権限・PR の不在・ネットワークのどれかを終了状態から分けられないため解消経路を約束しない。4 つ目の **照会期限到達** とは、gh 照会期限（1 回の照会で応答を待つ上限の長さ、decision-19 で 30 秒）に達したため Atlas が照会を終了させ、その Pull Request のコミット集合を得ないまま終えたことを指す。これは Atlas 自身が起こした事象なので照会失敗と分かれ、再取得で結果が変わり得る旨を書く。
- **狭い 2 配置が省くのは、状態そのものではなく原因ごとの説明である**。関連解決の状態は「関連が無い」ではなく「今は確かめられない」を意味するため、伏せると誤解を生む。よって狭い配置でも状態は 1 行で述べ（どの原因かを短く含む）、原因ごとの書き分けと解消の手掛かりは全面へ委ねる。省いた配置には、全面で読める旨の導線を必ず添える。
- **関連 PR は件数で出す**: 関連解決の参照手段（decision-14）が入ったので、狭い 2 配置は割当表どおり件数（関連 PR m 件）を出す。**m** は、このタスクのローカルコミットと共有コミットを持つ Pull Request の数である。照会できなかった Pull Request があるときは、件数だけでは「関連が無い」と読めてしまうため、同じ 1 行に原因（参照不能・対象外）とその件数を添える。
- **突き合わせ不能のときは件数を出さない**: **突き合わせ不能**とは、ローカルコミット一覧が得られていないため Pull Request のコミット集合と突き合わせる相手が無く、関連 PR の件数を言えない状態を指す（Git 対象不在・Git 読取不能のとき）。このとき参照手段は呼ばず、件数の代わりに突き合わせ不能である旨を出す。0 件と書けば「関連が無い」と読まれるためである。
- Git 履歴欄は読み取り専用であり、Git リポジトリを書き換えない。

## 6. 詳細からの編集操作

詳細画面からの編集（title・description・status 変更、ラベル/AC 増減、AC チェック、AC 差し替え、priority・milestone・assignee・dependencies 変更、References 編集、実装計画・ノート編集など）は、すべて Backlog 更新アダプター（doc-5）の更新操作として発行する。詳細画面は操作の入口であり、管理ファイルを直接書き換えない。各編集は doc-5 の操作写像に対応づき、利用者入力は引数配列要素として渡す（シェル非連結、doc-5）。Pull Request・Git 履歴は参照系であり、詳細画面からの編集対象にしない。ただし PR URL の登録は References 編集として扱い、**References 非空全置換**（doc-5 の `task edit --ref`。既存参照を含めて渡し、その非空集合で置き換える）に帰着させる。参照を空にする（最後の 1 件を消す）操作は v1.48.0 の CLI では行えないため、GUI では最後の参照削除を無効化し、必要なら外部エディタ経路へ案内する（doc-5 の 3 章）。dependencies 変更も同様に **非空全置換**（doc-5 の `task edit --depends-on`。既存依存を含めて渡し、その非空集合で置き換える）に帰着させ、依存を空にする（最後の 1 件を消す）操作は v1.48.0 の CLI では行えないため、GUI では最後の依存削除を無効化し、必要なら外部エディタ経路へ案内する（doc-5 の 3.1）。assignee の設定・変更は、GUI 上ではこの画面だけが扱う（doc-5 §3、TASK-57 の決定）。欄は 1 件で、`task edit -a` は最後の 1 値だけを採り、frontmatter の assignee 一覧を渡した 1 件だけの一覧へ置き換える（**assignee の 1 件化**とは、この置き換えで既存の複数 assignee が 1 件になることを指す。doc-5 §3 の実測）。したがって複数 assignee のタスクでは、保存すると 1 件になることを保存前に示す。空欄は「変更しない」であり解除ではない: `-a ""` は終了コード 0 で何も変えないため（doc-5 §3.1）、解除が要る場合は外部エディタ経路へ案内する。AC 本文の差し替えは、単一オプションではなく **複合操作**（既存全 index の `--remove-ac` ＋ 新項目の `--ac` ＋ 完了の `--check-ac` を 1 回の `task edit` で渡す。doc-5 の 3 章）で行い、1 項目単位の AC 増減・チェック（既存の `--ac`／`--remove-ac`／`--check-ac`）とは別操作として区別する。

以下は、元要望中核である GUI 編集操作の具体を定める。

### 6.1 編集部品（複数行・選択・置換・全選択）

- **編集部品**は、複数行のテキスト編集（description・実装計画・ノート・AC 本文など複数行になりうる項目）を担う。素の `textarea` を基本形とし、`textarea` へ Ace を昇格させる（serenebach の vendored + `textarea` フォールバックのパターンを流用）。Ace の読込に失敗しても `textarea` のまま編集不能にしない。
- **複数行入力**: 改行を含む入力を保持し、保存時は改行を含んだ 1 文字列として doc-5 の引数配列要素へ渡す（シェル非連結のため改行を含んでも安全、doc-5）。
- **マウス選択・置換・全選択**: 範囲選択、選択範囲の置換（入力・貼り付けで置き換え）、全選択（`Cmd/Ctrl+A`）は編集部品の標準機能に委ねる。`textarea`・Ace のいずれでも同じ操作ができることを要件とする（Ace 昇格で操作が変わらない）。

### 6.2 IME 変換確定中の Enter と保存の切り分け

「Enter」は 変換確定・改行・保存 の 3 つを取り違えやすい。本設計では **Enter を保存に割り当てない**ことでこれを分ける。

- **変換確定 Enter**: 日本語 IME の変換中に押す Enter は、変換候補の確定に使う。IME の composition（`compositionstart`〜`compositionend`）中は Enter を編集部品の確定処理へ渡さず、IME に消費させる。変換確定を保存や改行の契機にしない。
- **改行 Enter**: 変換していない状態で複数行フィールドに押す Enter は、改行を挿入する。保存の契機にしない。
- **明示保存**: 保存は Enter とは別の独立操作に固定する。保存ボタン、または修飾キー付きショートカット（例 `Cmd/Ctrl+Enter`）とし、素の Enter とは別キーにする。これにより変換確定・改行・保存が同じ Enter で衝突しない。この規則は画面に文言として示す（保存が明示操作であることを、押す前に読める状態にする）。

### 6.3 明示保存・キャンセル

- **編集セッション**: 編集開始から保存/キャンセルまで、**未保存入力**を画面側に保持する。入力の随時自動保存はしない（明示保存）。
- **保存**: 明示保存操作で、未保存入力を doc-5 の操作写像に沿った 1 回以上の CLI 更新として発行する。成否・失敗表示・成功後の再読込は doc-5 に従う。CLI 失敗時は詳細画面の表示を変えず失敗理由を示し、未保存入力を保持したまま再試行できる。成功時は再読込契機で当該タスクを読み直して詳細を更新し、編集セッションを終える。
- **キャンセル**: 未保存入力を破棄し、編集セッションを終える。破棄前に未保存入力があれば確認する（誤破棄の防止）。管理ファイルには何も発行しない。
- **破棄前確認を通す経路**: キャンセル・閉じる・別タスクを開く・前後移動・詳細配置の切替。文言は 5 経路で同じものを使う。確認は上部帯の ①（doc-7 §5.3）として出す。本節が定めるのは編集セッション（本項冒頭）の未保存入力についてであり、5 という数はその経路の数である。モーダル（doc-11 §7 の被せ層）が持つ未保存入力の破棄前確認は、**同じ問いの文**を使うが、**進む側の答えだけは「破棄して閉じる」**であり（本節の 5 経路は行き先が同じでないので「破棄して続ける」と広く言う。モーダルの経路はどちらもその層を閉じることに限られる）、どの経路が確認を通るかも置き場も doc-11 §7 が定める（あちらは上部帯を覆うため、確認をモーダルの中に出す）。

### 6.4 未保存入力と外部変更（doc-9 競合）

編集セッション中に、同じタスクファイルが外部で変わる（doc-9 の外部変更）ことがある。

- **編集中の継続検出**: 編集セッション中に外部変更を検出しても、未保存入力を勝手に破棄・上書きしない（doc-9 の「編集中は入力を奪わない」）。外部で変わったことを知らせるにとどめる。
- **保存時の更新前競合**: 明示保存の実行時に doc-9 の更新前競合検出を通す。保存操作時点で読取版指標がずれていれば、CLI を起動せず競合として提示し、(i) 最新を読み直してやり直す、(ii) 未保存入力を最新に対して再適用する、のいずれかへ導く（doc-9 の 5 章）。古い版への上書きはしない。
- **best-effort の限界**: 更新前競合検出は best-effort であり、照合後競合窓での上書き喪失は防げない（doc-9 の 4.1）。詳細画面はこの限界を、防げる競合の未然提示と区別して扱う（doc-9 の 5 章）。

### 6.5 保存区分別の編集可否

doc-7 では active だけでなく draft・completed・archive のカードからも詳細画面を開ける。一方 v1.48.0 では、completed・archive 内の TASK-ID への `task edit` は `Task … not found`（終了コード 1）になる（実測）。詳細画面の編集操作は、対象タスクの保存区分（doc-4 の 3.4）別に定める。

- **active**: 本章の通常編集（`task edit` 系）と、状態遷移 `task demote`／`task archive`／`task complete`（いずれも doc-5 の操作写像）。`task archive` は status を問わず実行できるが、`task complete` は status が `Done` のときのみ成功する（非 Done では「is not Done」で失敗、実測）。GUI は `task complete` を Done のタスクに限って能動化し、対象外では理由付きで無効化する。
- **draft**: `draft promote`／`draft archive` のみ（doc-5 の 3.3）。内容編集は GUI に出さず、必要なら外部エディタ経路（7 章）へ案内する。
- **completed・archive**: CLI による内容編集は提供しない（`task edit` が not found になるため）。読み取り専用とし、内容を変えたい場合は外部エディタ経路（7 章）へ案内する。

保存区分ごとに、詳細画面は提供する操作だけを能動化し、提供しない操作は理由が分かる形で無効化する（doc-5 の縮退提示に準ずる。無効化の表し方は doc-11 §5）。編集可否は表示（どの区画を出すか）とは別で、参照系（Type・References・Pull Request・Git 履歴）はどの保存区分でも読み取り表示する。**状態遷移は 5 件とも実行前確認を通る**（doc-11 §12。2026-08-11 に二度押し確定から替えた。TASK-137）。控えの語には `…` を付ける（`draft へ差し戻す…`。同 §12 の ②）。**5 件を「逆操作の無いもの」で絞らないのは、押す前の状態へ戻せるものが 1 件も無いためである**（2026-08-11 に `backlog task --help`・`backlog draft --help` で実測）: どちらのサブコマンド一覧にもアーカイブと完了整理を戻す操作が無く（`task` は create・list・edit・view・archive・complete・demote、`draft` は list・create・archive・promote・view だけ）、`task demote` と `draft promote` は互いの行き先へ戻せるものの id を採番し直すので、押す前の TASK-ID のタスクには戻らない。

## 7. 外部エディタ経路

複数行・大量の編集を利用者の使い慣れた道具へ逃がすため、タスクの管理ファイルを外部エディタで開く**外部エディタ経路**を設ける。

- **管理ファイルのパスを示す**: この区画は対象タスクの管理ファイルの絶対パスを表示する（TASK-72 で見出しから移した。3 章）。開く操作の隣がパスの置き場である — 何を開こうとしているのかは、開く前に読めていなければならない。
- **開く対象と方式（直接開く方式）**: 対象タスクの管理ファイルそのもの（`<backlog_root>/…/task-….md`）を、利用者の外部エディタで開く（`$EDITOR`／OS の関連付け起動）。書くのは外部エディタ（利用者）であり、Atlas は管理ファイルを書かない。したがって doc-2 の「Atlas 自身は管理対象 Markdown を書き込まない」不変は破らない。ただしこの経路は、管理対象 Markdown に Backlog CLI を通さず届く例外経路である（doc-2・decision-2 の write 契約の例外）。Atlas 自身が書かない不変は保つが、更新経路は CLI 媒介の操作写像（doc-5）に限られず、利用者の直接編集は CLI のスキーマ保護（frontmatter 構造・オプション検査）を受けない（難点は下項）。
- **起動指定の解決順**: アプリ設定（decision-13）の外部エディタ指定があればそれを使い、無ければ `$VISUAL`／`$EDITOR` を使う。アプリ設定に置くのは、環境変数がデスクトップアプリのプロセスへ届かない起動経路（Finder・ランチャーからの起動）があり、環境変数だけでは指定手段が無い利用者が生じるためである。いずれの指定も引数配列として渡し、シェル文字列へ連結しない（AGENTS）。
- **書き戻し（継続検出が動いている場合）**: 外部エディタでの保存は doc-9 のファイル監視（外部変更検出）が拾い、再読込でドメインモデルへ反映する。エディタの終了検知は不要（監視が変更を拾うため）。
- **書き戻し（継続検出が止まっている場合）**: 継続検出は、監視の失敗でも、アプリ設定で切った場合でも止まる（doc-9 §3.1）。止まっている間は外部エディタの保存が自動では届かないため、この経路は次の 2 つを満たす。
  - **開く前に伝える**: 起動の直前に、この保存は自動反映されないこと、反映には当該ルートの再読込が要ることを、frontmatter の注意（下項）と併せて示す。エディタを開いてから初めて知る形にしない。
  - **戻ってきたときに読み直せる**: 詳細画面から当該ルートの再読込を発行できるようにする（レーンヘッダ行の再読込（doc-7 §2.3）と同じ操作）。エディタから戻った利用者が、画面を離れずに反映まで到達できることを要件とする。
  監視が動いている場合との違いは、自動で届くか手動で読み直すかだけで、Atlas が管理ファイルを書かない不変（doc-2）と競合の扱い（下項）は変わらない。
- **doc-9 競合との関係**: 外部エディタ経路の編集も doc-9 の外部変更として扱う。GUI 内の編集セッションが開いたまま外部エディタでも編集した場合は、6.4 の扱い（編集中の継続検出・保存時の更新前競合）に従い、未保存入力と外部変更の二重取り込みを避ける。**未保存入力があるときは、起動そのものが実行前確認を通る**（doc-11 §12。2026-08-11 に二度押しから替えた。TASK-137）。問うているのは書き込みの可否ではなく二重取り込みなので、層の中で使う文はこの区画が出しているものと同じにする（同じ事柄を 2 通りに述べない。doc-11 §7 が破棄前確認で取った判断と同じ）。**未保存入力が無いときは問わない** — 毎回問うと 2 打目が反射になり、この注意が要る場合にだけ立つという性質が失われる。控えの語尾の `…` も、問うときだけ付く（doc-11 §12 の ②）。
- **難点と受け方**: 直接開く方式は frontmatter が利用者へ露出し、構造化フィールド（id・status・labels 等）を壊しうる。開く前に「frontmatter を壊すと不整合表示になる」旨を示し、壊れた場合は doc-4 の不整合表示で受ける（破棄しない）。
- **却下した対比案（一時ファイル書き戻し方式）**: 本文だけを一時ファイルへ抽出して編集させ、終了検知後に CLI 更新で書き戻す方式は、frontmatter を隠せる利点はあるが、(a) エディタの終了検知が要る、(b) CLI が設定できるフィールドにしか書き戻せず任意編集の価値を削ぐ、ため採らない。frontmatter 露出は上記の注意表示と不整合表示で扱う。
