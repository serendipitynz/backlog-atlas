# Backlog 更新アダプター 設計

TASK-9 の設計。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は decision-1（Tauri/Rust）・decision-2（読み取りは Backlog 管理ファイルの直接解析、更新は Backlog CLI へ委譲）・doc-3（プロジェクト台帳）・doc-4（読み取り層）。

**実測基準版**: 本書が「実測」と述べる記述は Backlog CLI v1.50.1 で確かめたものである（decision-7 の最低バージョン要件、decision-27）。個々の記述は版を名乗らない — 名乗るのは、2 つ以上の版の違いそのものを述べる版差記録だけである。最低バージョン要件が上がったら、本行の版と本書の実測記述を併せて測り直す。

## 1. 用語

- **更新操作** … タスク・文書・マイルストーンの内容を変える Atlas 上の 1 意図（作成・更新・status 変更など）。
- **操作写像** … 更新操作を写像先へ対応づける定義。写像先は原則 Backlog CLI のサブコマンドと引数配列であり、直接書き込み操作だけが例外である。
- **直接書き込み操作** … 更新操作のうち、写像先が Backlog CLI のサブコマンドではなく Atlas 自身のファイル書き込みであるもの。現在の唯一の実例は**マイルストーン説明の更新**で、それを認めた根拠・範囲・条件は decision-21 が定める。他の更新操作を直接書き込み操作にできるのは decision-21 の 3 条件をすべて満たす場合だけで、「CLI に手段が無い」ことは単独では理由にならない（3.1）。
- **CLI 失敗** … Backlog CLI プロセスが非ゼロ終了コードで終わる、または起動に失敗する事象。
- **再読込契機** … CLI 成功による管理ファイル変化を、読み取り層で読み直すべき時点。

## 2. 位置づけと責務

**Backlog 更新アダプター**（doc-2）は、Atlas の更新操作を、対象プロジェクトを作業ディレクトリとする Backlog CLI 呼び出しへ変換する部分である。読み取り層（doc-4）と経路を分け、次を担う。

1. 更新操作を受け取り、対象プロジェクトと引数を確定する。
2. 操作写像により、Backlog CLI のサブコマンドと引数配列を組み立てる。
3. 対象プロジェクトのプロジェクトルート（doc-3 の台帳エントリ）を作業ディレクトリとして CLI を実行する。
4. 終了コードと出力から成否を判定し、成功時は再読込契機を発火する。

アダプターが管理対象 Markdown を書き換えるのは、直接書き込み操作（1 章）としてそう定めたものだけである。それ以外は Backlog CLI が書き換え、アダプターはその呼び出しに徹する（decision-2・AGENTS）。正本は各プロジェクトの管理ファイルに残る。直接書き込み操作も、書く範囲・書き方（一時ファイル置換）・通す関門（更新前競合の検出）が decision-21 で閉じられているので、アダプターがファイルへ書く場面は列挙できる形に保たれている。

## 3. 操作写像

対象操作ごとに、Backlog CLI のサブコマンドと引数配列を定義する。引数はすべて配列要素として渡し、シェル文字列へ連結しない（4 章）。CLI の動作確認済み範囲は decision-7 の最低バージョン要件が定める（decision-2 のサポート範囲に準ずる）。**表の「サブコマンド」列に CLI 以外が現れるのは直接書き込み操作の行だけである**（1 章。現在 1 行）。

- **作成時に渡せる引数（2026-07-29 訂正）**: 本書の初版はタスク作成を title・description・status・labels・priority・milestone・AC に限ると記述していたが、`task create` は `-a`・`--plan`・`--notes`・`--ref`・`--depends-on` も受け取り、作成された管理ファイルへ保存する（一時プロジェクトで作成し `task view` で全項目の保持を確認）。上表の作成行はこの実測に合わせている。**GUI が作成フォームで受け取る範囲は、CLI が受け取れる範囲より狭くてよい**が、その場合に書く理由は「CLI に手段が無い」ではなく製品判断である（doc-10 §7）。**作成時に渡す範囲**（Atlas が `task create` の 1 回の呼び出しへ載せる項目集合。CLI が受け取れる範囲とは別）は、TASK-57 で title・description・status・labels・priority・milestone・AC に確定した。実装計画・ノート・参照・依存を作成時に出さないのは、作成時点で要るのは識別と分類であり、これらは作業の進行に伴って増える項目で編集経路（doc-8 §6）を持つためである。境界の型（`update.rs` の `TaskCreate`・`manage.ts` の `TaskCreateInput`）もこの範囲に合わせる。
- **assignee の写像（2026-07-29 訂正、2026-08-12 再訂正）**: `task create` と `task edit` はいずれも `-a` を受け取るが、**渡した値の読み方が違う**のは v1.49.3 までで、**v1.50.1 では両方がカンマで区切る**（実測。TASK-151 が非対称を測り、TASK-153 がそれが消えたことを測った。版差記録は 3.5）。`task edit -a "dave,erin"` はどちらの版でも `dave`・`erin` の 2 件を書き、`task create -a "dave,erin"` は v1.49.3 では `dave,erin` という 1 件、v1.50.1 では 2 件を書く。**Atlas はこの差に触れない** — 作成フォームは `-a` を出さない（3.2、doc-10 §7）。編集側は各要素の前後空白を落とし、空要素と重複を捨て、最初に現れた順で frontmatter の assignee 一覧を**置き換える**（`-a "bob,alice,bob"` は `bob`・`alice`、`-a "a,,b"` は `a`・`b`）。`-a` を複数回渡すと最後の 1 値だけが残る点は両側で同じである。**本書は初版から 2026-08-12 まで、この行に作成側の挙動（分割しない）を編集側の挙動として書いていた** — 初版は作成行・編集行のどちらにも `-a` を書いておらず（そのため `TaskEdit` 型にも assignee が無く、GUI から assignee を設定・変更する経路が存在しなかった）、2026-07-29 にその穴を閉じたときの実測が作成側だけだったためである。**TASK-57 は編集側で閉じると決めた**: assignee を設定・変更できる GUI 上の場所はタスク詳細の編集セッション 1 箇所とし（doc-8 §6）、`TaskEdit` に assignee を持たせて `--assignee` へ通す。作成フォームには出さない（作成時にだけ設定できて後から変えられない経路を作らないため。doc-10 §7）。**したがって assignee は References・依存と同じ全置換であり、GUI は集合として扱う**: 読み取り層が持つ現在の assignee を基に、追加・削除後の全集合を渡す。**空集合にもできる**（3.1。3 件のうちこれだけは `--clear-*` フラグが無いので空の値を送る、3.5）。**1 件の assignee 名にカンマを含めることはできない** — 編集側 `-a` がそこで分けるためで、GUI は保存を無効化して理由を述べる（doc-11 §5。`-l <labels>`・`--tags <tags>` に同じ規則がある）。**「assignee の 1 件化」は本書から廃した語である** — 複数 assignee のタスクを編集側で保存すると 1 件になるという記述は、原因が CLI の制約ではなく GUI の欄が 1 値だったことにあり、欄を集合へ改めた時点で現象そのものが起きない。
- **`-s <status>` の検査**: `-s` は対象プロジェクトの `config.yml` の `statuses` に宣言済みの値だけを受け取る。未宣言の値は `Invalid status: <値>. Valid statuses are: …` を出して終了コード 1 で失敗する（実測）。省略時は `default_status` が入る。正準ステータス列名（decision-4）と宣言済み status は一致するとは限らない点に注意する。`backlog init --defaults` が宣言するのは `To Do` / `In Progress` / `Done` の 3 つで、`In Review` は宣言されない（実測）。列から作成時の status を決める規則は doc-7 §4.1。
- 操作写像は「1 更新操作 → 1 サブコマンド呼び出し」を基本とする。1 画面操作が複数フィールドを同時に変える場合は、`task edit`・`doc update` の複数オプションを 1 呼び出しにまとめられる範囲でまとめ、まとめられない操作（別サブコマンドが要る）だけ複数回に分ける。
- **参照の全置換（`--ref`）**: `task edit --ref` は、渡した参照集合で**全置換**する（既存へ追加ではない）。アダプターは、読み取り層（doc-4）が持つ現在の参照を基に、追加・削除後の**全集合**を組み立てて渡す。1 件だけ加える PR URL 登録（doc-8）でも、既存参照を含めた全集合を `--ref` へ渡す。**空集合にするときは `--clear-refs` を出す**（3 章の表。`--ref ""` でも消えるが、上位版で沈黙無変更へ戻ったときに成功として報告されるので、フラグの形を採る — 3.5）。**最後の 1 件を消す操作は v1.50.1 から提供する**（v1.49.3 までは CLI に手段が無く提供していなかった）。`--content`（`doc update`、本文全置換）も単一オプションで全置換する。
- **依存の全置換（`--depends-on`）**: `task edit --depends-on` は、渡した集合でカンマ区切り全置換する（既存へ追加ではない）。**空集合にするときは `--clear-deps` を出す**（`--ref` と同じ理由。3 章の表、3.5）。加えて各値に `task_prefix` を前置して実在検証するため、`none` 等のセンチネルは不在エラーになる。**最後の 1 件を消して依存を空にする操作は v1.50.1 から提供する**（v1.49.3 までは `--depends-on ""` が終了コード 0 で何も消さず、提供していなかった。3.1）。
- **AC の差し替え（複合）**: 完了状態を伴う AC 全体の差し替えは単一オプションでは行えない（`--acceptance-criteria` は全置換するが `--check-ac` と併用できない、3.1）。AC 全体を置き換えるときは、1 回の `task edit` に既存全 index の `--remove-ac`・新項目の `--ac`・完了の `--check-ac`（差し替え後の新 index を指す）を併せて渡す。AC の 1 項目単位の増減・チェックだけを行う場合は、`--ac`／`--remove-ac`／`--check-ac` を単独で使い、差し替えとは使い分ける。

### 3.1 CLI に存在しない更新操作

動作確認版の CLI を実地確認した（`doc --help`・`milestone --help` と各サブコマンドの `--help`）。次の操作は CLI に対応サブコマンドが無い。

- **マイルストーン説明の更新**: `milestone` には `update`/`edit` サブコマンドが無い。説明（description）は `milestone add -d` で作成時にのみ設定でき、作成後に説明だけを更新する CLI 経路は無い。`rename` は title（名称）の変更に限られ、説明は変えない。**この 1 件だけは、CLI に手段が無いまま Atlas が提供する** — decision-21 が直接書き込み操作として認めたためで、写像は 3 章の表にある。以下の各項とはここで扱いが分かれるので、CLI に手段が無いことを理由に非提供と書いてある箇所を読むときは、この行が例外であることを併せて読む。
- **マイルストーン任意フィールドの編集**: 説明を除き、作成後に変更できるのは名称（`rename`）・存在（`remove`/`archive`）・紐づくタスクの扱い（`remove --task-handling`）に限られる。frontmatter を直接書き換えることは decision-21 の条件 2 が禁じている。
- 文書側は `doc update` が title・本文（`--content` は全置換）・type・path・tags を更新でき、部分更新（本文の一部差し替え・追記）や frontmatter の任意フィールド更新には対応しない。
- **完了状態を伴う AC 全体差し替えを単一オプションで行うこと**: `--acceptance-criteria` は既存 AC を全置換する（実測。v1.47.1 では名称に反して追加動作だった。TASK-58 で測り直した版差）。ただしこのオプションは `--ac`・`--remove-ac`・`--check-ac`・`--uncheck-ac` と併用できず、併用すると `Cannot combine --acceptance-criteria with …` を出して終了コード 1 で失敗する（実測）。差し替え後の項目のどれが完了かは `--check-ac` でしか表せないため、**完了状態を伴う差し替えは単一オプションでは行えない**。AC 全体の置き換えは引き続き、1 回の `task edit` に既存全 index の `--remove-ac`・新項目の `--ac`・完了の `--check-ac` を併せて渡す複合操作で行う（3 章の表）。複合は 1 呼び出しなので差し替えが分割されない利点も併せ持つ。
- **参照・assignee・依存 を空集合にする操作は、3.5 の版差記録の日付から CLI に手段がある。** 本節がこの 3 件を非提供として数えていたのは v1.49.3 までで、いまは操作写像（3 章）に載っている。3 件の書き方が揃っていないのは意図であり、理由は 3.5 が持つ。
- **1 件の値にカンマを含める操作**: 値をカンマで分けて読むオプションでは、1 件のつもりの値がその位置で分かれる。**アダプターが出せる 27 個を分類した結果、分けるのは 7 つである**（7 つとも実測）: `task create -l`、`task edit -a`／`--add-label`／`--remove-label`／`--depends-on`／`--ref`、`doc update --tags`。`task edit --add-label "a,b"` は labels に `a`・`b` の 2 件を書き、各要素の前後空白を落として空要素を捨てる（`" c , d "` は `c`・`d`、`"e,,f"` は `e`・`f`）。**数える軸は CLI の読み方であって、アダプターがカンマ連結しているかではない** — `--ref` は参照ごとに繰り返して渡すので連結は 1 か所も無いが、CLI は各値を分ける。**繰り返し可であることはどちらの側の根拠にもならない**: `--ac` は繰り返せてカンマを保ち（`--ac "first,second"` は 1 件）、`--ref` は繰り返せて分ける（どちらも実測）。**残る 20 個は分けないか、利用者の打った文字を運ばない。** **分けないことを測ったのは 13 個である**（本文・title・`--path`・`--milestone`・`--ac` はカンマを保ち、`--status`・`--priority`・`--type` は固定候補なので終了コード 1 で拒み、`--reassign-to` はカンマを含むマイルストーン名をそのまま解決した — Atlas 自身がその名前を作れるので測った）。**残る 7 個は測定ではなく構成による分類である**（AC の index 3 つと `--task-handling`・`--no-update-tasks`・`--clear-refs`・`--clear-deps`。値を Atlas が組むか、そもそも値を持たないので、CLI がどう読もうとカンマは届かない）。**この 7 個に「実測」と書かない** — 分類は同じ場所に落ちるが、測っていないものを測ったと述べることになる。GUI は発行前に拒み、理由を述べる（doc-11 §5）。
- **カンマを含む既存のラベルを消す操作**: `--remove-label "x,y"` は、labels に `x,y` を 1 件持つタスクに対して終了コード 0 と `Updated` を出しながら 1 件も消さない（実測。値を `x`・`y` の 2 件へ分けたうえで、そのどちらもタスクに無いため。存在しないラベル名を渡したときと同じ結末であり、`-a ""`・`--ref ""`・`--depends-on ""` と同型の沈黙無変更である）。**この場合を持つのは `--remove-label` だけである** — `-a`・`--depends-on`・`--ref`・`--tags` は渡す集合か 1 件ずつの値で全置換するので、カンマを含む既存要素は渡す値から外せば消え、引数のどこにもカンマが現れない。`-l` は作成時なので消す対象がそもそも無く、`--add-label` は追加なので削除側の場合を持たない。**ラベルだけが増減で発行され、消す値そのものが引数になる。** ここは数えずに名指しする — 7 つから 1 つ引いた 6 つと書くと、その 6 つに `--add-label` と `-l` が入り、直後の理由がそのどちらにも当たらない。GUI は発行前に拒み、理由を述べる（doc-11 §5）。**カンマを含むラベルは CLI では書けないので、この状態は管理ファイルの手編集から来る** — 一度書かれると CLI はそれを保つ（実測。別のラベル操作を通すと `- 'x,y'` と引用して保存し直す）。

**マイルストーン説明の更新を除き**、これらは decision-2 の「更新は Backlog CLI へ委譲」を保つ限り、CLI が提供するまで Atlas も提供しない。CLI 版が上がって対応サブコマンドが増えた場合に操作写像へ追加する（3 章末の版検査に従う）。**「CLI に手段が無い」ことは、それだけでは直接書き込み操作にする理由にならない** — decision-21 の 3 条件（CLI がその値を書く経路を現に持つ・frontmatter とファイル名に触れない・書く範囲が読み取り層の読む範囲と同一）をすべて満たすものだけが通る。上の各項でこれを満たすものは無い: ラベルと文書のタグはいずれも frontmatter であり（条件 2 に反する）、文書の削除はファイルそのものを消す操作で、範囲という形を持たない。**参照・依存・assignee はこの数え上げから外れた** — 条件 2 に反していたのは同じだが、CLI が現に書けるようになったので直接書き込みを検討する場面自体が無くなった（3.5）。`milestone update` 相当が CLI に現れた場合は、説明の更新を CLI へ戻す（decision-21 の後続への影響）。

**参照・assignee・依存 の 3 件の無効化は、2026-08-22 に無くなった**（TASK-153。3.5）。**2026-08-17 の改訂（TASK-192）はその 3 件の理由文が外部エディタ経路（doc-8 §7）を名指ししないと定めたもので、いまは理由文そのものが無い** — 無効化が消えたので述べる不可も無い。**外部エディタ経路は残っている**（doc-8 §7 の区画はどの保存区分でも同じ画面に出る）。**TASK-192 が定めた規則は生きている** — 掛かる先が 6.5 の draft・completed・archive の読み取り専用だけになった（doc-8 §6）。

### 3.2 GUI が提供する更新操作の範囲

上記制約から、タスク詳細（doc-8）・マイルストーン操作の GUI が提供する更新操作を次に限る。

- **タスク**: 3 章の `task create`/`task edit` 写像に載る操作（title・description・status・ラベル増減・AC 増減/チェック・AC 差し替え・References 全置換・priority・milestone・assignee・dependencies・実装計画/ノート等）。**Final Summary・Definition of Done・Comments の更新はここに含めると決まっており、まだ載っていない**（下項）。assignee は編集側だけが扱う（3 章）。assignee・References・dependencies の全置換は既存値を含めた全集合を渡す（3 章。空集合化は 3 章の表が持つ 3 通りの書き方で行う、3.5）。AC 差し替えは複合操作（`--remove-ac`＋`--ac`＋`--check-ac` を 1 呼び出し、3 章）。
- **draft**: 状態遷移（`draft promote`／`draft archive`／`task demote`）のみを提供し、draft の内容編集は GUI に出さない（3.3）。
- **active の状態遷移**: active タスクには内容編集に加え、`task demote`（→ draft）・`task archive`（→ `archive/tasks`、status を問わず可）・`task complete`（→ `completed`、status が `Done` のときのみ可）を提供する。`task complete` は非 Done では失敗するため（5 章）、Done のタスクに限って能動化する。
- **保存区分別の可否**: 上記タスク操作は保存区分（doc-4 の 3.4）が active のタスクに適用する。completed・archive のタスクは `task edit` が `not found`（終了コード 1）になるため、CLI による内容編集を提供しない（詳細画面での可否は doc-8 の 6.5）。
- **文書**: 作成（title・type・path）と更新（title・本文全置換・type・path・tags）。本文は全置換のみで、部分編集は「編集後の全文を `--content` で渡す」に帰着させる。
- **マイルストーン**: 作成（名称・作成時の説明）・**説明の更新**・改称（名称）・削除・アーカイブ。**説明の更新は直接書き込み操作である**（3 章の表、decision-21）。GUI は選んだマイルストーンの説明を編集して保存できる欄を持ち、空にすることもできる。**行頭が `##` の行を含む説明は入力検査で拒む** — 読み取り層は次の `##` で説明の本文範囲を切るので、そのまま許すと保存した文字列の一部が次の読み込みで画面から消える（doc-10 §6）。frontmatter の項目（title を含む）を直接書き換える欄は設けない。
- **Final Summary・Definition of Done・Comments の更新は提供すると決まっており、その回はまだ来ていない**（2026-08-17、オーナーの判断。TASK-185）。**CLI には 3 つとも手段がある** — `task edit --final-summary` / `--append-final-summary` / `--clear-final-summary`、`--dod` / `--check-dod` / `--uncheck-dod` / `--remove-dod`、`--comment` / `--comment-author`（実測）。**したがって 3.1 の「CLI に手段が無い」はここに当たらず、この段階で提供していない理由は製品判断である** — 3 つは編集セッション（doc-8 §6）を 3 系統ぶん増やし、Definition of Done は AC と同形なので完了状態を伴う全体差し替えの複合操作まで要り、Comments は CLI が追記しか持たない（1 件を消す経路が無い）。**TASK-185 は読み取りと表示だけを入れ、更新は TASK-189 が引き取る。** 引き取り先を台帳に置いてある — 置かないと、この段落だけが約束を持つことになる。
- 管理対象 Markdown を GUI から直接書き換えない境界（doc-2）は、直接書き込み操作として列挙したものを除いて保つ。**CLI に無い操作を、その都度の判断で直接書き込みへ回さない** — decision-21 の 3 条件を満たすことを確かめ、doc と decision に書いてから足す。
- 各サブコマンドの正確なオプション名は、動作確認した CLI 版の `--help` を基準に固定する。版が上がってオプションが変わる場合は、操作写像を版ごとに検査し、未知オプションは実行前に検知して当該操作を拒否する（縮退。5 章）。
- taskId は当該プロジェクト内の TASK-ID（横断タスクID の右辺）を用いる。アダプターは対象プロジェクトを作業ディレクトリに固定するため、slug 前置は不要（doc-3 の 5.3）。

### 3.3 draft の更新操作範囲

draft（doc-4 の保存区分 draft。frontmatter の id は `DRAFT-N`）に対して GUI が提供する更新操作は、**保存区分を変える状態遷移だけ**に限り、draft の内容編集は提供しない。各遷移は保存先だけでなく id を変え、promote は status を変えることがある（実測）。「保管状態のみを変える」ではない。

| 操作 | サブコマンド | 遷移前 → 遷移後（保存区分／id／status） |
|---|---|---|
| draft 昇格 | `draft promote <DRAFT-N>` | draft ／ `DRAFT-N` ／ status `Draft` → active ／ 新規 `TASK-M`（採番し直し） ／ 既定 status（`default_status`、例 `To Do`） |
| draft 昇格（demote 由来） | `draft promote <DRAFT-N>` | draft ／ `DRAFT-N` ／ 通常 status（例 `In Progress`） → active ／ 新規 `TASK-M`（採番し直し） ／ **遷移前の status を保持** |
| タスクの draft 差し戻し | `task demote <TASK-N>` | active ／ `TASK-N` ／ 任意 status → draft ／ 新規 `DRAFT-M`（採番し直し） ／ **遷移前の status を保持** |
| draft アーカイブ | `draft archive <DRAFT-N>` | draft ／ `DRAFT-N` ／ 任意 status → archive ／ `DRAFT-N`（保持） ／ status 保持 |

- promote・demote は保存先だけでなく id を付け替える（`DRAFT-N` ↔ `TASK-M`、番号も採番し直す）。promote の status 変化は**条件付き**で、status が `Draft` の draft のみ `default_status` へ変わり、通常 status を持つ draft（`task demote` 由来）は status を保持する（実測）。archive は id・status を保持して `archive/drafts` へ移す。したがって draft の status は一律 `Draft` ではない（`draft create` 直後だけが `Draft`。doc-4 の 3.4）。
- **内容編集は提供しない**: draft の title・description・AC・References 等の編集は GUI から提供しない。CLI には draft を対象にした `task edit` 相当が無いためで、decision-2 の CLI 委譲を保つ限り Atlas も提供できない。内容を編集したい場合は、`draft promote` で通常タスクにしてから `task edit` 系で編集するか、外部エディタ経路（doc-8）で直接編集する。
- **id と横断タスクID**: draft の横断タスクID 右辺は `DRAFT-N`（doc-3 の 5.1）。対象 ID は `draft promote`／`draft archive` が `DRAFT-N`、`task demote` が `TASK-N`。アダプターは対象プロジェクトを作業ディレクトリに固定するため slug 前置は不要（doc-3 の 5.3）。
- draft をスイムレーン／詳細に表示するか、既定でフィルタするかは doc-7（TASK-11）で扱う。本アダプターは表示可否に依らず、上記状態遷移だけを操作写像に載せる。

### 3.4 v1.47.1 から v1.48.0 で変わった挙動（TASK-58 実測）

本書の実測基準版は冒頭が宣言している。それでも次の 3 点は、旧版で書かれた実装・doc を読み直すときに意味が反転するので記録に残す。2026-08-01 に使い捨ての Backlog ルートへ同じ操作列を流し、両版の出力と管理ファイルを差分比較して確認した。

v1.48.0 が新たに受け取るオプションのうち、Atlas が使わないものと理由:

- **`--clear-ac`／`--clear-labels`**: どちらも既存の手段（全 index の `--remove-ac`、全ラベルの `--remove-label`）で同じ結果になることを実測で確認した。操作写像を増やす利得が無い。

コマンド構成では `sequence` が削除され `doctor` が加わったが、どちらも本書の操作写像に現れないので影響しない。

### 3.5 v1.49.3 から v1.50.1 で変わった挙動（TASK-153 実測）

本書の実測基準版は冒頭が宣言している。それでも下の各項は、旧版で書かれた実装・doc を読み直すときに意味が反転するので記録に残す。**数えずに並べる** — 数は次の版差で偽になり、そのとき何も落ちない。2026-08-22 に、両版を使い捨ての Backlog ルートへローカル導入し、同じ操作列を流して出力と管理ファイルを差分比較した。**v1.50.0 は要件にできない** — ブランチの多いリポジトリで `task view`・`task edit`・`task list` が数分掛かる退行を持ち込んでおり（no-op の `task edit` が 12.2 秒。上流の測定値）、Atlas は CLI 呼び出しに終了期限を持つ（5 章、decision-18）。v1.50.1 はその修正版で、要件になれるのはこちらだけである。

- **`--clear-docs`**: Atlas は documentation を編集する更新操作を持たない（3.2 のタスク編集の範囲に無い）。
- **`--add-ref`／`--remove-ref`**: References は全置換で足りる（3 章の表）。増分指定を足すと、同じ欄に 2 通りの写像先ができる。
- **`task list --ready`・`decision list`**: 読み取りは管理ファイルの直接解析であり（decision-2）、本書の操作写像に読み取りサブコマンドは無い。

**操作写像に現れないが利用者の画面に出る差**: 壊れた `config.yml` は、v1.49.3 が黙って既定値を当てていたのに対し v1.50.1 は `Backlog could not start because <file> has an invalid value for "<key>": …` を出して終了コード 1 で止まる。**起動時の版検査は影響を受けない** — `backlog --version` はプロジェクトを作業ディレクトリにせず走らせるので（3.2、4 章）、壊れた設定を持つルートでも終了コード 0 で版を返す（実測）。

## 4. 作業ディレクトリと引数配列渡し

- **作業ディレクトリ**: 対象プロジェクトのプロジェクトルート（doc-3 の台帳エントリ `project_root`）を作業ディレクトリに指定して CLI を起動する。Rust の `std::process::Command` の `current_dir` で与える（decision-1）。プロジェクトごとに CLI を常駐させず、更新操作ごとに固定サブコマンドで起動する。
- **引数配列渡し**: サブコマンドと各引数を `Command::arg`／`args` の配列要素として個別に渡す。利用者入力（タイトル・説明・ラベル値など）はシェルへ渡さず、配列の 1 要素として素通しする。シェル（`sh -c` 等）を介さないため、空白・記号・改行・シェルメタ文字を含む入力でも語分割・展開・注入が起きない（doc-2・AGENTS の「シェル文字列へ連結しない」の実装）。
- **実行ファイル解決の順序**（decision-16）: **実行ファイル解決の順序**とは、CLI のプロセスを起動する前に、どの絶対パスまたはプログラム名を `Command::new` へ渡すかを決める、上から順に試す規則の列を指す。順序は 3 段である。①アプリ設定 `backlog_cli`（実行ファイルの絶対パス。値があれば存在検査をせずそのまま使い、自動解決へ落とさない）②Windows で PATH 上に直接起動できる `backlog.exe` が無く、npm が置いた shim の所在からプラットフォーム別実行ファイル（`backlog.md-<platform>-<arch>` サブパッケージが持つ、インタプリタを介さず起動できる単一の実行ファイル）へ到達できる場合、その絶対パス ③プログラム名 `backlog`。macOS・Linux は ③ に到達し、利用者の PATH 上の `backlog` を呼ぶという従来の挙動になる。②は `.cmd`／`.ps1` を起動せず本物の実行ファイルを直接起動するので、インタプリタがチェーンへ戻らず、上の引数配列渡しの前提を崩さない。解決はこのアダプターの継ぎ目（`BacklogCli` の実装）の内側に閉じ、操作写像・作業ディレクトリ・引数配列渡しは呼び出し先の実体に依存しない。**この 3 段は decision-29 の 外部コマンド解決の順序 の 1 実例である**（2026-08-13、TASK-156）。上位の規則が置くのは「外部コマンド指定（アプリ設定が持つ実行ファイルの絶対パス）を最優先に置く」ことだけで、①がそれに当たる。②③はこの外部コマンド固有の自動解決であり、上位の規則はその中身を揃えない。**したがって段は 3 段のまま増えない。** 変わったのは①を設定画面から編集できるようになったことで、読み方（値があれば存在検査をせずそのまま使い、自動解決へ落とさない）は変えていない。**空白のみの値は未設定として読む** — 欄を空にしたという意思を毎回の起動失敗へ変えないためである。**sidecar 同梱は採らないと決まった**（decision-26。TASK-99 が decision-7 の同梱検討契機 第 1 に対して判断した）ので、**順序は上の 3 段のままで、同梱バイナリ解決の段を足さない**。decision-7 の残る 2 契機で再検討が起きた場合も、差し替えるのはこの順序だけである。

## 5. CLI 失敗時の扱い

CLI 失敗（非ゼロ終了・起動失敗・期限到達）を、更新の不成立として扱う。

- **成否判定**: プロセスの終了コードで判定する。0 を成功、非ゼロを失敗とする。起動自体の失敗（実行ファイル不在・権限不足など）も失敗に含める。
- **CLI 終了期限**（decision-18）: **CLI 終了期限**とは、CLI の 1 回の起動について、終了を待つのをやめて子プロセスを強制終了するまでに許す経過時間を指す。値は 30 秒で、1 画面操作が複数回の起動に分かれる場合は起動 1 回ごとに掛かる。期限に達したら子プロセスを強制終了して回収し、**期限到達**として失敗を報告する。期限到達は非ゼロ終了ではない — 終了コードを観測していないためであり、CLI が判断を返したことも含意しない。
- **後始末猶予**（decision-18）: **後始末猶予**とは、子プロセスの終了を待つのをやめたあと、その後始末に使ってよい上限時間を指す。値は 1 秒。後始末は 2 つあり、どちらも上限を置かなければ無期限になる。①**強制終了した子プロセスの回収** — 強制終了が効くとは限らず、効かなければそのプロセスは終わらないかもしれないので、無条件のブロッキング待機は使わず反復確認に留め、猶予を過ぎたら回収せずに戻ってその旨を失敗理由に書く。②**配管の読み切り** — パイプが終端に達するのは書込み側が 1 つ残らず閉じたときなので、子プロセスを終了させても終端が来るとは限らない（配管を継承した子孫プロセスが持ち続ける）。子プロセスが自分で終了した場合は後始末猶予まで待って読めた分を取り、期限到達で強制終了した場合は読み出しをまったく待たない。**1 回の起動が Atlas を止める時間の上限は「CLI 終了期限 ＋ 後始末猶予」、正常終了した場合は「子プロセスの所要時間 ＋ 後始末猶予」である。** 猶予を過ぎて届いた出力は失われ得るし、回収できなかった子プロセスは残り得るが、判断は終了コードであり出力はその理由文なので、掲げる保証は上限内に戻ることに留める。
- **失敗時の状態**: 失敗した更新操作は、Atlas 側のドメインモデルを変更しない。CLI が管理ファイルを変えていない前提を、成否判定の後の再読込（次章）で裏取りする。標準エラー出力を失敗理由として保持し、利用者へ提示する（どのサブコマンド・どの対象が失敗したか）。
- **部分適用の回避**: 1 画面操作を複数サブコマンド呼び出しへ分ける場合、途中の呼び出しが失敗したら以降の呼び出しを行わず、そこまでの結果を再読込で観測できる状態にして失敗を報告する。アダプターは CLI をまたいだロールバックを持たない（CLI が正本を所有するため）。代わりに、失敗後は再読込で現状を正しく写し、利用者が続行/再試行を判断できるようにする。
- **要再読込**: **要再読込**とは、更新が失敗したあと、ディスク上の管理ファイルが呼び出し前と同じだと Atlas が言えない状態を指す。次の 2 つがこれに当たり、失敗の報告は要再読込かどうかを伴う。①2 回目以降の呼び出しでの失敗（先行する呼び出しが既に書いている＝部分適用）②期限到達（強制終了は捕捉できないので、強制終了した呼び出しが書いたかどうか分からない。decision-18）。要再読込である失敗は、掲げる保証を「再読込で現状を画面へ写す」ことに留める — 管理ファイルが無傷であることは掲げない。
- **未知オプション・未知サブコマンド**: 操作写像がサポート範囲外（版差でオプションが消えた等）と判定したら、CLI を起動せず操作を拒否する（縮退）。
- **直接書き込みの失敗**（decision-21）: 直接書き込み操作は CLI プロセスを起こさないので CLI 失敗ではないが、**失敗の扱いは同じ**にする — 更新の不成立として扱い、失敗理由を利用者へ提示し、1 画面操作の以降の呼び出しを行わない。終了コードの代わりに書き込みが返す入出力の失敗を成否とする。**単独で行った直接書き込みの失敗は要再読込ではない** — 一時ファイル置換（decision-17）が、途中で失敗したときに旧ファイルをそのまま残すためである。先行する呼び出しがある場合に要再読込になるのは CLI 失敗と同じ。**`## Description` 見出しで開かれていない説明**への書き込みは、起動前に拒否する側に置く。該当は「見出しも `SECTION:DESCRIPTION` 対も無いファイル」と「説明が `SECTION:DESCRIPTION` 対で開かれているファイル」の 2 つで、どちらも書けば CLI が書かない形を Atlas が作ることになり、decision-21 の条件 1 に反する。後者では読み取りが書き込みより広い（説明は画面に出るが保存は拒まれる）が、これは decision-21 が用意している拒否である。

## 6. 再読込契機

読み取りはファイル解析（decision-2）であり、更新は CLI 経由であるため、更新の結果はファイルを読み直して初めてドメインモデルへ入る。この読み直しの時点を再読込契機として定義する。

- **成功時の発火**: CLI 成功後、当該更新操作が触れた対象（タスク・文書・マイルストーンの属するルート、可能なら変更ファイル単位）について読み取り層の再読込を発火する。再読込の単位は doc-4 のドメインモデル再構築単位（ルート／ファイル）に合わせる。**直接書き込み操作（1 章）も同じ扱い**で、書き込みが成功したら再読込を発火する — 書いたのが Atlas 自身であっても、ドメインモデルへ入る経路はファイルの読み直し 1 つに保つ（読み書きで経路を分ける decision-2 の趣旨は、書き手が誰かではなく、モデルの正本がファイルであることにある）。
- **失敗時**: CLI 失敗時は更新が成立していないため、原則として再読込を発火しない。ただし §5 の**要再読込**にあたる場合（複数呼び出しの途中失敗、および期限到達）は、現状を正しく写すため対象ルートの再読込を行い、実ファイルの状態をドメインモデルへ反映する。監視（doc-9 §3）が拾うことを当てにしない — doc-9 §3 は監視を保証された経路として扱っていない。
- **外部変更との統合**: 同一 Backlog ルートを別ウィンドウ・別プロセスやファイル監視が更新する場合の競合検出・再読込は TASK-14 で設計する。本アダプターの成功後再読込は、その再読込機構と同じ経路に載せ、CLI 由来の変化も外部由来の変化も同一の読み直しとして扱えるようにする。

## 7. 後続への影響

- 競合検出とファイル監視による再読込の具体は TASK-14。本章の再読込契機はその機構へ載せる。
- 実行ファイル解決の順序は decision-16 が定める（TASK-60。Windows では npm が `backlog.exe` を置かないため、PATH 解決だけでは更新経路が全面発行不能になる）。**sidecar 同梱は採らない**（decision-26。TASK-99）ので、順序に同梱バイナリ解決の段は入らない。
- タスク詳細画面（TASK-12）からの更新操作は本アダプターの操作写像を入口とする。
