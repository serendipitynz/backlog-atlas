# プロジェクト台帳と横断タスクID 設計

TASK-4 の設計。用語は [doc-1](doc-1)・[doc-2](doc-2) に従い、本書で導入する語は初出に定義を置く。
前提は decision-1（Tauri/Rust 採用）・decision-2（読み取りは Backlog 管理ファイルの直接解析）。

## 1. 対象と用語

- **プロジェクト台帳** … Atlas が読み込む対象プロジェクトの一覧と各属性を保持する論理的な登録簿。タスク正本ではない（正本は各 Backlog ルートに残る）。
- **台帳ファイル** … プロジェクト台帳を永続化する単一の設定ファイル。
- **台帳エントリ** … 台帳に登録された 1 プロジェクト分の記録。
- project slug・横断タスクID・Backlog ルート・プロジェクトルートは doc-2 の定義を用いる。

## 2. 台帳ファイル（保存場所・形式・書き込み）

### 2.1 保存場所

台帳ファイルは、Tauri の `app_config_dir()` が返す OS のアプリ設定ディレクトリ直下に単一ファイルとして置く。

- macOS: `~/Library/Application Support/<bundle-identifier>/projects.toml`
- Linux: `${XDG_CONFIG_HOME:-~/.config}/<bundle-identifier>/projects.toml`
- Windows: `%APPDATA%\<bundle-identifier>\projects.toml`

台帳は Atlas 固有の設定であり、いずれのプロジェクトの Backlog ルートにも置かない。プロジェクト側のファイルに Atlas の登録情報を書き込まない（正本と設定の分離）。

同じディレクトリには、アプリ設定ファイル（decision-13、`settings.toml`）も置く。両者は別ファイルであり、台帳ファイルが読み取り専用へ縮退しても（2.2）アプリ設定の保存はできる。台帳は「どのプロジェクトを読むか」を、アプリ設定は「読んだものをどう見せるか」を持ち、片方の版が上がっても他方を書けなくしない。

### 2.2 形式

形式は TOML とする。理由は、手編集しやすく、Rust（serde）で素直に読み書きでき、配列テーブルで台帳エントリの並びを表せるためである。JSON も候補だが、手編集容易性で TOML を採る。将来 UI からのみ編集する運用に寄せる場合も、形式自体は変えない。

```toml
schema_version = 1

[[project]]
slug = "geomyth"
project_root = "/path/to/geomyth"
backlog_root = "/path/to/geomyth/backlog"
git_remote_present = true

[[project]]
slug = "backlog-atlas"
project_root = "/path/to/backlog-atlas"
backlog_root = "/path/to/backlog-atlas/backlog"
git_remote_present = false
```

例中の `/path/to/...` はプレースホルダである。実際の値は、その環境で解決できる絶対パスを書く。

- `schema_version` … 台帳ファイルのスキーマ版。読み込み時に既知の版か検査し、未知の上位版は上書き保存で破壊しないよう読み取り専用で縮退する。
- `[[project]]` … 台帳エントリの配列。並び順は表示既定順に用いる。
- `[project.status_aliases]` … 任意。**status 別名表**（3.3）。省略時は空とみなす。上の 2 エントリは Backlog.md 既定 4 status を名称一致で対応づけられるため別名表を持たない。

台帳ファイルの読み書きは Atlas 自身が行う。これは decision-2 の「Backlog **管理ファイル**は直接解析し、更新は Backlog CLI へ委譲する」境界の外側であり、Backlog CLI の管理対象ではないため矛盾しない。台帳ファイルは Backlog.md のタスク正本ではなく、Atlas の設定である。

### 2.3 書き込み（一時ファイル置換）

台帳ファイルへの書き込みは、**一時ファイル置換**で行う（decision-17）。**一時ファイル置換**とは、保存先と同じディレクトリに作った一時ファイルへ内容を全量書いてから、保存先の名前へ `rename` で置き換える書込み手順を指す。保存先を切り詰めてから書く方法（`std::fs::write`）は採らない。切詰めと書込み完了の間で失敗すると、空または途中までの TOML が保存先の名前に残り、次回起動時に **`load` が台帳全体をエラーにするため登録済みの全プロジェクトが開けない**（2.2 の版検査より前に、TOML として読めない）。

耐久性水準は**ファイル同期**まで（一時ファイルの内容を記憶デバイスへ書き出させてから `rename` する）とし、**親ディレクトリ同期は行わない**。掲げる保証は「**書込み途中の失敗**が保存先に中途の内容を残さない」ことで、容量不足・書込みエラー・プロセス強制終了のいずれで止まっても、台帳ファイルの名前を読んだ者は旧内容の全体か新内容の全体しか見ない。**電源断・OS 障害の後に何が残るかは掲げる保証の外にある** — `rename` によるディレクトリエントリの変更を記憶デバイスへ書き出させていないので、その先はファイルシステム自身のクラッシュ時の規則に委ねられる。選択の理由と却下した代替は decision-17 にある。

同じ手順をアプリ設定ファイル（decision-13）も通る。Atlas が自分で書くファイルはこの 2 つだけで、対象プロジェクトの管理ファイルは decision-2 により Backlog CLI が書くので、この節の対象ではない。

## 3. 台帳エントリの属性

台帳エントリは 1 プロジェクトにつき 1 件で、次の属性を持つ。

| 属性 | 型 | 必須 | 説明 |
|---|---|---|---|
| `slug` | 文字列 | 必須 | project slug。台帳内で一意。登録後は不変（横断タスクID の左辺・Git 履歴表示の鍵になるため）。 |
| `project_root` | 絶対パス | 必須 | プロジェクトルート。Git 履歴・PR 参照（TASK-10）と Backlog ルートの解決基点。 |
| `backlog_root` | 絶対パス | 必須 | Backlog ルート。既定は `project_root/backlog`。異なる場合は明示する。読み取り層（TASK-5）の入力。 |
| `git_remote_present` | 真偽 | 必須 | **Git remote 有無属性**。エントリのプロジェクトルートに remote があるか否かを判定して台帳エントリへ保存する真偽値。 |
| `status_aliases` | テーブル（文字列→文字列） | 任意 | **status 別名表**。プロジェクト固有 status 値を正準ステータス列へ対応づける（decision-4）。既定は空。詳細は 3.3。 |

### 3.1 slug の規則

- 文字種は `[a-z0-9][a-z0-9-]*`。区切り文字 `:` と空白を含まない（横断タスクID の解析を一意にするため）。
- 既定値は project_root のディレクトリ名を小文字化・正規化して導く。衝突する場合は登録を拒否し、利用者が別 slug を指定する。
- 台帳内で一意。登録後は変更しない。改称が必要なら削除して再登録する（横断タスクID・履歴表示の同一性が切れることを明示する）。

### 3.2 Git remote 有無属性

**Git remote 有無属性**とは、エントリのプロジェクトルートに remote があるか否かを判定して台帳エントリへ保存する真偽値を指す。

- 判定は、プロジェクトルートの Git リポジトリに設定済み remote が 1 つ以上あるか否か（`git remote` 相当）で行う。固定サブコマンドと引数配列で実行し、シェル文字列へ連結しない（AGENTS）。
- 登録時に判定して保存し、実行時に再判定して更新しうる（remote の後付けに追随）。プロジェクトルートが Git リポジトリでない場合は偽。
- タスクラベルではなく台帳属性として持つ（doc-2）。この値は、コミットと Pull Request の関連解決が可能かの判断根拠であり、解決手段そのものの設計は TASK-10 に委ねる。

### 3.3 status 別名表

**status 別名表**とは、台帳エントリの任意属性で、プロジェクト固有 status 値を正準ステータス列（To Do / In Progress / In Review / Done）へ対応づける表を指す（decision-4）。列対応規則の別名対応を、対象 Markdown を書き換えず Atlas 側の解釈として台帳に持つためのものである（doc-2 の境界）。

- **形式**: TOML の `[project.status_aliases]` サブテーブル。キーがプロジェクト固有 status 値、値が対応先の正準ステータス列名。値は正準 4 列のいずれかに限る（正準列は固定、decision-4）。空白を含む status 値はキーを引用符で囲む（例 `"In Dev" = "In Progress"`）。
- **既定は空**: 省略時は別名なし。別名表に無い status は、名称一致（大文字小文字・前後空白を無視）で正準列へ対応づける（decision-4）。Backlog.md 既定 4 status はこれで一致するため別名表は要らない。
- **対応づかない値**: 別名表にも名称一致にも該当しない status は未対応 status とし、スイムレーンの未対応区画へ出す（decision-4・doc-7）。値に正準 4 列以外を書いた別名は不正として無視し、当該 status を未対応として扱う。不正な別名は台帳ファイルから取り除かず、値をそのまま保持したうえで列対応の時点で無視する。読み込み時に削除すると、別名不在（そのプロジェクトが別名を設定していない状態）と区別がつかなくなり、名称一致へ戻って当該 status が正準列へ入ってしまうためである。

必要なプロジェクトだけが設定する例（プロジェクト固有 status を運用する場合）:

```toml
[[project]]
slug = "example"
project_root = "/path/to/example"
backlog_root = "/path/to/example/backlog"
git_remote_present = true

# status 別名表: プロジェクト固有 status → 正準ステータス列。既定は空。
[project.status_aliases]
Doing = "In Progress"
Review = "In Review"
Closed = "Done"
Cancelled = "Done"
```

## 4. Backlog ルートの登録・削除手順

すべて台帳ファイルに対する操作で、対象プロジェクトの管理ファイルには一切書き込まない。

画面上の入口は粒度で分ける。登録（4.1）は台帳全体に対する操作なのでスイムレーンの固定ヘッダに置き（doc-7 §2.1）、既存エントリの更新（4.3）と削除（4.2）は 1 プロジェクトに対する操作なのでプロジェクト詳細画面に置く（doc-10 §4）。

### 4.1 登録

1. 利用者がプロジェクトルート（または Backlog ルート）を指定する。
2. Backlog ルートを解決する（既定 `project_root/backlog`、明示指定があればそれ）。`config.yml` と `tasks/` の存在を確認する。読めない場合は登録を拒否し理由を示す（TASK-5 のルート読取不能に相当）。
3. slug を導出または利用者指定で確定し、一意性を検査する。
4. Git remote 有無属性を判定する。
5. 台帳エントリを組み立て、台帳ファイルへ追記して保存する。status 別名表（3.3）は登録時は空を既定とし、必要なプロジェクトだけ後から設定する（4.3）。

### 4.2 削除

- slug を指定してエントリを台帳から取り除き、台帳ファイルを保存する。
- 対象プロジェクトの Backlog ルート・管理ファイル・Git リポジトリには触れない。削除は「Atlas が読む対象から外す」だけであり、タスク正本は残る。

### 4.3 更新

- 変更してよいのは `backlog_root`・`git_remote_present`（再判定）・`status_aliases`（status 別名表、3.3）と、表示上の並び順である。`slug` は不変。`project_root` を変える場合は同一プロジェクトの移動として扱い、slug を保って両パスを更新する。

## 5. 横断タスクID

**横断タスクID** … project slug とプロジェクト内 TASK-ID を区切り文字 `:` で連結した、横断画面上のタスク識別子（doc-2）。

### 5.1 生成

- 形は `<slug>:<TASK-ID>`。`<TASK-ID>` は当該プロジェクトの `config.yml` の task_prefix に従うプロジェクト内 ID（既定は `TASK-N`）。draft は例外として `DRAFT-N` を右辺に取り、`<slug>:DRAFT-N` を draft の正規の横断タスクID 形式とする（draft の frontmatter id は `DRAFT-N`、doc-4 の 3.4）。draft も doc-7 のカードで横断タスクID を要するため、右辺形式として明示的に許可する。
- 連結子は単一の `:`。slug 側・TASK-ID 側とも前後に空白を入れない。
- 横断タスクID は表示・参照のための導出値であり、台帳にも管理ファイルにも保存しない。slug（台帳）と TASK-ID（管理ファイル frontmatter の id）から都度組み立てる。

### 5.2 解析

- 入力文字列を**最初の** `:` で 2 分割する。左を slug、右を TASK-ID とする。
- slug は `:` を含まないため、最初の `:` での分割は一意に定まる（TASK-ID 側に `:` が現れても左辺の確定に影響しない。なお Backlog の TASK-ID は `:` を含まない）。
- 左辺 slug が台帳エントリに存在することを検査する。存在しなければ未登録プロジェクト参照として拒否する。
- 右辺が当該プロジェクトの ID 形式に一致することを検査する。許容する形式は、task_prefix に従う通常 ID（既定 `TASK-N`）と、draft の `DRAFT-N` の 2 つとする。いずれにも一致しなければ不正な ID として拒否する。
- 接頭辞の一致は大文字小文字を無視する。`backlog init --defaults` は `config.yml` に task_prefix `task`（小文字）を書く一方、生成する ID は `TASK-N`（大文字）であり（v1.48.0 実測）、区別すると既定初期化のルートが自身の TASK-ID を不正な ID として拒否する。判定のみ大小文字非依存とし、ID 自体は管理ファイルの表記のまま保持する（5.1 の生成・5.3 の表示は正本の表記を変えない）。
- `:` を含まない入力は、現在文脈のプロジェクト内 ID（`TASK-N` または `DRAFT-N`）とみなす（下記 5.3）。

### 5.3 表示

- 横断画面（プロジェクト別スイムレーン、横断検索結果など複数プロジェクトが混在する面）では常に `<slug>:<TASK-ID>` を表示する。
- 単一プロジェクトに絞った文脈（あるプロジェクトの詳細内など）では `TASK-ID` のみを表示してよい。
- 各プロジェクト内のコミットメッセージ・Pull Request では従来どおり `TASK-N` を使う（doc-2）。draft の `DRAFT-N` は横断表示・カード識別にのみ用い、コミット・PR には現れない（作業前段階のため）。Atlas は横断表示のためだけに slug を前置し、正本側の ID 体系を変えない。

## 6. Backlog ルートからのプロジェクト決定規則

- あるタスクの所属プロジェクトは、そのタスクを読み込んだ Backlog ルートに対応する台帳エントリの slug で決定する。
- タスクへ `project:<slug>` ラベルを付けて所属を表す方式は採用しない（doc-2）。ラベルは Type と通常ラベルにのみ用いる（TASK-5・TASK-8）。
- 実装上は、読み取り層（TASK-5）が各 Backlog ルートを走査して得たタスクに、その走査元ルートの台帳エントリを対応づける。台帳エントリと Backlog ルートは 1 対 1 であり、この対応づけが横断タスクID の左辺（slug）を与える。
- 同一タスクが複数ルートから読まれることは、各プロジェクトに Backlog ルートを一つ置く前提（doc-2）により起きない。

## 7. 後続への影響

- 読み取り層がタスクにルート由来のプロジェクトを付与する具体は TASK-5 で設計する。
- Git remote 有無属性を用いたコミット・PR の関連解決手段は TASK-10 で決める。
- 対象 repo・Backlog ルート・コミット不在時の表示は TASK-13 で決める。
- status のプロジェクト共通／個別は TASK-7、`kind:*` からの Type 導出は TASK-8 で決める。
- status 別名表（3.3）は台帳エントリの任意属性として、decision-4 の列対応規則の別名対応を与える。別名表・名称一致・未対応区画を用いた正準ステータス列への対応づけとその見せ方はスイムレーン（TASK-11、doc-7）で設計する。
